Distributed Systems — When One Computer Isn't Enough

1. What is a Distributed System?

A

📖 Distributed System: A collection of independent computers that appear to its users as a single coherent system.

Analogy: A single restaurant vs a chain of restaurants. If a single restaurant kitchen catches fire, operations stop. In a chain, if one location closes, others can still serve customers, but coordinating the menu and prices across all locations becomes a challenge.

2. CAP Theorem

The CAP Theorem states that in a distributed data store, you can only guarantee two out of three properties:

  • Consistency (C): Every read receives the most recent write.
  • Availability (A): Every request receives a (non-error) response, without guarantee that it contains the most recent write.
  • Partition Tolerance (P): The system continues to operate despite an arbitrary number of messages being dropped or delayed by the network between nodes.

Because network partitions (P) are unavoidable, you must choose between Consistency (CP) and Availability (AP).

Figure 1: The CAP Theorem Triangle

Java 21 
public class CAPSimulation {
    // Simulates a network partition between two nodes
    static boolean networkPartition = true;
    static String node1Data = "V1";
    static String node2Data = "V1";

    public static void writeData(String newData) {
        node1Data = newData;
        if (!networkPartition) {
            node2Data = newData; // Replicate if no partition
        }
    }

    public static void main(String[] args) {
        writeData("V2"); // Write goes to Node 1
        
        // AP System Behavior (Available, but Inconsistent)
        System.out.println("AP Read Node 2: " + node2Data); // Returns stale "V1"
        
        // CP System Behavior (Consistent, but Unavailable)
        if (networkPartition) {
            System.err.println("CP Read Node 2: ERROR - Node isolated, rejecting read to maintain consistency");
        }
    }
}

3. PACELC Theorem

An extension to CAP: If there is a Partition (P), how does the system trade off Availability and Consistency (A and C); Else (E), when the system is running normally, how does it trade off Latency and Consistency (L and C).

4. Consistency Models

  • Strong Consistency: After a write, any subsequent read will see the updated value.
  • Eventual Consistency: If no new updates are made, eventually all accesses will return the last updated value.
  • Causal Consistency: Operations that are causally related are seen by every node in the same order.
  • Read-Your-Writes: A client will always see its own updates.

5. Consistent Hashing

Traditional hashing (hash(key) % N) breaks down when a server is added or removed (N changes), causing almost all keys to be remapped.

📖 Consistent Hashing: Distributes data across a ring such that adding or removing a node only affects a minimal number of keys.

Java 21 
import java.util.SortedMap;
import java.util.TreeMap;

public class ConsistentHashRing {
    private final SortedMap<Integer, String> ring = new TreeMap<>();
    private final int numberOfVirtualNodes = 3;

    public void addNode(String nodeName) {
        for (int i = 0; i < numberOfVirtualNodes; i++) {
            int hash = (nodeName + i).hashCode();
            ring.put(hash, nodeName);
        }
    }

    public String getNode(String key) {
        if (ring.isEmpty()) return null;
        int hash = key.hashCode();
        SortedMap<Integer, String> tailMap = ring.tailMap(hash);
        int nodeHash = tailMap.isEmpty() ? ring.firstKey() : tailMap.firstKey();
        return ring.get(nodeHash);
    }
}

6. Replication Strategies

  • Leader-Follower: Writes go to the leader, reads can go to followers.
  • Multi-Leader: Multiple nodes accept writes. Complex conflict resolution.
  • Leaderless: Any node accepts writes (e.g., Cassandra). Uses quorums for reads/writes.

7. Distributed Locks

In a single machine, you use `synchronized` or `ReentrantLock`. In a distributed system, you need an external store like Redis or ZooKeeper.

8. Leader Election & 9. Consensus

Consensus algorithms (like Raft or Paxos) allow a cluster of machines to agree on values, even if some nodes fail. They often start with Leader Election to pick a single coordinator to handle writes.

10. CQRS

📖 CQRS (Command Query Responsibility Segregation): Separates the models and databases used for reading data (Queries) from those used for updating data (Commands).

11. Event Sourcing

Instead of storing the current state, store the sequence of events that led to it. Analogy: Your bank balance (current state) is just the sum of all your deposits and withdrawals (events).

Java 21 
public sealed interface Event permits AccountCreated, MoneyDeposited {}
record AccountCreated(String id, double initialBalance) implements Event {}
record MoneyDeposited(String id, double amount) implements Event {}

public class BankAccount {
    private double balance = 0;
    
    // Rebuild state by replaying events
    public void apply(List<Event> events) {
        for (Event e : events) {
            switch (e) {
                case AccountCreated ac -> this.balance = ac.initialBalance();
                case MoneyDeposited md -> this.balance += md.amount();
            }
        }
    }
}

12. Saga Pattern

Used for distributed transactions. Instead of locking multiple databases, a Saga executes a sequence of local transactions. If one fails, it executes compensating transactions to undo the previous steps.

13. Outbox Pattern

Ensures a message is reliably sent to a queue when a database transaction commits. You save the business entity AND an `OutboxMessage` in the same database transaction. A background worker then publishes the outbox messages to Kafka/RabbitMQ.

public record OutboxMessage(UUID id, String topic, String payload, boolean processed) {}

14. Distributed Transactions (2PC)

Two-Phase Commit (2PC) coordinates commits across multiple databases. It is slow and blocking, hence why modern systems prefer Sagas.

15. Idempotency

Making operations safe to retry is critical because in distributed systems, network packets fail. If a client doesn't get an ACK, they will retry. Idempotency ensures the operation isn't duplicated.
