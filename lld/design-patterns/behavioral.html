Behavioral Design Patterns: The Definitive Masterclass

Behavioral patterns define not just the structure of objects, but the communication patterns, responsibilities, and algorithms between them.

1. The Observer Pattern

PILLAR 1: Ground-Zero Theory & The Pain Point

The Observer Pattern defines a one-to-many dependency between objects. When one object (the Subject) changes state, all its dependents (Observers) are notified automatically. The massive pain point it solves is the polling anti-pattern, where consumers constantly check a producer for updates, wasting CPU cycles and network bandwidth.

PILLAR 2: Architectural Decision Rationales & Modifier Deep Dives

Using a `CopyOnWriteArrayList` or standard `List` with `synchronized` blocks for observer registries is crucial to prevent `ConcurrentModificationException` when observers add/remove themselves during notification. We often use interfaces for Observers to keep the Subject decoupled from concrete consumer classes.

PILLAR 3: Step-by-Step Evolution

From tight coupling -> Polling -> Event-driven push notifications.

PILLAR 4: Production-Grade Java 21 Code


public interface Subscriber {
    void update(double stockPrice);
}

public class StockExchange {
    // Thread-safe collection to prevent modification issues during iteration
    private final List<Subscriber> subscribers = new CopyOnWriteArrayList<>();
    private double currentPrice;

    public void addSubscriber(Subscriber sub) {
        subscribers.add(sub);
    }

    public void setPrice(double newPrice) {
        this.currentPrice = newPrice;
        notifySubscribers();
    }

    private void notifySubscribers() {
        for (Subscriber sub : subscribers) {
            // Using modern virtual threads for isolated asynchronous notification
            Thread.startVirtualThread(() -> sub.update(currentPrice));
        }
    }
}

PILLAR 5: The Grill Round

Trap: The "Lapsed Listener" memory leak.

Answer: "If a subject holds strong references to short-lived observers, those observers cannot be garbage collected. The architectural fix is to use `WeakReference` in the subscriber list or strictly enforce deregistration in `finally` blocks."

PILLAR 6: Trade-offs

Notifications can cascade unpredictably in complex systems, leading to infinite loops if Observers trigger state changes in the Subject. It also obscures control flow, making debugging difficult.

2. The Strategy Pattern

PILLAR 1: Theory

The Strategy Pattern extracts families of algorithms into separate classes, allowing them to be swapped at runtime. The pain point is massive, monolithic `switch` statements.

PILLAR 4: Production-Grade Java 21 Code


@FunctionalInterface
public interface PaymentStrategy {
    void pay(double amount);
}

public class ShoppingCart {
    private PaymentStrategy strategy;

    public void setPaymentStrategy(PaymentStrategy strategy) {
        this.strategy = strategy;
    }

    public void checkout(double amount) {
        // Strategy executes without the context knowing the details
        strategy.pay(amount);
    }
}

PILLAR 5: The Grill Round

Trap: How is Strategy different from State? Answer: "Strategy implies the client chooses the algorithm. State implies the object transitions itself internally, reacting differently based on its internal state life-cycle."

3. The Command Pattern

PILLAR 1: Theory

Encapsulates a request as an object, allowing you to parameterize clients with queues, logs, and undo operations.

PILLAR 5: The Grill Round

Trap: "How do you handle transaction rollback?" Answer: "By storing reverse operations or previous states (using Memento) inside the Command object itself, making `undo()` fully deterministic."

4. The State Pattern

PILLAR 1: Theory

Allows an object to alter its behavior when its internal state changes. Replaces state machine boolean flags with polymorphic classes.

PILLAR 4: Production-Grade Java 21 Code


public sealed interface VendingMachineState permits HasCoinState, NoCoinState {
    void insertCoin();
    void dispense();
}
// State transition handled inside the state context gracefully.

PILLAR 5: The Grill Round

Trap: "Who controls transitions?" Answer: "For simple, linear workflows, Context controls it. For dynamic graphs, States should return the Next State or mutate the Context directly, though this tightly couples States to the Context."

5. The Template Method Pattern

PILLAR 1: Theory

Defines the skeleton of an algorithm in a base class, letting subclasses override specific steps without changing the overall structure.

PILLAR 5: The Grill Round

Trap: "Template Method vs Strategy?" Answer: "Template Method works at the class level via inheritance (white-box reuse), altering parts of an algorithm. Strategy works at the object level via composition (black-box reuse), replacing the entire algorithm."

6. Chain of Responsibility

PILLAR 1: Theory

Passes a request along a chain of handlers. Handlers can process the request, pass it, or short-circuit the chain.

PILLAR 5: The Grill Round

Trap: "Where is this used in the real world?" Answer: "Java Servlet Filters and Spring Security's `SecurityFilterChain`. Each filter checks headers/auth; if it fails, it short-circuits by writing a 401 response and skipping `chain.doFilter()`."
