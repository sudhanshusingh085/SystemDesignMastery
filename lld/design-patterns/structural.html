Structural Design Patterns: The Definitive Masterclass

Welcome to the exhaustive, textbook-grade deep dive into Structural Design Patterns. Structural patterns deal with object composition and typical ways to build large, robust structures while keeping these structures flexible and efficient.

1. The Adapter Pattern

PILLAR 1: Ground-Zero Theory & The Pain Point

At its core, the Adapter Pattern acts as a translator between two incompatible interfaces. In enterprise software, you frequently encounter scenarios where your beautifully crafted, domain-driven modern application needs to integrate with a legacy system or a third-party SDK. The pain point is visceral: the third-party library expects data in a specific format (e.g., XML) and provides methods with names completely alien to your ubiquitous language. Without an adapter, your pristine domain logic becomes polluted with conversion logic and foreign dependencies. This pollution is what we call vendor lock-in or domain leakage.

PILLAR 2: Architectural Decision Rationales & Modifier Deep Dives

When designing an adapter, a critical architectural decision is choosing between a Class Adapter (using inheritance) and an Object Adapter (using composition). In modern Java, composition is heavily preferred. Inheriting from a legacy class exposes its entire API (including potentially dangerous or obsolete methods) to your application. By using composition, you encapsulate the adaptee as a `private final` instance variable. The adapter implements only your modern target interface, ensuring that the legacy footprint is entirely isolated behind strict access modifiers.

PILLAR 3: Step-by-Step Evolution & Thought Process

Imagine your interviewer asks you to integrate an old `LegacyXmlBankingApi` into a new `PaymentGateway` interface. The naive approach is to modify the existing `PaymentGateway` to accept XML, or directly instantiate `LegacyXmlBankingApi` in your payment processing service. This fails the Open/Closed Principle immediately. As the system evolves, the realization hits: you need a middleman. You define `PaymentGateway` (the Target), keep `LegacyXmlBankingApi` untouched (the Adaptee), and create `XmlBankingAdapter` that implements `PaymentGateway` and holds a reference to `LegacyXmlBankingApi`.

PILLAR 4: Production-Grade Java 21 Code


// The Target Interface expected by our modern system
public interface PaymentGateway {
    boolean processPayment(String accountId, double amount);
}

// The Adaptee: A legacy 3rd-party system we cannot modify
final class LegacyXmlBankingApi {
    public String executeTransaction(String xmlPayload) {
        // Complex XML processing...
        return "<status>SUCCESS</status>";
    }
}

// The Object Adapter using composition and modern Java features
public final class BankingAdapter implements PaymentGateway {
    
    // Encapsulated adaptee, immutable reference
    private final LegacyXmlBankingApi legacyApi;

    public BankingAdapter(LegacyXmlBankingApi legacyApi) {
        this.legacyApi = legacyApi;
    }

    @Override
    public boolean processPayment(String accountId, double amount) {
        // 1. Translate modern request to legacy format
        String xmlRequest = """
            <transaction>
                <account>%s</account>
                <amount>%.2f</amount>
            </transaction>
            """.formatted(accountId, amount);
        
        // 2. Delegate to the adaptee
        String xmlResponse = legacyApi.executeTransaction(xmlRequest);
        
        // 3. Translate legacy response to modern return type
        return xmlResponse.contains("<status>SUCCESS</status>");
    }
}

PILLAR 5: The Interviewer's Deep Follow-Up Questions

The Grill Round: "What is the difference between Adapter, Decorator, and Facade?"

Senior Answer: "It's all about intent. The Adapter's intent is to make two incompatible interfaces work together; it changes the interface. The Decorator's intent is to add responsibilities to an object dynamically; it keeps the interface the same. The Facade's intent is to provide a simplified, unified interface to a complex subsystem; it creates a new, simpler interface."

PILLAR 6: Trade-offs & When NOT To Use It

Nothing is free. Adapters add a layer of indirection, slightly impacting performance and increasing cognitive load for developers debugging stack traces. You should not use an adapter if you actually have control over the legacy source code and refactoring it to match the new interface is feasible and safe. Adapters are for boundaries you do not own or cannot afford to change.

2. The Decorator Pattern

PILLAR 1: Ground-Zero Theory & The Pain Point

The Decorator pattern is the ultimate weapon against class explosion. The pain point occurs when you have base components (like Coffee) and a multitude of optional add-ons (Milk, Whip, Caramel). If you use inheritance, you end up with classes like CoffeeWithMilkAndWhip, leading to combinatorial explosion.

PILLAR 2: Architectural Decision Rationales

Why do we use an abstract class or interface for the Decorator? The Decorator must implement the same interface as the component it decorates so it can stand in its place. The `private final` component reference inside the decorator ensures we can recursively delegate calls.

PILLAR 3: Step-by-Step Evolution

From naive subclassing (fails at scale) -> to a single base class with a dozen boolean flags (violates Open/Closed and makes the base class huge) -> to Dynamic Composition via Decorator, where we wrap objects at runtime.

PILLAR 4: Production-Grade Java 21 Code


public sealed interface Beverage permits Espresso, BeverageDecorator {
    String description();
    double cost();
}

public final record Espresso() implements Beverage {
    @Override public String description() { return "Espresso"; }
    @Override public double cost() { return 1.99; }
}

public sealed abstract class BeverageDecorator implements Beverage permits Milk, Whip {
    protected final Beverage component;
    protected BeverageDecorator(Beverage component) { this.component = component; }
}

public final class Milk extends BeverageDecorator {
    public Milk(Beverage component) { super(component); }
    @Override public String description() { return component.description() + ", Milk"; }
    @Override public double cost() { return component.cost() + 0.50; }
}

PILLAR 5: The Grill Round

Trap: Does order matter in decorators? Answer: Generally, the pattern aims to be order-independent for pure additive operations. But if decorators apply discounts (e.g., half-off), the order of wrapping fundamentally changes the mathematical outcome.

PILLAR 6: Trade-offs

Trade-offs involve debugging nightmares. A deeply nested decorator stack (`new Whip(new Milk(new Espresso()))`) makes stack traces complex and object identity checks (`instanceof`) effectively useless since the outer wrapper masks the inner types.

3. The Facade Pattern

PILLAR 1: Ground-Zero Theory & The Pain Point

When clients interact with a myriad of intricate subsystems—like an audio encoder, video decoder, bit-rate allocator, and file writer—the client code becomes massively bloated and tightly coupled. The Facade Pattern provides a simple, high-level interface that shields clients from this internal chaos.

PILLAR 4: Production-Grade Java 21 Code


// A simplified clean API over complex sub-systems
public class VideoConverterFacade {
    public File convertVideo(String fileName, String format) {
        VideoFile file = new VideoFile(fileName);
        Codec sourceCodec = CodecFactory.extract(file);
        Codec destinationCodec = format.equals("mp4") ? new MPEG4CompressionCodec() : new OggCompressionCodec();
        VideoFile buffer = BitrateReader.read(file, sourceCodec);
        VideoFile intermediateResult = BitrateReader.convert(buffer, destinationCodec);
        return new AudioMixer().fix(intermediateResult);
    }
}

PILLAR 5: The Grill Round

Trap: "Does a Facade prevent clients from accessing subsystems?" Answer: "No. A Facade provides a convenient default path. Power users can still bypass the Facade and interact with subsystems directly if they need granular control."

4. The Proxy Pattern

PILLAR 1: Theory

The Proxy pattern uses a surrogate or placeholder object to control access to another object. This solves the pain of expensive initialization (Virtual Proxy), security (Protection Proxy), or network boundaries (Remote Proxy).

PILLAR 5: The Grill Round

Trap: "How does Spring AOP use Proxies?" Answer: "Spring uses JDK Dynamic Proxies if the target implements interfaces, or CGLIB to subclass target classes if they do not. Proxies intercept method calls to inject cross-cutting concerns like `@Transactional`."

5. The Composite Pattern

PILLAR 1: Theory

The Composite Pattern lets you compose objects into tree structures and then work with these structures as if they were individual objects. The pain point is writing branch logic (`if (node is directory) then traverse, else return size`).

PILLAR 5: The Grill Round

Trap: "Safety vs Transparency?" Answer: "Placing child-management methods (`add`, `remove`) in the base Component interface gives client Transparency (treat all nodes exactly identically) but loses Safety (calling `add` on a Leaf throws an exception). Moving them to the Composite class provides Safety at the cost of requiring type casts."
