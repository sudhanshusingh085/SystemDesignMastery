Object-Oriented Programming (OOP) Fundamentals — Complete Deep Dive

Object-Oriented Programming is a paradigm based on the concept of "objects", which can contain data and code. Let's dive deep into the fundamental concepts of OOP in Java 21.

1. Class & Object

What is it? A class is a blueprint, and an object is an actual instance created from that blueprint.

📖 Class: A template or blueprint that defines the state (fields) and behavior (methods) of a certain type of item.
📖 Object: A specific instance of a class, existing in memory with its own unique state.

Real-World Analogy

Think of a class as a cookie cutter. It defines the shape of a cookie. The objects are the actual cookies you bake using that cutter. You can make many cookies from one cutter.

graph LR A[Cookie Cutter (Class)] --> B[Cookie 1 (Object)] A --> C[Cookie 2 (Object)] A --> D[Cookie 3 (Object)]

Figure 1: Class vs Object

Java 
public class Dog {
    // Fields (State)
    private String name;
    private String breed;
    private int age;

    // Constructor
    public Dog(String name, String breed, int age) {
        this.name = name;
        this.breed = breed;
        this.age = age;
    }

    // Methods (Behavior)
    public void bark() {
        System.out.println(name + " says: Woof!");
    }
}

public class Main {
    public static void main(String[] args) {
        // Creating objects (instantiation)
        Dog myDog = new Dog("Buddy", "Golden Retriever", 3);
        Dog neighborDog = new Dog("Max", "German Shepherd", 5);

        myDog.bark(); // Buddy says: Woof!
    }
}

2. Encapsulation

What is it? Bundling data and methods that operate on that data within a single unit, and restricting direct access to some of the object's components.

📖 Encapsulation: Hiding internal state and requiring all interaction to be performed through an object's methods.

Real-World Analogy

A car dashboard hides the complex engine mechanics. You press a button to start the car, but you don't need to manually ignite fuel. You only interact with the exposed, safe controls.

graph TD A[Client Code] -->|Allowed via Methods| B[Public Interface] B -->|Manages| C[Private Data / Internal Logic] A -.->|Blocked| C

Figure 2: Encapsulation

Java 
public class BankAccount {
    // Private state: hidden from the outside world
    private double balance;

    public BankAccount(double initialBalance) {
        if (initialBalance >= 0) {
            this.balance = initialBalance;
        }
    }

    // Public method: controlled access to internal state
    public void deposit(double amount) {
        if (amount > 0) {
            balance += amount;
            System.out.println("Deposited: $" + amount);
        } else {
            System.out.println("Invalid deposit amount.");
        }
    }

    public void withdraw(double amount) {
        if (amount > 0 && balance >= amount) {
            balance -= amount;
            System.out.println("Withdrawn: $" + amount);
        } else {
            System.out.println("Insufficient funds or invalid amount.");
        }
    }

    // Read-only access
    public double getBalance() {
        return balance;
    }
}

3. Abstraction

What is it? Hiding complex implementation details and showing only the essential features of an object.

📖 Abstraction: The process of simplifying complex reality by modeling classes appropriate to the problem, exposing only what is necessary.

Real-World Analogy

Using an ATM. You interact with a screen and buttons to withdraw cash. You don't see or need to understand the complex internal wiring, network requests to the bank, and mechanical cash dispensing mechanisms.

graph LR A[User] -->|Interacts with| B[ATM Interface] B -->|Hides complex logic| C[Bank Servers & Mechanics]

Figure 3: Abstraction

Java 
// Abstract class defines the concept but hides implementation
public abstract class Shape {
    protected String color;

    public Shape(String color) {
        this.color = color;
    }

    // Abstract method: what to do, not how to do it
    public abstract double area();
    
    public void display() {
        System.out.println("This is a " + color + " shape.");
    }
}

// Concrete classes provide the specific implementation
public class Circle extends Shape {
    private double radius;

    public Circle(String color, double radius) {
        super(color);
        this.radius = radius;
    }

    @Override
    public double area() {
        return Math.PI * radius * radius;
    }
}

public class Rectangle extends Shape {
    private double length, width;

    public Rectangle(String color, double length, double width) {
        super(color);
        this.length = length;
        this.width = width;
    }

    @Override
    public double area() {
        return length * width;
    }
}

4. Inheritance

What is it? A mechanism where a new class derives properties and behaviors (methods) from an existing class.

📖 Inheritance: Establishing an "is-a" relationship to promote code reuse.

Real-World Analogy

A child inherits traits (like eye color or surname) from their parents, but can also have their own unique traits or behaviors.

classDiagram Animal <|-- Dog Dog <|-- GoldenRetriever class Animal{ +eat() } class Dog{ +bark() } class GoldenRetriever{ +fetch() }

Figure 4: Inheritance Hierarchy

Types of Inheritance:

  • Single: Class B extends Class A.
  • Multilevel: Class C extends Class B, which extends Class A.
  • Hierarchical: Class B and Class C both extend Class A.
  • Note: Java does not support Multiple Class Inheritance (where a class extends multiple classes) to avoid the Diamond Problem, though a class can implement multiple interfaces.
Java 
public class Animal {
    public void eat() {
        System.out.println("This animal is eating.");
    }
}

// Single Inheritance
public class Dog extends Animal {
    public void bark() {
        System.out.println("Woof!");
    }
}

// Multilevel Inheritance
public class GoldenRetriever extends Dog {
    public void fetch() {
        System.out.println("Fetching the ball!");
    }
}

5. Polymorphism

What is it? The ability of a single interface or method to take on multiple forms.

📖 Polymorphism: "Many forms." Treating objects of different classes through a common interface or superclass.

Real-World Analogy

The word 'draw' means different things depending on the context. To an artist, it means creating a picture. To a cowboy, it means pulling out a gun. The action is the same, but the behavior changes.

graph TD A[Method 'draw'] -->|Artist| B[Creates Art] A -->|Cowboy| C[Pulls Gun]

Figure 5: Polymorphism

Types of Polymorphism:

  • Compile-time (Method Overloading): Multiple methods with the same name but different parameters in the same class.
  • Runtime (Method Overriding): A subclass provides a specific implementation of a method already provided by its parent class.
Java 
// 1. Compile-time Polymorphism (Overloading)
public class Calculator {
    public int add(int a, int b) {
        return a + b;
    }
    
    // Same method name, different parameters
    public double add(double a, double b) {
        return a + b;
    }
}

// 2. Runtime Polymorphism (Overriding)
public class Main {
    public static void main(String[] args) {
        // Using the Shape hierarchy from earlier
        Shape s1 = new Circle("Red", 5.0);
        Shape s2 = new Rectangle("Blue", 4.0, 5.0);
        
        // Polymorphic calls: java decides at runtime which area() to call
        printArea(s1);
        printArea(s2);
    }
    
    public static void printArea(Shape shape) {
        // shape.area() behaves differently depending on the actual object type
        System.out.println("Area: " + shape.area());
    }
}

6. Association

What is it? A relationship where two objects are related, but they have independent lifecycles. They can exist without each other.

Real-World Analogy

A teacher and a student. A teacher teaches many students, and a student can have many teachers. Both can exist independently.

classDiagram Teacher "1" -- "*" Student : teaches

Figure 6: Association

Java 
public class Student {
    private String name;
    
    public Student(String name) { this.name = name; }
    public String getName() { return name; }
}

public class Teacher {
    private String name;
    
    public Teacher(String name) { this.name = name; }
    
    // Association: Teacher interacts with Student, but doesn't own them
    public void teach(Student student) {
        System.out.println(this.name + " is teaching " + student.getName());
    }
}

7. Aggregation

What is it? A specialized form of association indicating a "HAS-A" relationship, but the child object can exist independently of the parent object. It represents a weak ownership.

Real-World Analogy

A university department and professors. A department HAS professors. If the department closes, the professors still exist and can join another department.

classDiagram Department o-- Professor

Figure 7: Aggregation

Java 
import java.util.List;

public class Professor {
    private String name;
    public Professor(String name) { this.name = name; }
}

public class Department {
    private String name;
    // Aggregation: Department has Professors, but they are passed in from outside
    private List professors;

    public Department(String name, List professors) {
        this.name = name;
        this.professors = professors;
    }
}

8. Composition

What is it? A strict "HAS-A" relationship where the child object's lifecycle depends strictly on the parent object. If the parent dies, the child dies.

Real-World Analogy

A house and its rooms. A house HAS rooms. If the house is demolished, the rooms cease to exist.

classDiagram House *-- Room

Figure 8: Composition

Java 
import java.util.ArrayList;
import java.util.List;

class Room {
    private String name;
    public Room(String name) { this.name = name; }
}

public class House {
    private List rooms;

    public House() {
        // Composition: Rooms are created INSIDE the House.
        // They die when the House is garbage collected.
        rooms = new ArrayList<>();
        rooms.add(new Room("Living Room"));
        rooms.add(new Room("Bedroom"));
    }
}

9. Association vs Aggregation vs Composition

Concept Relationship Type Lifecycle Dependency Example
Association Uses-a / Interacts-with Independent Doctor and Patient
Aggregation Has-a (Weak) Independent Car and Passengers
Composition Part-of (Strong) Dependent (Parent dies, child dies) Car and Engine

10. Coupling

What is it? How much one class depends on the internal details of another class.

📖 Coupling: The degree of interdependence between software modules. Tight = bad, Loose = good.

Real-World Analogy

A lamp hardwired into the wall is tightly coupled. If the lamp breaks, you have to tear the wall open. A lamp with a plug is loosely coupled. You can easily unplug it and plug in a different lamp.

Tightly Coupled (Bad)

// OrderService directly depends on MySQL
public class OrderService {
    private MySqlDatabase db;

    public OrderService() {
        this.db = new MySqlDatabase();
    }
}

Loosely Coupled (Good)

// OrderService depends on an Interface
public class OrderService {
    private Database db;

    public OrderService(Database db) {
        this.db = db;
    }
}

11. Cohesion

What is it? How closely related the responsibilities of a single class are. A highly cohesive class does one thing well.

📖 Cohesion: The degree to which elements inside a module belong together. High = good, Low = bad.

Real-World Analogy

A Swiss Army Knife has low cohesion (does a bit of everything: cutting, screwing, filing). A dedicated power drill has high cohesion (does exactly one job exceptionally well).

Low Cohesion (Bad)

public class UserService {
    public void createUser() { ... }
    public void sendEmail() { ... }
    public void logError() { ... }
    public void connectToDb() { ... }
}

High Cohesion (Good)

public class UserService {
    private EmailService emailService;
    private UserRepository repo;
    
    public void createUser() { 
        // delegate to dedicated classes
    }
}

12. Summary: Coupling vs Cohesion

The ultimate goal in system design and OOP is to achieve Low Coupling and High Cohesion. Modules should be independent of each other, but highly focused on their single responsibility.

In the case study sections (Parking Lot, Chess, etc.), look for comments like // OOP: Composition — Engine cannot exist without Car. These principles form the bedrock of scalable software architecture.
