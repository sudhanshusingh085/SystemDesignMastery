Scalability Deep Dive — Handling Growth

1. What is Scalability?
Scalability is a system's ability to handle an increasing amount of work (more users, more data) by adding resources, without degrading performance.

2. Vertical vs 3. Horizontal Scaling

There are two main ways to scale a system:

AspectVertical Scaling (Scale Up)Horizontal Scaling (Scale Out)
What is it?Adding more CPU/RAM to a single machine.Adding more machines to the pool.
LimitsHardware has a hard limit.Virtually limitless.
ProsSimple to implement. No code changes.High availability, fault tolerance.
ConsSingle point of failure. Expensive at high end.Complex to manage. Requires stateless apps.

5. Auto-Scaling

Dynamically adjusting the number of servers based on traffic.

Java 21 
public class AutoScaler {
    // Java 21 records
    record SystemMetrics(double cpuUsage, int activeConnections) {}
    
    public void evaluateScaling(SystemMetrics metrics) {
        if (metrics.cpuUsage() > 80.0) {
            System.out.println("Scale Out: Adding 1 instance");
        } else if (metrics.cpuUsage() < 20.0) {
            System.out.println("Scale In: Removing 1 instance");
        }
    }
}

6. Load Balancing Deep Dive

Distributes incoming traffic across multiple backend servers.

graph TD A[Clients] --> B[Load Balancer] B -->|Algorithm| C[Server 1] B -->|Algorithm| D[Server 2] B -->|Algorithm| E[Server 3]

Figure 1: Load Balancer

Algorithms:

  • Round Robin: Sequential distribution.
  • Least Connections: Sends traffic to the server with fewest active connections.
  • IP Hash: Uses client IP to consistently route to the same server (good for stateful apps).

7. Database Scaling

Scaling databases is harder than scaling stateless web servers.

  • Read Replicas: Master DB handles writes, multiple replica DBs handle reads.
  • Sharding: Splitting data across multiple databases (e.g., Users A-M on DB1, N-Z on DB2).
  • Connection Pooling: Reusing database connections to save overhead.

10. Stateless vs Stateful Services

To easily scale horizontally, your application must be Stateless — meaning it doesn't store session data locally. Store sessions in a shared Redis cache instead.

Java 21 
public class StatelessServiceDemo {
    // BAD: Stateful - cannot be easily scaled horizontally
    private int userSessionScore = 0;
    
    public void incrementScore() { userSessionScore++; }
    
    // GOOD: Stateless - delegates state to an external store (e.g., Redis)
    public void incrementScoreStateless(String userId, RedisClient redis) {
        redis.increment("score:" + userId);
    }
    
    record RedisClient() {
        void increment(String key) { /* Call external DB */ }
    }
}

11. Queue-Based Load Leveling

If traffic spikes unpredictably, place a Message Queue (like Kafka or RabbitMQ) in front of your workers. The queue buffers requests so workers aren't overwhelmed.

12. Data Partitioning

When sharding, how do you know where data goes? Hash-based partitioning applies a hash function to the ID (e.g., hash(userId) % numberOfServers). Consistent Hashing minimizes reorganization when servers are added/removed.

13. Capacity Planning & 14. Bottleneck Identification

Back-of-the-envelope math (estimating QPS, storage requirements). Remember Amdahl's Law: the overall performance improvement is limited by the fraction of the system that cannot be sped up.

15. Summary Checklist

System Design Scaling Checklist:
  • Add a Load Balancer
  • Make Web Servers Stateless
  • Add caching (Redis/Memcached)
  • Use a CDN for static assets
  • Scale Database (Replication -> Sharding)
  • Use Queues for asynchronous tasks
