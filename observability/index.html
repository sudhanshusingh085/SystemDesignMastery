Observability — Monitoring, Logging, Tracing

1. What is Observability?
Observability is the ability to understand the internal state of your system just by looking at its external outputs (data).

Real-World Analogy: Your car's dashboard. You don't need to open the hood to know you are running out of fuel, the engine is overheating, or how fast you're going. The dashboard gives you all that data.

2. The 3 Pillars of Observability

A truly observable system requires three main components:

  • Metrics: Numerical data measured over time (e.g., CPU usage %, memory used, requests per second).
  • Logs: Immutable, timestamped records of discrete events (e.g., "User logged in", "Database connection failed").
  • Traces: The journey of a single request across multiple microservices.

3. Metrics Deep Dive

What should you measure? Two common frameworks:

  • RED Method (for services): Rate (requests/sec), Errors (failures/sec), Duration (latency).
  • USE Method (for resources): Utilization (% busy), Saturation (queue length), Errors.
import java.util.concurrent.atomic.AtomicLong;
import java.util.concurrent.atomic.DoubleAdder;

public class MetricsDemo {
    record MetricsCollector(
        AtomicLong requestCounter,
        AtomicLong activeConnections,
        DoubleAdder totalResponseTime
    ) {
        public MetricsCollector() {
            this(new AtomicLong(0), new AtomicLong(0), new DoubleAdder());
        }

        public void recordRequest(long durationMs) {
            requestCounter.incrementAndGet();
            totalResponseTime.add(durationMs);
        }
        
        public void openConnection() { activeConnections.incrementAndGet(); }
        public void closeConnection() { activeConnections.decrementAndGet(); }
    }
}
using System.Diagnostics.Metrics;

public class MetricsDemo
{
    private static readonly Meter AppMeter = new("Ecommerce.Api", "1.0.0");
    private static readonly Counter<long> RequestCounter = AppMeter.CreateCounter<long>("requests.total");
    private static readonly UpDownCounter<int> ActiveConnections = AppMeter.CreateUpDownCounter<int>("connections.active");
    private static readonly Histogram<double> RequestDuration = AppMeter.CreateHistogram<double>("request.duration.ms");

    public void RecordRequest(double durationMs)
    {
        RequestCounter.Add(1);
        RequestDuration.Record(durationMs);
    }

    public void OpenConnection() => ActiveConnections.Add(1);
    public void CloseConnection() => ActiveConnections.Add(-1);
}

4. Logging Best Practices

Logs should be structured (usually JSON) so they can be easily queried and filtered by tools like Elasticsearch or Splunk.

BAD LOGGING log.error("Error occurred");

No context! Which user? What time? What error?

GOOD LOGGING (Structured) {"level": "ERROR", "timestamp": "2026-10-01T12:00:00Z", "correlationId": "abc-123", "service": "payment-api", "message": "Failed to charge card", "userId": "881"} 
import java.time.Instant;

public class LoggingDemo {
    record LogMessage(
        String level, 
        Instant timestamp, 
        String correlationId, 
        String service, 
        String message
    ) {
        public String toJson() {
            return """
                {
                    "level": "%s",
                    "timestamp": "%s",
                    "correlationId": "%s",
                    "service": "%s",
                    "message": "%s"
                }
                """.formatted(level, timestamp, correlationId, service, message);
        }
    }
}

5. Distributed Tracing

When a single request hits 5 different microservices, how do you debug a failure? Distributed tracing assigns a unique Trace ID to the request at the gateway. This ID is passed to every downstream service.

public class TracingDemo {
    record Span(String traceId, String spanId, String parentSpanId, String name, long startTime, long endTime) {}
    
    public class Tracer {
        private static final ThreadLocal<String> currentTraceId = new ThreadLocal<>();
        
        public static void setTraceId(String traceId) { currentTraceId.set(traceId); }
        public static String getTraceId() { return currentTraceId.get(); }
        public static void clear() { currentTraceId.remove(); }
    }
}
using System.Diagnostics;

public class TracingDemo
{
    // Industry standard W3C Activity Source in .NET 8 / OpenTelemetry
    private static readonly ActivitySource Source = new("Ecommerce.DistributedTracer");

    public static Activity? StartSpan(string operationName)
    {
        return Source.StartActivity(operationName, ActivityKind.Server);
    }

    // Fallback ambient trace context using AsyncLocal for async flows
    public static class AsyncLocalTracer
    {
        private static readonly AsyncLocal<string?> CurrentTraceId = new();
        public static void SetTraceId(string traceId) => CurrentTraceId.Value = traceId;
        public static string? GetTraceId() => CurrentTraceId.Value;
    }
}

6. Alerting

Don't alert on everything. Alert Fatigue happens when engineers ignore alerts because there are too many false positives. Alert on symptoms (high latency, high error rate) rather than causes (high CPU).

7. SLI, SLO, SLA

  • SLI (Service Level Indicator): The actual metric (e.g., 99.5% of requests completed in < 200ms).
  • SLO (Service Level Objective): Your internal target (e.g., We aim for 99.9% of requests to complete in < 200ms).
  • SLA (Service Level Agreement): The legal contract with clients (e.g., We guarantee 99.5% uptime, or we refund you money).

8. Dashboards & 9. Tools

A good dashboard shows the Golden Signals (Latency, Traffic, Errors, Saturation). Popular tools:

  • Metrics: Prometheus, Datadog
  • Dashboards: Grafana
  • Logs: ELK Stack (Elasticsearch, Logstash, Kibana)
  • Tracing: Jaeger, Zipkin
