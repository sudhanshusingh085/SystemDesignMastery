Simulation 1: HLD — Design a Ride-Sharing App (like Uber)

A classic High-Level Design (HLD) question. Notice how the candidate starts by clarifying requirements before jumping into solutions.

🎙️ INTERVIEWER: Design a ride-sharing app like Uber.

🎓 CANDIDATE: Before I start, I'd like to ask a few clarifying questions to understand the scope.

  • Who are our primary users? (Riders and Drivers?)
  • What is the core functionality? Just booking a ride, or do we need carpooling, scheduled rides, and food delivery?
  • How many Daily Active Users (DAU) are we expecting?
  • What regions are we operating in? Global or local?
  • Do we need to handle payments within the app?
  • How critical is the ETA accuracy?

🎙️ INTERVIEWER: Great questions. Primary users are Riders and Drivers. Let's focus on the core functionality: a rider requests a ride, and a nearby driver accepts it. No carpooling or food delivery for now. Assume 50 million DAU, global operation. Yes, handle payments, and ETA should be reasonably accurate but doesn't have to be perfect initially.

🎓 CANDIDATE: Great, let me summarize the requirements.

Functional Requirements:
  • Riders can request a ride.
  • Drivers can accept or decline a ride request.
  • Riders can see nearby drivers and track their driver's location in real-time.
  • System calculates ETA and pricing.
  • Payment processing at the end of the ride.
Non-Functional Requirements:
  • Low Latency: Ride matching should be fast.
  • High Availability: The system shouldn't go down.
  • Scalability: Must handle high concurrent requests (50M DAU).
  • Consistency: Payment and ride state must be strongly consistent.

🎓 CANDIDATE: Let me start with the high-level architecture. I'll break this into a few microservices: A Rider Service, a Driver Service (Location Tracking), a Ride Matching Service, and a Payment Service.

graph TD Rider[Rider App] --> API[API Gateway] Driver[Driver App] --> API API --> RiderSvc[Rider Service] API --> DriverLoc[Driver Location Service] API --> Matching[Ride Matching Service] API --> Payment[Payment Service] DriverLoc --> Redis[(Redis Geo Hash)] Matching --> Redis Matching --> TripDB[(Trip DB / PostgreSQL)] Payment --> PaymentGateway[External Payment Gateway]

Figure 1: High-Level Architecture of a Ride-Sharing App

📖 Redis Geo Hash: A data structure in Redis that allows you to store coordinates (longitude and latitude) and easily search for nearby points (like finding drivers within a 3km radius).

🎙️ INTERVIEWER: How does the Driver Location Service handle real-time updates? Drivers are moving constantly.

🎓 CANDIDATE: Drivers send their GPS coordinates every few seconds. We can use a WebSocket connection for real-time, bi-directional communication. If they send it every 5 seconds, that's a lot of writes. We shouldn't write this directly to a traditional relational database because it will overwhelm the database. Instead, I'd write these updates to Redis or an in-memory datastore using Geo-hashing, which is optimized for high read/write throughput and spatial queries.

🎙️ INTERVIEWER: What about the Ride Matching algorithm? How do you ensure two riders don't book the same driver?

🎓 CANDIDATE: Good point. The Ride Matching Service will query Redis for nearby available drivers. We can use a distributed lock (like Redlock) on the driver's ID when a request is sent to them. Or, better yet, we can use an optimistic concurrency control mechanism in our Trip Database. If two requests try to assign the same driver, the database will only allow one transaction to succeed, and the other rider's request will retry and pick the next available driver.

🎙️ INTERVIEWER: Excellent. Let's move on.

Simulation 2: LLD — Design a Movie Ticket Booking System

A Low-Level Design (LLD) interview focuses on classes, objects, design patterns, and core logic.

🎙️ INTERVIEWER: Design a movie ticket booking system like BookMyShow or Fandango.

🎓 CANDIDATE: Sure! A few questions first to clarify the scope:

  • Are we focusing on the backend APIs and classes?
  • Can a theater have multiple screens, and each screen multiple shows?
  • How do we handle concurrency? E.g., two users trying to book the exact same seat at the same time.
  • Do we need to support different payment methods?

🎙️ INTERVIEWER: Yes to backend classes. Yes, multiple screens and shows. Concurrency is critical—only one user should get the seat. And yes, support multiple payment methods.

🎓 CANDIDATE: Let me identify the main entities and their relationships. We'll need `Movie`, `Theater`, `Screen`, `Show`, `Seat`, `Booking`, `User`, and payment classes.

🎓 CANDIDATE: I'll now write the Java 21 code for this. I'll use record types for immutable data and the Strategy Pattern for payments.

Java 21 

import java.util.List;
import java.util.concurrent.locks.ReentrantLock;

// Using Java records for simple data carriers (Immutable)
public record User(String id, String name, String email) {}
public record Movie(String id, String title, int durationInMinutes) {}

// Enums
enum SeatStatus { AVAILABLE, LOCKED, BOOKED }
enum SeatType { REGULAR, PREMIUM }

class Seat {
    private final String id;
    private final SeatType type;
    private SeatStatus status;
    private final ReentrantLock lock; // For thread-safe booking

    public Seat(String id, SeatType type) {
        this.id = id;
        this.type = type;
        this.status = SeatStatus.AVAILABLE;
        this.lock = new ReentrantLock();
    }

    // Thread-safe method to lock a seat temporarily during checkout
    public boolean lockSeat() {
        if (lock.tryLock()) {
            try {
                if (this.status == SeatStatus.AVAILABLE) {
                    this.status = SeatStatus.LOCKED;
                    return true;
                }
            } finally {
                lock.unlock();
            }
        }
        return false; // Seat is already locked or booked
    }

    public void confirmBooking() {
        this.status = SeatStatus.BOOKED;
    }
}

// Design Pattern: Strategy Pattern for Payments
// SOLID: Open/Closed Principle - We can add new payment methods without changing existing code.
sealed interface PaymentStrategy permits CreditCardPayment, UPIPayment {
    boolean pay(double amount);
}

final class CreditCardPayment implements PaymentStrategy {
    @Override
    public boolean pay(double amount) {
        System.out.println("Paid " + amount + " via Credit Card.");
        return true;
    }
}

final class UPIPayment implements PaymentStrategy {
    @Override
    public boolean pay(double amount) {
        System.out.println("Paid " + amount + " via UPI.");
        return true;
    }
}

// Booking Service handling the core logic
class BookingManager {
    // SOLID: Single Responsibility Principle - This class only handles the booking flow.
    public boolean bookTickets(User user, Show show, List selectedSeats, PaymentStrategy paymentMethod) {
        // 1. Try to lock all seats to prevent double booking
        boolean allLocked = true;
        for (Seat seat : selectedSeats) {
            if (!seat.lockSeat()) {
                allLocked = false;
                break;
            }
        }

        if (!allLocked) {
            // Rollback: unlock seats if we couldn't lock all of them
            System.out.println("Sorry, some seats were just taken!");
            return false;
        }

        // 2. Process Payment
        double totalAmount = calculateTotal(selectedSeats);
        boolean paymentSuccess = paymentMethod.pay(totalAmount);

        // 3. Confirm or Release
        if (paymentSuccess) {
            selectedSeats.forEach(Seat::confirmBooking);
            System.out.println("Booking successful for " + user.name());
            return true;
        } else {
            // Handle payment failure, release locks (implementation omitted for brevity)
            System.out.println("Payment failed.");
            return false;
        }
    }

    private double calculateTotal(List seats) {
        // Simplified pricing
        return seats.stream().mapToDouble(s -> 10.0).sum(); 
    }
}

🎙️ INTERVIEWER: The lock on the Seat object handles threads in a single JVM. What if we have multiple instances of this backend service running across different servers?

🎓 CANDIDATE: Ah, excellent point. In a distributed environment, standard Java locks won't work across different JVM instances. We would need a Distributed Lock. We could use Redis (Redlock) or a database-level lock (e.g., SELECT ... FOR UPDATE) on the Seat table row to ensure only one server can lock a specific seat at a time.

Simulation 3: Mixed — Design a Payment Gateway

Often, interviews blur the lines between HLD and LLD. You might be asked to architect a system and then dive deep into the code of a critical component.

🎙️ INTERVIEWER: Design a Payment Gateway that processes payments for merchants (like Stripe).

🎓 CANDIDATE: Got it. To gather requirements:

  • Are we taking the credit card details directly, or redirecting to a bank? (Assume direct API)
  • What is the expected throughput? (Say, 1000 TPS)
  • We definitely need absolute consistency and idempotency. No one should be charged twice for the same order.

🎙️ INTERVIEWER: Exactly. Let's briefly look at the High-Level flow.

🎓 CANDIDATE: Sure, here is the basic flow.

sequenceDiagram participant Client participant API as API Gateway participant PG as Payment Gateway participant DB as Payment DB participant Bank as Bank API Client->>API: POST /charge (Idempotency-Key: X) API->>PG: Process Payment PG->>DB: Check if Key X exists alt Key exists (Duplicate) DB-->>PG: Return previous status PG-->>API: 200 OK (Previous Result) else New Request PG->>DB: Save Pending State PG->>Bank: Process Transfer Bank-->>PG: Success / Fail PG->>DB: Update State PG-->>API: 200 OK end

Figure 3: Sequence of Idempotent Payment Processing

📖 Idempotency: The property of an operation where doing it once has the same effect as doing it multiple times. If a user clicks "Pay" twice by accident, an idempotent API ensures they are only charged once.

🎙️ INTERVIEWER: Perfect. Now, let's write the core Java code for the Payment Processor, focusing on how you'd structure the result handling and retries.

🎓 CANDIDATE: I'll use Java 21's sealed interfaces and pattern matching for safe and exhaustive handling of different payment outcomes.

Java 21 

import java.util.UUID;

// Immutable record for the request
public record PaymentRequest(String idempotencyKey, double amount, String merchantId, String currency) {}

// Sealed interface for strict outcome control
// SOLID: Open/Closed - We know exactly what outcomes are possible.
sealed interface PaymentResult {
    record Success(String transactionId) implements PaymentResult {}
    record Failure(String reason, boolean retryable) implements PaymentResult {}
    record Pending(String statusUrl) implements PaymentResult {}
}

interface BankClient {
    PaymentResult executeTransfer(PaymentRequest request);
}

class PaymentProcessor {
    private final BankClient bankClient;
    private final Database db; // Hypothetical DB interface

    public PaymentProcessor(BankClient bankClient, Database db) {
        this.bankClient = bankClient;
        this.db = db;
    }

    public PaymentResult process(PaymentRequest request) {
        // 1. Check Idempotency (Prevent double charging)
        if (db.exists(request.idempotencyKey())) {
            return db.getPreviousResult(request.idempotencyKey());
        }

        // 2. Process with the bank
        PaymentResult result = bankClient.executeTransfer(request);

        // 3. Handle the result using Java 21 Pattern Matching for switch
        switch (result) {
            case PaymentResult.Success s -> {
                System.out.println("Payment successful! TX: " + s.transactionId());
                db.save(request.idempotencyKey(), s);
            }
            case PaymentResult.Failure f when f.retryable() -> {
                System.out.println("Payment failed due to: " + f.reason() + ". Queuing for retry.");
                // Add to retry queue logic...
                db.save(request.idempotencyKey(), f);
            }
            case PaymentResult.Failure f -> {
                System.out.println("Hard failure: " + f.reason() + ". Do not retry.");
                db.save(request.idempotencyKey(), f);
            }
            case PaymentResult.Pending p -> {
                System.out.println("Payment pending, check status at: " + p.statusUrl());
                db.save(request.idempotencyKey(), p);
            }
        }

        return result;
    }
}

🎙️ INTERVIEWER: Very clean. Using switch expressions with sealed types ensures you never forget to handle an outcome type. Great job.

Scoring Rubric

Wondering how you are actually graded? Here is a typical rubric used by major tech companies.

Criteria Weight What They Look For
Requirement Gathering 15% Did they ask good, scoping questions? Did they identify scale and bottlenecks?
Architecture & Design 25% Did they choose the right components? Is the system scalable and highly available?
Deep Dives & Problem Solving 25% Did they understand trade-offs? How well did they handle edge cases (e.g., concurrency, network failures)?
Code Quality (LLD) 20% Clean Object-Oriented Design, use of SOLID principles and appropriate Design Patterns.
Communication 15% Clear explanations, structured thinking, and receptiveness to hints.

🚩 Common Red Flags (What Gets You Rejected)

  • Starting to draw architecture without asking any clarifying questions.
  • No mention of scalability or assuming a single server will handle everything.
  • Ignoring error handling, retries, or failure scenarios.
  • Monolithic thinking when distributed solutions are required.
  • Defensiveness when challenged, or failing to discuss trade-offs (e.g., "SQL is always better than NoSQL").

✅ Green Flags (What Impresses Interviewers)

  • Structured approach (e.g., Requirements → API → High-Level → Deep Dive).
  • Proactive trade-off discussion (e.g., "We gain speed with Redis, but risk data loss if it crashes without persistence").
  • Mentioning monitoring, logging, and alerting in the design.
  • Quick back-of-the-envelope capacity estimations.
  • Clean, modular code with proper Object-Oriented principles.
