Load Balancing

What is Load Balancing?

If you have horizontally scaled your application to use 10 servers, how does a user's browser know which server to talk to? The answer is a Load Balancer.

Think of a load balancer like a traffic cop standing at a busy intersection. Instead of letting all the cars crowd into one lane and cause a massive jam, the traffic cop directs cars evenly across all available lanes so traffic flows smoothly.

📖 Load Balancer (LB): A device or software application that distributes incoming network or application traffic across multiple servers.

Why do we need it?

  • Prevent Overload: Ensures no single server bears too much demand, which could cause it to crash.
  • High Availability: If one server goes down, the load balancer stops sending traffic to it and redirects it to the remaining healthy servers.
  • Performance: Distributes requests to the server closest to the user or the one with the lowest latency.

Types of Load Balancers

Hardware Load Balancers

Physical devices designed specifically to handle massive amounts of traffic (e.g., F5 BIG-IP). Very expensive and hard to configure, but extremely fast.

Software Load Balancers

Software running on standard servers (e.g., Nginx, HAProxy) or provided as a cloud service (AWS ELB). Flexible, cheaper, and highly scalable.

Load Balancing Algorithms

How does the load balancer decide which server gets the next request? It uses an algorithm.

  1. Round Robin: Takes turns. Server A, then Server B, then Server C, then back to A. Good when all servers have identical specs.
  2. Weighted Round Robin: Takes turns, but servers with higher "weights" (e.g., a beefier machine) get more requests.
  3. Least Connections: Sends the request to the server with the fewest active connections. Great for long-lived connections (like WebSockets or heavy DB queries).
  4. IP Hash: Uses the client's IP address to mathematically determine the server. Ensures a specific user always hits the same server (good for session persistence).
  5. Random: Just picks a random server. Simple, but can lead to uneven distribution under small loads.

Layer 4 vs Layer 7 Load Balancing

Load balancers can operate at different levels of the OSI model.

  • Layer 4 (Transport Layer): Routes traffic based on IP address and port (TCP/UDP). It's very fast because it doesn't look at the content of the message.
  • Layer 7 (Application Layer): Routes traffic based on the actual content of the HTTP request (like the URL, headers, or cookies). Slower, but allows smart routing (e.g., sending `/api` requests to one set of servers and `/images` to another).

Health Checks

A load balancer continuously monitors the "health" of its backend servers. It periodically sends a small request (like a ping or an HTTP GET to `/health`). If a server doesn't respond in time, the LB removes it from the pool until it recovers.

Java 21 Code: Load Balancing Strategies

Let's use Java 21's modern features to represent different load balancing algorithms.

Java 
import java.util.List;
import java.util.concurrent.atomic.AtomicInteger;
import java.util.concurrent.ThreadLocalRandom;
import java.util.Comparator;

record ServerNode(String ip, int weight, AtomicInteger activeConnections) {}

sealed interface LoadBalancingStrategy 
    permits RoundRobin, WeightedRoundRobin, LeastConnections, IPHash, RandomStrategy {
    
    ServerNode selectServer(List<ServerNode> servers, String clientIp);
}

final class RoundRobin implements LoadBalancingStrategy {
    private final AtomicInteger counter = new AtomicInteger(0);

    @Override
    public ServerNode selectServer(List<ServerNode> servers, String clientIp) {
        int index = Math.abs(counter.getAndIncrement()) % servers.size();
        return servers.get(index);
    }
}

final class WeightedRoundRobin implements LoadBalancingStrategy {
    private final AtomicInteger counter = new AtomicInteger(0);
    // Simplified implementation: in reality, you'd expand the list or use a weighted selection algorithm
    @Override
    public ServerNode selectServer(List<ServerNode> servers, String clientIp) {
        int totalWeight = servers.stream().mapToInt(ServerNode::weight).sum();
        int index = Math.abs(counter.getAndIncrement()) % totalWeight;
        
        for (ServerNode server : servers) {
            index -= server.weight();
            if (index < 0) return server;
        }
        return servers.getFirst();
    }
}

final class LeastConnections implements LoadBalancingStrategy {
    @Override
    public ServerNode selectServer(List<ServerNode> servers, String clientIp) {
        return servers.stream()
                .min(Comparator.comparingInt(s -> s.activeConnections().get()))
                .orElseThrow();
    }
}

final class IPHash implements LoadBalancingStrategy {
    @Override
    public ServerNode selectServer(List<ServerNode> servers, String clientIp) {
        int index = Math.abs(clientIp.hashCode()) % servers.size();
        return servers.get(index);
    }
}

final class RandomStrategy implements LoadBalancingStrategy {
    @Override
    public ServerNode selectServer(List<ServerNode> servers, String clientIp) {
        int index = ThreadLocalRandom.current().nextInt(servers.size());
        return servers.get(index);
    }
}
💡 Interview Tip: Always draw a load balancer between your client and web servers, and another one between your web servers and app servers. Mention "Nginx" or "HAProxy" and state that you'd use Round Robin initially, but might switch to Least Connections if requests take highly variable amounts of time.
