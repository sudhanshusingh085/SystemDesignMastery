CAP Theorem

What is a Distributed System?

Before understanding CAP, we must understand distributed systems. A distributed system is a group of independent computers (nodes) that appear to the user as a single, coherent system. They talk to each other over a network.

The CAP Theorem Explained

The CAP theorem states that in a distributed data store, you can only guarantee two out of the three following characteristics simultaneously:

  1. C - Consistency: Every read receives the most recent write. If you update your profile picture on Node A, and your friend looks at your profile on Node B a millisecond later, they must see the new picture. Everyone sees the exact same data at the same time.
  2. A - Availability: Every request receives a non-error response. The system is always up and running, even if some nodes fail.
  3. P - Partition Tolerance: The system continues to operate despite an arbitrary number of messages being dropped or delayed by the network between nodes. (i.e., a network wire gets cut).
The Harsh Reality: In modern distributed systems running on the internet, network failures are inevitable. Therefore, you must support Partition Tolerance (P). This means the real choice is between Consistency (C) and Availability (A).

The Real-World Analogy: Two Librarians

Imagine a library with two branches across town (Node A and Node B). They share the same catalog over a phone line (Network).

A customer goes to Branch A and borrows the last copy of "Harry Potter". Librarian A updates her ledger and tries to call Librarian B to tell him the book is gone. But suddenly, the phone lines go down! (Network Partition!).

At that exact moment, a customer walks into Branch B and asks Librarian B to borrow "Harry Potter". Librarian B has a choice to make:

  • Choice 1 (Choose Consistency - CP): Librarian B says, "Sorry, my phone is down, I can't verify if this book is truly available, so I have to close the library until the phones are fixed." (System is Consistent, but Not Available).
  • Choice 2 (Choose Availability - AP): Librarian B says, "According to my ledger it's available, here you go!" He loans out a book he doesn't actually have, creating a conflict later. (System is Available, but Not Consistent).

CP Systems (Consistency + Partition Tolerance)

Used when data accuracy is critical, like financial transactions. If a node loses connection, it will return an error rather than risk showing outdated bank balances. Examples: MongoDB, HBase, Redis, etcd.

AP Systems (Availability + Partition Tolerance)

Used when system uptime is more important than showing the absolute latest data. If Facebook shows you a post that is 5 seconds old instead of 1 second old, it's fine as long as the site doesn't crash. Examples: Cassandra, DynamoDB, CouchDB.

CA Systems (Consistency + Availability)

This implies no partition tolerance, which means all data lives on a single machine. It is not truly distributed. Examples: Traditional single-node PostgreSQL or MySQL.

Java 21 Code: Simulating CAP

Let's model two database nodes. When the network partition happens, we dictate how the node responds based on its CAP configuration.

Java 
import java.util.Optional;

// Enum representing the system's choice during a partition
enum CAP_Mode {
    CP_CONSISTENT, AP_AVAILABLE
}

// Represents a node in our distributed system
class DBNode {
    private String name;
    private String data = "Initial State";
    private boolean networkPartitionActive = false;
    private CAP_Mode mode;

    public DBNode(String name, CAP_Mode mode) {
        this.name = name;
        this.mode = mode;
    }

    public void setNetworkPartition(boolean broken) {
        this.networkPartitionActive = broken;
    }

    // Simulate reading data
    public Optional<String> readData() {
        if (networkPartitionActive) {
            return switch (mode) {
                // In CP mode, we refuse to serve stale data during a network split
                case CP_CONSISTENT -> {
                    System.out.println(name + " [CP Mode]: ERROR - Cannot guarantee consistency. Returning Null.");
                    yield Optional.empty(); 
                }
                // In AP mode, we return whatever data we have, even if it might be stale
                case AP_AVAILABLE -> {
                    System.out.println(name + " [AP Mode]: SUCCESS - Returning stale data.");
                    yield Optional.of(data);
                }
            };
        }
        System.out.println(name + ": SUCCESS - Network is healthy.");
        return Optional.of(data);
    }
}

public class CAPDemo {
    public static void main(String[] args) {
        DBNode bankNode = new DBNode("Banking-DB", CAP_Mode.CP_CONSISTENT);
        DBNode socialNode = new DBNode("SocialMedia-DB", CAP_Mode.AP_AVAILABLE);

        System.out.println("--- Normal Operation (No Partition) ---");
        bankNode.readData();
        socialNode.readData();

        System.out.println("\n--- Network Cable Cut! (Partition Occurs) ---");
        bankNode.setNetworkPartition(true);
        socialNode.setNetworkPartition(true);

        bankNode.readData();   // Fails to maintain consistency
        socialNode.readData(); // Succeeds, but might be stale
    }
}

Beyond CAP: PACELC Theorem

CAP only talks about what happens during a failure (a partition). But what happens during normal operation? The PACELC theorem extends CAP:

PAC: If there is a Partition (P), trade off Availability (A) and Consistency (C).
ELC: Else (E), during normal operation, trade off Latency (L) and Consistency (C).

For example, if you want high Consistency during normal operations, you must endure higher Latency (waiting for all nodes to acknowledge a write).

💡 Interview Tip: When designing a system, explicitly state your choice. "Since we are building a payment gateway, we need strong consistency, so we will favor a CP system. But for the user comments section, we will favor an AP system for high availability."
