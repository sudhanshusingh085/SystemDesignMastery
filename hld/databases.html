Databases & Sharding

SQL vs NoSQL: A Quick Recap

Choosing the right database is one of the most critical decisions in system design.

Feature SQL (Relational) NoSQL (Non-Relational)
Examples PostgreSQL, MySQL, Oracle MongoDB, Cassandra, DynamoDB
Structure Tables with strict schemas (rows & columns) Flexible (JSON documents, Key-Value, Graphs)
Relations Excellent. Powerful JOIN operations. Poor. Data is usually denormalized (duplicated).
Transactions Strong ACID guarantees (very safe) Often eventual consistency (faster, less strict)
Scaling Mostly Vertically (hard to shard) Easily scales Horizontally out-of-the-box
Rule of thumb: Use SQL for financial data, complex relations, and when data integrity is paramount. Use NoSQL for massive amounts of rapidly changing data, simple lookups, or unstructured data.

Database Replication

As traffic grows, a single database becomes a bottleneck. Replication involves keeping copies of your database on multiple machines.

Master-Slave (Primary-Replica)

You have one Master node that handles ALL writes. It then asynchronously copies the data to multiple Slave (Replica) nodes. The Replicas handle read queries.

  • Why? It scales read-heavy applications (most web apps have 10x more reads than writes) and provides backups if the Master fails.

Master-Master (Multi-Primary)

Multiple nodes can accept write operations. Great for availability across different geographic regions, but resolving write conflicts (two people updating the same row at the same time on different masters) is incredibly difficult.

What is Database Sharding?

Replication helps with reads, but what if you have too much data to fit on one hard drive, or too many WRITE requests for one Master? You need Sharding (Partitioning).

Sharding means splitting your massive database into smaller, independent databases (shards) across multiple servers. Each shard contains a distinct subset of the data.

📖 Shard Key: A specific column in your data used to determine which shard a row belongs to. Choosing this is critical!

Types of Sharding

Horizontal Sharding

Splitting tables by rows. E.g., Users with IDs 1-1000 go to DB 1, users 1001-2000 go to DB 2. The schema is identical on both databases.

Vertical Sharding

Splitting by features/tables. E.g., The User table goes to DB 1, the Orders table goes to DB 2. Usually an early step in moving towards microservices.

The Problems with Sharding

  • No more JOINs: You cannot easily join a User table with an Orders table if they live on completely different servers.
  • Hotspots: If you shard by alphabet (A-M on DB1, N-Z on DB2), and everyone suddenly creates accounts starting with 'A', DB1 will crash while DB2 is idle. This is called "Celebrity Problem" or uneven load.
  • Rebalancing: If DB1 gets full, you have to add a new shard and move data around while the system is running.

Java 21 Code: Shard Routing

Here is a basic abstraction of how application code might route a request to a specific database shard using modern Java.

Java 
import java.util.List;

// Abstract representation of a database connection
record DatabaseShard(String dbUrl, String name) {}

// Strategy for picking a shard
sealed interface ShardingStrategy permits HashSharding, RangeSharding {
    DatabaseShard getShard(String shardKey);
}

final class HashSharding implements ShardingStrategy {
    private final List<DatabaseShard> shards;

    public HashSharding(List<DatabaseShard> shards) {
        this.shards = shards;
    }

    @Override
    public DatabaseShard getShard(String shardKey) {
        // Simple modulo hash to distribute keys evenly
        int hash = Math.abs(shardKey.hashCode());
        int shardIndex = hash % shards.size();
        return shards.get(shardIndex);
    }
}

final class RangeSharding implements ShardingStrategy {
    private final DatabaseShard shardA;
    private final DatabaseShard shardB;

    public RangeSharding(DatabaseShard shardA, DatabaseShard shardB) {
        this.shardA = shardA;
        this.shardB = shardB;
    }

    @Override
    public DatabaseShard getShard(String shardKey) {
        // e.g., ShardKey is a User ID string
        char firstChar = shardKey.toUpperCase().charAt(0);
        // A to M goes to Shard A, N to Z goes to Shard B
        return switch (firstChar) {
            case 'A','B','C','D','E','F','G','H','I','J','K','L','M' -> shardA;
            default -> shardB;
        };
    }
}

public class ShardRouterDemo {
    public static void main(String[] args) {
        var shards = List.of(
            new DatabaseShard("jdbc:mysql://db1", "Shard-0"),
            new DatabaseShard("jdbc:mysql://db2", "Shard-1"),
            new DatabaseShard("jdbc:mysql://db3", "Shard-2")
        );
        
        ShardingStrategy router = new HashSharding(shards);
        
        System.out.println("User_999 goes to: " + router.getShard("User_999").name());
        System.out.println("User_42  goes to: " + router.getShard("User_42").name());
        System.out.println("User_7   goes to: " + router.getShard("User_7").name());
    }
}

Indexing and Denormalization

Indexing: Think of an index like the index at the back of a textbook. Instead of reading every page to find a topic, you look at the index, which tells you exactly which page to go to. Databases use B-Trees for indexes, speeding up searches dramatically (O(log N)) at the cost of slightly slower writes (because the index must be updated).

Denormalization: In highly scaled systems, doing SQL JOINs is slow. To fix this, we intentionally duplicate data. Instead of keeping a separate `User` table and doing a JOIN, we might just copy the `UserName` directly into the `Order` table. It takes up more space, but reads become lightning fast.

💡 Interview Tip: Never jump straight to Sharding in an interview! It's incredibly complex. Start with a single Master SQL database. If they ask about scale, propose Master-Slave replication and Caching first. Only propose Sharding when data volume absolutely demands it.
