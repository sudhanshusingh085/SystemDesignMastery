Microservices vs Monoliths

What is a Monolith?

A Monolithic Architecture is a traditional model of software design where all parts of the application (user interface, business logic, data access) are woven together into a single, indivisible unit and deployed as one large application.

Real-World Analogy: A monolith is like a giant, traditional restaurant. The chefs, waiters, cashiers, and dishwashers all work in the same building. If the restaurant needs to close for plumbing repairs in the kitchen, the whole business stops.

What are Microservices?

Microservices Architecture breaks down the application into many small, loosely coupled, and independently deployable services. Each service represents a specific business function.

Real-World Analogy: Microservices are like a modern food court. You have a burger stall, a taco stall, and a coffee stall. They operate independently. If the coffee stall's espresso machine breaks, the burger and taco stalls can keep selling food. They just talk to each other when needed (e.g., using a shared cleaning service).

Comparison

Feature Monolith Microservices
Deployment Deploy the entire application at once. Slow and risky. Deploy individual services independently. Fast and less risky.
Scaling Must scale the whole app, even if only one feature needs it. Scale only the services that have high traffic.
Technology Stack Locked into a single language and framework. Each service can use the best tool/language for the job.
Complexity Codebase becomes a tangled "big ball of mud" over time. Individual services are simple, but managing the network of them is complex.

When to use which?

Use a Monolith when:

  • You are a startup building an MVP (Minimum Viable Product).
  • Your team is small.
  • The domain logic is simple.
  • You need to move fast initially without devops overhead.

Use Microservices when:

  • The application is highly complex and large.
  • You have multiple large engineering teams working concurrently.
  • Different parts of the system need to scale differently.
  • You need high availability (one failure shouldn't take down everything).

Key Concepts in Microservices

Service Communication

How do microservices talk to each other?

  • Synchronous: Using HTTP/REST or gRPC. The caller waits for a response.
  • Asynchronous: Using Message Queues (Kafka, RabbitMQ). The caller fires an event and forgets.

Service Discovery

📖 Service Discovery: Since services might have dynamic IP addresses, a registry keeps track of where every service lives so they can find each other.

Data Management & Distributed Transactions

In microservices, the rule is Database Per Service. Services should never share a database, otherwise they become tightly coupled. But how do you handle a transaction that spans multiple services (like placing an order, deducting inventory, and charging a card)?

📖 Saga Pattern: A sequence of local transactions. If one step fails, the system runs compensating transactions to undo the previous steps (e.g., if charging the card fails, run a transaction to add the inventory back).

Java 21 Code Example: Refactoring

Let's look at how code changes from a Monolith to Microservices using Java 21's sealed interfaces and records.

Java 
// ==========================================
// 1. THE MONOLITH APPROACH
// Everything in one place, calling methods directly.
// ==========================================
class MonolithEcommerceApp {
    
    public void checkout(String userId, String itemId) {
        // Direct, tight coupling
        boolean inStock = checkInventory(itemId);
        if (inStock) {
            boolean paid = chargeUser(userId, 50.0);
            if (paid) {
                createOrder(userId, itemId);
                System.out.println("Monolith: Order placed successfully.");
            }
        }
    }
    
    private boolean checkInventory(String itemId) { return true; }
    private boolean chargeUser(String userId, double amount) { return true; }
    private void createOrder(String userId, String itemId) {}
}

// ==========================================
// 2. THE MICROSERVICES APPROACH
// Services are isolated and communicate via explicit boundaries.
// ==========================================

// Domain Models using Records
record Item(String id, double price) {}
record User(String id) {}
record Order(String orderId, String userId, String itemId) {}

// A sealed interface represents network communication results
sealed interface NetworkResponse<T> permits Success, Failure {}
record Success<T>(T data) implements NetworkResponse<T> {}
record Failure<T>(String error) implements NetworkResponse<T> {}

// Service 1: Inventory
class InventoryMicroservice {
    public NetworkResponse<Boolean> reserveItem(String itemId) {
        // Simulating checking database
        return new Success<>(true);
    }
}

// Service 2: Payment
class PaymentMicroservice {
    public NetworkResponse<Boolean> processPayment(String userId, double amount) {
        return new Success<>(true);
    }
}

// Service 3: Order (The Orchestrator)
class OrderMicroservice {
    private final InventoryMicroservice inventoryService;
    private final PaymentMicroservice paymentService;

    // In reality, these would be HTTP or gRPC clients, not direct references
    public OrderMicroservice(InventoryMicroservice inv, PaymentMicroservice pay) {
        this.inventoryService = inv;
        this.paymentService = pay;
    }

    public void placeOrder(String userId, String itemId) {
        // Java 21 Pattern Matching with switch
        var inventoryStatus = inventoryService.reserveItem(itemId);
        
        switch (inventoryStatus) {
            case Success<Boolean> s when s.data() == true -> {
                
                var paymentStatus = paymentService.processPayment(userId, 50.0);
                
                switch (paymentStatus) {
                    case Success<Boolean> p when p.data() == true -> {
                        System.out.println("Microservices: Order placed successfully.");
                        // Save to local order DB
                    }
                    case Success<Boolean> p -> System.out.println("Payment declined.");
                    case Failure<Boolean> f -> System.out.println("Payment service down: " + f.error());
                }
            }
            case Success<Boolean> s -> System.out.println("Item out of stock.");
            case Failure<Boolean> f -> System.out.println("Inventory service down: " + f.error());
        }
    }
}

public class MicroserviceDemo {
    public static void main(String[] args) {
        new MonolithEcommerceApp().checkout("user123", "item456");
        
        var inventory = new InventoryMicroservice();
        var payment = new PaymentMicroservice();
        var order = new OrderMicroservice(inventory, payment);
        order.placeOrder("user123", "item456");
    }
}

Challenges of Microservices

  • Distributed Debugging: A single request might travel through 5 different services. Tracing an error is hard.
  • Network Latency: Method calls in a monolith are instantaneous. Network calls between microservices take time and can fail.
  • Operational Overhead: You need complex infrastructure (Kubernetes, CI/CD pipelines, monitoring) to manage dozens of services.
Interview Tip: Never say "Microservices are always better." The correct architectural answer is always "It depends." Emphasize that microservices solve organizational scaling problems but introduce massive technical complexity.
