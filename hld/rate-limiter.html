1. Fundamentals & Real-World Context

1.1 What Is Rate Limiting?

Rate limiting controls how many requests a client is allowed to make within a particular rate policy.

💡 Rate Policy Example

User: user123 | Policy: 100 requests / minute
If the user sends requests 1 through 100, all 100 are accepted. Request 101 within that minute is rejected with HTTP 429 Too Many Requests.

1.2 Why Do We Need Rate Limiting?

1. Protect Applications

Prevents sudden traffic spikes (e.g., 100,000 req/sec) from exhausting CPU, threads, or memory, crashing application servers.

2. Protect Databases

Prevents expensive database queries or downstream microservice calls from overwhelming data layers.

3. Prevent Abuse & Scraping

Mitigates brute-force credential stuffing, API scraping, accidental infinite retry loops, and application-layer DoS.

4. Ensure Resource Fairness

Prevents a single noisy tenant from consuming 90% of shared capacity, ensuring multi-tenant isolation.

5. Protect Expensive Operations

Enforces stricter tiers for heavy CPU/IO endpoints (e.g., PDF generation or ML inference) vs cheap reads.

1.3 Rate Limiting vs Throttling vs Backpressure

TermQuestion AskedMechanism
Rate Limiting"How much traffic are you allowed to send?"Rejects excess traffic with HTTP 429 based on quota policies.
Throttling"How much traffic are we willing/able to process?"Slows down or delays requests instead of immediately failing them.
Backpressure"Downstream is overloaded; slow the producer."Feedback mechanism telling upstream publishers to reduce generation rate.

1.4 Where Should Rate Limiting Be Implemented?

  • Client-Side: UI disables buttons / queues requests. Good UX, but not a security boundary.
  • API Gateway (Recommended): Centralized enforcement before requests hit microservices. Protects backend infrastructure, centralizes policy management.
  • Service-Level: Internal microservice enforcement for domain-specific or endpoint-cost-based limits.
  • Multi-Layer Architecture: Gateway enforces global IP limits (10,000 req/sec), Service enforces user limits (100 req/min), Endpoint enforces heavy operation limits (10 req/min).

1.5 Rate-Limit Keys

A rate limit key uniquely identifies the request bucket:

  • rate_limit:ip:10.10.10.10 – IP Address (anonymous traffic; subject to NAT/proxy sharing).
  • rate_limit:user:user123 – Authenticated User ID.
  • rate_limit:apikey:abc123 – API Key (b2b developer portals).
  • rate_limit:user123:/generate-report – Composite key (User ID + Endpoint).

2. Fixed Window Counter Algorithm

Time is divided into fixed windows (e.g., 12:00:00–12:00:59). For each client, we track the current window identifier and a simple counter.

Fixed Window Counter Logic
flowchart TD Req[Incoming Request] --> Key[Identify Client & Current Window] Key --> CheckWindow{Window Changed?} CheckWindow -- Yes --> Reset[Set Window = Current, Count = 0] CheckWindow -- No --> CheckLimit{Count >= Limit?} Reset --> CheckLimit CheckLimit -- Yes --> Reject[Return 429 Too Many Requests] CheckLimit -- No --> Incr[Count = Count + 1] --> Allow[Allow Request to Service]

2.1 Naïve Fixed Window C# Implementation

public class WindowCounter
{
    public long Window { get; set; }
    public int Count { get; set; }
}

public class FixedWindowRateLimiter
{
    private readonly int _maxRequests;
    private readonly TimeSpan _windowSize;
    private readonly Dictionary<string, WindowCounter> _counters = new();

    public FixedWindowRateLimiter(int maxRequests, TimeSpan windowSize)
    {
        _maxRequests = maxRequests;
        _windowSize = windowSize;
    }

    public bool AllowRequest(string clientId)
    {
        long currentWindow = DateTimeOffset.UtcNow.ToUnixTimeMilliseconds() 
            / (long)_windowSize.TotalMilliseconds;

        if (!_counters.TryGetValue(clientId, out var counter))
        {
            counter = new WindowCounter { Window = currentWindow, Count = 0 };
            _counters[clientId] = counter;
        }

        if (counter.Window != currentWindow)
        {
            counter.Window = currentWindow;
            counter.Count = 0;
        }

        if (counter.Count >= _maxRequests)
            return false;

        counter.Count++;
        return true;
    }
}
⚠️ Understanding `currentWindow` Math

Using DateTimeOffset.UtcNow.ToUnixTimeMilliseconds() / windowSizeMs creates continuous integer window buckets (e.g., Window 100000, 100001). This avoids the hour-wrapping bug of DateTime.UtcNow.Minute.

2.2 Thread Safety & Concurrency Trap

The naïve implementation suffers from a Check-Then-Act race condition. If two threads read Count = 99 simultaneously when limit is 100, both see 99 < 100, both increment, allowing 101 requests.

🚩 Senior Interview Tip ConcurrentDictionary makes dictionary operations thread-safe; it does not make multi-step business logic (Read-Check-Increment) atomic! An explicit lock or atomic CAS is required per client.

2.3 Fixed Window Boundary Burst Problem

If a client sends 100 requests at 12:00:59 (end of Window 1) and another 100 requests at 12:01:00 (start of Window 2), 200 requests pass within a 2-second span, breaking rate smoothing while technically respecting fixed limits.

3. Redis Fixed Window & Atomic Lua Scripting

In a distributed multi-server setup, shared state must live in Redis. Using separate Redis INCR and EXPIRE calls introduces a failure window: if the app crashes between INCR and EXPIRE, the key persists forever without a TTL, leaking memory.

3.1 Atomic Redis Lua Script Solution

-- Redis Lua Script: Atomic Fixed Window Counter
local count = redis.call('INCR', KEYS[1])
if count == 1 then
    redis.call('EXPIRE', KEYS[1], ARGV[1])
end
return count
public class RedisFixedWindowRateLimiter
{
    private readonly IDatabase _redis;
    private readonly int _maxRequests;
    private readonly TimeSpan _windowSize;

    private const string LuaScript = """
        local count = redis.call('INCR', KEYS[1])
        if count == 1 then
            redis.call('EXPIRE', KEYS[1], ARGV[1])
        end
        return count
        """;

    public RedisFixedWindowRateLimiter(IDatabase redis, int maxRequests, TimeSpan windowSize)
    {
        _redis = redis;
        _maxRequests = maxRequests;
        _windowSize = windowSize;
    }

    public async Task<bool> AllowRequestAsync(string clientId)
    {
        long currentWindow = DateTimeOffset.UtcNow.ToUnixTimeMilliseconds() / (long)_windowSize.TotalMilliseconds;
        string key = $"rate_limit:{clientId}:{currentWindow}";
        int ttlSeconds = (int)_windowSize.TotalSeconds;

        var result = await _redis.ScriptEvaluateAsync(
            LuaScript,
            new RedisKey[] { key },
            new RedisValue[] { ttlSeconds }
        );

        return (long)result <= _maxRequests;
    }
}

4. Sliding Window Log & Sliding Window Counter

4.1 Sliding Window Log

Stores timestamps of every request in a sorted queue. On each request, removes timestamps older than now - windowSize. If remaining log size < limit, enqueues current timestamp and allows request.

  • Pros: 100% precise rolling window. Completely solves boundary burst problem.
  • Cons: High memory consumption. Stores every timestamp in memory (proportional to request volume).

4.2 Sliding Window Counter (Weighted Approximation)

Combines current window count and previous window count weighted by the elapsed time ratio.

📐 The Weighted Formula

elapsedRatio = elapsedInCurrentWindow / windowSize
previousWeight = 1.0 - elapsedRatio
estimatedCount = (previousCount * previousWeight) + currentCount

public class SlidingWindowCounterRateLimiter
{
    private readonly int _maxRequests;
    private readonly TimeSpan _windowSize;
    private readonly Dictionary<string, WindowCounterState> _counters = new();

    public bool AllowRequest(string clientId)
    {
        DateTimeOffset now = DateTimeOffset.UtcNow;
        long windowMs = (long)_windowSize.TotalMilliseconds;
        long currentWindowNumber = now.ToUnixTimeMilliseconds() / windowMs;
        long windowStartMs = currentWindowNumber * windowMs;
        double elapsedRatio = (double)(now.ToUnixTimeMilliseconds() - windowStartMs) / windowMs;

        if (!_counters.TryGetValue(clientId, out var counter))
        {
            counter = new WindowCounterState { WindowNumber = currentWindowNumber };
            _counters[clientId] = counter;
        }

        if (counter.WindowNumber != currentWindowNumber)
        {
            counter.PreviousCount = counter.CurrentCount;
            counter.CurrentCount = 0;
            counter.WindowNumber = currentWindowNumber;
        }

        double previousWeight = 1.0 - elapsedRatio;
        double estimatedCount = (counter.PreviousCount * previousWeight) + counter.CurrentCount;

        if (estimatedCount >= _maxRequests)
            return false;

        counter.CurrentCount++;
        return true;
    }
}

public class WindowCounterState
{
    public long WindowNumber { get; set; }
    public int CurrentCount { get; set; }
    public int PreviousCount { get; set; }
}

5. Token Bucket Algorithm

A bucket holds up to Capacity tokens. Tokens refill at a steady rate of RefillRate per second. Each request consumes 1 token. If tokens >= 1, request is allowed; otherwise rejected.

Token Bucket Mental Model & Lazy Refill
flowchart TD Refill["Refill Rate (e.g. 2 tokens/sec)"] --> Bucket["Token Bucket (Capacity = 10)"] Req[Incoming Request] --> Check{Tokens >= 1?} Check -- Yes --> Consume[Tokens = Tokens - 1] --> Allow[Allow Request] Check -- No --> Reject[Return 429 Too Many Requests] subgraph LazyRefill["Lazy Refill on Request Arrival"] Calc["elapsed = now - lastRefillTime
tokensToAdd = elapsed * refillRate
tokens = min(capacity, tokens + tokensToAdd)"] end

5.1 Thread-Safe Local C# Implementation (Lazy Refill)

public class TokenBucket
{
    private readonly int _capacity;
    private readonly double _refillRate;
    private double _tokens;
    private DateTimeOffset _lastRefillTime;
    private readonly object _lock = new();

    public TokenBucket(int capacity, double refillRate)
    {
        _capacity = capacity;
        _refillRate = refillRate;
        _tokens = capacity;
        _lastRefillTime = DateTimeOffset.UtcNow;
    }

    public bool TryConsume()
    {
        lock (_lock)
        {
            Refill();
            if (_tokens < 1.0)
                return false;

            _tokens -= 1.0;
            return true;
        }
    }

    private void Refill()
    {
        DateTimeOffset now = DateTimeOffset.UtcNow;
        double elapsedSeconds = (now - _lastRefillTime).TotalSeconds;
        double tokensToAdd = elapsedSeconds * _refillRate;
        
        _tokens = Math.Min(_capacity, _tokens + tokensToAdd);
        _lastRefillTime = now;
    }
}
💡 Why Lazy Refill?

Lazy refill calculates accumulated tokens only when a request arrives (using elapsed * refillRate). This avoids running active background timer loops for millions of idle user buckets.

6. Distributed Token Bucket with Redis & Lua

In a distributed API Gateway environment, multiple nodes reading and updating Redis hash states (tokens and lastRefill) creates race conditions. We execute the full refill and consumption logic inside a single atomic Redis Lua script.

public class RedisTokenBucketRateLimiter
{
    private readonly IDatabase _redis;
    private readonly int _capacity;
    private readonly double _refillRate;

    private const string TokenBucketLua = """
        local key = KEYS[1]
        local now = tonumber(ARGV[1])
        local capacity = tonumber(ARGV[2])
        local refillRate = tonumber(ARGV[3])

        local tokens = tonumber(redis.call('HGET', key, 'tokens'))
        local lastRefill = tonumber(redis.call('HGET', key, 'lastRefill'))

        if tokens == nil then
            tokens = capacity
            lastRefill = now
        end

        local elapsed = (now - lastRefill) / 1000.0
        local newTokens = math.min(capacity, tokens + (elapsed * refillRate))

        if newTokens < 1.0 then
            redis.call('HSET', key, 'tokens', newTokens, 'lastRefill', now)
            return 0
        else
            newTokens = newTokens - 1.0
            redis.call('HSET', key, 'tokens', newTokens, 'lastRefill', now)
            return 1
        end
        """;

    public RedisTokenBucketRateLimiter(IDatabase redis, int capacity, double refillRate)
    {
        _redis = redis;
        _capacity = capacity;
        _refillRate = refillRate;
    }

    public async Task<bool> AllowRequestAsync(string clientId)
    {
        string key = $"rate_limit:{clientId}";
        long nowMs = DateTimeOffset.UtcNow.ToUnixTimeMilliseconds();

        var result = await _redis.ScriptEvaluateAsync(
            TokenBucketLua,
            new RedisKey[] { key },
            new RedisValue[] { nowMs, _capacity, _refillRate }
        );

        return (long)result == 1;
    }
}

7. Date/Time Concepts, Clock Skew & Redis TIME

7.1 `DateTimeOffset.UtcNow` vs Clock Skew

DateTimeOffset.UtcNow standardizes all servers to UTC, eliminating time-zone offsets. However, physical server clocks drift slightly due to hardware variances. Even with NTP synchronization, clock skew (e.g., 20–50 ms difference between app servers) can cause token refill jitter.

7.2 Redis `TIME` for Centralized Authoritative Time

To eliminate client clock skew entirely, the Lua script can query Redis's internal clock via redis.call('TIME'), ensuring all servers use Redis as the single source of truth for time.

-- Query authoritative time inside Redis Lua
local timeArray = redis.call('TIME')
local nowMs = (tonumber(timeArray[1]) * 1000) + math.floor(tonumber(timeArray[2]) / 1000)

8.2 Multi-Region Considerations

  • Local Regional Redis: Fast (<1ms), but user can exhaust quota N times across N regions.
  • Central Global Redis: Strict enforcement, but adds cross-region WAN latency (100ms+).
  • Quota Allocation (Hybrid): Divide global quota across regions (e.g., US gets 60%, EU gets 40%) with periodic sync background daemons.

17 Essential Interview Questions & Model Answers

Q1

Why can't we keep rate-limiter state in local application memory?

In horizontally scaled architectures, load balancers distribute requests across multiple instances. Local memory counters allow clients to bypass global limits by hitting different servers. A centralized state store like Redis is required.

Q2

Why is Lua scripting essential for Redis rate limiting?

Lua scripts execute atomically in Redis. Without Lua, multiple concurrent requests performing separate `HGET`, math calculation, and `HSET` calls introduce race conditions, allowing quota overruns.

Q3

What is the difference between Token Bucket and Leaky Bucket?

Token Bucket allows short bursts of requests up to its capacity while maintaining a steady refill rate. Leaky Bucket processes requests at a strictly constant output rate regardless of incoming bursts (queueing excess calls).

Q4

What HTTP status code and headers should a rate limiter return?

Returns HTTP 429 Too Many Requests along with X-RateLimit-Limit, X-RateLimit-Remaining, and Retry-After headers.

Q5

How do you handle clock skew between application servers?

Use DateTimeOffset.UtcNow across all machines and NTP synchronization. For ultra-strict precision, query Redis's internal authoritative clock via redis.call('TIME') inside Lua scripts.
