Caching

What is Caching?

Caching is the practice of storing a copy of frequently accessed data in a temporary, extremely fast storage location (usually RAM) so that future requests for that data can be served much faster.

Real-world analogy: Imagine you want a glass of milk. Walking all the way to the grocery store every time you get thirsty takes too long (fetching from the Database). Instead, you buy a gallon and keep it in your fridge (the Cache). Now, getting milk takes seconds instead of minutes. Your fridge is a cache for the grocery store!

📖 Cache Hit: When the requested data is found in the cache. Fast!
📖 Cache Miss: When the requested data is NOT in the cache, forcing the system to fetch it from the slower, underlying database.

Where can caching happen?

Caching isn't just one box in a diagram; it happens at almost every layer of modern systems:

  • Client (Browser): Caching images, CSS, and JS files locally.
  • CDN (Content Delivery Network): Caching static assets on servers geographically close to users.
  • Server/App Level: In-memory caches (like Redis or Memcached) storing database query results or computed data.
  • Database Level: Databases themselves cache frequently accessed pages in memory.

Caching Strategies

1. Cache-Aside (Lazy Loading)

The application first asks the cache. If data is there (hit), great. If not (miss), the application queries the DB, reads the data, puts it in the cache, and returns it. Good for read-heavy workloads.

2. Write-Through

Every time the application writes data, it writes it to the cache AND the database simultaneously. Pro: Cache is always up-to-date. Con: Writes take longer.

3. Write-Behind (Write-Back)

The application writes data ONLY to the cache and immediately returns success to the user. A background process asynchronously writes the data to the DB later. Pro: Lightning fast writes. Con: Risk of data loss if the cache crashes before syncing.

4. Read-Through

Similar to Cache-Aside, but the application only talks to the cache. If it's a miss, the cache component itself is responsible for fetching from the DB. Keeps application code cleaner.

Cache Eviction Policies

A cache is usually RAM, which is expensive and limited. When the cache is full, we must kick out old data to make room for new data. This is eviction.

  • LRU (Least Recently Used): Evict the item that hasn't been accessed for the longest time. (Most common).
  • LFU (Least Frequently Used): Evict the item that has been accessed the fewest times overall.
  • FIFO (First In, First Out): Evict the oldest item, regardless of how often it's used.
  • TTL (Time To Live): Data automatically expires and deletes itself after a set time (e.g., 5 minutes).

Java 21 Code: LRU Cache Implementation

Java's LinkedHashMap has a built-in mechanism that makes implementing an LRU cache incredibly easy.

Java 
import java.util.LinkedHashMap;
import java.util.Map;
import java.util.Optional;

// A generic Cache interface
interface Cache<K, V> {
    void put(K key, V value);
    Optional<V> get(K key);
}

// LRU Cache utilizing Java's LinkedHashMap
class LRUCache<K, V> implements Cache<K, V> {
    private final int capacity;
    private final Map<K, V> internalCache;

    public LRUCache(int capacity) {
        this.capacity = capacity;
        // The magic parameters: initialCapacity, loadFactor, accessOrder
        // accessOrder = true means it orders by recently accessed, not insertion order!
        this.internalCache = new LinkedHashMap<>(capacity, 0.75f, true) {
            @Override
            protected boolean removeEldestEntry(Map.Entry<K, V> eldest) {
                // Automatically evict when size exceeds capacity
                return size() > capacity;
            }
        };
    }

    @Override
    public void put(K key, V value) {
        internalCache.put(key, value);
    }

    @Override
    public Optional<V> get(K key) {
        return Optional.ofNullable(internalCache.get(key));
    }
    
    public void printCache() {
        System.out.println("Cache state: " + internalCache);
    }
}

public class CacheDemo {
    public static void main(String[] args) {
        LRUCache<String, String> userCache = new LRUCache<>(3); // Max 3 items
        
        userCache.put("u1", "Alice");
        userCache.put("u2", "Bob");
        userCache.put("u3", "Charlie");
        
        // Cache is full. Now we access "u1", making it the MOST recently used.
        userCache.get("u1");
        
        // Add a 4th item. This will trigger eviction of the LEAST recently used.
        // Since u1 was just accessed, u2 is the oldest/least recently used!
        userCache.put("u4", "Dave");
        
        userCache.printCache(); 
        // Output will show: {u3=Charlie, u1=Alice, u4=Dave}. Bob (u2) was evicted!
    }
}

Cache Invalidation: The Hardest Problem

As the famous quote goes: "There are only two hard things in Computer Science: cache invalidation and naming things."

If the data in your database changes, the data in your cache is now stale (incorrect). You must invalidate (delete) the cached copy so the next read fetches the fresh data. If this fails, users see old, wrong data.

When NOT to cache

  • When data changes constantly (e.g., real-time stock prices). The overhead of constantly updating the cache is worse than just reading the DB.
  • When data is rarely read twice. (Caching implies reuse).
💡 Interview Tip: In a design interview, mention Redis or Memcached. Propose using a Cache-Aside pattern with a TTL (Time-To-Live) on records to ensure stale data eventually expires automatically as a safety net.
