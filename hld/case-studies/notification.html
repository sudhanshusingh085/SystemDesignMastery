Design a Notification System

A notification system alerts users via various channels (Push, SMS, Email) about important events, messages, or promotions.

📖 Idempotency: The property of certain operations in mathematics and computer science whereby they can be applied multiple times without changing the result beyond the initial application. (e.g., ensuring a user isn't notified twice for the same event).

Step 1 — Requirements

Functional Requirements

  • Send notifications via Push (iOS/Android), SMS, and Email.
  • Respect user preferences (opt-outs, quiet hours).
  • Support templating for messages.

Non-functional Requirements

  • High reliability (at-least-once delivery).
  • Low latency (< 5 seconds delay for urgent messages).
  • Scale: 10 Million notifications per day.

Step 3 — Deep Dive

Deduplication

We must ensure we don't spam users with the same notification. We can generate a unique ID for each notification event and use a cache (like Redis) to store this ID for a short period. Before sending, we check if the ID exists in the cache.

Priority Queues

Not all notifications are equal. OTPs and security alerts are high priority and should bypass marketing emails. We use different message queues (e.g., Kafka topics or RabbitMQ queues) based on priority.

⚖️ Architectural Decision Matrix: Why This, Why Not Other?

Architectural Decision Chosen Approach Alternative Considered WHY THIS? (Winning Strengths) WHY NOT THE OTHER? (Disqualifying Trade-offs)
Queue Architecture Multiple Dedicated Priority Queues (OTP vs Marketing) Single Monolithic Shared Queue Guarantees that 50 million promotional discount blast emails do not block time-critical 2FA login OTP SMS codes (< 2s SLA). In a single queue, urgent OTPs wait behind millions of marketing messages (Head-of-Line Blocking), causing users to fail logins.
Deduplication Mechanism Distributed Redis Lock with Idempotency Key (24h TTL) Relational Database Unique Constraint Atomic SETNX executes in < 0.5ms without taking relational database row locks. Scales linearly with traffic. Checking a database table with millions of rows on every notification causes high CPU query spikes and DB write lock contention.
Message Failure Handling Dead Letter Queue (DLQ) with Exponential Backoff Infinite In-Memory Retry Loop Isolates permanently corrupted payloads or invalid phone numbers so they don't block workers from processing healthy notifications. Infinite in-memory retries waste worker threads, cause thread exhaustion, and crash workers if third-party providers (SendGrid, Twilio) experience an outage.
External Provider Integration Third-Party Vendors (Twilio, SendGrid, APNs, FCM) Building in-house SMS/Email gateways Telecom carriers require global carrier partnerships and spam reputation management that takes decades to build. Telcos block unverified private SMS gateways; deliverability rates drop to near zero.

class RetryHandler {
    private static final int MAX_RETRIES = 3;

    public void executeWithRetry(Runnable action) {
        int attempt = 0;
        while (attempt < MAX_RETRIES) {
            try {
                action.run();
                return; // Success
            } catch (Exception e) {
                attempt++;
                try {
                    // Exponential backoff
                    Thread.sleep((long) Math.pow(2, attempt) * 1000);
                } catch (InterruptedException ie) {
                    Thread.currentThread().interrupt();
                }
            }
        }
        System.err.println("Failed after max retries. Sending to DLQ.");
    }
}

public class NotificationWorker {
    private final DeduplicationFilter filter = new DeduplicationFilter();
    private final RetryHandler retryHandler = new RetryHandler();

    public void processNotification(Notification n, NotificationChannel channel) {
        if (filter.isDuplicate(n.id())) {
            return;
        }

        retryHandler.executeWithRetry(() -> {
            boolean success = channel.send(n);
            if (!success) throw new RuntimeException("Delivery failed");
        });
    }
}
    
using System;
using System.Threading;
using System.Threading.Tasks;
using Microsoft.Extensions.Caching.Distributed;

public enum NotificationType { Urgent, Promotional, Transactional }

public record Notification(string Id, string UserId, string Message, NotificationType Type);

// Interface for multi-channel delivery
public interface INotificationChannel
{
    Task SendAsync(Notification notification, CancellationToken ct = default);
}

public class PushChannel : INotificationChannel
{
    public Task SendAsync(Notification n, CancellationToken ct = default)
    {
        Console.WriteLine($"[Push] To {n.UserId}: {n.Message}");
        return Task.FromResult(true);
    }
}

public class SmsChannel : INotificationChannel
{
    public Task SendAsync(Notification n, CancellationToken ct = default)
    {
        Console.WriteLine($"[SMS] To {n.UserId}: {n.Message}");
        return Task.FromResult(true);
    }
}

public class EmailChannel : INotificationChannel
{
    public Task SendAsync(Notification n, CancellationToken ct = default)
    {
        Console.WriteLine($"[Email] To {n.UserId}: {n.Message}");
        return Task.FromResult(true);
    }
}

// Distributed Deduplication using Redis SETNX (Atomic Set if Not Exists)
public class DeduplicationFilter(IDistributedCache cache)
{
    public async Task IsDuplicateAsync(string notificationId)
    {
        string key = $"notif:dedup:{notificationId}";
        var existing = await cache.GetStringAsync(key);
        if (existing is not null) return true;

        // Reserve key for 24 hours to prevent duplicate delivery
        await cache.SetStringAsync(key, "1", new DistributedCacheEntryOptions
        {
            AbsoluteExpirationRelativeToNow = TimeSpan.FromHours(24)
        });
        return false;
    }
}

// Notification Worker with Exponential Backoff Retries & Polly resilience
public class NotificationWorker(
    DeduplicationFilter dedupFilter,
    IDeadLetterQueue dlq)
{
    public async Task ProcessAsync(Notification n, INotificationChannel channel, CancellationToken ct = default)
    {
        // 1. Idempotency Check
        if (await dedupFilter.IsDuplicateAsync(n.Id))
        {
            Console.WriteLine($"Skipping duplicate notification {n.Id}");
            return;
        }

        // 2. Retry Loop with Exponential Backoff
        const int maxRetries = 3;
        int attempt = 0;

        while (attempt < maxRetries)
        {
            try
            {
                bool sent = await channel.SendAsync(n, ct);
                if (sent) return; // Delivered successfully
                throw new InvalidOperationException("Channel returned failure");
            }
            catch (Exception ex)
            {
                attempt++;
                if (attempt >= maxRetries)
                {
                    // 3. Max retries exceeded: Route to Dead Letter Queue (DLQ)
                    await dlq.EnqueueFailedNotificationAsync(n, ex.Message);
                    return;
                }
                await Task.Delay((int)Math.Pow(2, attempt) * 1000, ct);
            }
        }
    }
}

public interface IDeadLetterQueue
{
    Task EnqueueFailedNotificationAsync(Notification n, string errorReason);
}

Step 5 — Optimization

  • Batch Processing: Batch non-urgent notifications (like weekly digests) to save bandwidth and compute.
  • Timezone Awareness: Don't send promotional notifications at 3 AM in the user's local timezone.
  • Analytics: Track delivery, open, and click rates to improve notification templates.
💡 Interview Tip: Always mention a Dead Letter Queue (DLQ) for failed notifications. This shows you think about error handling and system reliability in the real world.
