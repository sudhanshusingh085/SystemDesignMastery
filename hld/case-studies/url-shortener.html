Design a URL Shortener (TinyURL / bit.ly)

A masterclass in designing a highly available, scalable URL shortening service capable of handling billions of redirects.

📖 URL Shortener: A service that maps long, unwieldy URLs into succinct, short aliases, enabling easier sharing, tracking, and aesthetic formatting.

PILLAR 1: Ground-Zero Theory & The Pain Point

What happens if we don't have URL shorteners? Long URLs break in emails, look suspicious on social media, consume SMS character limits, and completely lack built-in click analytics. The core pain point is mapping a massive domain of long URLs to a tiny domain of short URLs without collisions, at extreme read-heavy scale.

Phase 1: Clarifying Requirements & Capacity Estimation

Functional Requirements:

  • Generate a unique short alias for a given long URL.
  • Redirect short aliases to the original URL seamlessly (301 vs 302).
  • Optional: Custom aliases chosen by the user.
  • Optional: Expiration times for links.
  • Analytics: Track click counts, referrers, and geo-data.

Non-Functional Requirements:

  • High Availability: If the service goes down, millions of links across the internet break.
  • Low Latency: Redirections must be sub-10ms.
  • Unpredictability: Users shouldn't be able to guess the next short URL (security against enumeration).
  • Read-to-Write Ratio: Extremely read-heavy, roughly 100:1.

Capacity Estimation (Back-of-the-Envelope)

  • Traffic: 100 Million URLs generated per month.
  • Write QPS: 100M / (30 * 24 * 3600) ≈ 40 URLs/sec.
  • Read QPS: 100:1 ratio = 4,000 Reads/sec (Peak ~8,000 QPS).
  • Storage (5 Years): 100M * 12 months * 5 years = 6 Billion URLs. Assuming 500 bytes per record = ~3 TB of data.
  • Cache Memory: Following the 80/20 rule (cache 20% of daily reads). 4000 QPS * 86400 seconds * 20% * 500 bytes ≈ 34.5 GB of RAM for Redis.

Deep Dive 1: Hash Function vs Base62 Encoding

The naive approach is hashing the long URL using MD5 or SHA256. However, MD5 yields 128 bits (32 hex characters) and SHA256 yields 256 bits (64 hex characters). If we truncate the hash to 7 characters to keep it short, we introduce Collisions.

Flawed: Hashing & Truncation

Requires DB lookups to check if the truncated hash already exists. If yes, append a string and rehash. This causes extreme latency on writes and DB bottlenecks.

Optimal: Base62 with Distributed ID

Generate a unique 64-bit integer ID, then convert it to Base62 (characters `[0-9a-zA-Z]`). 62^7 = 3.5 trillion URLs. Zero collisions mathematically guaranteed.

Deep Dive 2: Key Generation Service (KGS)

Generating sequential IDs at scale introduces race conditions across distributed web servers. We introduce an independent Key Generation Service (KGS). KGS pre-computes random 7-character strings (or generates IDs) and stores them in a highly available internal database. It keeps a pool of unused keys in memory. When a web server needs a key, KGS dispenses it instantly. This eliminates the DB write bottleneck and race conditions.

Deep Dive 3: Database Schema & Sharding

A relational DB (like PostgreSQL) works, but NoSQL (like Cassandra or DynamoDB) is better because we only need basic Key-Value lookups, not complex joins. Sharding by hash(short_url) ensures uniform distribution across partitions, avoiding hotspots.

PILLAR 4: Production-Grade Java 21 Code

Here we leverage modern Java 21 features: Records for DTOs, Pattern Matching, and structured concurrency principles.

Java 21 
import java.util.Optional;
import java.time.Instant;
import java.util.concurrent.ConcurrentHashMap;

/**
 * PILLAR 2 Rationales:
 * - 'record' for immutability and zero-boilerplate data carrying.
 * - 'Instant' for precise expiration tracking.
 */
public record UrlMapping(String shortUrl, String longUrl, Instant expiresAt) {}

/**
 * Sealed interfaces provide exhaustive pattern matching for the API layer.
 */
public sealed interface RedirectResult permits RedirectResult.Success, RedirectResult.NotFound, RedirectResult.Expired {
    record Success(String longUrl) implements RedirectResult {}
    record NotFound() implements RedirectResult {}
    record Expired() implements RedirectResult {}
}

/**
 * Thread-safe Base62 Encoder. 
 * Final class to prevent inheritance, static immutable alphabet.
 */
final class Base62Encoder {
    private static final String ALPHABET = "abcdefghijklmnopqrstuvwxyzABCDEFGHIJKLMNOPQRSTUVWXYZ0123456789";
    private static final int BASE = ALPHABET.length();
    
    public static String encode(long id) {
        if (id == 0) return String.valueOf(ALPHABET.charAt(0));
        StringBuilder sb = new StringBuilder();
        while (id > 0) {
            sb.append(ALPHABET.charAt((int)(id % BASE)));
            id /= BASE;
        }
        return sb.reverse().toString(); // Big-endian representation
    }
}

/**
 * Core Service orchestrating caching and DB interactions.
 */
public class UrlShortenerService {
    private final UrlRepository dbRepository;
    private final Cache redisCache;
    private final KGSClient kgsClient;

    public UrlShortenerService(UrlRepository dbRepository, Cache redisCache, KGSClient kgsClient) {
        this.dbRepository = dbRepository;
        this.redisCache = redisCache;
        this.kgsClient = kgsClient;
    }

    public String shorten(String longUrl, Optional<String> customAlias) {
        String shortAlias = customAlias.orElseGet(kgsClient::fetchPreGeneratedKey);
        
        UrlMapping mapping = new UrlMapping(shortAlias, longUrl, Instant.now().plus(java.time.Duration.ofDays(365 * 5)));
        dbRepository.save(mapping);
        // Eager cache population for immediate reads
        redisCache.put(shortAlias, mapping);
        
        return shortAlias;
    }

    public RedirectResult resolve(String shortAlias) {
        // 1. Check Cache (Sub-millisecond)
        Optional<UrlMapping> cached = redisCache.get(shortAlias);
        if (cached.isPresent()) {
            return validate(cached.get());
        }

        // 2. Cache Miss -> Check DB
        Optional<UrlMapping> dbResult = dbRepository.findByShortUrl(shortAlias);
        if (dbResult.isEmpty()) {
            return new RedirectResult.NotFound();
        }

        // 3. Populate Cache and Return
        UrlMapping mapping = dbResult.get();
        redisCache.put(shortAlias, mapping);
        return validate(mapping);
    }

    private RedirectResult validate(UrlMapping mapping) {
        if (Instant.now().isAfter(mapping.expiresAt())) {
            return new RedirectResult.Expired();
        }
        return new RedirectResult.Success(mapping.longUrl());
    }
}

interface UrlRepository {
    void save(UrlMapping mapping);
    Optional<UrlMapping> findByShortUrl(String shortUrl);
}
interface Cache {
    void put(String key, UrlMapping value);
    Optional<UrlMapping> get(String key);
}
interface KGSClient {
    String fetchPreGeneratedKey();
}

PILLAR 5: The Interviewer's Deep Follow-Up Questions (The Grill Round)

Q1: What if an attacker spams our endpoint to generate billions of URLs?
Senior Answer: Implement rate-limiting per IP and API Key using an algorithm like Token Bucket in Redis. Introduce CAPTCHA for unauthenticated users. If spam persists, ban the malicious IPs at the Web Application Firewall (WAF) level.
Q2: How do you prevent URL enumeration / crawling?
Senior Answer: If we use sequential IDs translated to Base62, an attacker can easily guess `abc1`, `abc2`, etc. To fix this, we shuffle the Base62 alphabet, or use a block cipher like Format-Preserving Encryption to map the sequential ID to a pseudo-random ID before encoding. The independent KGS generating random strings completely solves this natively.
Q3: 301 Permanent Redirect vs 302 Temporary Redirect?
Senior Answer:
  • 301 (Permanent): The browser caches the redirect. Future requests bypass our servers entirely. Good for reducing load, BAD for analytics because we lose click tracking.
  • 302 (Temporary): The browser hits our server every single time. Good for analytics (tracking every single click), BAD for server load. For a product like Bit.ly, 302 is mandatory to provide accurate analytics.

PILLAR 6: Trade-offs & When NOT To Use It

  • Cache Invalidation vs Expiration: Instead of active cron jobs deleting expired links (which stresses the DB), use Lazy Cleanup. Delete it only when a user visits an expired link, or rely on Redis TTL for cache evictions.
  • RDBMS vs NoSQL: If your system requires heavy relational analytics on user accounts, PostgreSQL makes sense. If you just need pure scalability for Key-Value mapping, DynamoDB/Cassandra is vastly superior.
