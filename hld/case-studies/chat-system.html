Design a Chat System (WhatsApp / Slack)

A rigorous masterclass on designing a massive, low-latency, real-time messaging platform handling billions of messages daily.

📖 Real-time Messaging: Systems that push data to clients instantly as it becomes available, bypassing traditional request-response polling limits.

PILLAR 1: Ground-Zero Theory & The Pain Point

HTTP is fundamentally stateless and request-driven. The client asks for data, the server responds, and the connection drops. In a chat application, a user can receive a message at any unpredictable millisecond. If we rely on standard HTTP, clients would have to relentlessly poll the server ("Any new messages? Any new messages?"), causing catastrophic network overhead and battery drain on mobile devices.

Phase 1: Clarifying Requirements & Capacity

Functional Requirements:

  • 1-on-1 private messaging and Group chats (up to 500 members).
  • Online presence (status indicators) and Read receipts.
  • Media sharing (Images, Videos, Documents).
  • Push notifications for offline users.

Non-Functional Requirements:

  • Ultra-Low Latency: Message delivery in <200ms.
  • Strict Ordering: Messages must appear in chronological order.
  • High Availability: Users must be able to view chat history even if underlying nodes fail.

Capacity Calculations (500M DAU)

  • Traffic: Assuming 500M Daily Active Users, sending 40 messages/day = 20 Billion messages/day.
  • Throughput: 20B / 86400 ≈ 231,000 messages per second (Peak ~500k MPS).
  • Storage: 20B messages * 100 bytes = 2 TB / day. Media storage will be exponentially higher (PB/month).

PILLAR 2: Communication Protocol Deep Dive

Choosing the right bidirectional transport is the most critical architectural decision.

HTTP Short & Long Polling

Short polling creates massive HTTP handshake overhead. Long polling holds connections open but requires re-establishing a connection after every message, leading to latency spikes and excessive server thread consumption.

WebSockets

A persistent, full-duplex TCP connection. Once the initial HTTP handshake upgrades to WS, data flows efficiently in both directions with negligible overhead. This is the industry standard for real-time chat.

Deep Dive 1: Message Sequencing & Ordering

Using standard database auto-increments fails in a distributed system, and using NTP timestamps fails because server clocks drift. We must use a distributed ID generator like Twitter Snowflake (64-bit ID). Snowflake generates locally ordered IDs based on timestamp, worker ID, and a sequence number, guaranteeing strict chronological ordering across global clusters.

Deep Dive 2: Message Delivery Flow

User A sends a message to User B: 1) Payload hits User A's connected WebSocket Gateway. 2) Gateway drops it into Kafka to ensure durability. 3) Message Service consumes it, queries Session Service to find which Gateway User B is connected to. 4) Message Service routes it to User B's Gateway, which pushes it over the socket. 5) If User B is offline, push notification triggered via APNS/FCM.

Deep Dive 3: Group Chat Architecture

For small groups (e.g., WhatsApp, max 256/512 members), we use Fan-out on Write. One message is cloned into every recipient's individual message inbox queue. For massive channels (e.g., Slack general, Discord), this fails miserably. Instead, we use Fan-out on Read, where clients pull messages from a single channel timeline.

Deep Dive 4: Online Presence System

Clients send a heartbeat every 5 seconds. The Presence Service updates a Redis key with an expiration (TTL) of 30 seconds. If a user drops connection silently, Redis natively deletes the key after 30s, broadcasting an "Offline" event to their friends.

PILLAR 4: Production-Grade Java 21 Code

import java.util.concurrent.ConcurrentHashMap;
import java.time.Instant;
import java.util.concurrent.atomic.AtomicLong;
import java.util.Optional;

/**
 * PILLAR 2 Rationales:
 * - Records provide absolute immutability for thread-safe message passing.
 * - Sealed types strictly define routing outcomes.
 */
public record ChatMessage(long messageId, String senderId, String receiverId, String content, Instant timestamp) {}

public sealed interface RoutingResult permits RoutingResult.Delivered, RoutingResult.QueuedForOffline {}
    record Delivered() implements RoutingResult {}
    record QueuedForOffline() implements RoutingResult {}

/**
 * Snowflake ID Generator for distributed chronological ordering.
 */
final class SnowflakeGenerator {
    private final long machineId;
    private AtomicLong sequence = new AtomicLong(0L);
    private volatile long lastTimestamp = -1L;

    public SnowflakeGenerator(long machineId) {
        this.machineId = machineId;
    }

    public synchronized long nextId() {
        long currentTimestamp = System.currentTimeMillis();
        if (currentTimestamp < lastTimestamp) {
            throw new RuntimeException("Clock moved backwards.");
        }
        if (currentTimestamp == lastTimestamp) {
            long seq = sequence.incrementAndGet() & 4095; // 12 bits
            if (seq == 0) { // Sequence exhausted, wait for next ms
                while (currentTimestamp <= lastTimestamp) {
                    currentTimestamp = System.currentTimeMillis();
                }
            }
        } else {
            sequence.set(0L);
        }
        lastTimestamp = currentTimestamp;
        // Simplified shift: 41 bits time | 10 bits machine | 12 bits sequence
        return (currentTimestamp << 22) | (machineId << 12) | sequence.get();
    }
}

/**
 * WebSocket Connection Manager leveraging Java 21 Virtual Threads 
 * for handling millions of concurrent persistent connections effortlessly.
 */
class WebSocketSessionManager {
    // Maps userId to their active WebSocket connection
    private final ConcurrentHashMap<String, WebSocketConnection> activeSessions = new ConcurrentHashMap<>();

    public void onConnect(String userId, WebSocketConnection connection) {
        activeSessions.put(userId, connection);
    }

    public void onDisconnect(String userId) {
        activeSessions.remove(userId);
    }

    public Optional<WebSocketConnection> getConnection(String userId) {
        return Optional.ofNullable(activeSessions.get(userId));
    }
}

/**
 * Message Router handling the fan-out and delivery logic.
 */
public class MessageRouter {
    private final WebSocketSessionManager sessionManager;
    private final NotificationService apnsService;
    private final Database db;

    public MessageRouter(WebSocketSessionManager sessionManager, NotificationService apnsService, Database db) {
        this.sessionManager = sessionManager;
        this.apnsService = apnsService;
        this.db = db;
    }

    public RoutingResult routeMessage(ChatMessage msg) {
        // 1. Persist asynchronously to Cassandra
        db.save(msg);

        // 2. Check if user is connected to THIS gateway
        Optional<WebSocketConnection> conn = sessionManager.getConnection(msg.receiverId());
        
        if (conn.isPresent()) {
            conn.get().send(msg); // Push over TCP
            return new RoutingResult.Delivered();
        } else {
            // Push Notification to offline user
            apnsService.sendPushNotification(msg.receiverId(), "New Message from " + msg.senderId());
            return new RoutingResult.QueuedForOffline();
        }
    }
}

interface WebSocketConnection {
    void send(ChatMessage message);
}
interface NotificationService {
    void sendPushNotification(String userId, String text);
}
interface Database {
    void save(ChatMessage msg);
}

PILLAR 5: The Interviewer's Deep Follow-Up Questions (The Grill Round)

Q1: How do you handle End-to-End Encryption (E2EE)?
Senior Answer: Implement the Signal Protocol. The server never sees plaintext. Clients exchange public keys (Diffie-Hellman Key Exchange) via the server. Messages are symmetrically encrypted on the device, sent as ciphertexts, and decrypted only by the receiver's private key. The server just routes binary blobs.
Q2: How do you handle network blips and out-of-order delivery?
Senior Answer: Idempotency keys and local SQLite caching. When a mobile client sends a message, it attaches a unique UUID. The server deduplicates based on this UUID. Clients render messages instantly locally with a "clock" icon, and mark them "Sent" (single tick) only upon server ACK. Snowflake IDs guarantee timeline ordering upon fetch.
Q3: How do you synchronize state across multiple devices (Web, Mobile, Tablet)?
Senior Answer: Shift from a pure messaging model to an Event Sourcing / Delta Sync model. The server maintains a unified append-only log of events (MessageReceived, MessageRead, MessageDeleted). Devices connect, fetch the last known watermark (Cursor), and pull down all events that happened while they were offline to rebuild local state.

PILLAR 6: Trade-offs & When NOT To Use It

  • Cassandra vs RDBMS: We chose Cassandra (Wide-Column NoSQL) because chat generates massive write velocity, and reads are mostly sequential range queries (fetching history). Using MySQL would result in catastrophic B-Tree index fragmentation under this write load. Trade-off: Cassandra lacks strong ACID transactions, which is fine for chat, but disastrous for financial systems.
  • WebSocket vs gRPC: While gRPC over HTTP/2 supports bi-directional streaming, WebSockets enjoy 100% browser compatibility and pass through corporate firewalls/proxies much more reliably than raw gRPC streams.
