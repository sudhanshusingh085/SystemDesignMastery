Design a News Feed (Twitter / Instagram)

A news feed is a constantly updating list of content generated by a user's connections or accounts they follow.

📖 Eventual Consistency: A guarantee that, if no new updates are made to a given piece of data, eventually all accesses to that item will return the last updated value.

Step 1 — Requirements

Functional Requirements

  • Users can publish text and media posts.
  • Users can view a personalized feed composed of posts from people they follow.
  • Users can follow/unfollow other users.

Non-functional Requirements

  • Feed generation should be fast (loads in < 500ms).
  • System must handle 200M Daily Active Users.
  • Eventual consistency is acceptable for feed updates.

Step 3 — Deep Dive

Fanout Strategy

Fanout is the process of delivering a post to all followers. We have two main approaches:

Fanout on Write (Push)

Pre-compute the feed during post creation. Fast reads, but slow writes for users with millions of followers (celebrities).

Fanout on Read (Pull)

Compute feed dynamically when user loads the app. Slow reads, but no heavy background processing required.

The Solution: Hybrid Approach. Use Push for normal users, and Pull for celebrities to avoid overloading the system when a celebrity posts.

⚖️ Architectural Decision Matrix: Why This, Why Not Other?

Architectural Decision Chosen Approach Alternative Considered WHY THIS? (Winning Strengths) WHY NOT THE OTHER? (Disqualifying Trade-offs)
Feed Fan-Out Model Hybrid Fan-Out (Push for Normal, Pull for Celebrities) Pure Fan-Out on Write (Push) OR Pure Fan-Out on Read (Pull) Gives 99% of normal users sub-50ms O(1) feed reads while shielding the system from write amplification when celebrities post. Pure Push collapses when Elon Musk/Cristiano Ronaldo posts (100M+ duplicate writes). Pure Pull requires querying 1,000 followees and merge-sorting on every single feed load, causing massive DB lag.
Feed Storage Cache Redis Sorted Sets (ZSET) Relational DB (PostgreSQL / MySQL) ZREVRANGEBYSCORE fetches paginated post IDs by timestamp in O(log N + M) in-memory time. Capped via ZREMRANGEBYRANK to keep only the top 800 recent posts per user. Fetching feeds by running relational multi-table JOINs across millions of rows on every feed refresh saturates database IOPS.
Social Graph Storage Graph DB (Neo4j) / Distributed KV (Redis / DynamoDB) Relational Self-Referential Table Traversing 2nd-degree friend connections ("Friends of Friends", "People You May Know") executes in sub-10ms without recursive SQL CTE joins. Relational self-joins (SELECT * FROM Follows f1 JOIN Follows f2 ...) don't scale past hundreds of millions of user edges.
Feed Worker Decoupling Kafka Partitioned Message Broker Synchronous HTTP Post Calls Publishing a post returns in <10ms. Fan-out workers consume asynchronously in batches. If 500 workers crash, messages remain durable in Kafka. Synchronous fan-out locks the HTTP request thread until all 50,000 followers are updated; an error midway causes partial delivery with zero retry resilience.

import java.util.List;
import java.util.ArrayList;

// Java 21 Record for a post
public record Post(String postId, String authorId, String content, long timestamp) {}

interface FanoutStrategy {
    void process(Post post, List<String> followers);
}

class PushFanout implements FanoutStrategy {
    private final FeedCache cache;
    public PushFanout(FeedCache cache) { this.cache = cache; }
    
    @Override
    public void process(Post post, List<String> followers) {
        // Push to all followers' caches
        for (String followerId : followers) {
            cache.addPostToFeed(followerId, post);
        }
    }
}

class PullFanout implements FanoutStrategy {
    @Override
    public void process(Post post, List<String> followers) {
        // Do nothing on write. Feeds are constructed on read.
    }
}

class HybridFanout implements FanoutStrategy {
    private final PushFanout push;
    private final PullFanout pull;
    private static final int CELEBRITY_THRESHOLD = 100_000;

    public HybridFanout(PushFanout push, PullFanout pull) {
        this.push = push;
        this.pull = pull;
    }

    @Override
    public void process(Post post, List<String> followers) {
        if (followers.size() > CELEBRITY_THRESHOLD) {
            pull.process(post, followers);
        } else {
            push.process(post, followers);
        }
    }
}

using System;
using System.Collections.Generic;
using System.Threading.Tasks;

// C# 12 Record for Post
public record Post(string PostId, string AuthorId, string Content, long Timestamp);

public interface IFanoutStrategy
{
    Task ProcessAsync(Post post, IReadOnlyList followers);
}

// Push Fanout: Writes directly to followers' Redis mailboxes
public class PushFanout(IFeedCache cache) : IFanoutStrategy
{
    public async Task ProcessAsync(Post post, IReadOnlyList followers)
    {
        foreach (var followerId in followers)
        {
            await cache.AddPostToFeedAsync(followerId, post);
        }
    }
}

// Pull Fanout: No-op on write; merged dynamically at read time
public class PullFanout : IFanoutStrategy
{
    public Task ProcessAsync(Post post, IReadOnlyList followers) => Task.CompletedTask;
}

// Hybrid Fanout: Routes based on celebrity threshold (e.g. 50,000 followers)
public class HybridFanout(PushFanout push, PullFanout pull) : IFanoutStrategy
{
    private const int CelebrityThreshold = 50_000;

    public async Task ProcessAsync(Post post, IReadOnlyList followers)
    {
        if (followers.Count > CelebrityThreshold)
        {
            await pull.ProcessAsync(post, followers); // Celebrities skipped on push!
        }
        else
        {
            await push.ProcessAsync(post, followers);
        }
    }
}

public interface IFeedCache
{
    Task AddPostToFeedAsync(string userId, Post post);
}

// Feed Service orchestrating publishing
public class FeedService(IFanoutStrategy fanout, ISocialGraphService graph)
{
    public async Task PublishPostAsync(Post post)
    {
        var followers = await graph.GetFollowersAsync(post.AuthorId);
        await fanout.ProcessAsync(post, followers);
    }
}

public interface ISocialGraphService
{
    Task> GetFollowersAsync(string userId);
}

Step 5 — Optimization

  • Caching Hot Feeds: Store active users' feeds in memory (Redis) to ensure sub-millisecond read times.
  • Sharding: Shard the feed data by User ID.
  • CDN for Media: Serve images and videos from a CDN to reduce load on the primary servers.
