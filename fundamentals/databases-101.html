Databases 101

A server's memory is temporary. If the server reboots, everything stored in its RAM is lost forever. To keep data safe permanently, we need a Database.

What is a Database?

📖 Database: An organized collection of structured information, or data, typically stored electronically in a computer system. Think of it as a highly advanced digital filing cabinet.

Why not just save to a text file?

You might wonder, "Why can't my server just write data to a file like users.txt?" You can, but databases solve massive problems that simple files cannot:

  • Searching: Finding a specific user in a 10GB text file takes forever. Databases use Indexes to find data instantly.
  • Concurrency: If 1,000 users try to write to a text file at the exact same millisecond, the file gets corrupted. Databases safely manage thousands of simultaneous connections.
  • Integrity: Databases ensure rules are followed (e.g., "Email addresses must be unique", or "Age cannot be negative").

Relational Databases and SQL

The most common type of database is a Relational Database (RDBMS). It organizes data into Tables, which look exactly like Excel spreadsheets.

  • Tables: A collection of related data (e.g., a "Users" table).
  • Columns: The properties of the data (e.g., ID, Name, Email).
  • Rows: Individual entries (e.g., a single user).

To talk to these databases, we use SQL (Structured Query Language).

Example SQL Query:
SELECT name, email FROM Users WHERE age > 18;

Keys and Relationships

Relational databases connect data using keys:

  • Primary Key: A unique identifier for a row (like a Social Security Number for a citizen).
  • Foreign Key: A reference to a Primary Key in another table, creating a link between them.

CRUD Operations

Almost all database interactions fall into four basic categories, known by the acronym CRUD:

  • Create (Insert new data)
  • Read (Select/fetch data)
  • Update (Modify existing data)
  • Delete (Remove data)

Transactions and ACID Properties

A Transaction is a sequence of database operations treated as a single unit of work. It is "all-or-nothing."

Analogy: The ATM Transfer
If you transfer $100 from Checking to Savings, two things must happen:
1. Deduct $100 from Checking.
2. Add $100 to Savings.
If the system crashes after step 1, you lose $100! A transaction ensures that if step 2 fails, step 1 is automatically reversed (rolled back).

Relational databases guarantee ACID properties:

  • Atomicity: All-or-nothing.
  • Consistency: Data remains valid according to defined rules.
  • Isolation: Simultaneous transactions don't interfere with each other.
  • Durability: Once saved, data remains saved even if power is lost.

SQL vs NoSQL

In modern system design, you aren't limited to Relational (SQL) databases. There are also NoSQL databases designed for massive scale and flexibility.

Type Best for Examples
Relational (SQL) Strict schemas, financial systems, complex relationships. PostgreSQL, MySQL, Oracle
Key-Value (NoSQL) Extreme speed, caching, simple lookups. Redis, DynamoDB
Document (NoSQL) Flexible schema, JSON data, content management. MongoDB, CouchDB
Graph (NoSQL) Social networks, recommendation engines. Neo4j

Java 21 Code: Simulating a Simple Database Repository

In Java, we typically wrap database logic in a "Repository" or "Data Access Object (DAO)". Here is a simple in-memory simulation using a HashMap and Java records.

import java.util.HashMap;
import java.util.Map;
import java.util.Optional;

public class DatabaseBasics {
    public record User(Integer id, String name, String role) {}

    public static class UserRepository {
        private final Map<Integer, User> dataStore = new HashMap<>();
        private int currentId = 1;

        public User create(String name, String role) {
            User newUser = new User(currentId++, name, role);
            dataStore.put(newUser.id(), newUser);
            return newUser;
        }

        public Optional<User> read(Integer id) {
            return Optional.ofNullable(dataStore.get(id));
        }

        public boolean update(Integer id, String newName, String newRole) {
            if (dataStore.containsKey(id)) {
                dataStore.put(id, new User(id, newName, newRole));
                return true;
            }
            return false;
        }

        public boolean delete(Integer id) {
            return dataStore.remove(id) != null;
        }
    }
}
using System.Collections.Concurrent;

public record User(int Id, string Name, string Role);

public class UserRepository
{
    private readonly ConcurrentDictionary<int, User> _dataStore = new();
    private int _currentId;

    public User Create(string name, string role)
    {
        int id = Interlocked.Increment(ref _currentId);
        var user = new User(id, name, role);
        _dataStore[id] = user;
        return user;
    }

    public User? Read(int id) => _dataStore.GetValueOrDefault(id);

    public bool Update(int id, string newName, string newRole)
    {
        if (_dataStore.ContainsKey(id))
        {
            _dataStore[id] = new User(id, newName, newRole);
            return true;
        }
        return false;
    }

    public bool Delete(int id) => _dataStore.TryRemove(id, out _);
}
Interview Tip: In an interview, don't just say "I will use MongoDB." You must explain why. If the system needs strict ACID transactions (like a banking app), choose SQL. If it needs to store massive amounts of unstructured data quickly, choose NoSQL.
