Java 11-21 Modern Features — The New Java

1. var (Type Inference)

PILLAR 1: Theory
Introduced in Java 10. Allows the compiler to infer the type of a local variable from its initializer. It reduces verbosity.

PILLAR 6: Trade-offs
Do not use var when it obscures the type and harms readability (e.g., var result = calculate();). Use it when the RHS explicitly shows the type (e.g., var cache = new HashMap<String, Trade>();).

2. Text Blocks

Multi-line string literals (Java 15). Eliminates the need for cumbersome concatenation and escaping, perfect for SQL queries, JSON, or FIX messages in trading systems.

3. Records

PILLAR 1: Theory
Introduced in Java 16, Records are transparent carriers for immutable data. They automatically generate constructors, accessors, equals(), hashCode(), and toString().


public record Trade(String tradeId, String currencyPair, BigDecimal amount, LocalDateTime timestamp) {
    // Compact constructor for validation
    public Trade {
        if (amount.compareTo(BigDecimal.ZERO) <= 0) {
            throw new IllegalArgumentException("Trade amount must be positive");
        }
    }
}

📋 How to Answer This in an Interview

Records vs Lombok @Value vs Classes: "Records are a language-level feature guaranteeing immutability and providing a standard semantic for data carriers. Unlike Lombok, which relies on annotation processing and bytecode manipulation, Records are natively understood by the JVM, which optimizes them (e.g., in serialization). They are ideal for DTOs and API responses."

4. Sealed Classes

PILLAR 1: Theory
Restricts which classes can extend or implement a class/interface. Provides exhaustiveness for pattern matching.


public sealed interface OrderType permits MarketOrder, LimitOrder, StopOrder {}

5. Pattern Matching

Allows instanceof to declare a binding variable, eliminating explicit casting. Combined with switch expressions, it creates expressive, data-oriented logic.


public void processOrder(OrderType order) {
    switch(order) {
        case MarketOrder m -> executeMarket(m);
        case LimitOrder l when l.price().compareTo(currentPrice) >= 0 -> executeLimit(l);
        case LimitOrder l -> queueLimit(l);
        case StopOrder s -> monitorStop(s);
    }
}

6. Virtual Threads (Project Loom)

PILLAR 1: Theory
Java 21 feature. Virtual threads are lightweight, JVM-managed threads. They solve the thread-per-request bottleneck in I/O-heavy applications (like trading gateways). Millions of virtual threads can be created, running on a small pool of platform (OS) threads.

📋 How to Answer This in an Interview

Why use Virtual Threads? "Platform threads map 1:1 to OS threads, which are expensive (~1MB stack, context switching overhead). In blocking I/O applications, threads sit idle waiting for responses. Virtual threads map M:N to OS threads. When a virtual thread blocks on I/O, the JVM unmounts it from the carrier platform thread, allowing another virtual thread to execute. This achieves reactive-level scalability (millions of concurrent connections) without the complex, callback-hell programming model of reactive frameworks like WebFlux."

🎯 Interviewer Follow-Up Questions

  • Trap: "Will virtual threads make CPU-intensive tasks faster?"
    Answer: No. Virtual threads excel at blocking I/O tasks. For pure CPU-bound tasks, platform threads or parallel streams are better.
  • Trap: "What is thread pinning?"
    Answer: If a virtual thread performs a blocking operation while inside a synchronized block or native method, it pins the carrier thread to the OS thread, blocking others. We must migrate synchronized to ReentrantLock to prevent this.

7. Structured Concurrency (Preview)

Provides a clean way to manage multi-threaded tasks as a single unit of work, simplifying error handling and cancellation. E.g., querying 3 different exchanges and cleanly canceling the others once the fastest responds.
