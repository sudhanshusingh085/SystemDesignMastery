2. The N+1 Problem (The Silent Killer)

Pillar 1: Ground-Zero Theory & The Pain Point

The N+1 problem occurs when an ORM framework executes one query to retrieve a parent entity, and then executes N additional queries to fetch the lazy-loaded children for each of the N parents. In a financial app, querying 100 Portfolios might trigger 100 separate queries to fetch the Trades for each portfolio. This floods the database with thousands of sub-millisecond queries, utterly destroying application throughput.

📋 How to Answer This in an Interview

Q: "What is the N+1 problem in Hibernate/JPA and how would you solve it?"

Candidate: "The N+1 problem is a massive performance flaw where JPA issues 1 query to fetch a list of parent entities, and then N queries to initialize their lazily-loaded associations. My primary solution is to use JOIN FETCH in JPQL to eagerly load the association in a single SQL join query. If the entity has multiple associations and Cartesian products become a concern, I use @EntityGraph for dynamic fetching, or @BatchSize(size = 50) at the entity level to fetch children in chunks using an IN clause, reducing N queries to N/50 queries."

3. LazyInitializationException & OSIV

🎯 Interviewer Follow-Up Questions

Q: "A LazyInitializationException occurs in production but not in development. Why?"

A: "Because of Open Session In View (OSIV). Spring Boot enables OSIV by default. In development, this keeps the Hibernate Session open during the entire HTTP request rendering phase, so lazy loading works in the Controller/View. However, in production, senior engineers rightfully disable OSIV (`spring.jpa.open-in-view=false`) because keeping DB connections open during HTTP transport exhausts connection pools. When disabled, the Session closes immediately after the @Transactional Service method completes. When the Controller tries to access a lazy collection, there's no Session left, resulting in the Exception."
