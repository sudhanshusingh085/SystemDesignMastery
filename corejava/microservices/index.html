Microservices Architecture — Distributed Trading Platform

Architecting robust, fault-tolerant financial systems at scale.

PILLAR 1: Ground-Zero Theory & The Pain Point

Monolith vs Microservices: A monolith bundles all financial domains (Trading, Settlement, KYC) into one deployable unit. Microservices split them into independent, deployable services.

The Pain Point: In a monolith, a memory leak in the KYC module crashes the Trading engine. Scaling is all-or-nothing. Microservices allow independent scaling and fault isolation, but introduce distributed system complexities.

PILLAR 2: Architectural Decision Rationales & Modifier Deep Dives

Database-per-Microservice

Rule: Never share a database between microservices. If Trade Service needs user data, it must call the User Service API. Why? Schema isolation. If User Service changes a column, Trade Service shouldn't break.

Inter-service Communication

Use REST/OpenFeign for synchronous queries (e.g., "Get real-time price"). Use Kafka/Messaging for asynchronous commands/events (e.g., "Execute Trade"). Use gRPC for low-latency internal communication.

PILLAR 3: Step-by-Step Evolution & Thought Process

Saga Pattern: How do we handle distributed transactions? (e.g., deduct funds + execute trade).

Attempt 1: Two-Phase Commit (2PC). Fails because it's synchronous and locks resources, causing bottlenecks.

Attempt 2: Saga Pattern. A sequence of local transactions. If one fails, we execute compensating transactions to rollback previous steps (e.g., refund the deducted amount). Implemented via Choreography (events) or Orchestration (central coordinator).

// OpenFeign Client for synchronous Inter-service communication
@FeignClient(name = "pricing-service", fallback = PricingFallback.class)
public interface PricingClient {
    @GetMapping("/api/v1/prices/{symbol}")
    PriceDTO getPrice(@PathVariable("symbol") String symbol);
}

// Circuit Breaker with Resilience4j
@Service
public class TradeExecutionService {

    @CircuitBreaker(name = "pricingService", fallbackMethod = "cachedPriceFallback")
    public BigDecimal getTradePrice(String symbol) {
        return pricingClient.getPrice(symbol).price();
    }
    
    public BigDecimal cachedPriceFallback(String symbol, Throwable t) {
        // Fallback to last known price in Redis
        return redisCache.get(symbol);
    }
}

PILLAR 5: The Interviewer's Deep Follow-Up Questions

📋 How to Answer This in an Interview

Q: Explain the Saga pattern for a fund transfer system.
Candidate: A fund transfer spans Account A and Account B. Using an Orchestrator Saga: 1. Saga initiates "Debit A". 2. If successful, it initiates "Credit B". 3. If B's credit fails (e.g., account frozen), the Orchestrator fires a compensating transaction "Refund A" to maintain eventual consistency.

Q: Can Saga be implemented without Kafka?
Candidate: Yes. We can use REST with HTTP Webhooks/Callbacks, or the Outbox pattern with database polling, though Kafka provides better guarantees and throughput.

🎯 Interviewer Follow-Up Questions

Q: Service A calls B. B is unavailable. A keeps retrying, preventing B from recovering. What pattern fixes this?
Answer: Circuit Breaker. After N failures, the circuit OPENS, failing fast and giving B time to recover. It moves to HALF_OPEN to test if B is back, then CLOSED if successful.

Q: How would you migrate a monolithic application to microservices?
Answer: Strangler Fig Pattern. Put an API Gateway in front. Gradually extract domains (e.g., KYC first) into a microservice. Route KYC traffic to the new service, keeping the rest pointing to the monolith.

Q: What are the different Rate Limiting algorithms?
Answer: Token Bucket (smooth bursts), Leaky Bucket (constant rate), Fixed Window (simple but allows bursts at edges), Sliding Window Log/Counter (accurate).

PILLAR 6: Trade-offs & When NOT To Use It

Microservices Trade-offs: Increased operational overhead, network latency, difficult debugging (requires Distributed Tracing like Jaeger/Zipkin). Do NOT use microservices for a small startup finding product-market fit; build a modular monolith instead.
