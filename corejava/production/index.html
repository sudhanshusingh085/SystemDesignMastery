1. HashMap 1M Entries Degrading: The FIX Engine Choke

🔴 Incident Summary & Symptoms: At market open, the FIX Engine's CPU spiked to 100%. Latency for processing `ExecutionReport` messages skyrocketed from 50µs to 200ms. HFT clients began disconnecting due to heartbeat timeouts.
🔍 Root Cause Analysis: The OMS maintained an in-memory `HashMap` initialized with default capacity (16). As 1M trades poured in, the map suffered continuous resizing. Poor hash implementations of the ID object caused hash collisions, degrading buckets into long linked lists, making `get()` operations O(N).
// ✅ FIXED CODE (Java 21)
Map<String, Trade> tradeCache = HashMap.newHashMap(1_333_334); 
public record OrderId(String client, String id) {} // Excellent default hashCode
🛠️ Diagnostic Tools: async-profiler -d 30 -f flamegraph.html PID revealed 80% CPU cycles in HashMap.resize().

📋 How to Answer This

"I describe a latency spike at market open in our FIX engine... I fixed it by explicitly sizing the map and using records for robust hashing."

🎯 The Grill Round

Q: "Why did it degrade to a linked list? Doesn't Java 8 use Red-Black trees?" A: "Only if the key implements `Comparable`. Our custom key didn't."

2. Synchronized Everywhere Bottleneck: Matching Engine Deadlock

🔴 Incident Summary & Symptoms: During a flash crash, order throughput dropped to zero. Load balancers dropped connections.
🔍 Root Cause Analysis: The central `OrderBook` class used `synchronized` on every method. 150 worker threads were `BLOCKED` waiting on the single monitor lock.
// ✅ FIXED CODE (Java 21)
private final ReentrantReadWriteLock lock = new ReentrantReadWriteLock();
public void addOrder(Order order) { lock.writeLock().lock(); try { ... } finally { lock.writeLock().unlock(); } }
🛠️ Diagnostic Tools: jstack PID > thread_dump.txt. Grep for BLOCKED (on object monitor).

📋 How to Answer This

"I took a thread dump using jstack and found 150 threads BLOCKED. I refactored to use ReentrantReadWriteLock for concurrent top-of-book reads."

🎯 The Grill Round

Q: "Why not ConcurrentHashMap?" A: "An order book requires strict ordering (price-time priority); ConcurrentHashMap doesn't maintain sorted order. We needed a concurrent skip list or locked trees."

3. Double-Checked Locking Singleton Without Volatile

🔴 Incident Summary & Symptoms: NullPointerExceptions intermittently thrown fetching `RiskConfiguration` on startup.
🔍 Root Cause Analysis: Instruction reordering (`allocate -> assign -> construct`). Without `volatile`, other threads saw a half-initialized object.
// ✅ FIXED CODE (Java 21) - Bill Pugh Singleton
public class RiskManager {
    private RiskManager() {}
    private static class Holder { static final RiskManager INSTANCE = new RiskManager(); }
    public static RiskManager getInstance() { return Holder.INSTANCE; }
}
🛠️ Diagnostic Tools: Core dump analysis. JVM flags `-XX:+PrintAssembly` to see memory barriers (or lack thereof).

📋 How to Answer This

"We had race conditions in our risk singleton. I explained the Java Memory Model's happens-before relationship and fixed it using the Bill Pugh Holder idiom for thread-safe lazy initialization."

🎯 The Grill Round

Q: "What if we just used `volatile`?" A: "That works post-Java 1.5, but adds a memory barrier to every read. The static holder class is completely lock-free and relies on the JVM classloader guarantees."

4. ThreadLocal Memory Leak in Thread Pool

🔴 Incident Summary: OOM after 3 days of high-volume trading.
🔍 Root Cause Analysis: Worker threads never die; ThreadLocal maps retain huge `UserContext` objects because `remove()` wasn't called in a `finally` block.
// ✅ FIXED CODE
try { ThreadLocalContext.set(context); processTrade(); } 
finally { ThreadLocalContext.remove(); }
🛠️ Diagnostic Tools: Eclipse MAT on heap dump. Path to GC roots showed `ThreadLocalMap$Entry`.

📋 How to Answer This

"I found a memory leak in our thread pools using Eclipse MAT. ThreadLocal contexts weren't cleared, tying objects to long-lived threads."

🎯 The Grill Round

Q: "Why are ThreadLocal keys WeakReferences?" A: "To allow classloader unloading in web apps, but values are hard references, causing leaks if not removed."

5. wait() vs sleep() Deadlock in Order Matching

🔴 Incident Summary: Entire pricing engine froze.
🔍 Root Cause Analysis: `sleep()` holds the lock while waiting for market condition, starving the producer thread.
// ✅ FIXED CODE
synchronized(monitor) { while(!condition) monitor.wait(); }
🛠️ Diagnostic Tools: `jcmd PID Thread.print` showing deadlocks.

📋 How to Answer This

"A junior dev used sleep() inside a synchronized block. I replaced it with wait() which releases the monitor lock, allowing state updates."

🎯 The Grill Round

Q: "Why wait in a while loop?" A: "Spurious wakeups from the OS require checking the condition again."
