1. SecurityFilterChain & Architecture

Pillar 1: Ground-Zero Theory & The Pain Point

Spring Security acts as a massive bouncer before requests ever reach your DispatcherServlet. It operates entirely on Servlet Filters. Without it, you would manually check headers, cookies, and tokens in every single controller. The SecurityFilterChain is an ordered list of these filters. If a request fails a filter (e.g., missing JWT), it is rejected with a 401/403 before your application logic even knows it existed.

Pillar 3: Step-by-Step Evolution

                flowchart LR
                    A[Client Request] --> B[DelegatingFilterProxy]
                    B --> C[FilterChainProxy]
                    C --> D[SecurityContextPersistenceFilter]
                    D --> E[UsernamePasswordAuthenticationFilter / JwtAuthenticationFilter]
                    E --> F[AuthorizationFilter]
                    F --> G[DispatcherServlet (Controllers)]

📋 How to Answer This in an Interview

Q: "How does SecurityFilterChain work?"

Candidate: "Spring Security hooks into the standard Servlet Filter API via a DelegatingFilterProxy. This proxy delegates work to a Spring Bean called FilterChainProxy. The FilterChainProxy manages one or more SecurityFilterChains. Each chain is a sequence of highly specialized filters—some handle CORS, some extract JWTs, some handle authentication (AuthN), and finally, the AuthorizationFilter handles access control (AuthZ). If all filters pass, the request proceeds to the DispatcherServlet."

4. JWT Structure, Creation, Validation

Pillar 1: Ground-Zero Theory

JSON Web Tokens (JWT) are a stateless, cryptographically verifiable way to transmit claims between parties. Traditional session management requires storing session IDs in a central database (Redis) which introduces a network hop and scalability limits. JWTs solve this because the server only needs its private/public key to verify the token's authenticity.

Pillar 4: Production-Grade Java 21 Code


@Component
public sealed class JwtTokenProvider permits InternalJwtTokenProvider {
    private final RSAPrivateKey privateKey;
    private final RSAPublicKey publicKey;

    public String generateToken(Authentication auth) {
        var user = (CustomUserDetails) auth.getPrincipal();
        Instant now = Instant.now();
        
        return Jwts.builder()
                .subject(user.getUsername())
                .claim("roles", user.getAuthorities())
                .claim("trader_id", user.getTraderId())
                .issuer("finance-auth-server")
                .issuedAt(Date.from(now))
                .expiration(Date.from(now.plusSeconds(3600)))
                .signWith(privateKey)
                .compact();
    }
}

🎯 Interviewer Follow-Up Questions

Q: "When API Gateway generates a JWT token and forwards to microservice A, should A validate the token again?"

A: "YES. This is the principle of Defense in Depth. While the API Gateway validates the signature and expiry to prevent bad traffic from entering the network, Microservice A must also validate the token. The Gateway shouldn't know the intricate business roles required for every endpoint in Service A. Service A validates the JWT to extract claims and enforce method-level authorization (AuthZ) using @PreAuthorize."
