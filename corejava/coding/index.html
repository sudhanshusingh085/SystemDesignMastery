1. Reverse a String (FIX Tag Value)

PILLAR 1: Ground-Zero Theory & The Pain Point

String reversal is a fundamental algorithmic test. In finance, this often applies to parsing or reversing serialized data like FIX protocol tags (e.g., reversing a transaction ID). If done inefficiently (using + operator in a loop), it causes severe memory bloat due to String immutability, creating O(N) garbage objects.

PILLAR 2: Architectural Decision Rationales

We use StringBuilder or a simple char[] swap. StringBuilder is standard because it handles surrogate pairs (UTF-16) correctly, whereas naive char[] reversal might corrupt emojis or complex characters (less common in FIX, but good to mention). We avoid recursion due to StackOverflowError risks on long strings.

PILLAR 3: Step-by-Step Evolution

Naive: String s = ""; for(int i=len-1; i>=0; i--) s+=orig.charAt(i); (O(N^2) time).
Better: char[] swap in-place (O(N) time, O(N) space for array).
Best: new StringBuilder(str).reverse().toString().

PILLAR 4: Production-Grade Java 21 Code


public record FixTag(int tag, String value) {
    public FixTag reverseValue() {
        if (value == null || value.isEmpty()) return this;
        // Fast, standard, handles unicode surrogates
        String reversed = new StringBuilder(value).reverse().toString();
        return new FixTag(tag, reversed);
    }
}

PILLAR 5: The Interviewer's Deep Follow-Up Questions

📋 How to Answer This in an Interview

Mention time/space complexity (O(N) time, O(N) space) and highlight the UTF-16 surrogate pair edge case. If they ask to implement it without StringBuilder:


char[] chars = value.toCharArray();
for (int i = 0, j = chars.length - 1; i < j; i++, j--) {
    char temp = chars[i]; chars[i] = chars[j]; chars[j] = temp;
}
return new String(chars);

🎯 Interviewer Follow-Up Questions

Q: What if the string is 10GB? A: You cannot hold it in memory. You must stream it from disk using a RandomAccessFile or memory-mapped buffer, reversing chunks.

PILLAR 6: Trade-offs & When NOT To Use It

In-place char array swap uses less memory overhead than StringBuilder but requires careful handling if surrogate pairs are present.

2. Frequency of Each Character (FIX Message Analysis)

PILLAR 1: Ground-Zero Theory

Counting character frequencies is crucial for data compression (like Huffman coding) or anomaly detection in FIX message payloads.

PILLAR 2: Architectural Decision Rationales

We use a HashMap<Character, Integer> or a flat int[] array if we know the charset is strictly ASCII (which FIX tags often are). The array approach is O(1) space and vastly faster than boxing/unboxing in a Map.

PILLAR 3: Step-by-Step Evolution

Naive: Nested loops (O(N^2)).
Better: Java 8 Streams Collectors.groupingBy (Concise but slow due to boxing overhead).
Best: int[256] frequency array (O(N) time, O(1) space, zero garbage).

PILLAR 4: Production-Grade Java 21 Code


public static Map<Character, Long> countFixDelimitersStream(String fixMessage) {
    return fixMessage.chars()
            .mapToObj(c -> (char) c)
            .collect(Collectors.groupingBy(Function.identity(), Collectors.counting()));
}

// Low Latency approach
public static int[] countFixDelimitersFast(String fixMessage) {
    int[] freq = new int[256];
    for (int i = 0; i < fixMessage.length(); i++) {
        freq[fixMessage.charAt(i) % 256]++;
    }
    return freq;
}

PILLAR 5: The Grill Round

📋 How to Answer This in an Interview

Present the array approach as the "HFT/Low-Latency" answer to show you care about GC pauses, then write the Stream approach to show you know modern Java.

🎯 Follow-Ups

Q: Why avoid Streams in low-latency trading? A: Autoboxing primitives to Objects creates immense GC pressure.
