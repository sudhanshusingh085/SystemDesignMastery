1. Formal Textbook Definitions & 10-Second Elevator Pitch

🧠 The 10-Second Elevator Pitch

"Spring Boot 3 provides opinionated, rapid enterprise application bootstrapping on top of Java 17/21. Its core engine builds an Inversion of Control (IoC) ApplicationContext through modular Auto-Configuration (evaluating conditions from AutoConfiguration.imports). Cross-cutting concerns—like transactions, security, and caching—are transparently woven using AOP dynamic proxies (CGLIB/ByteBuddy). Combined with DispatcherServlet front-controller routing and native Virtual Thread execution, Spring Boot scales to millions of concurrent requests with enterprise-grade resilience."

ApplicationContext (IoC Container)

The central interface providing application configuration. It implements Inversion of Control (IoC) and Dependency Injection (DI) by managing bean lifecycles, configuration metadata, event publication, and resource loading via an internal DefaultListableBeanFactory.

Auto-Configuration

A declarative bootstrapping system driven by @EnableAutoConfiguration. In Spring Boot 3, it reads configuration class candidates from META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports and applies them conditionally based on classpath presence and existing user beans.

BeanPostProcessor

A foundational SPI interface allowing custom modification of new bean instances. Its two methods (postProcessBeforeInitialization and postProcessAfterInitialization) hook into the bean lifecycle, enabling Spring to wrap beans in AOP proxies (for @Transactional, @Async, etc.).

AOP Dynamic Proxy

A runtime proxy pattern implementation. Spring AOP uses JDK Dynamic Proxies (for classes implementing interfaces) or CGLIB / ByteBuddy (for class-based inheritance proxies). The proxy intercepts method invocations to execute advice before, after, or around the target method.

DispatcherServlet

The Front Controller for Spring MVC web applications. It centralizes request routing, delegates URL matching to HandlerMapping, dispatches execution via HandlerAdapter, handles interceptors, and marshals responses via HttpMessageConverter.

Self-Invocation Trap

A subtle architectural failure where a bean calls another method within the same class using this.method(). Because the call bypasses the Spring AOP proxy wrapper, annotations like @Transactional, @Cacheable, and @Async fail to execute silently.

Spring Boot 3: The Death of `spring.factories`

In Spring Boot 2.x, auto-configuration classes were listed in META-INF/spring.factories under the key org.springframework.boot.autoconfigure.EnableAutoConfiguration. In Spring Boot 3.0+, this legacy mechanism was completely removed in favor of a clean, newline-delimited file:

META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports

The Big Three Conditional Annotations

  • @ConditionalOnClass(DataSource.class): Activates configuration only if the specified class exists on the application's runtime classpath.
  • @ConditionalOnMissingBean(DataSource.class): Only registers the default bean if the developer has not defined their own custom bean of that type. This provides out-of-the-box defaults that back off gracefully.
  • @ConditionalOnProperty(name = "feature.enabled", havingValue = "true"): Evaluates external configuration properties in application.yml.

⚠️ The @PostConstruct AOP Trap

Notice that @PostConstruct (Step 5) fires before BeanPostProcessor.postProcessAfterInitialization() (Step 8). Because AOP proxies are created in Step 8, calling an @Async or @Transactional method from within a @PostConstruct method will not execute asynchronously or within a transaction! The proxy does not yet exist; the call invokes the raw, un-proxied bean directly.

4. Spring AOP Dynamic Proxies & The Self-Invocation Trap

Spring AOP is proxy-based. When a bean is annotated with @Transactional, Spring does not modify the original class bytecode. Instead, it creates a CGLIB/ByteBuddy subclass that acts as a wrapper.

Architectural Solutions to Self-Invocation

  1. Extract to a Separate Service (Recommended): Move the @Transactional method to a dedicated collaborator class and inject it via constructor injection. This honors the Single Responsibility Principle.
  2. Self-Injection: Inject the bean into itself via @Lazy private final OrderService self; and invoke self.executeTrade().
  3. Compile-Time AspectJ Weaving: Use AspectJ's bytecode weaver (ajc) instead of runtime Spring dynamic proxies. AspectJ modifies the actual compiled bytecode, so this.method() calls are intercepted directly.

7. Production-Grade Java 21 Spring Boot 3 Trading Service

Below is a production-hardened institutional trading controller and service demonstrating constructor injection, self-invocation avoidance, RFC 7807 global exception handling, and Java 21 record DTOs.

package com.finance.trading.boot;

import jakarta.validation.Valid;
import jakarta.validation.constraints.*;
import org.springframework.http.*;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;
import org.springframework.web.bind.annotation.*;

import java.math.BigDecimal;
import java.time.Instant;
import java.util.UUID;

// =========================================================================
// 1. JAVA 21 IMMUTABLE DTO RECORDS
// =========================================================================
public class TradingApplication {

    public record CreateOrderRequest(
        @NotBlank String symbol,
        @DecimalMin("0.01") BigDecimal price,
        @Positive int quantity,
        @NotBlank String clientAccount
    ) {}

    public record OrderResponse(
        UUID orderId,
        String symbol,
        BigDecimal executedPrice,
        int quantity,
        String status,
        Instant timestamp
    ) {}

    // =========================================================================
    // 2. PRODUCTION REST CONTROLLER
    // =========================================================================
    @RestController
    @RequestMapping("/api/v1/orders")
    public static class OrderController {
        private final OrderExecutionService executionService;

        public OrderController(OrderExecutionService executionService) {
            this.executionService = executionService;
        }

        @PostMapping(consumes = MediaType.APPLICATION_JSON_VALUE, produces = MediaType.APPLICATION_JSON_VALUE)
        public ResponseEntity<OrderResponse> submitOrder(@Valid @RequestBody CreateOrderRequest request) {
            OrderResponse response = executionService.routeAndExecute(request);
            return ResponseEntity.status(HttpStatus.CREATED).body(response);
        }
    }

    // =========================================================================
    // 3. SERVICE WITH EXPLICIT TRANSACTION BOUNDARIES (NO SELF-INVOCATION)
    // =========================================================================
    @Service
    public static class OrderExecutionService {
        private final LedgerService ledgerService; // Separated collaborator to prevent self-invocation trap

        public OrderExecutionService(LedgerService ledgerService) {
            this.ledgerService = ledgerService;
        }

        public OrderResponse routeAndExecute(CreateOrderRequest request) {
            System.out.printf("[LOG] Validating routing limits for account %s%n", request.clientAccount());
            // Calling transactional collaborator via Spring CGLIB proxy
            UUID txId = ledgerService.debitAccountTransactional(request.clientAccount(), 
                request.price().multiply(BigDecimal.valueOf(request.quantity())));
                
            return new OrderResponse(txId, request.symbol(), request.price(), request.quantity(), "FILLED", Instant.now());
        }
    }

    @Service
    public static class LedgerService {
        @Transactional
        public UUID debitAccountTransactional(String account, BigDecimal amount) {
            System.out.printf("[TX-ACTIVE] Deducting %s from account %s within JDBC transaction%n", amount, account);
            return UUID.randomUUID();
        }
    }

    // =========================================================================
    // 4. RFC 7807 GLOBAL REST CONTROLLER ADVICE
    // =========================================================================
    @RestControllerAdvice
    public static class GlobalTradingExceptionHandler {

        @ExceptionHandler(IllegalArgumentException.class)
        public ProblemDetail handleIllegalArgument(IllegalArgumentException ex) {
            ProblemDetail problem = ProblemDetail.forStatusAndDetail(HttpStatus.BAD_REQUEST, ex.getMessage());
            problem.setTitle("Invalid Trading Parameter");
            problem.setProperty("timestamp", Instant.now());
            problem.setProperty("errorCode", "TRD-4001");
            return problem;
        }
    }
}

8. The Principal Engineer's 10-Question Grill Round

Q1

How has Auto-Configuration discovery changed from Spring Boot 2.x to Spring Boot 3.x?

In Spring Boot 2.x, auto-configuration classes were declared in META-INF/spring.factories under the key org.springframework.boot.autoconfigure.EnableAutoConfiguration. In Spring Boot 3.0+, this mechanism was completely replaced. Auto-configuration classes must now be listed in META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports, with one fully qualified class name per line. If a legacy library still relies solely on spring.factories, its auto-configuration will fail to load in Spring Boot 3 without an adapter.

🚩 Red Flag to Avoid Claiming that spring.factories is still the primary auto-configuration configuration mechanism in Spring Boot 3.
Q2

Explain the exact mechanism of the Self-Invocation Trap with `@Transactional` or `@Async`.

Spring AOP implements cross-cutting concerns by wrapping beans in runtime CGLIB or JDK dynamic proxies. When an external caller invokes a method, the proxy intercepts the call, starts the transaction or offloads to a thread pool, and delegates to the target bean. If method a() calls method b() within the same class using this.b(), the invocation is executed directly on the underlying target instance, bypassing the Spring proxy wrapper entirely. Consequently, any annotations on b() (such as @Transactional, @Async, or @Cacheable) are silently ignored.

🚩 Red Flag to Avoid Suggesting that declaring the private method public will resolve the self-invocation issue.
Q3

Why does calling an `@Async` or `@Transactional` method inside `@PostConstruct` fail to work?

In the Spring bean lifecycle, @PostConstruct methods are invoked during Step 5 (initialization), whereas AOP proxies are created in Step 8 by BeanPostProcessor.postProcessAfterInitialization(). When @PostConstruct executes, the bean instance is still the raw, unadorned Java object; the proxy wrapper has not yet been synthesized. Therefore, calling an @Async or @Transactional method from @PostConstruct executes synchronously and outside any transaction.

🚩 Red Flag to Avoid Expecting asynchronous tasks or transactional boundaries to trigger inside bean initialization constructors.
Q4

Why is Constructor Injection preferred over Field Injection (`@Autowired` on private fields)?

Field injection relies on reflection to mutate private fields, hiding dependencies from the class contract. This makes unit testing painful without mocking frameworks or Spring test runners, prevents fields from being declared final (destroying immutability), and hides circular dependency design smells until runtime. Constructor injection guarantees that objects cannot be instantiated in an uninitialized state, permits final fields, allows clean POJO unit tests with standard new, and causes the IoC container to fail fast on circular dependencies at startup.

🚩 Red Flag to Avoid Defending field injection for "cleaner looking code" without recognizing testability and immutability hazards.
Q5

How does Spring resolve the Prototype Bean inside a Singleton Bean dilemma?

Because a singleton bean is initialized once during application startup, its dependencies are injected only once. If a prototype bean is injected directly via constructor injection, the singleton bean retains the identical prototype instance forever, nullifying the prototype scope. Solutions include: (1) Injecting ObjectProvider<PrototypeBean> or Provider<PrototypeBean> and calling .getObject() on each request; (2) Using @Lookup method injection, where CGLIB dynamically overrides an abstract method to query the ApplicationContext; (3) Configuring the prototype bean with @Scope(value = "prototype", proxyMode = ScopedProxyMode.TARGET_CLASS).

🚩 Red Flag to Avoid Claiming injecting the prototype bean normally will supply a new instance on every method invocation.
Q6

What is the difference between JDK Dynamic Proxies and CGLIB/ByteBuddy in Spring AOP?

JDK Dynamic Proxies require target classes to implement at least one interface. The proxy class implements the target interfaces and delegates invocations via an InvocationHandler. CGLIB (and modern ByteBuddy) creates a dynamic subclass of the target class at runtime and overrides methods using method interceptors. CGLIB can proxy classes without interfaces, but it cannot proxy final classes or override final methods. Since Spring Boot 2.x, CGLIB subclass proxying is enabled by default (spring.aop.proxy-target-class=true).

🚩 Red Flag to Avoid Stating that Spring always requires interfaces to generate AOP proxies.
Q7

How does the Spring MVC `DispatcherServlet` locate the correct controller method for an incoming request?

The DispatcherServlet iterates through registered HandlerMapping implementations, primarily RequestMappingHandlerMapping. This mapping contains an in-memory lookup registry created at startup that maps URL path patterns, HTTP methods, headers, and media types to a HandlerMethod wrapper. Once matched, it returns a HandlerExecutionChain containing the controller method and an ordered list of matching HandlerInterceptor instances.

🚩 Red Flag to Avoid Believing DispatcherServlet uses reflection to scan all classes on every incoming HTTP request.
Q8

What happens under the hood when `spring.threads.virtual.enabled=true` is set in Spring Boot 3.2+?

Spring Boot configures the embedded Tomcat / Jetty web server to use an Executor backed by Executors.newVirtualThreadPerTaskExecutor() instead of a fixed platform thread pool. For every incoming HTTP request, Tomcat spawns a new Java 21 Virtual Thread. Furthermore, Spring's applicationTaskExecutor and @Async processing are automatically adapted to use virtual threads. When a virtual thread performs blocking I/O (JDBC query, HTTP client call), it unmounts from its carrier platform thread, eliminating thread pool starvation.

🚩 Red Flag to Avoid Assuming virtual threads make CPU-intensive calculations run faster.
Q9

What is RFC 7807 (ProblemDetail) in Spring Boot 3, and why does it supersede custom error maps?

RFC 7807 is an IETF specification defining a standardized JSON format for HTTP API error responses. Before Spring 6 / Boot 3, teams created ad-hoc error response maps (e.g., { "timestamp": ..., "error": ..., "message": ... }) with differing schemas across services. Spring 6 introduced ProblemDetail as a first-class citizen, providing standardized fields: type (URI), title, status, detail, instance, and arbitrary extension properties. This enables API consumers and API Gateways to parse structured errors uniformly across polyglot microservices.

🚩 Red Flag to Avoid Returning generic strings or HTTP 500 error pages for client validation errors.
Q10

How do `@ConditionalOnMissingBean` and `@AutoConfigureAfter` coordinate custom starter priorities?

@ConditionalOnMissingBean enables Spring Boot's "convention over configuration" guarantee: auto-configured beans are registered only if no user-defined bean of that type exists in the BeanFactory. To ensure that user-defined configurations and dependency auto-configurations evaluate before downstream dependent configurations, starters use @AutoConfigureAfter and @AutoConfigureBefore. This enforces a deterministic topological sort of auto-configuration import ordering, preventing order-dependent startup race conditions.

🚩 Red Flag to Avoid Using @Order on @Configuration classes expecting it to control auto-configuration evaluation order. (It does not!).

9. CircuitBreaker Configuration

🛡️ Hidden Resilience4j Defaults

The @CircuitBreaker annotation by itself falls back to Resilience4j’s hidden default settings (e.g., a 50 % failure rate over the last 100 calls). Those defaults are often too permissive for production workloads, so you should always override them explicitly.

Approach 1: The Spring Boot YAML Way (Industry Standard)

# application.yml
resilience4j:
  circuitbreaker:
    configs:
      default:
        registerHealthIndicator: true
        slidingWindowSize: 20
        failureRateThreshold: 25   # fail if >25 % of last 20 calls fail
        waitDurationInOpenState: 30s
    instances:
      myService:
        baseConfig: default
        recordExceptions:
          - java.io.IOException
        ignoreExceptions:
          - org.springframework.web.client.HttpClientErrorException.NotFound

Approach 2: The Programmatic Way (Completing your snippet)

import io.github.resilience4j.circuitbreaker.CircuitBreakerConfig;
import io.github.resilience4j.circuitbreaker.CircuitBreakerRegistry;
import java.time.Duration;

@Configuration
public class CircuitBreakerConfigBean {
    @Bean
    public CircuitBreakerRegistry circuitBreakerRegistry() {
        CircuitBreakerConfig defaultConfig = CircuitBreakerConfig.custom()
            .failureRateThreshold(25)               // 25 % failures opens the circuit
            .slidingWindowSize(20)                 // last 20 calls examined
            .waitDurationInOpenState(Duration.ofSeconds(30))
            .recordExceptions(IOException.class)
            .ignoreExceptions(NotFoundException.class)
            .build();
        return CircuitBreakerRegistry.of(defaultConfig);
    }

    @Bean
    public CircuitBreaker myServiceCircuitBreaker(CircuitBreakerRegistry registry) {
        return registry.circuitBreaker("myService");
    }
}

10. How @EnableAutoConfiguration Works

@EnableAutoConfiguration is the core "magic" behind Spring Boot. At startup the framework scans the project's pom.xml (Maven) or build.gradle (Gradle) for present dependencies and then reads the file META-INF/spring/org.springframework.boot.autoconfigure.AutoConfiguration.imports. Each line in that file names a candidate auto‑configuration class.

For every candidate the engine evaluates a series of @Conditional annotations (@ConditionalOnClass, @ConditionalOnMissingBean, @ConditionalOnProperty, etc.). Only when all conditions are satisfied does the configuration class get imported into the ApplicationContext.

Example 1: The Web Server
Trigger: The classpath contains spring-boot-starter-web.
Action: Spring detects Tomcat and DispatcherServlet, automatically starts an embedded Tomcat on port 8080 and configures Spring MVC routing.

11. Field Injection – An Anti‑Pattern

Field injection relies on reflection to mutate private fields after object construction, which hides required dependencies and makes unit testing painful.

@Service
public class OrderService {
    @Autowired
    private PaymentGateway paymentGateway; // mutable, hidden, hard to test
}

By contrast, constructor injection makes dependencies explicit, allows final fields, and enables simple new OrderService(mockGateway) tests.

@Service
public class OrderService {
    private final PaymentGateway paymentGateway;

    public OrderService(PaymentGateway paymentGateway) {
        this.paymentGateway = paymentGateway;
    }
}
🚩 Red Flag Defending field injection as "cleaner looking code" ignores testability and immutability concerns.

CoffeeMaker analogy: Without Spring, creating new CoffeeMaker() would leave pump null, causing a NullPointerException. Constructor injection avoids that hidden requirement.

12. Self‑Invocation Trap & Fixes

When a bean method calls another method on the same instance using this, the call bypasses the Spring AOP proxy. Consequently, annotations such as @Transactional, @Async, or @Cacheable are ignored.

Four standard ways to solve the problem (ranked from best to last resort):

  1. Extract to a separate service (recommended): Move the @Transactional method into its own bean and inject that bean where needed.
  2. Self‑injection: Inject the bean into itself (e.g., @Lazy private final OrderService self;) and call self.executeTrade() to go through the proxy.
  3. Compile‑time AspectJ weaving: Use the AspectJ compiler (ajc) to weave advice directly into the bytecode, so this calls are also intercepted.
  4. Make the method public and call via ApplicationContext.getBean(): Less ideal because it couples code to the container.

13. Dependency Injection Overview

Dependency Injection (DI) is the technique by which a framework supplies an object’s required collaborators (its dependencies) rather than the object creating them itself. In Spring, DI is realized through the IoC container, which wires beans together via constructor injection, setter injection, or field injection (the latter being discouraged).
