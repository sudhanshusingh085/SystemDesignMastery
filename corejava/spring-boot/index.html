1. Spring MVC Request Flow

Pillar 1: Ground-Zero Theory & The Pain Point

In the dark ages of Java web development, developers mapped every single HTTP endpoint to a distinct HttpServlet. This resulted in thousands of classes, redundant parsing logic, and unmaintainable routing tables. Spring MVC introduced the Front Controller pattern via the DispatcherServlet. It acts as the single point of entry, routing incoming requests, managing the lifecycle, and delegating to the appropriate business logic. Without it, you are manually parsing HTTP streams, which is a disaster for latency and maintainability.

.jargon(Front Controller): A centralized entry point that handles all requests for a web application, providing a unified mechanism for routing, security, and rendering.

Pillar 2: Architectural Decision Rationales

Why a single DispatcherServlet instead of multiple servlets? By centralizing the entry point, Spring can uniformly apply Cross-Origin Resource Sharing (CORS) rules, security filters, and content-negotiation strategies. The HandlerMapping is abstracted as an interface rather than a concrete class, allowing teams to route by URL, headers, or even custom annotations seamlessly.

Pillar 4: Production-Grade Java 21 Code


@RestController
@RequestMapping("/api/v1/trades")
public class TradeController {
    
    private final TradeService tradeService;

    public TradeController(TradeService tradeService) {
        this.tradeService = tradeService;
    }

    @PostMapping(consumes = MediaType.APPLICATION_JSON_VALUE)
    public ResponseEntity<TradeResponse> executeTrade(@RequestBody @Valid TradeRequest request) {
        // DispatcherServlet routed us here via RequestMappingHandlerMapping
        TradeResponse response = tradeService.execute(request);
        return ResponseEntity.ok(response);
    }
}

Pillar 5: The Interviewer's Deep Follow-Up

📋 How to Answer This in an Interview

Q: "Explain the flow of Spring MVC from request to response."

Candidate: "The request hits the Servlet container and reaches the DispatcherServlet. It consults the HandlerMapping to find the exact Controller method mapped to the URL. If interceptors are defined, their preHandle methods fire. The DispatcherServlet then uses a HandlerAdapter to invoke the Controller. The Controller delegates to the Service and returns a payload. Finally, the HttpMessageConverter serializes the return object (like a Record) to JSON and sends it back in the HTTP response."

🎯 Interviewer Follow-Up Questions

Q: "What if the controller throws an exception? Where does the flow go?"

A: "It bypasses the normal return flow and is caught by the HandlerExceptionResolver, specifically handled by an @ControllerAdvice class if defined, which translates the exception into an RFC-7807 ProblemDetail response."

Pillar 6: Trade-offs & When NOT To Use It

Spring MVC is thread-per-request. For extremely high-concurrency systems (like real-time market data streaming), this model blocks threads. In such cases, Spring WebFlux (Reactive) or Java 21 Virtual Threads (which make blocking cheap) are better suited than traditional MVC.

2. Bean Lifecycle

Pillar 1: Ground-Zero Theory & The Pain Point

If you just use new Object(), you are responsible for initializing it, passing dependencies, and destroying it. Spring's Inversion of Control (IoC) container takes over. The Bean Lifecycle is the exact sequence of events Spring executes to create, wire, initialize, and destroy a bean. Failing to understand this means resource leaks (unclosed database connections) and NullPointerExceptions when accessing uninitialized properties.

@Component
public class TradeProcessingBean implements InitializingBean, DisposableBean, ApplicationContextAware {
    
    private final FIXEngine fixEngine; // Field 1
    private ApplicationContext context;

    // 1. Instantiation & DI
    public TradeProcessingBean(FIXEngine fixEngine) {
        this.fixEngine = fixEngine;
        System.out.println("1. Constructor: Dependencies injected");
    }

    // 2. Aware interfaces
    @Override
    public void setApplicationContext(ApplicationContext applicationContext) {
        this.context = applicationContext;
        System.out.println("2. ApplicationContextAware invoked");
    }

    // 3. JSR-250 Annotation
    @PostConstruct
    public void init() {
        System.out.println("3. @PostConstruct: Warming up FIX caches");
    }

    // 4. Spring specific initialization
    @Override
    public void afterPropertiesSet() throws Exception {
        System.out.println("4. InitializingBean: Checking FIX connection");
    }

    // 5. Destruction
    @PreDestroy
    public void shutdown() {
        System.out.println("5. @PreDestroy: Draining FIX messages cleanly");
    }

    @Override
    public void destroy() throws Exception {
        System.out.println("6. DisposableBean: Socket closed");
    }
}

5. The @Transactional TRAP

Pillar 1: Ground-Zero Theory

@Transactional guarantees ACID properties for database operations. If an exception occurs, changes are rolled back. However, Spring uses proxy-based Aspect-Oriented Programming (AOP). Spring wraps your bean in a proxy. When an external caller invokes the method, the proxy starts the transaction, delegates to your class, and commits. The trap occurs during self-invocation.

📋 How to Answer This in an Interview

Q: "@Transactional is applied to a private method. Why does it silently have no effect?"

Candidate: "Spring AOP relies on dynamic proxies (CGLIB or JDK). Proxies can only intercept public method calls coming from OUTSIDE the bean. If a method is private, the proxy cannot override it to inject transaction management logic. Furthermore, if a public non-transactional method inside the same bean calls a public transactional method inside that same bean, the transaction will ALSO fail to start. This is known as the self-invocation problem, because the internal call uses this.method(), completely bypassing the Spring proxy."

Pillar 4: Production-Grade Java 21 Code


@Service
public class OrderService {

    // TRAP: Caller hits this non-transactional method.
    public void processOrder(Order order) {
        // self-invocation! 'this' reference used. Bypasses proxy.
        // @Transactional below is completely IGNORED.
        saveToDatabase(order); 
    }

    @Transactional
    public void saveToDatabase(Order order) {
        // database ops...
    }
}

The Fix: Either extract saveToDatabase into a separate OrderRepositoryService so it's called through a proxy, or use AspectJ weaving instead of Spring AOP proxies (which operates at byte-code level and doesn't suffer from self-invocation).
