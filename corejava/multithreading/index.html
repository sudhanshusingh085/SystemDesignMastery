Multithreading — Concurrent Trading System Internals

PILLAR 1: Ground-Zero Theory & The Pain Point

A modern trading system cannot process ticks sequentially. If an exchange sends 100,000 market data ticks per second, processing them on a single thread will cause unbounded queue growth, stale prices, and massive financial loss. Multithreading allows a JVM to execute multiple instruction streams concurrently. However, sharing mutable state (like an order book) across threads introduces race conditions, deadlocks, and memory visibility hazards.

PILLAR 2: Architectural Decision Rationales

Thread Creation: Runnable vs Callable

We rarely extend Thread because Java doesn't support multiple inheritance. We implement Runnable for fire-and-forget tasks (e.g., flushing logs). We implement Callable<T> when we need a return value (e.g., calculating portfolio risk and returning a RiskReport) or when we need to throw checked exceptions.

start() vs run()

Calling run() just executes the method synchronously on the current thread. Calling start() invokes native OS calls (via the JVM) to allocate a new call stack, register the thread with the OS scheduler, and then asynchronously invoke run().

The volatile keyword

volatile solves the CPU cache visibility problem. It does NOT solve atomicity. It instructs the JVM to read the variable directly from main memory and flush writes directly to main memory, bypassing L1/L2 caches, preventing instruction reordering.

PILLAR 3: Step-by-Step Evolution & Thought Process

Naive approach: Shared state without locks → Race conditions.
Fix 1: Add synchronized everywhere → System bottlenecks, lock contention.
Fix 2: Use volatile → Still fails because i++ is read-modify-write (not atomic).
Fix 3: Use AtomicInteger / LongAdder or lock striping (ConcurrentHashMap).

package com.finance.trading.concurrency;

import java.util.concurrent.*;
import java.util.concurrent.atomic.AtomicInteger;
import java.util.concurrent.locks.ReentrantLock;

// 1. Callable for Risk Calculation
public record RiskReport(String portfolioId, double var) {}

public class RiskCalculator implements Callable<RiskReport> {
    private final String portfolioId;
    public RiskCalculator(String portfolioId) { this.portfolioId = portfolioId; }
    
    @Override
    public RiskReport call() throws Exception {
        // Expensive simulation
        return new RiskReport(portfolioId, 45000.50);
    }
}

// 2. Race Condition Fix via AtomicInteger
public class TradeCounter {
    private final AtomicInteger tradeCount = new AtomicInteger(0);
    
    public void increment() {
        tradeCount.incrementAndGet(); // Atomic CAS operation
    }
}

// 3. ThreadLocal (Beware of Thread Pool Leaks!)
public class TradeContextHolder {
    // ThreadLocal stores user context per thread. 
    // MUST call .remove() in a finally block to prevent leaks in thread pools!
    public static final ThreadLocal<String> currentTrader = new ThreadLocal<>();
}

// 4. Deadlock Example & Prevention
public class AccountManager {
    // ReentrantLock provides tryLock() with timeout, preventing deadlocks
    public void transfer(Account from, Account to, double amount) {
        // Always lock in a globally consistent order (e.g., by Account ID) to prevent circular wait!
        Account first = from.id().compareTo(to.id()) < 0 ? from : to;
        Account second = from.id().compareTo(to.id()) < 0 ? to : from;
        
        synchronized(first) {
            synchronized(second) {
                from.debit(amount);
                to.credit(amount);
            }
        }
    }
}

PILLAR 5: The Interviewer's Deep Follow-Up Questions

📋 How to Answer This in an Interview

Always frame multithreading in terms of throughput vs latency, and correctness vs liveness. Be ready to explain the Java Memory Model (JMM), Happens-Before relationships, and exactly how locks behave.

🎯 Interviewer Follow-Up Questions

Trap Question: "What is the difference between volatile, transient, and synchronized?"

Answer: volatile guarantees memory visibility and prevents instruction reordering (JMM boundary). synchronized guarantees both visibility AND mutual exclusion (atomicity) by acquiring a monitor lock. transient has nothing to do with multithreading; it tells the JVM to ignore the field during object serialization.

Trap Question: "A ThreadLocal variable is causing a memory leak in our web server. How does it happen?"

Answer: Web servers use thread pools. When a request finishes, the thread isn't destroyed; it's returned to the pool. If you don't call ThreadLocal.remove(), the thread holds a strong reference to the object in its ThreadLocalMap, preventing garbage collection for the lifetime of the application.

Trap Question: "wait() vs sleep() - how can incorrect usage lead to deadlocks?"

Answer: wait() releases the monitor lock of the object it's called on, allowing other threads to enter the synchronized block and eventually call notify(). Thread.sleep() pauses the thread but holds onto the lock. If a thread sleeps inside a synchronized block, no other thread can acquire the lock, potentially stalling the entire system.

PILLAR 6: Trade-offs & When NOT To Use It

Trade-off: Raw threads map 1:1 to OS platform threads (1MB stack space each). Spawning 10,000 platform threads will crash the JVM. Context switching between OS threads is expensive (saving/restoring registers, CPU cache invalidation). For massive concurrency (e.g., maintaining 100k open FIX connections), raw Thread is obsolete—use Java 21 Virtual Threads instead.
