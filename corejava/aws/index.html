AWS & Deployment — Cloud Infrastructure for Trading Systems

Architecting low-latency, highly available financial systems on the Cloud.

1. Compute: EC2 vs ECS vs Lambda

PILLAR 1: Ground-Zero Theory & The Pain Point

In a trading system, you have diverse computational needs. A FIX (Financial Information eXchange) engine requires persistent, long-lived TCP connections. A trade processing engine requires scalable microservices. A daily reconciliation report runs once a day. If you use a single server for all three, you either pay for idle capacity or face starvation during market open. AWS provides three main compute paradigms:

  • EC2 (Elastic Compute Cloud): Full Virtual Machines. You control the OS, networking, and patching.
  • ECS (Elastic Container Service): Container orchestration (often via AWS Fargate). You deploy Docker containers without managing the underlying VMs.
  • Lambda: Serverless compute. You deploy code, and AWS runs it in response to events, billing by the millisecond.

Pain Point: Choosing the wrong compute primitive leads to either bloated AWS bills (running EC2s for batch jobs) or disconnected clients (using Lambda for long-lived FIX sessions).

PILLAR 2: Architectural Decision Rationales

Compute Primitive Control & Scaling Startup Time Finance Use Case
EC2 Total control, slow manual/ASG scaling Minutes FIX engines needing kernel tuning, persistent IP, and long-lived TCP sockets.
ECS (Fargate) High control, auto-scaling containers Seconds Order Management System (OMS) Microservices, Pricing engines.
AWS Lambda Low control, hyper-scaling (event-driven) Milliseconds (Cold starts vary) Trade reconciliation batch jobs, EOD (End-of-Day) report generation, S3 trigger parsing.

PILLAR 3: Step-by-Step Evolution

Naive Approach: Deploy everything on giant EC2 instances ("Lift and Shift"). Result: Wasted money during non-market hours and slow deployments.
Evolution 1: Move microservices to ECS. Dockerizes the OMS, allowing seamless Blue-Green deployments and faster scaling during market volatility.
Evolution 2: Offload event-driven tasks to Lambda. When a generic end-of-day trade file lands in S3, a Lambda wakes up, parses it, updates the DB, and dies.

PILLAR 5: The Interviewer's Deep Follow-Up Questions

📋 How to Answer This in an Interview

Q: Difference between EC2, ECS and Lambda in your trading architecture?
A: "I map compute to workload characteristics. For our FIX engine, we use EC2 because FIX relies on long-lived TCP sockets and sequence numbers, which Lambda and standard HTTP-based load balancers on ECS struggle with. For our core Order Routing microservices, we use ECS with Fargate because it provides scalable container orchestration without managing VMs. For End-of-Day reconciliation or processing files dropped in S3, we use Lambda because it's purely event-driven, scaling to zero when not in use."

🎯 Interviewer Follow-Up Questions

  • "What is a Lambda Cold Start and how do you mitigate it in Java?" -> SnapStart, GraalVM native images, or Provisioned Concurrency.
  • "Can a Lambda run for an hour?" -> No, Lambda has a hard 15-minute timeout. For long batch jobs, use AWS Batch or ECS tasks.

PILLAR 6: Trade-offs & When NOT To Use It

  • Lambda: Do not use for low-latency market data processing. Cold starts and unpredictable JVM pauses will violate SLA.
  • EC2: Do not use for simple web APIs; the operational overhead of OS patching and AMIs is too high compared to ECS/EKS.

2. Deployment Flow — CI/CD for Microservices

PILLAR 1: Ground-Zero Theory & The Pain Point

A trading floor cannot endure downtime. Deploying new code by manually SSHing into servers is a recipe for disaster. CI/CD (Continuous Integration / Continuous Deployment) automates the pipeline from Git commit to production release.

PILLAR 3: Step-by-Step Evolution & Visual Flow

Modern deployment on AWS typically follows this flow:

flowchart TD A[Developer Push Git] --> B[AWS CodePipeline] B --> C[AWS CodeBuild: Maven Test/Build] C --> D[Docker Build & Tag] D --> E[AWS ECR: Container Registry] E --> F[ECS Blue/Green Deployment] F --> G{Health Checks Pass?} G -- Yes --> H[Traffic shifts to Green] G -- No --> I[Rollback to Blue]

Blue-Green Deployment: 'Blue' is the current live version. 'Green' is the new version. Both run simultaneously. Traffic is switched at the load balancer level only when Green passes health checks. Zero downtime.

Canary Deployment: Release the new version to a small percentage of users (e.g., 5% of internal traders) before rolling out to everyone.

PILLAR 5: The Interviewer's Deep Follow-Up Questions

📋 How to Answer This in an Interview

Q: Have you deployed microservices on AWS? Explain the deployment flow.
A: "Yes, we use a fully automated CI/CD pipeline via GitHub Actions and AWS CodePipeline. Code is built using Maven, and tests are run. Upon success, a Docker image is built and pushed to Amazon ECR. We use ECS with Fargate for execution, and AWS CodeDeploy manages a Blue-Green deployment. CodeDeploy spins up the new 'Green' task set, runs health checks against the /actuator/health endpoint, and if successful, shifts ALB traffic from Blue to Green. If a health check fails, it instantly rolls back without customer impact."

3. Messaging: SQS vs SNS vs Kafka

PILLAR 1 & 2: Theory & Architectural Decisions

  • SQS (Simple Queue Service): Point-to-point message queuing. Great for decoupling components (e.g., Decoupling the Trade Capture system from the Settlement system). Consumer pulls messages.
  • SNS (Simple Notification Service): Pub/Sub messaging. Great for fan-out. Push-based. E.g., A trade is executed -> SNS pushes to Email alert system, SMS alert, and an SQS queue for downstream processing.
  • Kafka (MSK on AWS): Distributed commit log. High throughput, low latency, replayable. Best for massive market data firehoses or event-sourcing ledgers where order and replayability are paramount.

PILLAR 5: Interviewer Questions

Q: When would you use Kafka over SQS in a financial system?
A: "I use SQS for simple, asynchronous task queues like sending trade confirmation emails, where order isn't strictly critical and once it's processed, it can be deleted. I use Kafka for the core Order Routing fabric or Market Data feeds, because Kafka guarantees strict ordering within a partition, allows multiple distinct consumer groups to read the same stream without deleting the message, and supports replaying historical events to rebuild state—critical for financial auditing and event-sourcing architectures."

4. Essential AWS Services for Finance

  • Monitoring (CloudWatch & X-Ray): CloudWatch handles metrics and logs. X-Ray provides distributed tracing (adding trace IDs to HTTP headers) so you can track a trade lifecycle across 15 different microservices.
  • S3 (Simple Storage Service): Immutable object storage. Perfect for storing immutable trade archives, regulatory reports, and daily market data dumps. Using Glacier lifecycle policies saves costs for 7-year regulatory retention.
  • RDS vs DynamoDB:
    • RDS (Relational - PostgreSQL/Aurora): ACID compliance is mandatory for financial ledger balances and core transactional data.
    • DynamoDB (NoSQL): Millisecond latency at any scale. Used for user session state, high-frequency tick data caching, or configurations where strict relational joins are not required.
  • VPC & Security Groups: Network isolation. The Database tier (RDS) resides in a Private Subnet with no internet route. Only the Application tier (ECS in another private subnet) can reach it via Security Group rules. The ALB sits in the Public Subnet.
  • IAM: Identity and Access Management. Never use hardcoded AWS credentials in Java code. Use IAM Task Roles for ECS so the container inherently has permission to read from a specific S3 bucket (Least Privilege).
