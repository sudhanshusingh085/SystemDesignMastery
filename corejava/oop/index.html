OOP Deep Dive — Object-Oriented Architecture for Financial Systems

An exhaustive, textbook-grade masterclass on Object-Oriented Programming principles tailored specifically for tier-1 investment bank, hedge fund, and electronic trading interviews.

1. The 4 Pillars of OOP in Electronic Trading

Object-Oriented Programming (OOP) is not merely a syntactic construct; it is a fundamental architectural paradigm designed to manage complexity. In high-frequency trading (HFT) and order management systems (OMS), representing reality accurately and securely is paramount. The 4 Pillars of OOP serve as the guardrails for robust financial systems.

1.1 Encapsulation: Guarding The Vault

The Conceptual Theory: Encapsulation is the bundling of data (state) and the methods that operate on that data into a single unit, restricting direct access to some of the object's components. It is the core mechanism for maintaining class invariants.

The Real-World Finance Pain Point: Imagine an Account class where the balance or marginUtilization is a public double. Any external service—a buggy reporting job or an erratic risk checker—could arbitrarily mutate the balance. Such public fields lead directly to multi-million dollar accounting discrepancies and regulatory fines. Encapsulation ensures state mutations strictly adhere to domain rules.

Java 21 
import java.math.BigDecimal;
import java.util.concurrent.locks.ReentrantLock;

public class MarginAccount {
    // 1. Data Hiding: Private state
    private final String accountId;
    private BigDecimal availableMargin; // NEVER use double for currency
    private final ReentrantLock lock = new ReentrantLock(); // Thread-safety for concurrent trades

    public MarginAccount(String accountId, BigDecimal initialMargin) {
        this.accountId = accountId;
        this.availableMargin = initialMargin;
    }

    // 2. Controlled Access & Validation
    public void deductMargin(BigDecimal marginRequired) {
        lock.lock();
        try {
            if (marginRequired.compareTo(BigDecimal.ZERO) <= 0) {
                throw new IllegalArgumentException("Margin required must be positive");
            }
            if (availableMargin.compareTo(marginRequired) < 0) {
                throw new InsufficientMarginException("Trade rejected: Margin limit breached for account: " + accountId);
            }
            this.availableMargin = this.availableMargin.subtract(marginRequired);
        } finally {
            lock.unlock();
        }
    }
    
    // Defensive copy or immutable return type
    public BigDecimal getAvailableMargin() {
        return this.availableMargin; 
    }
}
📋 How to Answer This in an Interview

"Encapsulation in our trading systems isn't just about getters and setters; it's about enforcing domain invariants. By keeping state private and exposing only behavior that validates inputs, we guarantee that a Trade or Account object can never be pushed into an inconsistent state. We also employ immutable objects (like Java Records for MarketData) wherever possible to completely eliminate state mutation anomalies across threads."

1.2 Abstraction: The Universal Execution Gateway

The Conceptual Theory: Abstraction involves hiding complex, low-level implementation details and exposing only the essential, high-level features of a component. It defines a strict contract of what an object can do, completely divorcing it from how it executes under the hood.

The Real-World Electronic Trading Pain Point: An institutional Order Management System (OMS) must route trades to dozens of external execution venues:

  • Nasdaq / BATS: High-speed binary protocol (OUCH / ITCH over UDP/TCP).
  • CME / London Stock Exchange: FIX 4.4 tag-value ASCII protocol over TCP sockets.
  • Crypto Exchanges (Binance / Coinbase): REST and WebSocket APIs using JSON payloads.
If the core OMS order routing engine had to know about byte buffers, FIX tags, JSON serializers, and socket reconnections, the codebase would become an unmaintainable disaster. Any change to a venue's wire protocol would risk breaking the core trade matching logic.

The Architectural Solution: We create an abstract base class TradingVenueGateway. It provides concrete infrastructure (session sequence numbering, heartbeat watchdog, pre-trade risk checks, latency metrics via Template Method Pattern) while forcing subclasses to implement abstract methods for protocol-specific wire serialization.

Java 21 
import java.math.BigDecimal;
import java.time.Instant;
import java.util.concurrent.atomic.AtomicLong;

// The Domain Models
public record Order(String orderId, String ticker, BigDecimal price, long quantity, String side) {}
public record ExecutionReport(String execId, String orderId, String status, BigDecimal fillPrice, Instant timestamp) {}

// Production Abstraction: Abstract Gateway with Template Method
public abstract class TradingVenueGateway {
    protected final String venueId;
    protected final AtomicLong sequenceNumber = new AtomicLong(1);
    protected volatile boolean isConnected = false;

    protected TradingVenueGateway(String venueId) {
        this.venueId = venueId;
    }

    // Concrete Template Method: Dictates the mandatory execution workflow
    public final ExecutionReport submitOrder(Order order) {
        if (!isConnected) {
            throw new IllegalStateException("Cannot route trade: Venue " + venueId + " is disconnected");
        }
        
        // 1. Common Pre-Trade Latency Timestamping
        long startNanos = System.nanoTime();

        // 2. Common Pre-Trade Risk Invariant Checks
        validateOrder(order);

        // 3. Delegate to Venue-Specific Abstract Wire Encoding
        byte[] wirePayload = encodeAndTransmit(order);
        System.out.println("Dispatched " + wirePayload.length + " bytes to " + venueId + " [Seq: " + sequenceNumber.getAndIncrement() + "]");

        // 4. Simulate reading venue response and parse via abstract method
        byte[] simulatedAck = receiveRawAck();
        ExecutionReport report = parseExecutionReport(simulatedAck);

        long latencyMicros = (System.nanoTime() - startNanos) / 1000;
        System.out.println("Order " + order.orderId() + " acknowledged by " + venueId + " in " + latencyMicros + " µs");
        return report;
    }

    private void validateOrder(Order order) {
        if (order.quantity() <= 0 || order.price().compareTo(BigDecimal.ZERO) <= 0) {
            throw new IllegalArgumentException("Invalid order parameters for venue: " + venueId);
        }
    }

    private byte[] receiveRawAck() {
        return new byte[]{0x01, 0x02, 0x03}; // Simulated raw network packet
    }

    // --- Abstract Hooks: Concrete Subclasses MUST implement wire specifics ---
    protected abstract byte[] encodeAndTransmit(Order order);
    protected abstract ExecutionReport parseExecutionReport(byte[] rawPayload);
}

// 1. Concrete FIX Protocol Implementation (ASCII Tag=Value)
public final class FixTradingGateway extends TradingVenueGateway {
    public FixTradingGateway() { super("CME-FIX-4.4"); this.isConnected = true; }

    @Override
    protected byte[] encodeAndTransmit(Order order) {
        // Serializes into FIX wire format: 35=D|11=ORD123|55=AAPL|...
        String fixMsg = "35=D|11=" + order.orderId() + "|55=" + order.ticker() + "|38=" + order.quantity() + "|44=" + order.price() + "|";
        return fixMsg.getBytes();
    }

    @Override
    protected ExecutionReport parseExecutionReport(byte[] rawPayload) {
        return new ExecutionReport("FIX-EXEC-101", "ORD-1", "FILLED", BigDecimal.valueOf(185.50), Instant.now());
    }
}

// 2. Concrete Nasdaq Binary Protocol Implementation (Ultra-Low Latency OUCH)
public final class NasdaqOuchGateway extends TradingVenueGateway {
    public NasdaqOuchGateway() { super("NASDAQ-OUCH"); this.isConnected = true; }

    @Override
    protected byte[] encodeAndTransmit(Order order) {
        // Packs raw binary struct: 1-byte type, 8-byte price, 4-byte qty directly into ByteBuffer
        byte[] binaryBuffer = new byte[32];
        binaryBuffer[0] = 'O'; // OUCH Enter Order message type
        return binaryBuffer;
    }

    @Override
    protected ExecutionReport parseExecutionReport(byte[] rawPayload) {
        return new ExecutionReport("OUCH-ACK-909", "ORD-1", "NEW", BigDecimal.valueOf(185.50), Instant.now());
    }
}
📋 Why Abstract Class vs. Interface Here? (Interview Question)

Interviewer: "Why did you use an abstract class instead of an interface for TradingVenueGateway?"

Senior Answer: "We use an abstract class when subclasses share common mutable or immutable state (like sequenceNumber, venueId, socket handles) and shared foundational behavior (like latency benchmarking and pre-trade risk validation). Interfaces cannot hold instance state (non-static fields). Furthermore, the Template Method Pattern relies on non-overridable final methods to enforce execution order, which cannot be implemented in interfaces prior to Java 8, and even with Java 8 default methods, interface methods cannot be declared final."

1.3 Inheritance & The Classic Diamond Problem Deep Dive

The Conceptual Theory: Inheritance models an "IS-A" relationship, allowing a class to inherit fields and methods from a parent class. While powerful for reuse, inheritance creates the tightest form of coupling in object-oriented programming.

Part A: Why Java Banned Multiple Class Inheritance (`extends A, B`)

Many languages like C++ permit a class to inherit from multiple classes. Java's designers deliberately banned multiple class inheritance to avoid the fatal Diamond Problem.

flowchart TD A["Class Asset (defines balance)"] --> B["Class EquityAsset (overrides calculateRisk)"] A --> C["Class CryptoAsset (overrides calculateRisk)"] B --> D["Class HybridToken (extends EquityAsset, CryptoAsset - ILLEGAL IN JAVA)"] C --> D

The Diamond Problem introduces two fatal architectural dilemmas:

  1. State Ambiguity (The Two-Copy Dilemma): If Asset has an instance variable double balance, does HybridToken inherit one copy of balance or two separate copies? If it has two copies, updating the balance via an EquityAsset method leaves the CryptoAsset balance out of sync, leading to catastrophic financial balance corruption. C++ solves this using "virtual base classes", which adds complex pointer indirection and messy constructor initialization order.
  2. Behavior Ambiguity: If both EquityAsset and CryptoAsset provide their own implementations of calculateRisk(), when someone calls hybridToken.calculateRisk(), which method should execute? There is no clean, unambiguous compiler choice.

Part B: The Java 8 Default Methods Diamond Problem (The Killer Interview Question)

⚠️ The Trap Question

Interviewer: "Java prohibits multiple inheritance, so the Diamond Problem can never happen in modern Java. True or False?"

Correct Answer: FALSE! Since Java 8 introduced default methods in interfaces, the behavioral Diamond Problem has returned to Java.

Consider this real-world algorithmic trading scenario where an order router implements two distinct routing strategies:

Java 21 — The Conflict 
// Top of the Diamond
interface OrderRouter {
    default void route(Order order) {
        System.out.println("Default OrderRouter: Routing to primary lit market.");
    }
}

// Left branch overrides default
interface SmartOrderRouter extends OrderRouter {
    @Override
    default void route(Order order) {
        System.out.println("SmartOrderRouter: Splitting order across lit pools based on depth.");
    }
}

// Right branch overrides default
interface DarkPoolRouter extends OrderRouter {
    @Override
    default void route(Order order) {
        System.out.println("DarkPoolRouter: Routing stealth order to institutional dark pools.");
    }
}

// Bottom of the Diamond — COMPILATION ERROR!
public class HybridTradingEngine implements SmartOrderRouter, DarkPoolRouter {
    // COMPILER ERROR:
    // class HybridTradingEngine inherits unrelated defaults for route(Order) 
    // from types SmartOrderRouter and DarkPoolRouter
}

How Java Resolves Interface Diamond Conflicts (The 3 Rules):

When interface default methods collide, the Java compiler enforces three strict rules:

  1. Rule 1: Class Wins Rule (Superclass Overrides Interface): Any method declared in a class or superclass always takes absolute precedence over any default method declared in any interface.
  2. Rule 2: Sub-interface Wins Rule (Most Specific Default Wins): If interface B extends interface A, and both provide a default method, the method in the more specific sub-interface (B) is automatically chosen.
  3. Rule 3: Explicit Disambiguation: If two completely unrelated interfaces provide the same default method signature, the compiler rejects the class. The developer MUST explicitly override the method and choose which interface to delegate to using InterfaceName.super.methodName().
Java 21 — The Working Solution 
public class HybridTradingEngine implements SmartOrderRouter, DarkPoolRouter {

    // Resolving the Diamond Conflict explicitly
    @Override
    public void route(Order order) {
        if (order.quantity() > 100_000) {
            // For block trades, delegate to DarkPoolRouter default logic
            DarkPoolRouter.super.route(order);
        } else {
            // For standard orders, delegate to SmartOrderRouter default logic
            SmartOrderRouter.super.route(order);
        }
    }
}

1.4 Method Overriding & Dynamic Dispatch (The Object Creation vs. Invocation Traps)

Candidates routinely fail technical interviews not because they don't know what overriding is, but because they get tricked by Reference Type vs. Runtime Object Type binding rules.

📖 The Golden Rule of Polymorphism

Methods are Virtual by Default in Java: Method execution is determined at RUNTIME by the actual object instantiated on the heap (Dynamic Method Dispatch via vtable).
Variables and Static Methods are NOT Virtual: Variable access and static method invocations are determined at COMPILE TIME by the declared reference type on the stack!

Trap 1: Field Hiding (Variables Are NEVER Polymorphic!)

What does this code print?

Java 21 
class Order {
    public double executionFee = 10.0; // Base fee
    
    public double getFee() { return executionFee; }
}

class InstitutionalOrder extends Order {
    public double executionFee = 2.0;  // Discounted fee for hedge funds
    
    @Override
    public double getFee() { return executionFee; }
}

public class InterviewTrapTest {
    public static void main(String[] args) {
        Order order = new InstitutionalOrder(); // Reference: Order, Object: InstitutionalOrder

        // TRAP 1: Accessing variable directly vs method
        System.out.println("order.executionFee = " + order.executionFee); // PRINTS: 10.0! NOT 2.0!
        System.out.println("order.getFee()      = " + order.getFee());      // PRINTS: 2.0!
    }
}

Explanation: Field access does not use dynamic dispatch. Because the reference type is Order, order.executionFee binds directly to Order.executionFee at compile time. However, order.getFee() uses dynamic dispatch and executes InstitutionalOrder.getFee().

Trap 2: Static Method Hiding (Static Methods Are NEVER Overridden!)

Java 21 
class TradeEngine {
    public static void printEngineType() {
        System.out.println("Standard Matching Engine");
    }
}

class FastTradeEngine extends TradeEngine {
    // This is METHOD HIDING, NOT Method Overriding!
    public static void printEngineType() {
        System.out.println("Ultra-Low Latency Kernel Bypass Engine");
    }
}

public class StaticTrap {
    public static void main(String[] args) {
        TradeEngine engine = new FastTradeEngine();
        engine.printEngineType(); // PRINTS: "Standard Matching Engine"!
        // Compiler converts this to: TradeEngine.printEngineType();
    }
}

Trap 3: Overloading with Inheritance (Overloading is Compile-Time, Overriding is Runtime)

Java 21 
class RiskManager {
    public void evaluateRisk(Order order) {
        System.out.println("Generic Order Risk Evaluation");
    }

    public void evaluateRisk(InstitutionalOrder order) {
        System.out.println("Institutional Large-Trader Risk Evaluation");
    }
}

public class OverloadTrap {
    public static void main(String[] args) {
        Order order = new InstitutionalOrder(); // Reference is Order
        RiskManager risk = new RiskManager();
        
        risk.evaluateRisk(order); // PRINTS: "Generic Order Risk Evaluation"! NOT Institutional!
    }
}

Explanation: Which overloaded method to call is decided at COMPILE TIME based on the reference type of the argument (Order), not the runtime type (InstitutionalOrder)!

Trap 4: The Deadly "Constructor Calling Overridden Method" Trap

This is a classic senior interview trap that causes silent NullPointerException or corrupted state during object initialization:

Java 21 
class BaseOrder {
    public BaseOrder() {
        System.out.println("BaseOrder constructor start");
        validate(); // DEADLY TRAP: Calling virtual method in constructor!
        System.out.println("BaseOrder constructor complete");
    }

    public void validate() {
        System.out.println("Base validation passed");
    }
}

class CryptoOrder extends BaseOrder {
    // Instance field initializer runs AFTER super() constructor finishes!
    private String walletAddress = "0x71C...B29";

    @Override
    public void validate() {
        System.out.println("Validating crypto wallet: " + walletAddress.toUpperCase());
    }
}

public class ConstructorTrap {
    public static void main(String[] args) {
        // What happens here?
        new CryptoOrder();
    }
}
💥 Output & Crash Analysis
BaseOrder constructor start
Exception in thread "main" java.lang.NullPointerException: Cannot invoke "String.toUpperCase()" because "this.walletAddress" is null
    at CryptoOrder.validate(ConstructorTrap.java:18)
    at BaseOrder.<init>(ConstructorTrap.java:4)
    at CryptoOrder.<init>(ConstructorTrap.java:12)

The Execution Sequence:

  1. Memory is allocated for CryptoOrder on the heap. All instance fields default to zero/null (walletAddress = null).
  2. CryptoOrder() constructor invokes super() (i.e. BaseOrder()).
  3. Inside BaseOrder(), it calls validate().
  4. Because methods in Java are virtual, dynamic dispatch routes the call to CryptoOrder.validate()!
  5. In CryptoOrder, the field initializer walletAddress = "0x71C...B29" has not executed yet!
  6. walletAddress is null, and calling .toUpperCase() throws a fatal NullPointerException inside the constructor.
Rule: Never call overridable (non-final, non-private) methods inside constructors!

Trap 5: Exception Rules in Method Overriding

When overriding a method, the subclass CANNOT throw broader or new checked exceptions (enforcing the Liskov Substitution Principle). It can, however, throw fewer checked exceptions, narrower (subclass) checked exceptions, or any unchecked RuntimeException.

Java 21 
import java.io.IOException;
import java.io.FileNotFoundException;

class OrderPersister {
    public void persist(Order order) throws IOException { ... }
}

class FastOrderPersister extends OrderPersister {
    // VALID: Narrower checked exception (FileNotFoundException is a subclass of IOException)
    @Override
    public void persist(Order order) throws FileNotFoundException { ... }

    // VALID: Throwing NO checked exceptions at all
    // @Override
    // public void persist(Order order) { ... }

    // ILLEGAL: Cannot throw broader checked exception (Exception is broader than IOException)!
    // @Override
    // public void persist(Order order) throws Exception { ... } // COMPILATION ERROR!

    // VALID: Can throw any unchecked RuntimeException
    // @Override
    // public void persist(Order order) throws NullPointerException, IllegalStateException { ... }
}

1.5 Covariant Return Types: True Type-Safety Without Downcasting

The Conceptual Theory: Introduced in Java 5, a Covariant Return Type allows an overriding method in a subclass to return a subtype (narrower type) of the return type declared in the parent method.

The Historical Pain Point (Java 1.4 and earlier): Prior to Java 5, overriding methods had to return the exact same return type as the parent method. In enterprise factory patterns, this forced callers into unsafe, ugly downcasting:

// JAVA 1.4 ERA (WITHOUT COVARIANT RETURNS)
OrderFactory factory = new EquityOrderFactory();
EquityOrder order = (EquityOrder) factory.createOrder(); // Required manual, dangerous downcasting!

Modern Production Trading Example with Covariant Return Types

Java 21 
// Base Financial Order
public class Order {
    private final String orderId;
    public Order(String orderId) { this.orderId = orderId; }
    public String getOrderId() { return orderId; }
}

// Subclass Order with asset-specific fields
public class EquityOrder extends Order {
    private final String ticker;
    private final int shares;

    public EquityOrder(String orderId, String ticker, int shares) {
        super(orderId);
        this.ticker = ticker;
        this.shares = shares;
    }

    public String getTicker() { return ticker; }
    public int getShares() { return shares; }
}

// Base Factory
public class OrderFactory {
    public Order createOrder(String id) {
        System.out.println("Creating generic base order");
        return new Order(id);
    }
}

// Subclass Factory leveraging Covariant Return Type!
public class EquityOrderFactory extends OrderFactory {
    
    // COVARIANT RETURN TYPE: Returns EquityOrder instead of Order!
    // Since EquityOrder IS-A Order, this is 100% legal and type-safe.
    @Override
    public EquityOrder createOrder(String id) {
        System.out.println("Creating specialized EquityOrder for stock exchange routing");
        return new EquityOrder(id, "NVDA", 500);
    }
}

// Client Usage Showing Zero Downcasting
public class ClientTradeRunner {
    public static void main(String[] args) {
        EquityOrderFactory factory = new EquityOrderFactory();

        // 1. Direct type-safe assignment: NO CAST NEEDED!
        EquityOrder equityOrder = factory.createOrder("ORD-9988");

        // 2. Direct access to subclass-specific methods without cast
        System.out.println("Routed Ticker: " + equityOrder.getTicker());
        System.out.println("Share Volume:  " + equityOrder.getShares());
    }
}

Under The Hood: Synthetic Bridge Methods in Bytecode

🔬 How the JVM Handles Covariant Returns Under the Hood

In Java bytecode, a method signature includes both its name and its return type descriptor. Therefore, in bytecode:

  • Order createOrder(String id) has descriptor: (Ljava/lang/String;)LOrder;
  • EquityOrder createOrder(String id) has descriptor: (Ljava/lang/String;)LEquityOrder;
Because their return types differ in the class file, how does dynamic method dispatch still work when calling through a base reference OrderFactory f = new EquityOrderFactory(); f.createOrder("1");?

The Compiler's Secret: Synthetic Bridge Methods!
To maintain binary backward compatibility with polymorphism, the Java compiler automatically synthesizes an invisible Bridge Method inside EquityOrderFactory.class:

// Bytecode representation of compiler-generated Bridge Method
public synthetic bridge Order createOrder(String id) {
    // Delegates directly to the covariant method!
    return this.createOrder(id); 
}

This allows legacy callers expecting an Order to invoke the bridge method, which seamlessly forwards the call to the covariant EquityOrder method.

2. Functional Interface vs Marker Interface (Core Interview Question)

Understanding interface taxonomy is a classic litmus test for Java proficiency.

Feature Functional Interface Marker Interface
Definition An interface with exactly ONE abstract method (SAM - Single Abstract Method). An interface with ZERO methods or constants.
Purpose Provides target types for lambda expressions and method references. Facilitates functional programming in Java. Tags a class to convey metadata to the JVM or a framework at runtime.
Examples Runnable, Callable, Comparator, TradeValidator Serializable, Cloneable, Remote

The Code Perspective

Java 21 
// FUNCTIONAL INTERFACE
@FunctionalInterface
public interface TradeValidator {
    // Exactly one abstract method
    boolean isValid(Trade trade);
    
    // Can have multiple default/static methods
    default void logFailure(Trade trade) {
        System.err.println("Validation failed for trade: " + trade.tradeId());
    }
}

// Usage via Lambda in a Pricing Engine
TradeValidator notionalValidator = (trade) -> trade.notional().compareTo(MAX_LIMIT) < 0;

The Modern Replacement for Marker Interfaces

Marker interfaces are largely considered legacy. The modern, type-safe, and flexible replacement is Custom Annotations with @Retention(RetentionPolicy.RUNTIME).

Why annotations? A Marker interface pollutes the type hierarchy (if a parent implements it, all children are irreversibly marked). Annotations are declarative metadata that don't force an "IS-A" relationship.

📋 How to Answer This in an Interview

"A Functional interface, annotated with @FunctionalInterface, contains exactly one abstract method and is the backbone of Java's lambda expressions, allowing us to pass behaviors like TradeRoutingStrategy elegantly. A Marker interface, like Serializable, has zero methods and is historically used to signal the JVM. However, in modern Spring/Java development, we replace marker interfaces with custom Runtime Annotations. Annotations provide richer metadata (you can add parameters) and don't permanently tie a class to a type hierarchy, avoiding the fragility of forced inheritance."

3. Shallow Copy vs Deep Copy in Financial Portfolios

Copying objects incorrectly is a leading cause of subtle, catastrophic data corruption in shared memory spaces.

Catastrophic Bug Scenario: A risk engine needs to simulate a 10% market crash on a client's Portfolio. The developer performs a shallow copy of the portfolio. When the risk engine mutates the prices of the trades in the copied portfolio, the original client portfolio is updated as well because the list of trades points to the exact same objects in the heap. The client's live dashboard suddenly shows massive losses.

flowchart LR subgraph Shallow Copy P1[Portfolio A] --> T1[Trade 1] P1 --> T2[Trade 2] P2[Copied Portfolio B] --> T1 P2 --> T2 end subgraph Deep Copy P3[Portfolio A] --> T3[Trade 1] P3 --> T4[Trade 2] P4[Copied Portfolio B] --> T5[Cloned Trade 1] P4 --> T6[Cloned Trade 2] end

Implementation: Copy Constructor over Cloneable

Java's built-in Cloneable interface and clone() method are notoriously flawed (they bypass standard object construction, handle finals poorly, and default to shallow copying). The industry standard for Deep Copying is the Copy Constructor or a dedicated copy factory.

Java 21 
import java.math.BigDecimal;
import java.util.ArrayList;
import java.util.List;

public class Trade {
    private String tradeId;
    private BigDecimal price;

    public Trade(String tradeId, BigDecimal price) {
        this.tradeId = tradeId;
        this.price = price;
    }

    // Copy Constructor for Deep Copying
    public Trade(Trade original) {
        this.tradeId = original.tradeId; // String is immutable, safe to copy ref
        this.price = original.price;     // BigDecimal is immutable, safe to copy ref
    }

    public void setPrice(BigDecimal price) { this.price = price; }
    public BigDecimal getPrice() { return price; }
}

public class Portfolio {
    private List<Trade> trades;

    public Portfolio() { this.trades = new ArrayList<>(); }

    // Deep Copy Constructor
    public Portfolio(Portfolio original) {
        this.trades = new ArrayList<>();
        for (Trade t : original.trades) {
            this.trades.add(new Trade(t)); // Allocating NEW Trade objects on the heap!
        }
    }

    public void addTrade(Trade t) { trades.add(t); }
    public List<Trade> getTrades() { return trades; }
}

4. Object Relationships: Association, Aggregation, Composition

Understanding the strength of relationships determines how you manage object lifecycles and garbage collection.

classDiagram Trader "uses" --> "1..*" Exchange : Association Portfolio "has" o-- "0..*" Trade : Aggregation Order "owns" *-- "1..*" OrderLeg : Composition
Relationship Type Lifecycle Dependency Finance Domain Example
Association "Uses-a" Independent. Both objects can exist without each other. Trader and Exchange. A Trader sends orders to an Exchange, but if the Trader is deleted from the system, the Exchange continues to exist.
Aggregation Weak "Has-a" Independent. The child can outlive the parent. Portfolio and Trade. A Portfolio contains Trades. If a Portfolio is closed/liquidated, the historical Trade records must still exist for regulatory auditing.
Composition Strong "Has-a" Dependent. If parent is destroyed, child is destroyed. Order and OrderLeg (Multi-leg options). An OrderLeg fundamentally cannot exist without its parent Order. If the Order is deleted, the Legs are strictly garbage collected.

5. Coupling vs Cohesion

The golden rule of enterprise architecture is: High Cohesion, Loose Coupling.

  • Cohesion (Intra-class): How closely related and focused the responsibilities of a single class are. A TradeExecutionService should only handle execution (High Cohesion). If it also handles parsing FIX protocols, writing to a database, and sending emails, it has Low Cohesion (God Class anti-pattern).
  • Coupling (Inter-class): The degree of direct dependency between different classes. Tight coupling means changing one class forces changes in another. Loose coupling is achieved by depending on Abstractions (Interfaces) rather than concretions.
Java 21 
// LOOSE COUPLING EXAMPLE
public interface AuditLogger {
    void logEvent(String entityId, String eventType);
}

public class TradeEngine {
    // Depends on abstraction, not concrete FIXLogger or DBLogger
    private final AuditLogger logger; 

    // Dependency Injection allows swapping implementations without modifying TradeEngine
    public TradeEngine(AuditLogger logger) {
        this.logger = logger;
    }

    public void execute(Order order) {
        // execute logic
        logger.logEvent(order.orderId(), "EXECUTED_AT_EXCHANGE");
    }
}

6. Interviewer Trap Questions & Model Answers

🎯 Q1: "Why do senior architects favor Composition over Inheritance?"

The Trap: Juniors think inheritance is the primary OOP tool. It is not.

Senior Answer: "Inheritance breaks encapsulation because the subclass becomes tightly coupled to the implementation details of the parent class—this is known as the Fragile Base Class problem. If you change a method in the parent, you risk breaking all descendants. Composition ('has-a') provides extreme flexibility. Instead of an AlgorithmicTrade inheriting from a massive Trade hierarchy, a Trade is composed of an ExecutionStrategy interface. This allows us to swap behaviors at runtime via Strategy pattern, rather than being locked in at compile time."

🎯 Q2: "Can an abstract class have constructors? If it cannot be instantiated, what is the purpose of its constructor?"

The Trap: Testing your understanding of object instantiation hierarchies.

Senior Answer: "Yes, abstract classes absolutely have constructors. Even though you cannot instantiate an abstract class directly via the new keyword, its constructor is always invoked when a concrete subclass is instantiated (via super()). The purpose of the abstract class constructor is to initialize the inherited state—especially final fields—that the abstract class encapsulates, ensuring the foundational state is valid before the subclass constructor executes."
