SQL & Database — Mastering Financial Data Queries

Advanced SQL techniques, query optimization, and ACID properties for financial systems.

PILLAR 1: Ground-Zero Theory & The Pain Point

The Pain Point: Financial data must be impeccably accurate and highly available. Bad queries can lock up the settlement database, causing millions in losses. Knowing how the database executes queries and manages locks is critical.

Order of Execution

You write: SELECT ... FROM ... WHERE ... GROUP BY ... HAVING ... ORDER BY

The DB executes: FROM → JOIN → WHERE → GROUP BY → HAVING → SELECT → DISTINCT → ORDER BY → LIMIT

Why you can't use an alias in WHERE: The WHERE clause filters data before the SELECT clause creates the aliases.

PILLAR 3: Step-by-Step Evolution & Thought Process

Indexing Strategies

Naive: Create an index on every column. Result: Extremely slow inserts/updates, as B-Trees must be rebalanced.

Better: Composite Index. E.g., `INDEX(trader_id, trade_date)`. The order matters! It filters by `trader_id` first.

Best: Covering Index. If a query is `SELECT amount FROM trades WHERE trader_id = X`, and we have `INDEX(trader_id, amount)`, the DB never touches the actual table (Index-Only Scan).

PILLAR 4: Production-Grade SQL Code


-- Window Functions: Running Total of Daily P&L
SELECT 
    trade_date,
    daily_pnl,
    SUM(daily_pnl) OVER (ORDER BY trade_date ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW) as cumulative_pnl,
    LAG(daily_pnl, 1) OVER (ORDER BY trade_date) as previous_day_pnl
FROM daily_trader_stats
WHERE trader_id = 'T123';
            

-- Joins: Finding unmatched trades (Reconciliation)
SELECT 
    t.trade_id, t.amount, s.settlement_id
FROM trades t
LEFT JOIN settlements s ON t.trade_id = s.trade_id
WHERE s.settlement_id IS NULL; -- Trades that haven't been settled

PILLAR 5: The Interviewer's Deep Follow-Up Questions

📋 How to Answer This in an Interview

Q: What is the difference between RANK(), DENSE_RANK(), and ROW_NUMBER()?
Candidate: Let's say salaries are 100k, 100k, 90k.
- ROW_NUMBER(): 1, 2, 3 (always sequential)
- RANK(): 1, 1, 3 (skips the next rank after a tie)
- DENSE_RANK(): 1, 1, 2 (never skips ranks)

🎯 Interviewer Follow-Up Questions

Q: Write an SQL query to rank employees based on their experience (highest to lowest).
SELECT emp_id, exp_years, DENSE_RANK() OVER (ORDER BY exp_years DESC) as rank FROM employees;

Q: Given account transactions A:+100, B:+200, A:-50, C:+300, B:-100, A:+150, calculate the final balance for each account.
SELECT account_id, SUM(amount) as final_balance FROM transactions GROUP BY account_id;

Q: How would you identify and resolve a database bottleneck?
Answer: 1. Enable Slow Query Log. 2. Use EXPLAIN ANALYZE on the slow query to check for Full Table Scans. 3. Add appropriate B-Tree or Covering indexes. 4. Avoid `SELECT *`. 5. Implement application-level caching (Redis) for read-heavy data.

PILLAR 6: Trade-offs & When NOT To Use It

Relational DB Trade-offs: ACID compliance guarantees data integrity, but vertical scaling is expensive and horizontal scaling (sharding) is very complex compared to NoSQL databases. Don't use RDBMS for unstructured data, high-velocity time-series data (use InfluxDB/Kdb+), or heavy document storage.
