Kafka & Messaging — Event-Driven Trading Architecture

Mastering distributed event streaming for high-frequency trading platforms.

PILLAR 1: Ground-Zero Theory & The Pain Point

What is it? Apache Kafka is a distributed event streaming platform designed to handle trillions of events a day. In the finance domain, think of Kafka as the central nervous system of a trading platform.

The Pain Point: Without Kafka, microservices rely on synchronous REST or brittle message queues. If the matching engine is down, trade events are lost. If we use a traditional RDBMS to store transient events, it becomes a severe bottleneck.

PILLAR 2: Architectural Decision Rationales & Modifier Deep Dives

Producer Acks

acks=0: Fire and forget. acks=1: Leader acknowledgment. acks=all (or -1): Leader and all in-sync replicas (ISR) acknowledge. For financial trades, always use acks=all.

Idempotent Producer

enable.idempotence=true ensures that retries don't result in duplicate trades. It assigns a Producer ID (PID) and sequence number to messages.

Schema Registry

Financial messages evolve (e.g., adding a `taxRate` field). Schema Registry (Avro, Protobuf) enforces schemas, ensuring backward/forward compatibility. If an upstream service changes the message structure abruptly, the schema registry rejects it.

PILLAR 3: Step-by-Step Evolution & Thought Process

Naive: REST API to save trade -> DB crashes -> Trade lost.

Better: Messaging Queue (RabbitMQ) -> Good, but messages are deleted after reading. Hard to replay.

Best (Kafka): Distributed log. Messages persist. If the settlement service is down, it can resume from its last committed offset when it wakes up.

import org.springframework.kafka.core.KafkaTemplate;
import org.springframework.stereotype.Service;
import org.springframework.transaction.annotation.Transactional;

public record TradeEvent(String tradeId, String currencyPair, double amount, String action) {}

@Service
public class TradeProducerService {
    
    private final KafkaTemplate<String, TradeEvent> kafkaTemplate;
    
    public TradeProducerService(KafkaTemplate<String, TradeEvent> kafkaTemplate) {
        this.kafkaTemplate = kafkaTemplate;
    }
    
    // Exactly-once semantics with Transactional outbox/Kafka transactions
    @Transactional
    public void executeTrade(TradeEvent event) {
        // Partitioning by currencyPair ensures strict ordering for a given pair
        kafkaTemplate.send("fx-trades", event.currencyPair(), event);
    }
}

PILLAR 5: The Interviewer's Deep Follow-Up Questions

📋 How to Answer This in an Interview

Q: How would Kafka partitions help with ordering?
Candidate: Kafka only guarantees order within a partition. To maintain order for a specific entity (like all trades for `EUR/USD`), we use the entity ID as the message key. Kafka hashes the key to assign it to the same partition consistently.

🎯 Interviewer Follow-Up Questions

Q: How would you prevent duplicate transactions if the user clicks multiple times?
Answer: 1) UI debouncing. 2) Idempotent API with a unique `requestId` stored in a Redis/DB with a unique constraint. 3) Kafka Idempotent producer `enable.idempotence=true` prevents network retry duplicates.

Q: What happens when a database crashes while consuming data from Kafka?
Answer: Disable auto-commit (`enable.auto.commit=false`). Process the message, write to DB, and manually commit the offset. If DB crashes before commit, the consumer restarts and re-reads the uncommitted message. The DB write must be idempotent.

Q: How would you process 1 lakh (100,000) messages/second?
Answer: 1. Increase topic partitions. 2. Scale consumer instances (up to the number of partitions). 3. Tune `batch.size` and `linger.ms` on producer. 4. Use LZ4 or ZSTD compression. 5. Optimize consumer processing (e.g., async DB batch inserts).

PILLAR 6: Trade-offs & When NOT To Use It

REST vs Kafka

FeatureREST APIKafka (Event-Driven)
CommunicationSynchronous (Request-Reply)Asynchronous (Publish-Subscribe)
CouplingTight (Service A must know B's URL)Loose (Producers don't know Consumers)
Use CaseFetching balance, synchronous validationTrade execution, log aggregation

Don't use Kafka if: You need immediate, synchronous user feedback (e.g., login validation), or if the infrastructure overhead is too high for a simple CRUD app.
