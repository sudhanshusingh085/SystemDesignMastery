Requirement Gathering: The Architect's First Directive

The Fatal Mistake: Entering a System Design interview, hearing "Design Twitter", and immediately turning to the whiteboard to draw a Load Balancer and a Database. This results in an instant rejection at FAANG companies. Solving the wrong problem perfectly is the ultimate architectural failure.

Requirement gathering is not a formality; it is a calibration exercise. It is where you transform a deliberately vague, impossible prompt into a bounded, deterministic engineering problem. This masterclass will teach you how to extract the exact parameters you need to design a system that scales, survives, and satisfies the interviewer's hidden rubric.

PILLAR 1: Ground-Zero Theory & The Psychology of the Interviewer

In a typical System Design interview, the prompt is hilariously vague: "Design WhatsApp" or "Design a Parking Lot". This is not because the interviewer is lazy. It is a psychological stress test.

Why Interviewers Use Vague Prompts

  • Ambiguity Resolution: Senior engineers do not get handed perfect Jira tickets. They navigate corporate ambiguity. The interviewer wants to see if you can impose order on chaos.
  • Scoping Discipline: Designing all of WhatsApp in 45 minutes is impossible. Designing the 1-to-1 text messaging delivery mechanism is possible. Can you carve out a manageable MVP (Minimum Viable Product)?
  • Architectural Empathy: Do you ask about the user?
    📖 Architectural Empathy: The ability to understand that technical decisions (like consistency vs. availability) directly impact the human user experience.

Step 1: Clarify Core Features (The "What")

Define the exact boundaries of the system. What is explicitly in-scope, and more importantly, what is explicitly out-of-scope?

  • "For Twitter, are we focusing purely on the Home Timeline and Tweeting, or do we need to worry about Direct Messages, Search, and Trending Topics?" (Pro-tip: Push DMs and Search out of scope).
  • "For the Parking Lot, do we need to handle payment processing, or can we assume a third-party payment gateway?"

Step 2: Establish User Scale & Traffic Patterns (The "Who & How Much")

Scale dictates your database choice, caching strategy, and partitioning scheme.

  • DAU / MAU: What are the Daily Active Users?
  • Read-to-Write Ratio: Is this a read-heavy system (Twitter timeline, 100:1) or a write-heavy system (IoT metrics ingestion, 1:100)?
  • Peak vs Average: Are there massive traffic spikes? (e.g., Ticketmaster during a Taylor Swift concert).

Step 3: Define Non-Functional Requirements & SLAs (The "How Well")

These answers directly map to the CAP Theorem trade-offs you will make.

  • Latency: "Does this need to be real-time (< 200ms) or is batch processing acceptable?"
  • Availability vs Consistency: "If a user updates their profile picture, is it okay if their friends see the old picture for 30 seconds (Eventual Consistency), or must it be instantly updated for everyone (Strong Consistency)?"

Step 4: Storage & Retention Horizon (The "Where & How Long")

Data volume determines if you need a single relational DB or a sharded NoSQL cluster.

  • "How long do we retain the data? 1 year? 5 years? Forever?"
  • "What is the average size of a payload? Are we storing 280-character text, or 50MB 4K videos?"

Step 5: System Boundaries & Client Interfaces (The "Edges")

Understand the constraints of the clients talking to your system.

  • "Are our users primarily on mobile connections with high latency?"
  • "Does the app need an offline mode?"

PILLAR 2 Extension: The Master Sizing & Capacity Estimation Cheat Sheet

Back-of-the-envelope calculations prove you understand physical hardware limits. Memorize these formulas.

Mental Math Hack: There are exactly 86,400 seconds in a day. During an interview, loudly announce: "I will round 86,400 to 100,000 to simplify calculations." Interviewers love this.
Metric Formula / Rule of Thumb Architectural Decision Rationale
Average QPS (DAU × Requests per user per day) / 100,000 Determines how many app servers you need (Assuming 1 server handles ~1k-5k QPS).
Peak QPS Average QPS × 2 (up to × 5) Determines Auto-scaling groups and Load Balancer provisioning.
Storage (5-Year) (DAU × Writes/day × Size/Write) × 365 × 5 If > 5TB, you must discuss Database Sharding or NoSQL.
Cache Memory Daily Read Volume × 0.20 Based on the 80/20 Pareto principle. Determines Redis cluster sizing.

PILLAR 5: The Grill Round — Real-World Requirement Simulations

How does this actually sound in an interview? Here are 3 masterclass dialogues.

Simulation 1: High-Level Design — "Design TinyURL"

Candidate: "Before we dive in, I’d like to clarify the core features. Are we just generating short aliases for long URLs and redirecting them? Or do we need custom aliases and analytics?"
Interviewer: "Custom aliases are in scope. Analytics can be out of scope for now."
Candidate: "Got it. For scale, what traffic are we looking at?"
Interviewer: "About 100 million new URLs generated per month."
Candidate: "Okay, and since this is a URL shortener, I assume it’s heavily read-skewed. What's the read-to-write ratio?"
Interviewer: "Exactly. Assume 100:1 read-to-write."
Candidate: "Excellent. With 100M writes/month, we have 10 Billion reads/month. That's about 40 write QPS and 4,000 read QPS. Latency for redirection must be minimal, so caching will be critical."

Simulation 2: High-Level Design — "Design Twitter Feed"

Candidate: "For the feed, are we designing the global trending feed or the customized user timeline?"
Interviewer: "User timeline. showing tweets from people they follow."
Candidate: "Are we dealing with the 'Celebrity Problem' (Justin Bieber has 100M followers, posting a tweet causes a massive fan-out)? Or can we assume uniform follower counts?"
Interviewer (Smiling): "Yes, you absolutely must handle the celebrity problem."
Candidate: "Understood. For consistency vs availability: if a user tweets, is it acceptable if it takes 5 seconds to show up in all 100M followers' feeds, favoring high availability?"
Interviewer: "Yes, eventual consistency is perfectly fine here."

Simulation 3: Low-Level Design (LLD) — "Design a Parking Lot"

Candidate: "Since this is Object-Oriented Design, I'll focus on entities and constraints. Does the parking lot have multiple floors?"
Interviewer: "Yes, 5 floors."
Candidate: "Do we support multiple vehicle sizes, like motorcycles, compact cars, and buses?"
Interviewer: "Yes, all three. And buses take up 5 consecutive large spots."
Candidate: "Interesting. Are there multiple entrance and exit gates operating concurrently? This will impact thread-safety for spot allocation."
Interviewer: "Great catch. Yes, 4 entrances and 4 exits. Thread safety is critical."

PILLAR 4: Production-Grade Code Modeling

In a Low-Level Design (LLD) interview or when writing a design doc, you should model captured requirements explicitly in code using modern language features. We use Sealed Hierarchies and Immutable Records to create robust, compile-time verified configuration contracts. 

/**
 * PILLAR 4: Using Java 21 Sealed Interfaces and Records to model System Requirements.
 * 
 * Architectural Rationale:
 * - Records provide immutable, thread-safe data carriers for our constraints.
 * - Sealed interfaces restrict the types of system profiles we allow (e.g., ReadHeavy vs WriteHeavy),
 *   preventing invalid configurations at compile time.
 */
public sealed interface SystemRequirements permits ReadHeavySpec, WriteHeavySpec {
    
    // Common contract
    long dailyActiveUsers();
    double slaTargetLatencyMs();
    boolean requiresStrongConsistency();

    /**
     * Models a Read-Heavy system (e.g., Twitter, Netflix).
     * 
     * @param readToWriteRatio Must be > 1.
     */
    public record ReadHeavySpec(
        long dailyActiveUsers,
        double slaTargetLatencyMs,
        boolean requiresStrongConsistency,
        int readToWriteRatio,
        double cacheHitRatioTarget
    ) implements SystemRequirements {
        public ReadHeavySpec {
            if (readToWriteRatio <= 1) {
                throw new IllegalArgumentException("Read-heavy systems must have ratio > 1");
            }
            if (cacheHitRatioTarget < 0.0 || cacheHitRatioTarget > 1.0) {
                throw new IllegalArgumentException("Invalid cache target");
            }
        }
        
        // Helper to estimate Redis cluster sizing based on the 80/20 rule
        public long estimateDailyCachedReads() {
            long totalReads = dailyActiveUsers * 10 * readToWriteRatio; 
            return (long) (totalReads * cacheHitRatioTarget);
        }
    }

    /**
     * Models a Write-Heavy system (e.g., IoT Telemetry, Log Aggregation).
     */
    public record WriteHeavySpec(
        long dailyActiveUsers,
        double slaTargetLatencyMs,
        boolean requiresStrongConsistency,
        int writeBatchSize,
        long retentionPeriodDays
    ) implements SystemRequirements {
        public WriteHeavySpec {
            if (writeBatchSize < 1) throw new IllegalArgumentException("Batch size must be positive");
        }
        
        // Helper to estimate Kafka/Storage partitioning needs
        public long estimateDailyStorageRecords() {
            return dailyActiveUsers * writeBatchSize * 100; // 100 bursts per user
        }
    }
}
using System;

/// 
/// PILLAR 4: Using C# 12 Records & Discriminated Inheritance to model System Requirements.
/// 
/// Architectural Rationale:
/// - Positional records provide immutable, thread-safe value semantics.
/// - Closed type hierarchies enable exhaustive pattern matching during topology sizing.
/// 
public abstract record SystemRequirements(
    long DailyActiveUsers,
    double SlaTargetLatencyMs,
    bool RequiresStrongConsistency
);

/// 
/// Models a Read-Heavy system (e.g., Twitter, Netflix).
/// 
public sealed record ReadHeavySpec : SystemRequirements
{
    public int ReadToWriteRatio { get; init; }
    public double CacheHitRatioTarget { get; init; }

    public ReadHeavySpec(
        long dailyActiveUsers,
        double slaTargetLatencyMs,
        bool requiresStrongConsistency,
        int readToWriteRatio,
        double cacheHitRatioTarget
    ) : base(dailyActiveUsers, slaTargetLatencyMs, requiresStrongConsistency)
    {
        if (readToWriteRatio <= 1)
            throw new ArgumentException("Read-heavy systems must have ratio > 1");
        if (cacheHitRatioTarget is < 0.0 or > 1.0)
            throw new ArgumentException("Invalid cache target");

        ReadToWriteRatio = readToWriteRatio;
        CacheHitRatioTarget = cacheHitRatioTarget;
    }

    // Helper to estimate Redis cluster sizing based on the 80/20 rule
    public long EstimateDailyCachedReads()
    {
        long totalReads = DailyActiveUsers * 10 * ReadToWriteRatio;
        return (long)(totalReads * CacheHitRatioTarget);
    }
}

/// 
/// Models a Write-Heavy system (e.g., IoT Telemetry, Log Aggregation).
/// 
public sealed record WriteHeavySpec : SystemRequirements
{
    public int WriteBatchSize { get; init; }
    public long RetentionPeriodDays { get; init; }

    public WriteHeavySpec(
        long dailyActiveUsers,
        double slaTargetLatencyMs,
        bool requiresStrongConsistency,
        int writeBatchSize,
        long retentionPeriodDays
    ) : base(dailyActiveUsers, slaTargetLatencyMs, requiresStrongConsistency)
    {
        if (writeBatchSize < 1)
            throw new ArgumentException("Batch size must be positive");

        WriteBatchSize = writeBatchSize;
        RetentionPeriodDays = retentionPeriodDays;
    }

    // Helper to estimate Kafka/Storage partitioning needs
    public long EstimateDailyStorageRecords()
    {
        return DailyActiveUsers * WriteBatchSize * 100; // 100 bursts per user
    }
}

Interviewer deep-dive: By using strict type contracts, you demonstrate deep domain modeling. You ensure that a system cannot accidentally be instantiated as "ReadHeavy" while having a 1:10 ratio.

PILLAR 6: Trade-offs & The 25+ Universal Checklist

There is a trade-off in requirement gathering: Ask too few questions, and you fail for lack of scope. Ask too many questions, and you waste 15 minutes of a 45-minute interview, failing because you never actually design the system. Timebox this phase to 5-7 minutes.

Universal Question Checklist

Category Crucial Questions
Functional What are the 2 most important features? Do we need auth? Notifications? Search?
Non-Functional CAP theorem preference (Availability or Consistency)? Expected latency? P99 latency SLA?
Data & Scale DAU? Read:Write ratio? Average payload size? Data retention policy? Geographic distribution?

Red Flags vs. Green Flags

Red Flags 🚩 (Instant Fail) Green Flags 🟢 (Staff / Senior Level)
Writing code or drawing boxes instantly without asking a single question. Explicitly listing "Out of Scope" items on the whiteboard to manage time.
Asking random, disconnected questions just to fill time. Asking derivative questions: "Since the ratio is 100:1, caching is my primary concern. Can we tolerate eventual consistency for cache invalidation?"
Failing to clarify read-to-write ratio, resulting in a disastrous database choice later. Doing quick back-of-the-envelope math out loud and adjusting the architecture based on the result.
