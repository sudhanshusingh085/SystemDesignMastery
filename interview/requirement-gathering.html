Requirement Gathering

Why this matters: Requirement gathering is the most critical step in system design. Solving the wrong problem perfectly is still a failure. Many candidates skip this and start drawing boxes—don't be one of them!

Categories of Questions to Ask

To systematically gather requirements, break your questions down into these 5 categories:

  1. Users & Scale: How many users? What is the ratio of daily active users (DAU) to monthly active users (MAU)? Is the system read-heavy or write-heavy?
  2. Features: What are the core features? What is explicitly out of scope (to save time)?
  3. Performance: What is the acceptable latency? What is the availability target (e.g., 99.9% uptime)?
  4. Data: How much data will we store? How long must we retain it? What is the data format?
  5. Special Requirements: Does it need real-time updates? Offline support? Is it a global service requiring multi-region deployment?

Examples of Requirement Gathering

Example 1: "Design Twitter"

  • Users: How many DAU? (e.g., 150M)
  • Features: Can users post videos or just text? Do we need to design the timeline generation or just the tweeting mechanism?
  • Scale: Is it read-heavy? (Yes, typically 100:1 read-to-write ratio).
  • Performance: Does the timeline need to be real-time? (e.g., < 500ms latency).

Example 2: "Design a Parking Lot"

  • Users: Is this for a single building or a multi-city enterprise?
  • Features: Do we need to handle payment processing? Different vehicle sizes (motorcycle, compact, large)?
  • Data: Do we need to track historical data for analytics?

Java 21 Code: Modeling Requirements

Using Java 21

📖 Record: A compact syntax for declaring classes that are transparent carriers for immutable data.
, you can clearly model system requirements:

Java 
/**
 * A record to succinctly capture the parsed requirements during an interview.
 */
public record RequirementSpec(
    boolean isReadHeavy,
    long dailyActiveUsers,
    int readToWriteRatio,
    double targetLatencyMs,
    java.util.List coreFeatures
) {
    public RequirementSpec {
        if (targetLatencyMs < 0) {
            throw new IllegalArgumentException("Latency cannot be negative");
        }
    }
    
    // Derived metric helper
    public long estimatedRequestsPerSecond() {
        long totalDailyRequests = dailyActiveUsers * 10; // Assuming 10 requests/user/day
        return totalDailyRequests / 86400; // seconds in a day
    }
}

How to Write Down Requirements

During the interview, use the whiteboard or shared document to list requirements explicitly:

# Functional
1. Post tweet
2. View timeline
(Out of scope: Search, DMs)

# Non-Functional
- 100M DAU
- Read:Write = 100:1
- Low latency (< 200ms)
- High availability (Eventual consistency is fine)
Red Flags 🚩
  • Starting the architecture drawing before agreeing on requirements.
  • Assuming a 1 Billion user scale for a local mom-and-pop shop application.
  • Not asking about read-vs-write ratios, which drastically alters database choices.
