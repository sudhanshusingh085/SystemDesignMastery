Production Failure Scenarios — Learning From Real Outages

Designing a system is only half the battle. Keeping it alive in production is the real test. Here are 10 real-world failure scenarios, why they happen, and how to prevent them in Java 21.

1. Database Connection Pool Exhaustion

What happened: All database connections are used up. New requests to the application fail because they cannot get a connection to the DB.

Root cause: A slow query or external API call holding a connection open for too long. Since there are a finite number of connections (e.g., 50), 50 concurrent slow requests will consume the entire pool.

How to prevent: Enforce connection timeouts, query timeouts, and limit connection pool size.

Java 21 
// Using standard HikariCP configuration for connection pooling
import com.zaxxer.hikari.HikariConfig;
import com.zaxxer.hikari.HikariDataSource;

public class DatabaseConfig {
    public static HikariDataSource getDataSource() {
        var config = new HikariConfig();
        config.setJdbcUrl("jdbc:postgresql://localhost:5432/mydb");
        config.setUsername("user");
        config.setPassword("pass");
        
        // CRITICAL: Set limits and timeouts!
        config.setMaximumPoolSize(50); // Don't let it grow infinitely
        config.setConnectionTimeout(3000); // 3s wait for a connection
        config.setLeakDetectionThreshold(5000); // Log connections held > 5s
        
        return new HikariDataSource(config);
    }
}

2. Cascading Failure

What happened: Service A goes down. Service B depends on A, waits too long, and its threads get blocked. Soon, Service B crashes. Then Service C crashes. The whole system is down.

Root cause: Tight coupling and lack of fallback mechanisms (like a Circuit Breaker).

How to prevent: Use Circuit Breakers, Bulkheads, and strict timeouts.

3. Cache Stampede (Thundering Herd)

What happened: A popular item's cache expires. Immediately, 10,000 requests hit the server, miss the cache, and all try to fetch from the DB at the exact same time, crashing the DB.

Root cause: Massive concurrent cache misses due to the same TTL (Time To Live).

How to prevent: Add jitter to TTLs, or use a Mutex Lock to ensure only one thread fetches from the DB while others wait.

Java 21 
import java.util.concurrent.ConcurrentHashMap;
import java.util.concurrent.locks.ReentrantLock;

public class CacheService {
    private final ConcurrentHashMap<String, String> cache = new ConcurrentHashMap<>();
    private final ConcurrentHashMap<String, ReentrantLock> locks = new ConcurrentHashMap<>();

    public String getData(String key) {
        String value = cache.get(key);
        if (value != null) return value; // Cache hit

        // Cache miss: lock specifically for this key
        var lock = locks.computeIfAbsent(key, k -> new ReentrantLock());
        lock.lock();
        try {
            // Double-checked locking
            value = cache.get(key);
            if (value != null) return value;

            // Simulate DB fetch
            value = fetchFromDatabase(key);
            cache.put(key, value);
            return value;
        } finally {
            lock.unlock();
        }
    }

    private String fetchFromDatabase(String key) {
        return "Data for " + key; 
    }
}

4. Split Brain

What happened: In a primary-secondary database setup, the network drops between them. The secondary thinks the primary is dead and promotes itself. The primary is still alive. Both accept writes. Data is corrupted.

Root cause: Network partition without proper quorum or fencing tokens.

How to prevent: Use Quorum (majority voting) for leader election. E.g., needing 3 out of 5 nodes to agree before promoting a new leader.

5. Memory Leak

What happened: Application steadily consumes more RAM over days, gets sluggish, and eventually crashes with OutOfMemoryError.

Root cause: Collections that grow infinitely, unclosed I/O streams, or static maps holding object references forever.

How to prevent: Use weak references, bound your collections, and ALWAYS use try-with-resources.

Java 21 
import java.io.BufferedReader;
import java.io.FileReader;
import java.io.IOException;

public class ResourceSafety {
    // Anti-pattern: List grows forever
    // private static List<String> history = new ArrayList<>();

    public void processFileSafely(String path) {
        // Java's try-with-resources ensures reader is CLOSED automatically
        // preventing file handle leaks and memory leaks
        try (BufferedReader reader = new BufferedReader(new FileReader(path))) {
            String line;
            while ((line = reader.readLine()) != null) {
                // process line
            }
        } catch (IOException e) {
            e.printStackTrace();
        }
    }
}

6. Hot Key / Hot Partition

What happened: A specific database shard CPU goes to 100% while other shards are at 5%.

Root cause: A celebrity tweets, or a viral product drops. The partition key hashes all that traffic to a single node.

How to prevent: Key salting (appending random numbers to keys to distribute them), or aggressively caching hot items locally in-memory.

7. Deployment Gone Wrong

What happened: Deployed v2.0 on Friday at 5 PM. It breaks. Rollback takes 2 hours.

Root cause: In-place upgrades, backwards-incompatible database migrations, no canary.

How to prevent: Blue-Green deployments or Canary releases.

8. DNS Failure

What happened: Your cloud provider's DNS goes down. Users see "Site not found" even though all your servers are perfectly fine.

Root cause: Single point of failure for domain name resolution.

How to prevent: Use multiple DNS providers and configure appropriate DNS TTLs.

9. Retry Storm

What happened: A database briefly stutters. Thousands of clients retry immediately. The sudden 10x traffic spike kills the recovered database instantly.

Root cause: Immediate, aggressive retries.

How to prevent: Exponential Backoff with Jitter.

Java 21 
import java.util.Random;

public class RetryStrategy {
    private static final Random random = new Random();

    public void executeWithBackoff() throws InterruptedException {
        int maxRetries = 3;
        int baseWaitMs = 1000;

        for (int attempt = 1; attempt <= maxRetries; attempt++) {
            try {
                // callExternalService();
                return; // Success!
            } catch (Exception e) {
                if (attempt == maxRetries) throw e;
                
                // Exponential backoff: 1s, 2s, 4s
                long waitTime = baseWaitMs * (1L << (attempt - 1));
                // Jitter: +/- 20% to prevent synchronized retries
                long jitter = (long) (waitTime * 0.2 * (random.nextDouble() * 2 - 1));
                
                Thread.sleep(waitTime + jitter);
            }
        }
    }
}

10. Data Inconsistency After Partial Failure

What happened: User's credit card was charged, but the "Order Created" step failed. User has no order but lost money.

Root cause: Two actions occurred across microservices without a distributed transaction protocol.

How to prevent: Saga Pattern, Outbox Pattern, or ensuring operations are Idempotent.

Incident Post-Mortem Template

When failures happen (and they will), don't assign blame. Write a blameless post-mortem:

  • Timeline: Exactly what happened and when.
  • Impact: How many users/transactions were affected.
  • Root Cause: The actual technical reason (ask "Why?" 5 times).
  • Action Items: Concrete steps to ensure it NEVER happens again.
