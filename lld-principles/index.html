LLD Principles — Beyond SOLID

💡 What to expect: Everyone knows SOLID, but true system design mastery requires understanding other core principles. This page covers the essential principles with analogies and Java 21 code.

1. DRY (Don't Repeat Yourself)

📖 DRY: Every piece of knowledge must have a single, unambiguous, authoritative representation within a system.

Analogy: If your company changes its logo, you don't want to update it on 50 different pages. You update it in one central logo file that everything else references.

❌ BAD: Repetitive Code

public void registerUser(String email, String phone) {
    if (email == null || !email.contains("@")) {
        throw new IllegalArgumentException("Invalid email");
    }
    // save user...
}

public void updateEmail(String email) {
    if (email == null || !email.contains("@")) {
        throw new IllegalArgumentException("Invalid email");
    }
    // update email...
}

✅ GOOD: Reusable Logic

public class Validator {
    public static void validateEmail(String email) {
        if (email == null || !email.contains("@")) {
            throw new IllegalArgumentException("Invalid email");
        }
    }
}

public void registerUser(String email, String phone) {
    Validator.validateEmail(email);
    // save user...
}

2. KISS (Keep It Simple, Stupid)

📖 KISS: Most systems work best if they are kept simple rather than made complicated. Simplicity should be a key goal.

Analogy: A Swiss Army Knife with 100 tools is useless if it's too heavy to carry. A simple pocket knife often does the job better.

❌ BAD: Over-engineered

// Over-engineered Calculator
public interface OperationStrategy {
    int execute(int a, int b);
}
public class AdditionStrategy implements OperationStrategy {
    public int execute(int a, int b) { return a + b; }
}
public class CalculatorContext {
    private OperationStrategy strategy;
    // ... setup and execute ...
}

✅ GOOD: Simple

// Just what we need
public class Calculator {
    public int add(int a, int b) {
        return a + b;
    }
}

3. YAGNI (You Aren't Gonna Need It)

📖 YAGNI: Always implement things when you actually need them, never when you just foresee that you need them.

Analogy: Buying snow chains for your car when you live in Miami, just in case you ever decide to drive to Alaska in winter. Don't waste money and space.

❌ BAD: Speculative Features

// Building a complex plugin architecture for a simple Todo app
public abstract class AbstractTodoPluginLoader {
    protected List<Plugin> plugins;
    public abstract void initializePlugins();
    public abstract void executePluginLifecycleHooks();
}

✅ GOOD: Immediate Needs

// Simple Todo App, extend later if requested
public class TodoService {
    public void addTodo(String task) {
        // just add it to DB
    }
}

4. Law of Demeter (Don't Talk to Strangers)

📖 Law of Demeter: A module should not know about the inner workings of the objects it manipulates. Only talk to your immediate friends.

Analogy: When you buy a coffee, you hand the barista your credit card. You don't hand them your wallet and tell them to open it and take out the card.

❌ BAD: Train Wreck

public void processDelivery(Order order) {
    // Talking to strangers
    String city = order.getCustomer().getAddress().getCity();
    System.out.println("Shipping to: " + city);
}

✅ GOOD: Delegation

public void processDelivery(Order order) {
    // Order delegates the request
    String city = order.getDeliveryCity();
    System.out.println("Shipping to: " + city);
}

// Inside Order class:
public String getDeliveryCity() {
    return this.customer.getDeliveryCity();
}

5. Composition over Inheritance

📖 Composition over Inheritance: Classes should achieve polymorphic behavior and code reuse by their composition (by containing instances of other classes that implement the desired functionality) rather than inheritance from a base or parent class.

Analogy: Instead of breeding a bird and a horse to get a flying horse (Inheritance), you attach jetpacks to a horse (Composition). Much more flexible!

❌ BAD: Deep Inheritance

class Animal {}
class FlyingAnimal extends Animal {}
class Bird extends FlyingAnimal {}

// Wait, Ostriches can't fly... we have a problem.
class Ostrich extends Bird {
    @Override 
    public void fly() { throw new UnsupportedOperationException(); }
}

✅ GOOD: Composition via Interfaces

// Java 21 interface with Strategy
interface FlyBehavior {
    void fly();
}
class FlyWithWings implements FlyBehavior {
    public void fly() { System.out.println("Flap flap"); }
}
class NoFly implements FlyBehavior {
    public void fly() { System.out.println("Can't fly"); }
}

class Bird {
    private final FlyBehavior flyBehavior;
    public Bird(FlyBehavior flyBehavior) {
        this.flyBehavior = flyBehavior;
    }
    public void performFly() {
        flyBehavior.fly();
    }
}

6. Tell, Don't Ask

📖 Tell, Don't Ask: You should tell objects what to do, rather than querying an object's state and making a decision on its behalf.

Analogy: Don't ask your dog if it's hungry, check its stomach fullness, and then manually place food in its mouth. Just tell the dog "Eat!" and provide food; the dog handles the rest.

❌ BAD: Asking for state

public void applyDiscount(Order order) {
    if (order.getTotalAmount() > 100 && !order.isDiscountApplied()) {
        order.setTotalAmount(order.getTotalAmount() * 0.9);
        order.setDiscountApplied(true);
    }
}

✅ GOOD: Telling to execute

public void applyDiscount(Order order) {
    // The Order class handles its own state and rules
    order.applyLoyaltyDiscount();
}

7. Principle of Least Surprise

📖 Principle of Least Surprise: The design of software should match the user's/developer's expectations. Functions should do exactly what their names imply.

If a method is named getUser(), it should return a user. It should NOT also delete the user or send an email.

8. Separation of Concerns

📖 Separation of Concerns: A program should be divided into distinct sections, such that each section addresses a separate concern.

Keep your UI logic separate from your business logic, which should be separate from your database logic.

9. Summary

PrincipleOne-line Description
DRYDon't copy-paste code; use single sources of truth.
KISSKeep solutions as simple as possible.
YAGNIDon't build features until you actually need them.
Law of DemeterDon't chain method calls deep into other objects.
Composition > InheritanceUse 'has-a' interfaces instead of deep 'is-a' class hierarchies.
Tell, Don't AskTell objects to do work, don't micromanage their internal state.
Least SurpriseCode should do exactly what its name suggests.
Separation of ConcernsKeep different responsibilities in different layers/classes.
🎯 Interview Tip: In LLD interviews, interviewers look for these principles just as much as design patterns. If you use Composition over Inheritance, explicitly tell the interviewer: "I'm using composition here because it gives us more flexibility at runtime." It shows seniority.
