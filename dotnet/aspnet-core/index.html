🌐 ASP.NET Core & Microservices Architecture in .NET 8

An architectural blueprint for tier-1 web APIs: Kestrel socket transport, the Russian-doll middleware pipeline, Minimal APIs vs MVC, .NET 8 built-in Rate Limiting algorithms, and server-side Output Caching.

1. The Kestrel Web Server Architecture

Kestrel is .NET's cross-platform, asynchronous HTTP server capable of serving over 7 million requests per second on modern hardware. It achieves this through three core systems:

flowchart TD Socket["OS Socket (Linux epoll / Windows IOCP)"] --> Pipelines["System.IO.Pipelines
(Zero-copy PipeReader / PipeWriter)"] Pipelines --> MemPool["MemoryPool<byte>.Shared
(Pooled byte slabs - 0 GC allocations!)"] MemPool --> HttpParser["Kestrel HTTP/1.1, HTTP/2 & HTTP/3 Parser"] HttpParser --> HttpContext["Constructs HttpContext"] HttpContext --> Middleware["Dispatches to Middleware Pipeline"]
  • System.IO.Pipelines: Replaces traditional byte buffer streams. Incoming network packets are written straight into pre-allocated memory slabs without copying bytes across user and kernel space.
  • Memory Pooling: Reuses 4KB/64KB memory slabs from MemoryPool<byte>.Shared, completely preventing high-frequency HTTP requests from generating Gen 0/LOH GC allocations.
  • Protocol Support: Native HTTP/1.1, HTTP/2 (binary framing & multiplexing), and HTTP/3 (QUIC over UDP for high-packet-loss mobile networks).

2. The Middleware Pipeline: The Russian Doll Pattern

📖 Middleware Mechanics

ASP.NET Core middleware is structured as a sequence of delegates (RequestDelegate = Func<HttpContext, Task>) wrapped around each other like Russian Matryoshka nesting dolls. Each middleware can execute code before and after the next component:

flowchart LR Req["Client Request"] --> M1["1. Exception Middleware"] M1 --> M2["2. CORS Middleware"] M2 --> M3["3. Authentication"] M3 --> M4["4. Authorization"] M4 --> M5["5. Rate Limiter"] M5 --> Endpoint["Endpoint Handler
(Minimal API / Controller)"] Endpoint -->|Response unwinds| M5 M5 --> M4 M4 --> M3 M3 --> M2 M2 --> M1 M1 --> Res["Client Response"]

Writing Custom Middleware (Performance Timing Example)

public sealed class RequestTimingMiddleware(RequestDelegate next, ILogger<RequestTimingMiddleware> logger)
{
    public async Task InvokeAsync(HttpContext context)
    {
        var stopwatch = ValueStopwatch.StartNew();

        try
        {
            // Pass execution down the pipeline
            await next(context);
        }
        finally
        {
            var elapsedMs = stopwatch.GetElapsedTime().TotalMilliseconds;
            if (elapsedMs > 500)
            {
                logger.LogWarning("Slow request detected: {Method} {Path} took {Elapsed:N2}ms",
                    context.Request.Method, context.Request.Path, elapsedMs);
            }
        }
    }
}

4. .NET 8 Built-in Rate Limiting Algorithms

ASP.NET Core contains native, production-grade rate limiting in System.Threading.RateLimiting, supporting four distinct algorithms without requiring third-party libraries:

Algorithm Mechanism Pros & Cons
Fixed Window Permits N requests per time window (e.g. 100 req / 1 min). Window resets. Simple; vulnerable to 2x burst traffic at the edge of window reset.
Sliding Window Divides window into segments; slides smoothly over time. Smoother rate curve; prevents burst spikes at boundaries.
Token Bucket Bucket holds max tokens; refills at constant rate. Requests consume tokens. Supports bursts of traffic while guaranteeing long-term steady rate.
Concurrency Limiter Restricts maximum concurrent in-flight requests (e.g. max 50). Protects backend CPU/database from saturation.

Configuring Sliding Window Partitioned by Client IP

using System.Threading.RateLimiting;

builder.Services.AddRateLimiter(options =>
{
    options.RejectionStatusCode = StatusCodes.Status429TooManyRequests;

    // Partition rate limits per client IP address
    options.AddPolicy("sliding-ip-limit", httpContext =>
    {
        var clientIp = httpContext.Connection.RemoteIpAddress?.ToString() ?? "anonymous";

        return RateLimitPartition.GetSlidingWindowLimiter(clientIp, _ => new SlidingWindowRateLimiterOptions
        {
            PermitLimit = 100,
            Window = TimeSpan.FromMinutes(1),
            SegmentsPerWindow = 6, // 10-second segments
            QueueLimit = 10,
            QueueProcessingOrder = QueueProcessingOrder.OldestFirst
        });
    });
});

app.UseRateLimiter();

5. Server-Side Output Caching (.NET 7/8)

Unlike ResponseCaching (which relies on HTTP client headers), Output Caching caches the full serialized HTTP response directly on the server (in memory or Redis) with cache tagging and granular eviction:

builder.Services.AddOutputCache(options =>
{
    options.AddPolicy("PortfolioCache", policy => policy
        .Expire(TimeSpan.FromMinutes(5))
        .SetVaryByQuery("portfolioId")
        .Tag("portfolios")); // Enables tag-based eviction!
});

app.UseOutputCache();

// Endpoint tagged with policy:
app.MapGet("/api/portfolios/{portfolioId}", async (Guid portfolioId, IPortfolioService svc) =>
{
    return Results.Ok(await svc.GetSummaryAsync(portfolioId));
})
.CacheOutput("PortfolioCache");

// Evict all tagged portfolio caches upon order execution:
app.MapPost("/api/orders/fill", async (IOutputCacheStore cacheStore) =>
{
    // Evicts all cache entries tagged with "portfolios" immediately!
    await cacheStore.EvictByTagAsync("portfolios", default);
    return Results.Ok();
});

6. The Senior Interviewer's Grill Round: ASP.NET Core

🔥 Question 1: What is the difference between app.Use(), app.Run(), and app.Map()?

Senior Answer:

  • app.Use(Func<HttpContext, Func<Task>, Task>): Chains a middleware component into the pipeline, giving it the ability to invoke the next middleware via next() or short-circuit.
  • app.Run(RequestDelegate): Adds a terminal middleware that does NOT call next(); execution immediately unwinds back up the pipeline.
  • app.Map(path, builder): Branches the pipeline based on the request URL path prefix, executing a distinct isolated branch of middleware for that route.

🔥 Question 2: Why should you never use HttpContext.Current in ASP.NET Core?

Senior Answer: HttpContext.Current was a static ThreadLocal property in legacy .NET Framework (ASP.NET MVC 5) that bound the context to a specific OS thread. In ASP.NET Core, asynchronous execution hops across different ThreadPool threads during I/O awaits. Static thread-local storage fails because continuations execute on different threads. In modern .NET, HttpContext must be injected via IHttpContextAccessor (which uses AsyncLocal<T> to flow execution context across threads) or passed directly as method arguments.

🔥 Question 3: How does Kestrel protect against Slowloris DDoS attacks?

Senior Answer: Kestrel enforces MinRequestBodyDataRate and MinResponseDataRate (defaulting to 240 bytes/second with a 5-second grace period). In a Slowloris attack, malicious clients send HTTP headers or bodies byte-by-byte at very slow intervals to keep server sockets open. Kestrel's internal timers detect when data throughput drops below the minimum rate threshold and forcefully terminates the connection, preventing socket exhaustion.
