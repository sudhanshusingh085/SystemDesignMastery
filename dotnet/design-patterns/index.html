2. The Singleton Masterclass: Thread-Safety & The Testability Trap

📖 Pattern Intent

Ensure a class has only one instance throughout the entire application lifecycle and provide a global point of access to it.

Evolution of Thread-Safe Singleton in C#

Implementing a Singleton in a multithreaded environment like ASP.NET Core requires careful synchronization to prevent race conditions where two threads initialize separate instances concurrently.

Approach A: Double-Checked Locking (Historical & Memory Barriers)

Prior to C# 6, double-checked locking was the canonical interview implementation. Notice the critical volatile keyword: it prevents the CLR JIT compiler and CPU from reordering memory writes (preventing another thread from observing a non-null instance whose constructor has not finished executing).

public sealed class DoubleCheckedSingleton
{
    private static volatile DoubleCheckedSingleton? _instance;
    private static readonly object _padlock = new();

    private DoubleCheckedSingleton()
    {
        // Expensive initialization (e.g., loading config or hardware handles)
    }

    public static DoubleCheckedSingleton Instance
    {
        get
        {
            if (_instance is null) // 1st check (lock-free read)
            {
                lock (_padlock)
                {
                    if (_instance is null) // 2nd check (synchronized)
                    {
                        _instance = new DoubleCheckedSingleton();
                    }
                }
            }
            return _instance;
        }
    }
}

Approach B: Thread-Safe Static Constructor (`beforefieldinit` Guarantee)

In C#, the CLR guarantees that static constructors are executed exactly once per AppDomain in a thread-safe manner before any instance of the class is created or any static member is referenced.

public sealed class StaticSingleton
{
    // The CLR initializes this when the class is first accessed.
    private static readonly StaticSingleton _instance = new();

    // Explicit static constructor tells C# compiler NOT to mark type with 'beforefieldinit',
    // guaranteeing precise lazy initialization upon first static member access.
    static StaticSingleton() { }

    private StaticSingleton() { }

    public static StaticSingleton Instance => _instance;
}

Approach C: Modern Idiomatic C# using `Lazy<T>` (Recommended GoF Approach)

Since .NET 4.0, System.Lazy<T> provides fully thread-safe, lazy initialization using LazyThreadSafetyMode.ExecutionAndPublication by default:

public sealed class ModernLazySingleton
{
    private static readonly Lazy<ModernLazySingleton> _lazyInstance =
        new(() => new ModernLazySingleton(), LazyThreadSafetyMode.ExecutionAndPublication);

    private ModernLazySingleton()
    {
        // Socket connection pool initialization
    }

    public static ModernLazySingleton Instance => _lazyInstance.Value;
}

⚠️ The Interviewer's Trap: Why Classic Singleton is an Anti-Pattern

🚨 Senior Architect Critique

In modern enterprise development, the classic GoF static Singleton (MySingleton.Instance) is widely considered an anti-pattern for three critical reasons:

  1. Hides Dependencies: Classes calling MySingleton.Instance.DoWork() do not declare their dependency in the constructor. Looking at the public API of a service gives no hint that it relies on a global state.
  2. Destroys Testability: Unit tests run in parallel by test runners (xUnit, NUnit). A static singleton introduces global shared mutable state. Test A mutates the singleton, causing Test B to intermittently fail (flaky tests). Furthermore, you cannot inject a mock instance into MySingleton.Instance.
  3. Violates Inversion of Control & SRP: The class controls its own lifecycle instead of delegating lifecycle management to the container.

The Modern Solution: DI-Managed Singleton

Instead of hardcoding a private constructor and a static Instance property, design the class as a normal POCO adhering to an interface, and let the ASP.NET Core IoC container enforce the single-instance lifetime:

// 1. Normal clean interface and implementation
public interface IMarketDataFeed
{
    decimal GetLatestPrice(string symbol);
}

public class FastMarketDataFeed : IMarketDataFeed
{
    public decimal GetLatestPrice(string symbol) => 182.45m;
}

// 2. Registration in Program.cs (IoC container guarantees 1 instance per AppDomain)
builder.Services.AddSingleton<IMarketDataFeed, FastMarketDataFeed>();

// 3. Consumer receives it via constructor injection (100% testable with Moq/NSubstitute!)
public class TradingEngine(IMarketDataFeed feed)
{
    public void Execute(string symbol)
    {
        var price = feed.GetLatestPrice(symbol);
        // Execute trade...
    }
}

3. Factory Patterns in Modern C#

The Factory family decouples object creation logic from client consumption. In enterprise C#, there are three distinct variations:

flowchart LR Client["Client Request"] --> SF["Simple Factory / Switch"] SF -->|Creates| ConcreteA["FixOrderGateway"] SF -->|Creates| ConcreteB["BinaryOrderGateway"] SF -->|Creates| ConcreteC["RestOrderGateway"]

A. Factory Method vs Abstract Factory

  • Factory Method: Defines an interface for creating an object, but lets subclasses decide which class to instantiate. Delegates creation to child classes.
  • Abstract Factory: Provides an interface for creating families of related or dependent objects without specifying their concrete classes (e.g., Windows UI vs Mac UI, or FIX Protocol family vs ITCH Protocol family).

B. Modern C# 12 Factory using Keyed Services & Pattern Matching

With .NET 8 Keyed Services, we can implement high-performance, container-native factories without reflection or bloated switch blocks:

public enum ExecutionVenue { NYSE, NASDAQ, CME, BINANCE }

public interface IOrderGateway
{
    Task<string> SubmitOrderAsync(string symbol, int qty, decimal price);
}

public class NyseOrderGateway : IOrderGateway
{
    public Task<string> SubmitOrderAsync(string symbol, int qty, decimal price) =>
        Task.FromResult($"[NYSE] Routed {qty} {symbol} @ {price}");
}

public class NasdaqOrderGateway : IOrderGateway
{
    public Task<string> SubmitOrderAsync(string symbol, int qty, decimal price) =>
        Task.FromResult($"[NASDAQ] Routed {qty} {symbol} @ {price}");
}

// Registration in Program.cs using .NET 8 Keyed Services:
builder.Services.AddKeyedScoped<IOrderGateway, NyseOrderGateway>(ExecutionVenue.NYSE);
builder.Services.AddKeyedScoped<IOrderGateway, NasdaqOrderGateway>(ExecutionVenue.NASDAQ);

// Modern Factory using IServiceProvider Keyed Resolution:
public interface IOrderGatewayFactory
{
    IOrderGateway GetGateway(ExecutionVenue venue);
}

public class OrderGatewayFactory(IServiceProvider serviceProvider) : IOrderGatewayFactory
{
    public IOrderGateway GetGateway(ExecutionVenue venue)
    {
        return serviceProvider.GetKeyedService<IOrderGateway>(venue)
            ?? throw new NotSupportedException($"No gateway registered for venue: {venue}");
    }
}

4. Strategy vs Factory: The Interview Dilemma

🎯 The Classic Interview Question

"What is the exact architectural difference between Strategy and Factory? Can they be used together?"

Feature Factory Pattern Strategy Pattern
Pattern Category Creational (concerned with object creation) Behavioral (concerned with execution & algorithms)
Primary Intent Decouple client code from concrete classes being instantiated. Encapsulate interchangeable algorithms so they can vary independently of clients.
What it Returns Returns a new or cached object instance to the caller. Executes an action or computes a result given dynamic context.
Runtime Mutability Factory is called to obtain an object; object type is fixed once created. Strategy can be swapped on the fly inside the context object during execution.
Client Knowledge Client asks for an object by type/key (e.g. "PDF", "CSV"). Client provides or switches the strategy that alters how an operation proceeds.

Synergy: Factory Creating the Strategy

In production trading engines, Factory and Strategy are almost always paired: A Factory creates or selects the appropriate Strategy at runtime based on market volatility or asset class!

// 1. The Strategy Interface (Behavioral)
public interface IExecutionStrategy
{
    OrderRoute CalculateRoute(Order order, MarketConditions conditions);
}

public class TWAPStrategy : IExecutionStrategy // Time-Weighted Average Price
{
    public OrderRoute CalculateRoute(Order order, MarketConditions conditions)
    {
        // Slice order evenly over time intervals to minimize market impact
        return new OrderRoute("Slice into 10 intervals of 1 minute each");
    }
}

public class VWAPStrategy : IExecutionStrategy // Volume-Weighted Average Price
{
    public OrderRoute CalculateRoute(Order order, MarketConditions conditions)
    {
        // Weight slices according to historical intra-day volume curves
        return new OrderRoute("Weight slices by historical 15-minute volume distribution");
    }
}

public class DarkPoolSniperStrategy : IExecutionStrategy
{
    public OrderRoute CalculateRoute(Order order, MarketConditions conditions)
    {
        // Route hidden orders directly to alternative liquidity pools
        return new OrderRoute("Route non-displayed liquidity to Citadel / Virtu dark pools");
    }
}

// 2. The Strategy Factory (Creational)
public class ExecutionStrategyFactory(IEnumerable<IExecutionStrategy> strategies)
{
    public IExecutionStrategy ResolveStrategy(MarketConditions conditions, Order order) =>
        (conditions.Volatility, order.NotionalValue) switch
        {
            (Volatility.Extreme, > 5_000_000m) => strategies.OfType<DarkPoolSniperStrategy>().First(),
            (Volatility.High, _)               => strategies.OfType<VWAPStrategy>().First(),
            _                                  => strategies.OfType<TWAPStrategy>().First()
        };
}

// 3. The Context using the Strategy
public class TradingExecutionEngine(ExecutionStrategyFactory factory)
{
    public void Execute(Order order, MarketConditions conditions)
    {
        // Factory decides the strategy based on real-time market telemetry
        IExecutionStrategy strategy = factory.ResolveStrategy(conditions, order);
        
        // Execute the chosen behavioral strategy
        OrderRoute route = strategy.CalculateRoute(order, conditions);
        Console.WriteLine($"Executing order via: {route.Description}");
    }
}

5. Structural Patterns: Decorator & Adapter in Production

A. Decorator Pattern with Dependency Injection

The Decorator pattern attaches additional responsibilities to an object dynamically without modifying its source code. In enterprise .NET, decorators are heavily used for cross-cutting concerns like Redis caching, OpenTelemetry tracing, and Polly retry resilience.

flowchart LR Caller["Client Request"] --> DecCache["CachedOrderRepository (Decorator)"] DecCache -->|Cache Miss| DecAudit["AuditingOrderRepository (Decorator)"] DecAudit --> Target["SqlOrderRepository (Concrete Target)"] 
public interface IOrderRepository
{
    Task<Order?> GetByIdAsync(long orderId);
}

// 1. Concrete Core Component
public class SqlOrderRepository(TradingDbContext db) : IOrderRepository
{
    public async Task<Order?> GetByIdAsync(long orderId) =>
        await db.Orders.FindAsync(orderId);
}

// 2. Decorator adding Distributed Redis Caching
public class CachingOrderRepository(
    IOrderRepository inner, 
    IDistributedCache cache, 
    ILogger<CachingOrderRepository> logger) : IOrderRepository
{
    public async Task<Order?> GetByIdAsync(long orderId)
    {
        string cacheKey = $"order:{orderId}";
        var cachedBytes = await cache.GetAsync(cacheKey);

        if (cachedBytes is not null)
        {
            logger.LogInformation("Cache hit for order {OrderId}", orderId);
            return JsonSerializer.Deserialize<Order>(cachedBytes);
        }

        logger.LogWarning("Cache miss for order {OrderId}. Fetching from database...", orderId);
        var order = await inner.GetByIdAsync(orderId);

        if (order is not null)
        {
            var serialized = JsonSerializer.SerializeToUtf8Bytes(order);
            await cache.SetAsync(cacheKey, serialized, new DistributedCacheEntryOptions
            {
                AbsoluteExpirationRelativeToNow = TimeSpan.FromMinutes(10)
            });
        }

        return order;
    }
}

Using the popular Scrutor NuGet package, this decorator can be registered in one clean line in Program.cs:

builder.Services.AddScoped<IOrderRepository, SqlOrderRepository>();
builder.Services.Decorate<IOrderRepository, CachingOrderRepository>();

6. Enterprise Patterns: Repository & Unit of Work with EF Core 8

🎯 The Burning Architectural Debate

"Is the Repository and Unit of Work pattern redundant when using Entity Framework Core?"

Many developers argue that EF Core's DbContext is already a Unit of Work, and DbSet<T> is already a Repository. Wrapping them in generic abstractions like IRepository<T> often leads to an anemic abstraction that leaks IQueryable or hides powerful EF Core capabilities like AsSplitQuery() and batch operations.

When is Repository Pattern Justified in Modern .NET?

  1. Domain-Driven Design (DDD): Repositories are defined on Aggregate Roots only, not every database table. They enforce transactional invariants and boundary encapsulation.
  2. Decoupling from Persistence Details: Isolates complex multi-tenant query filters, soft-delete filters, or specialized SQL stored procedures from business logic.
  3. In-Memory Mocking for Unit Tests: Allows mocking data operations without launching a test container or in-memory SQLite database.

Production Unit of Work & Aggregate Repository Implementation:

// 1. Aggregate Root Interface
public interface IOrderRepository
{
    Task<Order?> GetByIdWithLinesAsync(Guid orderId, CancellationToken ct = default);
    Task AddAsync(Order order, CancellationToken ct = default);
}

// 2. Unit of Work Interface
public interface IUnitOfWork : IDisposable
{
    IOrderRepository Orders { get; }
    Task<int> CommitAsync(CancellationToken ct = default);
}

// 3. Concrete EF Core Implementation
public class EfOrderRepository(TradingDbContext db) : IOrderRepository
{
    public async Task<Order?> GetByIdWithLinesAsync(Guid orderId, CancellationToken ct = default)
    {
        return await db.Orders
            .Include(o => o.Lines) // Eager load aggregate items
            .AsSplitQuery()        // Avoid Cartesian explosion
            .FirstOrDefaultAsync(o => o.Id == orderId, ct);
    }

    public async Task AddAsync(Order order, CancellationToken ct = default)
    {
        await db.Orders.AddAsync(order, ct);
    }
}

public class EfUnitOfWork(TradingDbContext db) : IUnitOfWork
{
    private IOrderRepository? _orders;

    public IOrderRepository Orders => _orders ??= new EfOrderRepository(db);

    public async Task<int> CommitAsync(CancellationToken ct = default)
    {
        // Executes within EF Core's implicit database transaction
        return await db.SaveChangesAsync(ct);
    }

    public void Dispose()
    {
        db.Dispose();
        GC.SuppressFinalize(this);
    }
}

7. The Senior Interviewer's Grill Round: Design Patterns in C#

🔥 Question 1: How does volatile prevent instruction reordering in Double-Checked Locking?

Senior Answer: When new DoubleCheckedSingleton() is executed, the runtime performs three operations: (1) allocates uninitialized memory on the heap, (2) invokes the constructor to initialize fields, (3) assigns the memory address to the reference variable _instance. Without the volatile keyword, the CLR JIT compiler or CPU out-of-order execution engine may reorder step 3 before step 2! If another thread executes the 1st lock-free check if (_instance is null) precisely at that microsecond, it observes a non-null reference, returns it, and dereferences fields that have NOT yet been initialized by the constructor, leading to hard-to-reproduce memory corruption bugs. volatile introduces a memory fence/barrier guaranteeing write-release semantics.

🔥 Question 2: Why should you avoid exposing IQueryable<T> from a Repository?

Senior Answer: Exposing IQueryable<T> from a repository completely destroys the purpose of the Repository pattern. It leaks persistence concerns (LINQ-to-Entities expressions) directly into the business/service layer. If a service calls repo.GetAll().Where(...).ToList(), business logic now dictates SQL generation. Furthermore, unit testing becomes extremely difficult because mocking IQueryable expression trees requires complex in-memory query providers. A clean repository should return concrete collections (Task<IReadOnlyList<T>>) or domain aggregates.

🔥 Question 3: What is the difference between Strategy pattern and State pattern?

Senior Answer: Structurally, both patterns share an identical UML class diagram (Context delegating to an interface with multiple concrete subclasses). However, their architectural intent and lifecycle differ completely:

  • In the Strategy Pattern, the client typically configures the context with a specific algorithm (e.g. TWAP vs VWAP). Strategies are usually unaware of each other, stateless, and do not trigger transitions between one another.
  • In the State Pattern, the context's internal behavior changes dynamically as its state changes (e.g. Order in Pending → Approved → Filled → Settled). Concrete states hold references to the context and trigger transitions to other states based on actions or events.
