1. The Architectural Philosophy: CQS vs CQRS

In traditional enterprise CRUD architectures, a single domain model and database schema are forced to satisfy two radically conflicting requirements:

  1. Transactional Writes (Commands): Require deep validation, strict boundary invariants, normalized schemas (3NF) to eliminate data redundancy, locking, and concurrency protection.
  2. High-Speed Reads (Queries): Require denormalized flat data, multi-table joins, aggregations, caching, and zero locking or change-tracking overhead.

Forcing both requirements through the same ORM entities (like standard EF Core tracking models) causes slow query performance, over-fetching, complex entity graphs, and database lock contention.

📖 CQS vs CQRS
  • Command-Query Separation (CQS): Formulated by Bertrand Meyer. A principle at the method/class level stating that every method should either mutate state (Command) or return data (Query), but never both.
  • Command Query Responsibility Segregation (CQRS): Formulated by Greg Young. An architectural pattern at the application level that splits the entire read and write paths into distinct data models, services, and optionally distinct physical databases.

2. Pragmatic CQRS: EF Core Commands + Dapper Queries

A widespread misconception is that CQRS requires Event Sourcing and multiple physical databases. In 90% of enterprise systems, Pragmatic CQRS using a single database (or primary write + read replicas) yields immense performance and architectural cleanliness:

  • Commands execute through Entity Framework Core: Benefiting from entity encapsulation, business invariants, optimistic concurrency (RowVersion), and transactional unit of work.
  • Queries bypass EF Core completely and execute through Dapper: Directly executing optimized SQL queries, utilizing SQL Server columnstore indexes or indexed views, deserializing straight into C# record DTOs without EF Core change-tracker overhead.

A. MediatR Pipeline Behavior (Cross-Cutting Validation)

Using MediatR pipeline behaviors, cross-cutting concerns like validation with FluentValidation, structured logging, and performance metrics are applied automatically without polluting handlers:

public sealed class ValidationBehavior<TRequest, TResponse>(
    IEnumerable<IValidator<TRequest>> validators)
    : IPipelineBehavior<TRequest, TResponse>
    where TRequest : notnull
{
    public async Task<TResponse> Handle(
        TRequest request, 
        RequestHandlerDelegate<TResponse> next, 
        CancellationToken cancellationToken)
    {
        if (!validators.Any())
            return await next();

        var context = new ValidationContext<TRequest>(request);
        var validationResults = await Task.WhenAll(
            validators.Select(v => v.ValidateAsync(context, cancellationToken)));

        var failures = validationResults
            .SelectMany(r => r.Errors)
            .Where(f => f is not null)
            .ToList();

        if (failures.Count != 0)
            throw new ValidationException(failures);

        return await next();
    }
}

    : IRequestHandler<CreateOrderCommand, Guid>

    {

        return order.Id;
    }

3. Event Sourcing: State as a Stream of Events

📖 Core Principle

Instead of persisting only the current state of an entity, Event Sourcing persists every state-changing event as an immutable, append-only log. The current state is calculated by replaying all past events.

Implementing an Event-Sourced Aggregate in C# 12

// Base Domain Event
public abstract record DomainEvent(DateTime TimestampUtc);

public sealed record OrderPlacedEvent(Guid OrderId, string Symbol, int Qty, decimal Price) 
    : DomainEvent(DateTime.UtcNow);

public sealed record OrderFilledEvent(Guid OrderId, int FilledQty, decimal ExecutionPrice) 
    : DomainEvent(DateTime.UtcNow);

// Event-Sourced Aggregate Root
public sealed class OrderAggregate
{
    public Guid Id { get; private set; }
    public string Symbol { get; private set; } = string.Empty;
    public int RemainingQty { get; private set; }
    public int FilledQty { get; private set; }
    public decimal AveragePrice { get; private set; }
    public int Version { get; private set; }

    private readonly List<DomainEvent> _uncommittedEvents = [];
    public IReadOnlyList<DomainEvent> UncommittedEvents => _uncommittedEvents.AsReadOnly();

    public OrderAggregate() { } // Required for replay

    // Factory method creating the aggregate
    public static OrderAggregate PlaceOrder(Guid id, string symbol, int qty, decimal price)
    {
        var aggregate = new OrderAggregate();
        aggregate.RaiseEvent(new OrderPlacedEvent(id, symbol, qty, price));
        return aggregate;
    }

    public void Fill(int filledQty, decimal price)
    {
        if (filledQty <= 0 || filledQty > RemainingQty)
            throw new InvalidOperationException("Invalid fill quantity.");

        RaiseEvent(new OrderFilledEvent(Id, filledQty, price));
    }

    private void RaiseEvent(DomainEvent @event)
    {
        ApplyEvent(@event);
        _uncommittedEvents.Add(@event);
    }

    // Mutates state by applying event
    public void ApplyEvent(DomainEvent @event)
    {
        switch (@event)
        {
            case OrderPlacedEvent e:
                Id = e.OrderId;
                Symbol = e.Symbol;
                RemainingQty = e.Qty;
                FilledQty = 0;
                break;

            case OrderFilledEvent e:
                decimal totalSpent = (FilledQty * AveragePrice) + (e.FilledQty * e.ExecutionPrice);
                FilledQty += e.FilledQty;
                RemainingQty -= e.FilledQty;
                AveragePrice = totalSpent / FilledQty;
                break;
        }
        Version++;
    }

    public void ClearUncommittedEvents() => _uncommittedEvents.Clear();
}

4. The Dual-Write Problem & The Transactional Outbox Pattern

🚨 The Dual-Write Trap

In microservices, you frequently need to save data to a relational database AND publish an event to Kafka or RabbitMQ. What happens when:

  1. You commit to SQL DB, but the network fails before Kafka receives the event? Data is saved, but downstream microservices are never notified.
  2. You publish to Kafka first, but the SQL commit fails due to a unique constraint violation? Events were sent for orders that do not exist!

The Transactional Outbox Pattern solves this by writing the outgoing event into an OutboxMessages table within the exact same local SQL transaction as the business entities:

Production Outbox Processor in .NET 8 (`BackgroundService`)

public sealed class OutboxMessage
{
    public Guid Id { get; set; } = Guid.NewGuid();
    public string EventType { get; set; } = string.Empty;
    public string Payload { get; set; } = string.Empty;
    public DateTime CreatedAtUtc { get; set; } = DateTime.UtcNow;
    public DateTime? ProcessedAtUtc { get; set; }
    public string? Error { get; set; }
}

public sealed class OutboxPublisherBackgroundService(
    IServiceScopeFactory scopeFactory, 
    ILogger<OutboxPublisherBackgroundService> logger) 
    : BackgroundService
{
    protected override async Task ExecuteAsync(CancellationToken stoppingToken)
    {
        while (!stoppingToken.IsCancellationRequested)
        {
            try
            {
                using var scope = scopeFactory.CreateScope();
                var db = scope.ServiceProvider.GetRequiredService<TradingDbContext>();
                var bus = scope.ServiceProvider.GetRequiredService<IMessageBus>();

                // Lock top 50 unhandled messages
                var messages = await db.OutboxMessages
                    .Where(m => m.ProcessedAtUtc == null)
                    .OrderBy(m => m.CreatedAtUtc)
                    .Take(50)
                    .ToListAsync(stoppingToken);

                foreach (var message in messages)
                {
                    try
                    {
                        await bus.PublishAsync(message.EventType, message.Payload, stoppingToken);
                        message.ProcessedAtUtc = DateTime.UtcNow;
                    }
                    catch (Exception ex)
                    {
                        message.Error = ex.Message;
                        logger.LogError(ex, "Failed to publish Outbox message {Id}", message.Id);
                    }
                }

                await db.SaveChangesAsync(stoppingToken);
            }
            catch (Exception ex)
            {
                logger.LogError(ex, "Error processing outbox batch.");
            }

            await Task.Delay(TimeSpan.FromSeconds(2), stoppingToken);
        }
    }
}

5. The Senior Interviewer's Grill Round: CQRS & Event Sourcing

🔥 Question 1: How do you solve the 'Read-Your-Own-Writes' latency problem in CQRS?

Senior Answer: When read models are updated asynchronously (Eventual Consistency), a user submitting an order might be immediately redirected to the Order Details page before the read projection has processed the event, resulting in a 404 or outdated data. Solutions include:

  • Optimistic UI: The frontend client immediately merges the submitted command payload into its local state before the read projection catches up.
  • Version-based Synchronization: The command returns the new Aggregate Version (or Sequence Number). When querying the read stack, the client passes ?minVersion=5. The read service polls or awaits until the read replica reaches version >= 5.
  • Command Returns DTO: Pragmatically return the created DTO directly from the command execution response for immediate UI rendering, bypassing the read model for the immediate response.

🔥 Question 2: How do you handle schema changes and event evolution in Event Sourcing?

Senior Answer: Because past events are immutable and cannot be altered, schema changes must be handled through Upcasting:

  1. Upcasters: Middleware sits between the Event Store and the Aggregate replay engine. When an old OrderPlacedEvent_v1 is deserialized, the Upcaster dynamically transforms it into OrderPlacedEvent_v2 by filling default values before handing it to the aggregate.
  2. Weak Schema Compatibility: Event payloads should use optional fields and default values, tolerating missing fields upon JSON deserialization.

🔥 Question 3: How does Event Sourcing comply with GDPR 'Right to be Forgotten'?

Senior Answer: Deleting events from an append-only event store violates immutability and corrupts cryptographic hash chains. The industry standard solution is Crypto-Shredding: Personal Identifiable Information (PII) inside event payloads is encrypted using a unique encryption key per user. When a user exercises their Right to be Forgotten, the user's encryption key is destroyed from the Key Management Service (KMS). The historical events remain structurally intact for financial audits, but the PII becomes cryptographically unrecoverable ciphertext.
