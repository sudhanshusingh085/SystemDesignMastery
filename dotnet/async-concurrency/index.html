2. Synchronization: `lock` vs `SemaphoreSlim` vs `ReaderWriterLockSlim`

Primitive Async Compatible? Kernel Transition? Ideal Scenario
lock(obj) ❌ No (Cannot await inside lock) Hybrid (User-mode spin, then kernel monitor) Ultra-fast, microsecond in-memory CPU mutations.
SemaphoreSlim ✅ Yes (await WaitAsync()) Lightweight hybrid (no heavy OS handle unless contested) Throttling async network requests, async critical sections.
ReaderWriterLockSlim ❌ No (Thread-affine) Hybrid Read-heavy caches (99% reads, 1% writes).
System.Threading.Lock (.NET 9 / C# 13) ❌ No Optimized fast-path lock object Replacement for standard object locks with better diagnostics.

Why Can You NOT Await Inside a `lock` Statement?

A C# lock is bound to Thread Affinity (Monitor.Enter stores the managed OS Thread ID of the calling thread). When an await expression suspends execution, the current thread is released back to the ThreadPool. When the asynchronous operation finishes, a completely different thread may resume execution! If that different thread attempted to exit the monitor (Monitor.Exit), the CLR would throw a SynchronizationLockException because the unlocking thread is not the thread that acquired the lock.

3. Lock-Free Concurrency & CAS (Compare-And-Swap) Loops

Locks block threads, causing CPU context switches (costing ~2,000 to 5,000 clock cycles per switch). In high-frequency trading and low-latency microservices, Lock-Free Programming uses hardware-level atomic CPU instructions (e.g. LOCK CMPXCHG on x86-64) via Interlocked:

flowchart TD Read["1. Read current balance into local variable (snapshot)"] --> Compute["2. Compute new proposed balance (balance - withdrawal)"] Compute --> CAS{"3. Interlocked.CompareExchange
(Is balance still equal to snapshot?)"} CAS -->|Yes (Match)| Success["Atomically update to new balance! 🚀"] CAS -->|No (Contention)| Read

High-Performance Lock-Free Bank Account Balance CAS Loop

public sealed class LockFreeAccount
{
    // Stored as long (cents) to allow 64-bit atomic Interlocked operations
    private long _balanceInCents;

    public LockFreeAccount(decimal initialBalance)
    {
        _balanceInCents = (long)(initialBalance * 100m);
    }

    public decimal Balance => Interlocked.Read(ref _balanceInCents) / 100m;

    public bool TryWithdraw(decimal amount)
    {
        long amountCents = (long)(amount * 100m);
        SpinWait spinner = new();

        while (true)
        {
            // 1. Snapshot current value
            long currentBalance = Interlocked.Read(ref _balanceInCents);

            if (currentBalance < amountCents)
                return false; // Insufficient funds

            long newBalance = currentBalance - amountCents;

            // 2. Atomic Compare-And-Swap:
            // Only writes 'newBalance' if _balanceInCents is STILL equal to 'currentBalance'
            if (Interlocked.CompareExchange(ref _balanceInCents, newBalance, currentBalance) == currentBalance)
            {
                return true; // Withdrawal succeeded without taking any locks!
            }

            // 3. Contention detected: another thread modified balance; spin and retry
            spinner.SpinOnce();
        }
    }
}

4. High-Performance Producer-Consumer with `System.Threading.Channels`

📖 Why Channels Beat BlockingCollection

System.Threading.Channels is a zero-allocation, fully asynchronous producer-consumer library. Unlike BlockingCollection<T> (which blocks threads synchronously), Channels allow publishers and consumers to yield execution asynchronously (WriteAsync / WaitToReadAsync) while enforcing strict bounded backpressure limits.

using System.Threading.Channels;

public sealed class MarketDataPipeline
{
    // Bounded channel: Holds maximum 10,000 ticks in RAM.
    // If full, producers asynchronously await rather than exhausting server RAM!
    private readonly Channel<MarketTick> _channel = Channel.CreateBounded<MarketTick>(
        new BoundedChannelOptions(10_000)
        {
            FullMode = BoundedChannelFullMode.Wait,
            SingleReader = true, // Enables single-consumer CPU optimizations
            SingleWriter = false
        });

    public async ValueTask PublishTickAsync(MarketTick tick, CancellationToken ct = default)
    {
        await _channel.Writer.WriteAsync(tick, ct);
    }

    public async Task StartConsumerLoopAsync(CancellationToken ct = default)
    {
        // Asynchronously streams items as they arrive:
        await foreach (MarketTick tick in _channel.Reader.ReadAllAsync(ct))
        {
            ProcessTick(tick);
        }
    }

    private void ProcessTick(MarketTick tick)
    {
        // Process tick without blocking producer threads
    }
}

5. The Senior Interviewer's Grill Round: Async & Concurrency

🔥 Question 1: What is ThreadPool Starvation? How does it happen in modern ASP.NET Core?

Senior Answer: ThreadPool Starvation occurs when application threads block synchronously on asynchronous tasks (sync-over-async via Task.Wait() or .Result). When 500 incoming web requests block 500 ThreadPool worker threads waiting for database calls, the ThreadPool runs out of available threads to complete the continuations! The ThreadPool thread injection heuristic only creates 1 or 2 new threads per second, resulting in skyrocketing latency, HTTP request timeouts (504 Gateway Timeout), and service collapse.

🔥 Question 2: Why should you avoid Task.Run in ASP.NET Core server endpoints?

Senior Answer: In ASP.NET Core, incoming HTTP requests are already executing on a ThreadPool worker thread. Calling await Task.Run(...) takes the current thread, queues the work to another ThreadPool thread, and makes the original thread wait or yield. This incurs an unnecessary thread hop, CPU cache invalidation, and queue scheduling overhead without adding any concurrency throughput. Task.Run is designed for GUI desktop apps to offload CPU work from the UI thread, not for server request pipelines.

🔥 Question 3: How does C# handle Task cancellation with CancellationToken?

Senior Answer: Cancellation in .NET is cooperative. When a cancellation is requested via CancellationTokenSource.Cancel(), it sets an internal boolean flag. Asynchronous operations periodically inspect the token via ct.ThrowIfCancellationRequested() or register callbacks with the OS socket/kernel driver. When triggered, it throws an OperationCanceledException (or TaskCanceledException), which transitions the Task to the TaskStatus.Canceled state.
