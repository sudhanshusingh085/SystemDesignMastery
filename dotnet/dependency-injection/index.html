💉 Dependency Injection & Service Lifecycles in .NET 8

A masterclass on the Microsoft.Extensions.DependencyInjection container, Transient vs Scoped vs Singleton lifecycles, the catastrophic Captive Dependency bug, IServiceScopeFactory patterns, and modern .NET 8 Keyed Services.

1. The Core Philosophy: IoC, DIP & DI

Modern enterprise applications cannot afford hardcoded class instantiations (new OrderService()). Tightly coupled dependencies destroy unit testability, prevent dynamic feature toggles, and make architectural evolution impossible.

📖 Architectural Distinctions
  • Inversion of Control (IoC): A broad design principle where control of object creation and application flow is inverted from the component itself to an external framework or container.
  • Dependency Inversion Principle (DIP): The SOLID design principle stating high-level policy modules should not depend on low-level implementation details; both must depend upon abstractions.
  • Dependency Injection (DI): A concrete software pattern implementing IoC by providing dependent objects (dependencies) to a class rather than allowing the class to create them directly.

2. The Three Service Lifetimes in ASP.NET Core

Every service registered with IServiceCollection must be assigned an explicit lifetime that dictates how the container creates, caches, and disposes of instances:

Lifetime Registration Method Instance Creation Disposal Timing Ideal Use Cases
Transient AddTransient<T, U>() Every single time the service is requested from the container. At the end of the HTTP/Scope boundary if IDisposable. Lightweight, stateless utility services, validators, calculators.
Scoped AddScoped<T, U>() Once per HTTP Request (or once per active IServiceScope). When the HTTP request finishes or scope is disposed. EF Core DbContext, Unit of Work, Current User session state.
Singleton AddSingleton<T, U>() Once per application lifetime (on first request or boot). When the entire application shuts down (Host termination). In-memory caches, TCP socket pools, Kafka producers, telemetry metrics.

3. The Captive Dependency Bug (The Silent Production Killer)

🚨 Definition of Captive Dependency

A Captive Dependency occurs when a service with a longer lifetime takes a dependency on a service with a shorter lifetime. Specifically, when a Singleton service injects a Scoped service into its constructor.

Why This Causes Devastating Production Outages

Because the Singleton is instantiated only once and held alive for the lifetime of the application, any service injected into its constructor is also captured and kept alive forever. Consider what happens when a Singleton service injects EF Core's DbContext (which is Scoped):

  1. Multithreaded Concurrency Crashes: EF Core's DbContext is explicitly not thread-safe. If two simultaneous HTTP requests hit the Singleton service, both threads execute queries on the exact same DbContext instance concurrently. This results in the infamous runtime crash: 
    System.InvalidOperationException: A second operation was started on this context 
instance before a previous operation completed. This is usually caused by different 
threads concurrently using the same instance of DbContext.
  2. Catastrophic Memory Leaks: EF Core's Change Tracker holds in-memory references to every entity queried or updated. Because the captive DbContext is never disposed, its Change Tracker grows indefinitely until the process triggers an OutOfMemoryException (OOM).
  3. Stale Data: Queries executed on a long-lived DbContext return entities from its in-memory first-level cache rather than fresh data from the database.

❌ The Buggy Code:

// Registered as Singleton
public class OrderNotificationEngine : IOrderNotificationEngine
{
    private readonly TradingDbContext _dbContext; // ❌ CAPTIVE DEPENDENCY!

    // Constructor injection binds Scoped DbContext to Singleton lifetime!
    public OrderNotificationEngine(TradingDbContext dbContext) 
    {
        _dbContext = dbContext;
    }

    public async Task ProcessPendingNotificationsAsync()
    {
        var orders = await _dbContext.Orders.Where(o => !o.Notified).ToListAsync();
        // Concurrency collision will happen here under load!
    }
}

✅ The Architectural Solution: `IServiceScopeFactory`

When a Singleton or BackgroundService needs to consume a Scoped dependency, it must inject IServiceScopeFactory and create an explicit, short-lived scope per execution unit:

public sealed class OrderNotificationEngine(IServiceScopeFactory scopeFactory, ILogger<OrderNotificationEngine> logger) 
    : IOrderNotificationEngine
{
    public async Task ProcessPendingNotificationsAsync(CancellationToken ct = default)
    {
        // 1. Create a dedicated scope for this execution boundary
        using var scope = scopeFactory.CreateScope();

        // 2. Resolve the scoped service safely from the scope's ServiceProvider
        var db = scope.ServiceProvider.GetRequiredService<TradingDbContext>();

        var orders = await db.Orders
            .Where(o => !o.Notified)
            .Take(100)
            .ToListAsync(ct);

        foreach (var order in orders)
        {
            order.Notified = true;
        }

        await db.SaveChangesAsync(ct);
        // 3. When exiting the 'using' block, the scope is disposed, 
        // cleanly disposing the DbContext and flushing the Change Tracker!
    }
}
🛡️ Built-in Scope Validation

ASP.NET Core includes a built-in safety net: ValidateScopes = true. When running in the Development environment, the host checks your dependency graph on startup and throws an InvalidOperationException immediately if a singleton captures a scoped service. However, this check is disabled by default in Production for performance reasons!

4. Modern .NET 8 Keyed Services

Prior to .NET 8, resolving different implementations of the same interface required custom factory delegates, switch statements, or third-party containers (Autofac). .NET 8 introduced native Keyed Services into Microsoft.Extensions.DependencyInjection:

// 1. Register multiple implementations with distinct keys
builder.Services.AddKeyedScoped<IPaymentGateway, StripePaymentGateway>("stripe");
builder.Services.AddKeyedScoped<IPaymentGateway, AdyenPaymentGateway>("adyen");
builder.Services.AddKeyedScoped<IPaymentGateway, CryptoPaymentGateway>("crypto");

// 2. Consume using [FromKeyedServices] attribute in C# 12 Primary Constructors
public sealed class CheckoutService(
    [FromKeyedServices("stripe")] IPaymentGateway primaryGateway,
    [FromKeyedServices("adyen")] IPaymentGateway backupGateway,
    ILogger<CheckoutService> logger)
{
    public async Task ProcessCheckout(decimal amount)
    {
        try
        {
            await primaryGateway.ChargeAsync(amount);
        }
        catch (Exception ex)
        {
            logger.LogWarning(ex, "Primary gateway failed. Falling back to Adyen.");
            await backupGateway.ChargeAsync(amount);
        }
    }
}

// 3. Keyed resolution in ASP.NET Core Minimal APIs:
app.MapPost("/pay/{gateway}", async (
    string gateway, 
    decimal amount, 
    IServiceProvider sp) =>
{
    var selectedGateway = sp.GetKeyedService<IPaymentGateway>(gateway);
    if (selectedGateway is null)
        return Results.BadRequest($"Unsupported gateway: {gateway}");

    await selectedGateway.ChargeAsync(amount);
    return Results.Ok();
});

5. Container Disposal Mechanics & Memory Traps

The DI container takes ownership of every instance it creates that implements IDisposable or IAsyncDisposable:

  • Transient / Scoped Disposables: Tracked by the active IServiceScope. When the HTTP request or scope completes, the scope calls Dispose() or DisposeAsync() on every resolved disposable in reverse order of creation.
  • Singleton Disposables: Held alive and disposed only when the root IHost is stopped.
⚠️ The Transient Disposable Leak Trap

If you resolve thousands of Transient objects that implement IDisposable inside a long-lived scope (e.g., inside an Azure Service Bus queue receiver scope), the scope holds references to all of them to dispose them later! This causes high memory consumption. Prefer resolving factory delegates or using short-lived explicit child scopes.

6. The Senior Interviewer's Grill Round: Dependency Injection

🔥 Question 1: What happens if a Scoped service injects a Transient service? Is it an anti-pattern?

Senior Answer: No, it is perfectly safe and valid. A Transient service has a shorter or equal lifespan to a Scoped service. The container creates a fresh instance of the Transient service specifically for that Scoped service. That Transient instance lives for the duration of the Scope and is disposed when the Scope is disposed. A Captive Dependency only happens in the reverse direction: when a longer-lived service (Singleton) injects a shorter-lived service (Scoped).

🔥 Question 2: Why should you avoid calling services.BuildServiceProvider() inside ConfigureServices / Program.cs?

Senior Answer: Calling services.BuildServiceProvider() creates a second, detached copy of the DI container. This leads to two critical problems:

  1. Duplicate Singletons: Any singleton resolved from the temporary provider will be a completely different instance from the singleton resolved by the runtime application host, violating the single-instance invariant.
  2. Memory Leaks: The temporary service provider is often not disposed, meaning any disposable singletons it constructed remain pinned in memory indefinitely.
In modern .NET 8, configuration or seed dependencies should be accessed via IConfigureOptions<T>, IHostedService, or by resolving from app.Services after app.Build().

🔥 Question 3: What is the difference between IServiceScopeFactory and IServiceProvider.CreateScope()?

Senior Answer: IServiceScopeFactory is a singleton registered in the root container designed specifically for creating child scopes from background workers and singletons. Calling IServiceProvider.CreateScope() is an extension method that internally delegates to IServiceScopeFactory.CreateScope(). However, using IServiceScopeFactory makes the class dependency explicit and avoids taking a direct dependency on IServiceProvider (which can be considered a Service Locator anti-pattern).
