1. LINQ Execution Pitfalls: Multiple Enumeration & Boxing

📖 Deferred Execution Mechanics

LINQ queries built via extension methods like .Where() and .Select() return IEnumerable<T> iterators that represent intent, not executed data. Execution only begins when an enumeration trigger (e.g. foreach, .ToList(), .First()) is invoked.

A. The Multiple Enumeration Bug

If an IEnumerable<T> is supplied by an unmaterialized data source (e.g., an EF Core query, a REST API streaming response, or a generator yielding calculated objects), calling LINQ methods repeatedly causes the underlying execution to rerun every single time:

// ❌ BUG: Multiple Enumeration causes 2 duplicate database queries!
public async Task ProcessOrdersBadAsync(IEnumerable<Order> orders)
{
    // 1st enumeration: Executes SQL query to check count
    if (orders.Count() > 0) 
    {
        // 2nd enumeration: Executes SQL query AGAIN to iterate orders!
        foreach (var order in orders) 
        {
            await ExecuteTradeAsync(order);
        }
    }
}

// ✅ FIXED: Materialize once, or use Any() / Count property
public async Task ProcessOrdersGoodAsync(IEnumerable<Order> orders)
{
    // If input is an unknown sequence, materialize once into a List or Array:
    var orderList = orders as IReadOnlyCollection<Order> ?? orders.ToList();

    if (orderList.Count > 0)
    {
        foreach (var order in orderList)
        {
            await ExecuteTradeAsync(order);
        }
    }
}

B. `Any()` vs `Count() > 0` vs `Length`

Expression Complexity Behavior
sequence.Count() > 0 O(N) for generic IEnumerable Iterates through all 1,000,000 items just to verify if the sequence is non-empty!
sequence.Any() O(1) Invokes MoveNext() once and immediately short-circuits.
list.Count > 0 / array.Length > 0 O(1) (Zero-call) Reads the internal field directly with no method dispatch overhead.

2. Collection & Loop Optimization: Avoiding Bounds Checks

A. Pre-allocating Capacity (Preventing Array Resizing Thrash)

A C# List<T> has an initial capacity of 0. When elements are added, it doubles: 0 → 4 → 8 → 16 → 32 → 64... Each resize allocates a new array on the heap, copies the old elements, and leaves the old array for the Garbage Collector (GC).

// ❌ BAD: Resizes array 15 times, generating GC Gen 0 garbage
var trades = new List<Trade>();
for (int i = 0; i < 50_000; i++)
    trades.Add(new Trade(i));

// ✅ GOOD: Single heap allocation of exact required size
var trades = new List<Trade>(50_000);
for (int i = 0; i < 50_000; i++)
    trades.Add(new Trade(i));

B. `CollectionsMarshal.AsSpan` (High-Performance Loops)

When indexing into a List<T>, the JIT compiler emits array bounds check instructions (cmp index, length; jge ThrowIndexOutOfRange). In high-frequency computing, we can bypass this overhead using .NET 8's CollectionsMarshal.AsSpan:

using System.Runtime.InteropServices;

public decimal CalculateTotalNotional(List<Trade> trades)
{
    // Access internal backing array directly as a Span<T>
    Span<Trade> tradeSpan = CollectionsMarshal.AsSpan(trades);
    
    decimal total = 0m;
    for (int i = 0; i < tradeSpan.Length; i++)
    {
        // JIT optimizes this loop by eliminating bounds checking completely!
        total += tradeSpan[i].Notional;
    }
    return total;
}

C. `Dictionary.TryGetValue` vs `ContainsKey` + Indexer

Calling ContainsKey(key) followed by dict[key] hashes the key twice and traverses the internal hash bucket chain twice (Double-Lookup penalty):

// ❌ SLOW: 2 Hash calculations + 2 Bucket lookups
if (cache.ContainsKey(symbol))
{
    var price = cache[symbol];
}

// ✅ FAST: 1 Hash calculation + 1 Bucket lookup
if (cache.TryGetValue(symbol, out var price))
{
    // Use price directly
}

3. Zero-Allocation High-Throughput: Span<T> & ArrayPool

📖 Span<T> Architecture

Span<T> is a ref struct allocated exclusively on the execution stack. It represents a contiguous window over arbitrary memory (managed array, stack memory via stackalloc, or unmanaged native pointers) without triggering any heap allocations.

A. Zero-Allocation String Parsing with `ReadOnlySpan<char>`

Traditional string parsing with string.Substring() or string.Split() allocates multiple new string objects on the heap per incoming network message. With ReadOnlySpan<char>, parsing FIX or CSV messages allocates zero bytes of heap memory:

public readonly record struct TradeOrder(ReadOnlyMemory<char> Symbol, int Quantity, decimal Price);

public static TradeOrder ParseFixMessageFast(ReadOnlySpan<char> fixMessage)
{
    // Format: "SYMBOL,QTY,PRICE" -> "AAPL,500,182.40"
    int firstComma = fixMessage.IndexOf(',');
    var symbolSpan = fixMessage[..firstComma];

    var remaining = fixMessage[(firstComma + 1)..];
    int secondComma = remaining.IndexOf(',');
    var qtySpan = remaining[..secondComma];
    var priceSpan = remaining[(secondComma + 1)..];

    // High-performance int & decimal parsing directly from Span!
    int quantity = int.Parse(qtySpan);
    decimal price = decimal.Parse(priceSpan);

    return new TradeOrder(symbolSpan.ToArray().AsMemory(), quantity, price);
}

B. Preventing LOH Garbage with `ArrayPool<T>`

Any managed array greater than or equal to 85,000 bytes is allocated directly onto the Large Object Heap (LOH). The LOH is collected only during expensive Gen 2 Garbage Collections. In web APIs processing file uploads or cryptographic hashing, allocating byte arrays repeatedly fragments memory and degrades server response times.

using System.Buffers;

public async Task ProcessLargeStreamAsync(Stream networkStream)
{
    // Rent a 128 KB buffer from the shared pool (ZERO heap allocation!)
    byte[] buffer = ArrayPool<byte>.Shared.Rent(128 * 1024);
    try
    {
        int bytesRead;
        while ((bytesRead = await networkStream.ReadAsync(buffer.AsMemory(0, buffer.Length))) > 0)
        {
            // Process bytesRead from buffer
            ProcessChunk(buffer.AsSpan(0, bytesRead));
        }
    }
    finally
    {
        // Return buffer to pool for reuse by subsequent requests
        ArrayPool<byte>.Shared.Return(buffer);
    }
}

4. Async/Await Pitfalls: Deadlocks, ValueTask & async void

A. The Catastrophic `async void` Crash

Except for event handlers, methods should never be declared as async void. Exceptions thrown inside an async void method cannot be caught by callers using try-catch; they bubble up straight to the AppDomain unhandled exception handler and terminate the entire web server process:

// ❌ DEADLY: Process crashes if an exception is thrown!
public async void SaveAuditLogAsync(AuditRecord log) 
{
    await _db.SaveAsync(log); // If DB fails, whole application terminates!
}

// ✅ CORRECT: Caller can await and catch exceptions safely
public async Task SaveAuditLogAsync(AuditRecord log)
{
    await _db.SaveAsync(log);
}

B. Sync-Over-Async Deadlock with `.Result` or `.Wait()`

Calling .Result or .Wait() on an uncompleted Task blocks the current thread while waiting for the background thread. In environments with a SynchronizationContext (like legacy ASP.NET or WPF/WinForms), this causes an irreversible deadlock:

C. When to use `ValueTask<T>`

Allocating a Task<T> object requires ~72 bytes of heap memory. In hot paths where an operation frequently completes synchronously (e.g. cache hit), ValueTask<T> is a struct that incurs zero heap allocations:

public ValueTask<SecurityToken> GetTokenAsync(string clientId)
{
    // Hot path: Token already cached in memory -> 0 Allocations!
    if (_cache.TryGetValue(clientId, out var cachedToken))
    {
        return new ValueTask<SecurityToken>(cachedToken);
    }

    // Cold path: Perform asynchronous network request
    return new ValueTask<SecurityToken>(FetchTokenFromOAuthServerAsync(clientId));
}

5. Diagnosing & Hunting Production Memory Leaks in .NET

🚨 The Top 4 Causes of .NET Memory Leaks
  1. Event Handler Subscriptions: If a short-lived subscriber attaches to an event on a long-lived publisher (publisher.TradeExecuted += subscriber.OnTrade;), the publisher holds a strong reference in its invocation list, preventing the subscriber from ever being garbage collected!
  2. Closures Capturing Outer Variables: Lambdas that capture local variables generate compiler-generated display classes. If the lambda is stored in a long-lived delegate or cache, the entire captured scope remains pinned in memory.
  3. Unbounded Caches: Using a static ConcurrentDictionary without an eviction policy (TTL, max size) causes perpetual memory accumulation.
  4. Unmanaged Handles / Finalizers: Forgetting to call Dispose() on native handles, sockets, or bitmap streams.

Production Diagnostic Toolchain

  • `dotnet-gcdump`: Captures a lightweight snapshot of the managed heap in seconds with near-zero performance pause on production pods.
  • `dotnet-dump`: Collects a full memory dump for offline analysis in WinDbg or Visual Studio.
  • `dotnet-trace`: Collects CPU profiling traces using EventPipe without attaching a debugger.

6. The Senior Interviewer's Grill Round: Optimization & Diagnostics

🔥 Question 1: What is the Golden Rule of ValueTask? Why can you not await it twice?

Senior Answer: A ValueTask<T> wraps either a result or an IValueTaskSource<T>. To maintain zero allocations, the backing IValueTaskSource objects are pooled and reused across the runtime! Once a ValueTask is awaited, its backing source is returned to the pool and may be reassigned to a completely different operation. Awaiting a ValueTask twice (or calling .Result after awaiting) results in undefined behavior, corrupted state, or race conditions. If multiple awaits are necessary, convert it once to a standard Task using vt.AsTask().

🔥 Question 2: Why should library authors specify ConfigureAwait(false)?

Senior Answer: By default (ConfigureAwait(true)), awaiting a Task captures the current SynchronizationContext and marshals the continuation back onto that context when the task completes. In class libraries (non-UI code), capturing the synchronization context is unnecessary, incurs thread-switch context latency, and causes deadlocks when consumers invoke sync-over-async methods (.Result). Specifying ConfigureAwait(false) tells the CLR that the continuation can execute on any available ThreadPool thread.

🔥 Question 3: How do you fix an event handler memory leak if you cannot easily unsubscribe?

Senior Answer: There are three architectural remedies:

  1. Weak Event Pattern: Use WeakReference<T> to reference the subscriber, allowing the GC to collect it even while registered with the publisher.
  2. IDisposable Encasement: Make the subscriber implement IDisposable, and inside Dispose(), explicitly unsubscribe: _publisher.TradeExecuted -= OnTrade;.
  3. Decouple with Message Brokers: Replace direct C# events with decoupled mediator pipelines or System.Threading.Channels.
