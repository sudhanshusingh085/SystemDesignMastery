02 · All JOIN Types, Physical Operators & Subqueries

Relational Algebra Joins, Physical Join Algorithms (Nested Loops, Merge, Hash Match), CROSS APPLY / OUTER APPLY Power Patterns, and Correlated Subqueries.

1. Logical Join Types vs Physical Join Operators

When you write a query, you specify a logical join (INNER, LEFT, RIGHT, FULL OUTER, CROSS). The SQL Server Cost-Based Optimizer (CBO) maps this to one of three physical join operators based on table statistics, cardinalities, and available indexes.

(One small input + Index Seek on inner)"] CBO --> Phys2["2. Merge Join
(Both inputs sorted on join key)"] CBO --> Phys3["3. Hash Match Join
(Large, unsorted inputs - builds in-memory hash table)"]
Physical Operator When SQL Server Uses It Memory Grant Requirement Performance Characteristic
Nested Loops One input is small (outer) and the other has an index on the join column (inner). 0 MB (Stream-based, pipelined) Sub-millisecond for OLTP seeks; catastrophic if inner input has no index (O(N*M) table scan).
Merge Join Both inputs are already sorted on the join key (e.g. Clustered Index on join keys). 0 MB (Stream-based) Fastest possible join algorithm for large datasets; linear O(N+M) time complexity.
Hash Match Neither input is sorted and inputs are large. Builds an in-memory hash table on the smaller input. High (Can spill to TempDB if memory grant is insufficient) Excellent fallback for ad-hoc DW queries; vulnerable to memory pressure and hash spills.

2. The Superpower: CROSS APPLY & OUTER APPLY

Standard ANSI joins evaluate both relations independently before applying the ON clause predicate. APPLY evaluates the right-side expression for every individual row produced by the left-side table, allowing the right side to reference columns from the left side.

CROSS APPLY

Acts like an INNER JOIN to a correlated table expression or function. If the right side produces 0 rows for a given left row, the left row is excluded.

OUTER APPLY

Acts like a LEFT OUTER JOIN. If the right side produces 0 rows for a given left row, the left row is still returned with NULL values in the right-side columns.

Key Production Use Cases for APPLY:

  1. Top N per Group: Finding the most recent 3 trades for every client account without scanning the whole table.
  2. Inline Table-Valued Functions (iTVFs): Passing row values directly into a TVF.
  3. JSON / XML Shredding: Using CROSS APPLY OPENJSON(...) or CROSS APPLY nodes(...).
  4. Calculation Re-use: Defining a derived column once and referencing it multiple times in WHERE and SELECT.

3. Correlated vs Non-Correlated Subqueries

  • Non-Correlated Subquery: Completely independent of the outer query. SQL Server evaluates it once, caches the scalar result or intermediate result set, and applies it to the outer query.
  • Correlated Subquery: References columns from the outer query row. Logically executes once per row of the outer table (unless the optimizer transforms it into a Semi-Join or Hash Match).

Exercise 2.1: Finding Accounts with Active Orders but Zero Executions
Easy
Context: Accounts, Orders, Executions

Requirement: Retrieve the AccountNumber, CashBalance, and total count of active orders for all accounts that have placed at least one Order, but have had zero fills/executions recorded in the Executions table. Order by CashBalance descending.

💡 View Solution & Explanation ▼ 
SELECT 
    a.AccountNumber,
    a.CashBalance,
    COUNT(o.OrderID) AS ActiveOrderCount
FROM Accounts a
INNER JOIN Orders o ON a.AccountID = o.AccountID
WHERE NOT EXISTS (
    SELECT 1 
    FROM Executions e
    WHERE e.OrderID = o.OrderID
)
GROUP BY a.AccountID, a.AccountNumber, a.CashBalance
ORDER BY a.CashBalance DESC;
Why NOT EXISTS: The optimizer converts NOT EXISTS into a high-performance Left Anti Semi Join, halting the inner search on the very first execution match found instead of counting rows.
Exercise 2.2: Top 3 Largest Executions per Security via CROSS APPLY
Medium
Context: Securities s, Orders o, Executions e

Requirement: For every active equity security, return the top 3 highest notional executions (FillQuantity * FillPrice) ever recorded. If a security has fewer than 3 executions, return whatever exists. Include Ticker, ExecutionID, FillQuantity, FillPrice, and TotalNotional.

💡 View Solution & Explanation ▼ 
SELECT 
    s.Ticker,
    top_execs.ExecutionID,
    top_execs.FillQuantity,
    top_execs.FillPrice,
    top_execs.TotalNotional,
    top_execs.ExecutedAt
FROM Securities s
CROSS APPLY (
    SELECT TOP (3)
        e.ExecutionID,
        e.FillQuantity,
        e.FillPrice,
        CAST(e.FillQuantity * e.FillPrice AS DECIMAL(18,2)) AS TotalNotional,
        e.ExecutedAt
    FROM Orders o
    INNER JOIN Executions e ON o.OrderID = e.OrderID
    WHERE o.SecurityID = s.SecurityID
    ORDER BY (e.FillQuantity * e.FillPrice) DESC
) AS top_execs
ORDER BY s.Ticker, top_execs.TotalNotional DESC;
CROSS APPLY Efficiency: Compared to a full-table window function over millions of rows, CROSS APPLY combined with an index on (SecurityID, OrderID) drives a lightning-fast loop seeking only the top 3 executions per security.
Exercise 2.3: Detecting Unsettled Discrepancies via FULL OUTER JOIN
Medium
Context: Orders o (Quantity, LimitPrice) vs LedgerTransactions lt (Amount)

Requirement: During end-of-day reconciliation, compare total order values placed today against actual ledger debits. Write a FULL OUTER JOIN query to detect: (1) Orders placed with no matching ledger transaction, and (2) Ledger debits that have no corresponding order record. Label each discrepancy with an alert flag.

💡 View Solution & Explanation ▼ 
WITH TodayOrders AS (
    SELECT 
        AccountID,
        SUM(Quantity * ISNULL(LimitPrice, 0)) AS TotalOrderAmount
    FROM Orders
    WHERE CAST(OrderTime AS DATE) = CAST(SYSUTCDATETIME() AS DATE)
    GROUP BY AccountID
),
TodayLedger AS (
    SELECT 
        AccountID,
        SUM(Amount) AS TotalLedgerDebit
    FROM LedgerTransactions
    WHERE TransactionType IN ('TRADE_BUY', 'FEE')
      AND CAST(TransactionTimestamp AS DATE) = CAST(SYSUTCDATETIME() AS DATE)
    GROUP BY AccountID
)
SELECT 
    COALESCE(o.AccountID, l.AccountID) AS AccountID,
    ISNULL(o.TotalOrderAmount, 0) AS OrderAmount,
    ISNULL(l.TotalLedgerDebit, 0) AS LedgerDebit,
    CASE 
        WHEN o.AccountID IS NULL THEN 'ORPHAN_LEDGER_DEBIT (No Order Found)'
        WHEN l.AccountID IS NULL THEN 'UNBILLED_ORDER (No Ledger Debit Found)'
        WHEN ABS(o.TotalOrderAmount - l.TotalLedgerDebit) > 0.01 THEN 'AMOUNT_MISMATCH'
        ELSE 'RECONCILED'
    END AS ReconciliationStatus
FROM TodayOrders o
FULL OUTER JOIN TodayLedger l ON o.AccountID = l.AccountID
WHERE o.AccountID IS NULL 
   OR l.AccountID IS NULL 
   OR ABS(o.TotalOrderAmount - l.TotalLedgerDebit) > 0.01;
Why FULL OUTER JOIN: Full outer joins are essential in financial reconciliation to identify orphan rows on either side of two independent ledger tables.
Exercise 2.4: Self Join for Security Price Volatility Spread
Medium
Context: Table Executions with FillPrice, ExecutedAt

Requirement: For each security that traded today, find every pair of consecutive executions where the execution price jumped or dropped by more than 5% within a 60-second window. Use a self-join approach.

💡 View Solution & Explanation ▼ 
WITH ExecsWithSecurity AS (
    SELECT 
        e.ExecutionID,
        o.SecurityID,
        e.FillPrice,
        e.ExecutedAt
    FROM Executions e
    INNER JOIN Orders o ON e.OrderID = o.OrderID
)
SELECT 
    e1.SecurityID,
    e1.ExecutionID AS EarlierExecID,
    e1.FillPrice AS EarlierPrice,
    e1.ExecutedAt AS EarlierTime,
    e2.ExecutionID AS LaterExecID,
    e2.FillPrice AS LaterPrice,
    e2.ExecutedAt AS LaterTime,
    CAST(ABS(e2.FillPrice - e1.FillPrice) * 100.0 / e1.FillPrice AS DECIMAL(5,2)) AS PctChange
FROM ExecsWithSecurity e1
INNER JOIN ExecsWithSecurity e2 
        ON e1.SecurityID = e2.SecurityID
       AND e2.ExecutedAt > e1.ExecutedAt
       AND e2.ExecutedAt <= DATEADD(SECOND, 60, e1.ExecutedAt)
WHERE ABS(e2.FillPrice - e1.FillPrice) / e1.FillPrice > 0.05;
Self-Join Key Concept: Joining a table to itself using inequality predicates (e2.ExecutedAt > e1.ExecutedAt) enables cross-event latency and delta tracking across chronological event feeds.
Exercise 2.5: Generating All Trading Day Cross Products via CROSS JOIN
Easy
Context: Securities, and a calendar table or date sequence

Requirement: Generate a Cartesian matrix of every active Equity security and the last 7 calendar dates. Show the total fills for that security on that date, outputting 0 if no fills occurred (do not drop dates with zero trades).

💡 View Solution & Explanation ▼ 
-- Generate 7 day date spine
WITH DateSpine AS (
    SELECT CAST(SYSUTCDATETIME() AS DATE) AS TradeDate
    UNION ALL
    SELECT DATEADD(DAY, -1, TradeDate)
    FROM DateSpine
    WHERE TradeDate > DATEADD(DAY, -6, CAST(SYSUTCDATETIME() AS DATE))
),
SecurityDateMatrix AS (
    SELECT 
        s.SecurityID,
        s.Ticker,
        d.TradeDate
    FROM Securities s
    CROSS JOIN DateSpine d
    WHERE s.AssetClass = 'EQUITY' AND s.IsActive = 1
)
SELECT 
    m.Ticker,
    m.TradeDate,
    ISNULL(COUNT(e.ExecutionID), 0) AS FillCount,
    ISNULL(SUM(e.FillQuantity), 0) AS TotalShares
FROM SecurityDateMatrix m
LEFT JOIN Orders o 
       ON m.SecurityID = o.SecurityID 
      AND CAST(o.OrderTime AS DATE) = m.TradeDate
LEFT JOIN Executions e 
       ON o.OrderID = e.OrderID
GROUP BY m.SecurityID, m.Ticker, m.TradeDate
ORDER BY m.Ticker, m.TradeDate DESC;
Cartesian Matrix Pattern: CROSS JOIN generates the complete continuous grid of dimensions (Tickers × Dates). Following with a LEFT JOIN guarantees that days with 0 trades are preserved in the reporting pipeline.
Exercise 2.6: Unpacking JSON FIX Audit Tags with CROSS APPLY OPENJSON
Hard
Context: AuditLogs (LogID, ChangePayload) where ChangePayload stores JSON: {"Tag35": "D", "ClOrdID": "ORD-991", "SenderCompID": "CITADEL"}

Requirement: Write a query to shred the JSON payload and return LogID, LoggedAt, and individual columns for ClOrdID and SenderCompID for all rows where Tag35 = 'D' (New Order Single).

💡 View Solution & Explanation ▼ 
SELECT 
    a.LogID,
    a.LoggedAt,
    j.ClOrdID,
    j.SenderCompID,
    j.MsgType
FROM AuditLogs a
CROSS APPLY OPENJSON(a.ChangePayload)
WITH (
    MsgType VARCHAR(10) '$.Tag35',
    ClOrdID VARCHAR(50) '$.ClOrdID',
    SenderCompID VARCHAR(50) '$.SenderCompID'
) AS j
WHERE j.MsgType = 'D';
Modern T-SQL Feature: OPENJSON with a strongly-typed WITH clause transforms JSON text into relational rows with zero string-parsing overhead.
Exercise 2.7: Forcing Physical Join Algorithms with Join Hints (When & Why)
Hard
Context: Performance tuning large joins between Orders and Executions

Requirement: Write queries explicitly forcing: (1) INNER LOOP JOIN, (2) INNER MERGE JOIN, and (3) INNER HASH JOIN. Explain why join hints are dangerous in production and when they are justified.

💡 View Solution & Explanation ▼ 
-- 1. Force Nested Loops
SELECT o.OrderID, e.FillPrice
FROM Orders o
INNER LOOP JOIN Executions e ON o.OrderID = e.OrderID;

-- 2. Force Merge Join (Both inputs must be sorted on OrderID!)
SELECT o.OrderID, e.FillPrice
FROM Orders o
INNER MERGE JOIN Executions e ON o.OrderID = e.OrderID;

-- 3. Force Hash Join
SELECT o.OrderID, e.FillPrice
FROM Orders o
INNER HASH JOIN Executions e ON o.OrderID = e.OrderID;
Why Join Hints are Risky: A hint overrides the Cost-Based Optimizer. If data volume grows from 10,000 rows to 50,000,000 rows, a hardcoded LOOP JOIN will freeze your server with billions of nested iterations. Use hints only as emergency hotfixes while statistics or indexes are rebuilt!
Exercise 2.8: Anti-Join Showdown: NOT EXISTS vs NOT IN vs LEFT JOIN / IS NULL
Hard
Context: Finding Clients who have never deposited funds.

Requirement: Write a comprehensive query comparing the generated execution plan operators for NOT EXISTS, NOT IN, and LEFT JOIN...WHERE IS NULL. Demonstrate how a single NULL row alters the NOT IN query behavior.

💡 View Solution & Explanation ▼ 
-- Demonstration of the NULL trap:
-- Assume a Ledger transaction exists with AccountID IS NULL (e.g. system rebalancing)
INSERT INTO LedgerTransactions (AccountID, TransactionType, Amount)
VALUES (NULL, 'FEE', 15.00);

-- Query A: NOT IN (RETURNS 0 ROWS! Completely Broken by the NULL above!)
SELECT c.ClientID, c.ClientName
FROM Clients c
WHERE c.ClientID NOT IN (
    SELECT a.ClientID 
    FROM Accounts a 
    INNER JOIN LedgerTransactions lt ON a.AccountID = lt.AccountID
    WHERE lt.TransactionType = 'DEPOSIT'
);

-- Query B: NOT EXISTS (PRODUCES CORRECT RESULTS REGARDLESS OF NULLs!)
SELECT c.ClientID, c.ClientName
FROM Clients c
WHERE NOT EXISTS (
    SELECT 1 
    FROM Accounts a 
    INNER JOIN LedgerTransactions lt ON a.AccountID = lt.AccountID
    WHERE a.ClientID = c.ClientID 
      AND lt.TransactionType = 'DEPOSIT'
);
Execution Plan Reality: Both NOT EXISTS and LEFT JOIN ... IS NULL compile to a Left Anti Semi Join in modern SQL Server. However, NOT IN introduces a defensive filter check to handle 3-valued logic, destroying performance and risking catastrophic empty result sets.

📋 How to Answer This in an Interview

Interviewer Question: "When would you choose CROSS APPLY over a standard INNER JOIN?"

Staff Engineer Response:

"I choose CROSS APPLY in three specific architectural situations:

1. Correlated Top-N Per Group Queries: When I need to fetch the top N records per parent entity (e.g., the 3 most recent executions per trading account). In standard SQL, this requires calculating a window function like ROW_NUMBER() across the entire million-row table before filtering. With CROSS APPLY, the query optimizer executes a targeted TOP (3) index seek per parent row, which is orders of magnitude faster.

2. Table-Valued Functions (TVFs) and Modern JSON/XML Parsing: Standard ANSI joins cannot pass columns from the outer table into parameters of a table-valued function or the OPENJSON() function. CROSS APPLY evaluates the function dynamically for every incoming row.

3. DRY Calculation Re-use: I frequently use CROSS APPLY (SELECT expression1 AS ColA, expression2 AS ColB) to compute complex mathematical formulas once, and immediately reuse those computed aliases in the outer SELECT, WHERE, and GROUP BY clauses without duplicating code."
