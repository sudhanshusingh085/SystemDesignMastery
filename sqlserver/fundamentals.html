01 · T-SQL Fundamentals, DML & All Aggregate Functions

Logical Query Processing Order, 3-Valued Boolean Logic, SARGability, Multi-Dimensional Grouping (ROLLUP, CUBE, GROUPING SETS), and Every Aggregate Function in SQL Server.

1. The Sacred Order of Logical Query Processing

In procedural languages like Java or C++, code executes line-by-line in the order written. In SQL, you declare what you want, not how to fetch it. The SQL Server query optimizer executes clauses in a strict mathematical sequence that differs fundamentally from lexical typing order.

flowchart TD Step1["1. FROM (Evaluate tables & Cartesian products)"] --> Step2["2. ON (Filter join predicates)"] Step2 --> Step3["3. JOIN (Produce joined virtual table)"] Step3 --> Step4["4. WHERE (Filter individual rows)"] Step4 --> Step5["5. GROUP BY (Aggregate rows into buckets)"] Step5 --> Step6["6. WITH CUBE / ROLLUP / GROUPING SETS"] Step6 --> Step7["7. HAVING (Filter aggregated buckets)"] Step7 --> Step8["8. SELECT (Evaluate column expressions & Window Functions)"] Step8 --> Step9["9. DISTINCT (Remove duplicates)"] Step9 --> Step10["10. ORDER BY (Sort result set)"] Step10 --> Step11["11. TOP / OFFSET...FETCH (Paginate & restrict rows)"]

⚠️ The Classic Trap: Column Aliases in the WHERE Clause

Why does SELECT FillQuantity * FillPrice AS GrossNotional FROM Executions WHERE GrossNotional > 1000000; fail with "Invalid column name 'GrossNotional'"?

Answer: Because the WHERE clause (Step 4) is evaluated long before the SELECT clause (Step 8) creates the alias! However, you can reference GrossNotional in the ORDER BY clause (Step 10) because ORDER BY executes after SELECT.

2. Three-Valued Logic (3VL) & NULL Traps

In relational algebra, NULL represents an unknown or missing value, not zero or an empty string. Any equality comparison with NULL yields UNKNOWN, not TRUE or FALSE.

Predicate Expression Result when Value is NULL Explanation
WHERE LimitPrice = NULL UNKNOWN (Evaluates to False in WHERE) Always returns 0 rows! Must use IS NULL.
WHERE LimitPrice <> 100 UNKNOWN (Filtered out!) Rows where LimitPrice is NULL are excluded because the inequality test evaluates to UNKNOWN!
WHERE NOT (LimitPrice = 100) UNKNOWN (Filtered out!) NOT(UNKNOWN) is still UNKNOWN.

ISNULL() vs COALESCE() — The Critical Interview Difference

Feature ISNULL(check_expr, replacement) COALESCE(expr1, expr2, ... exprN)
Origin Proprietary T-SQL built-in function ANSI SQL Standard compliant expression
Parameter Count Strictly 2 parameters 2 to unlimited parameters (returns first non-null)
Data Type Resolution Takes the data type of the first expression. If 1st is VARCHAR(5) and replacement is VARCHAR(20), replacement is truncated! Takes the data type with the highest precedence according to SQL Server type precedence rules.
Subquery Evaluation Evaluates subqueries only once. Internally rewrites to a CASE WHEN construct; subqueries might be evaluated multiple times in older builds!

3. Deep Dive: All SQL Server Aggregate Functions

SQL Server provides standard, statistical, and advanced modern aggregate functions. Aggregate functions ignore NULL values in their calculations (except for COUNT(*)).

A. Standard Aggregates

  • COUNT(*): Counts every row in the partition or table, including rows where all columns are NULL.
  • COUNT(column): Counts non-null values in that specific column.
  • COUNT(DISTINCT column): Counts unique non-null values.
  • COUNT_BIG(*): Returns an BIGINT (int64) instead of INT. Mandatory for partitioned tables or tables with over 2.14 billion rows, and required in indexed views with aggregation.
  • SUM(column): Calculates total. Throws arithmetic overflow if sum exceeds column datatype range (e.g. use SUM(CAST(Amount AS BIGINT))).
  • AVG(column): Calculates arithmetic mean. Trap: In integer columns, AVG(5 + 4) = 4 (integer division truncation). Must cast to DECIMAL: AVG(CAST(Qty AS FLOAT)).
  • MIN(column) / MAX(column): Returns smallest / greatest value. Works on numbers, strings (alphabetical collations), and dates.

B. Statistical Aggregates

  • STDEV(column) / STDEVP(column): Statistical sample standard deviation vs population standard deviation.
  • VAR(column) / VARP(column): Statistical sample variance vs population variance.

C. Modern & Advanced Aggregates (SQL Server 2017+)

  • STRING_AGG(expression, separator) WITHIN GROUP (ORDER BY sort_column): Concatenates string values from multiple rows into a single delimited string with explicit sorting. Eliminates legacy FOR XML PATH('') hacks!
  • CHECKSUM_AGG(column): Generates an integer checksum across a column. Ideal for detecting whether any record in a large table changed without scanning column by column.
  • APPROX_COUNT_DISTINCT(column): HyperLogLog-based probabilistic distinct counting. Consumes negligible memory compared to COUNT(DISTINCT), offering 97% accuracy with up to 50x speedups on multi-billion row tables.

D. Multi-Dimensional Aggregation: ROLLUP, CUBE & GROUPING SETS

Instead of running multiple GROUP BY queries combined with UNION ALL, SQL Server provides super-aggregate operators:

  • GROUP BY ROLLUP (Sector, AssetClass): Produces hierarchical subtotals: (Sector, AssetClass), (Sector), and Grand Total ().
  • GROUP BY CUBE (Sector, AssetClass): Produces all 2^N combinations: (Sector, AssetClass), (Sector), (AssetClass), and Grand Total ().
  • GROUPING_ID(Sector, AssetClass): Returns an integer bitmask indicating which columns are aggregated in the subtotal row, allowing you to label summary rows cleanly.

4. SARGability (Search Argument Able) Internals

A query predicate is SARGable if the query engine can exploit a B-Tree index seek instead of scanning every page in the table.

🚫 Anti-Pattern: Non-SARGable Query (Forces Table/Clustered Index Scan)

-- Non-SARGable: Wrapping indexed column in a function
SELECT OrderID, LimitPrice FROM Orders
WHERE YEAR(OrderTime) = 2024 AND MONTH(OrderTime) = 3;

-- Non-SARGable: Data type mismatch causing implicit conversion
SELECT OrderID FROM Orders WHERE AccountNumber = 1001; -- If AccountNumber is VARCHAR

✅ SARGable Query (Enables B-Tree Index Seek)

-- SARGable: Isolate column on one side of comparison with a date boundary
SELECT OrderID, LimitPrice FROM Orders
WHERE OrderTime >= '2024-03-01 00:00:00' 
  AND OrderTime < '2024-04-01 00:00:00';

Exercise 1.1: Aggregated Trade Volumes with Integer Truncation Guard
Easy
Context: Table Executions (ExecutionID, OrderID, FillQuantity, FillPrice, ExecutionFee, LiquidityFlag)

Requirement: Write a query to calculate for each liquidity flag ('A' for Added, 'R' for Removed): total execution count, total shares filled, total execution fees, and the exact arithmetic average fill price formatted to 4 decimal places. Ensure that average calculation does not suffer from integer division truncation.

💡 View Solution & Explanation ▼ 
SELECT 
    LiquidityFlag,
    COUNT(*) AS TotalFills,
    SUM(CAST(FillQuantity AS BIGINT)) AS TotalSharesFilled,
    SUM(ExecutionFee) AS TotalFees,
    CAST(AVG(CAST(FillPrice AS DECIMAL(18,4))) AS DECIMAL(18,4)) AS AvgFillPrice,
    -- Or Weighted Average Price (VWAP):
    CAST(SUM(CAST(FillQuantity AS DECIMAL(18,4)) * FillPrice) / 
         NULLIF(SUM(CAST(FillQuantity AS DECIMAL(18,4))), 0) AS DECIMAL(18,4)) AS VWAP
FROM Executions
GROUP BY LiquidityFlag;
Why this works: CAST(FillQuantity AS BIGINT) avoids arithmetic overflow when trading volumes exceed 2.14 billion shares. NULLIF(..., 0) prevents a fatal divide-by-zero exception if a group has 0 volume.
Exercise 1.2: Delimited Tickers Per Client using STRING_AGG
Easy
Context: Clients, Accounts, Orders, Securities

Requirement: For each active Institutional Client, generate a single comma-separated list of distinct stock tickers they have placed orders for, ordered alphabetically within the string (e.g. "AAPL, MSFT, NVDA"). Do not include NULLs or duplicates.

💡 View Solution & Explanation ▼ 
WITH DistinctClientOrders AS (
    SELECT DISTINCT 
        c.ClientID,
        c.ClientName,
        s.Ticker
    FROM Clients c
    INNER JOIN Accounts a ON c.ClientID = a.ClientID
    INNER JOIN Orders o ON a.AccountID = o.AccountID
    INNER JOIN Securities s ON o.SecurityID = s.SecurityID
    WHERE c.ClientType = 'INSTITUTIONAL'
)
SELECT 
    ClientID,
    ClientName,
    STRING_AGG(Ticker, ', ') WITHIN GROUP (ORDER BY Ticker ASC) AS TradedTickers
FROM DistinctClientOrders
GROUP BY ClientID, ClientName;
Key Insight: STRING_AGG() requires SQL Server 2017+. Because STRING_AGG(DISTINCT col) is not natively supported in earlier T-SQL versions, deduplication is cleanly pre-computed in a Common Table Expression (CTE) first.
Exercise 1.3: Multi-Dimensional Matrix Reporting with GROUPING SETS
Medium
Context: Securities (Sector, AssetClass), Orders (LimitPrice, Quantity)

Requirement: Generate an institutional risk summary showing total gross notional value (Quantity * LimitPrice) sliced by: (1) Sector and AssetClass, (2) Sector only, (3) AssetClass only, and (4) Grand Total. Include a column ReportLevel that cleanly labels the aggregation tier using GROUPING_ID().

💡 View Solution & Explanation ▼ 
SELECT 
    CASE GROUPING_ID(s.Sector, s.AssetClass)
        WHEN 0 THEN 'Sector & Asset Class'
        WHEN 1 THEN 'Sector Subtotal'
        WHEN 2 THEN 'Asset Class Subtotal'
        WHEN 3 THEN 'Company Grand Total'
    END AS ReportLevel,
    ISNULL(s.Sector, '[ALL SECTORS]') AS Sector,
    ISNULL(s.AssetClass, '[ALL ASSET CLASSES]') AS AssetClass,
    COUNT(o.OrderID) AS TotalOrders,
    SUM(CAST(o.Quantity AS DECIMAL(18,4)) * ISNULL(o.LimitPrice, 0.00)) AS TotalNotional
FROM Securities s
INNER JOIN Orders o ON s.SecurityID = o.SecurityID
GROUP BY GROUPING SETS (
    (s.Sector, s.AssetClass),
    (s.Sector),
    (s.AssetClass),
    ()
)
ORDER BY GROUPING_ID(s.Sector, s.AssetClass), s.Sector, s.AssetClass;
Engine Mechanism: GROUPING_ID() returns a binary bitmask where a bit is 1 if the corresponding column is aggregated into a subtotal, and 0 if it is grouped. This allows unambiguous distinction between real NULLs in the table versus subtotal NULLs.
Exercise 1.4: Refactoring a Non-SARGable Audit Query for Index Optimization
Medium
Context: AuditLogs (LogID, TableName, LoggedAt, ChangedBy) with an index on LoggedAt.

Requirement: A production report uses this slow query:
SELECT * FROM AuditLogs WHERE DATEDIFF(day, LoggedAt, GETUTCDATE()) <= 7;
Refactor this query to be 100% SARGable so the query engine utilizes an Index Seek on LoggedAt, and explain why.

💡 View Solution & Explanation ▼ 
-- SARGable Refactor:
DECLARE @CutoffDate DATETIME2(3) = DATEADD(DAY, -7, SYSUTCDATETIME());

SELECT LogID, TableName, RecordID, ChangedBy, LoggedAt
FROM AuditLogs
WHERE LoggedAt >= @CutoffDate;
Why this is faster: In the original query, DATEDIFF() had to be computed for every single row in AuditLogs, forcing an Index Scan across millions of pages. The refactored version calculates the parameter once and performs an instantaneous B-Tree Index Seek with a range scan.
Exercise 1.5: Detecting Missing High-Value Settlements with Anti-Null Guards
Hard
Context: Accounts, LedgerTransactions

Requirement: Find all Accounts that have never had a WITHDRAWAL transaction exceeding $100,000, but currently maintain an active CashBalance > $500,000. Write this using three distinct patterns: LEFT JOIN / IS NULL, NOT EXISTS, and NOT IN. Explain which one is safest when NULLs exist.

💡 View Solution & Explanation ▼ 
-- Method 1: NOT EXISTS (Safest & Most Performant with proper indexes)
SELECT a.AccountID, a.AccountNumber, a.CashBalance
FROM Accounts a
WHERE a.CashBalance > 500000.00
  AND NOT EXISTS (
      SELECT 1 
      FROM LedgerTransactions lt
      WHERE lt.AccountID = a.AccountID
        AND lt.TransactionType = 'WITHDRAWAL'
        AND lt.Amount > 100000.00
  );

-- Method 2: LEFT JOIN with IS NULL filter
SELECT a.AccountID, a.AccountNumber, a.CashBalance
FROM Accounts a
LEFT JOIN LedgerTransactions lt 
       ON a.AccountID = lt.AccountID 
      AND lt.TransactionType = 'WITHDRAWAL' 
      AND lt.Amount > 100000.00
WHERE a.CashBalance > 500000.00
  AND lt.TransactionID IS NULL;

-- Method 3: NOT IN (FATAL TRAP WARNING!)
-- If the subquery returns even a SINGLE NULL, NOT IN returns ZERO rows total!
SELECT a.AccountID, a.AccountNumber, a.CashBalance
FROM Accounts a
WHERE a.CashBalance > 500000.00
  AND a.AccountID NOT IN (
      SELECT lt.AccountID 
      FROM LedgerTransactions lt
      WHERE lt.TransactionType = 'WITHDRAWAL'
        AND lt.Amount > 100000.00
        AND lt.AccountID IS NOT NULL -- Mandatory NULL guard!
  );
Critical Interview Trap: If a subquery used with NOT IN returns a NULL, the condition evaluates to UNKNOWN for all outer rows, causing the entire query to return 0 rows! Always prefer NOT EXISTS.
Exercise 1.6: Probabilistic Counting on Multi-Billion Row Settlement Logs
Medium
Context: Table AuditLogs (LogID, ChangedBy, RecordID, LoggedAt)

Requirement: Write a query comparing the execution time and cardinality output of COUNT(DISTINCT ChangedBy) versus APPROX_COUNT_DISTINCT(ChangedBy) across the audit table. Explain the internal HyperLogLog algorithm.

💡 View Solution & Explanation ▼ 
-- Compare exact vs approximate aggregation
SELECT 
    COUNT(DISTINCT ChangedBy) AS ExactUniqueUsers,
    APPROX_COUNT_DISTINCT(ChangedBy) AS ApproxUniqueUsers,
    ABS(COUNT(DISTINCT ChangedBy) - APPROX_COUNT_DISTINCT(ChangedBy)) * 100.0 / 
        NULLIF(COUNT(DISTINCT ChangedBy), 0) AS ErrorPercentage
FROM AuditLogs;
Internal Mechanics: COUNT(DISTINCT) requires sorting or hashing every single distinct value into TempDB memory worktables. APPROX_COUNT_DISTINCT uses HyperLogLog (HLL) hashing: it hashes values into 64-bit binaries and tracks the maximum number of leading zeros in buckets. It guarantees within 2% of actual cardinality using only ~1.5 KB of fixed memory!
Exercise 1.7: Instant Table Tamper Detection with CHECKSUM_AGG
Hard
Context: Securities (SecurityID, Ticker, IsActive, LotSize)

Requirement: Write a query that computes a single 4-byte signature representing the exact state of all active securities. Demonstrate how changing a single lot size alters the checksum without querying the entire table.

💡 View Solution & Explanation ▼ 
-- 1. Compute table state signature
SELECT CHECKSUM_AGG(BINARY_CHECKSUM(SecurityID, Ticker, LotSize, IsActive)) AS TableSignature
FROM Securities
WHERE IsActive = 1;

-- 2. Verification scenario:
-- If an external process modifies a lot size, CHECKSUM_AGG immediately returns a different integer.
-- High-frequency trading engines poll this signature to invalidate local in-memory caches.
Engineering Pattern: BINARY_CHECKSUM computes an XOR/hash of the row attributes, and CHECKSUM_AGG reduces the column of checksums to a single integer. Ideal for cache invalidation protocols.
Exercise 1.8: Atomic Upsert using T-SQL MERGE with OUTPUT Clause
Hard
Context: PortfolioPositions (AccountID, SecurityID, PositionUnits, AverageEntryPrice)

Requirement: When a new fill arrives, upsert the position: if the (AccountID, SecurityID) pair exists, update the units and recalculate weighted average price; if it does not exist, insert it. Output the action taken ($action) and before/after values.

💡 View Solution & Explanation ▼ 
DECLARE @NewAccountID INT = 1001;
DECLARE @NewSecurityID INT = 5001;
DECLARE @FilledQty INT = 500;
DECLARE @FillPrice DECIMAL(18,4) = 185.50;

MERGE PortfolioPositions WITH (HOLDLOCK) AS target
USING (SELECT @NewAccountID AS AccountID, @NewSecurityID AS SecurityID) AS source
   ON target.AccountID = source.AccountID 
  AND target.SecurityID = source.SecurityID
WHEN MATCHED THEN
    UPDATE SET 
        target.AverageEntryPrice = 
            ((target.PositionUnits * target.AverageEntryPrice) + (@FilledQty * @FillPrice)) / 
            (target.PositionUnits + @FilledQty),
        target.PositionUnits = target.PositionUnits + @FilledQty,
        target.LastValuationTime = SYSUTCDATETIME()
WHEN NOT MATCHED THEN
    INSERT (AccountID, SecurityID, PositionUnits, AverageEntryPrice, CurrentMarketPrice, LastValuationTime)
    VALUES (source.AccountID, source.SecurityID, @FilledQty, @FillPrice, @FillPrice, SYSUTCDATETIME())
OUTPUT 
    $action AS MergeAction,
    inserted.AccountID,
    inserted.SecurityID,
    deleted.PositionUnits AS OldUnits,
    inserted.PositionUnits AS NewUnits,
    inserted.AverageEntryPrice AS NewAvgPrice;
Concurrency Warning: Always include WITH (HOLDLOCK) on the target of a T-SQL MERGE statement. Without HOLDLOCK, concurrent transactions can experience race conditions leading to PRIMARY KEY / UNIQUE constraint violations!

📋 How to Answer This in an Interview

Interviewer Question: "Explain the Logical Query Processing Order in SQL Server and why it matters."

Staff Engineer Response:

"In SQL Server, queries do not execute in the syntactic order they are written (SELECT-FROM-WHERE). Instead, logical processing follows an 11-step sequence: FROM and ON first evaluate tables and joins, followed by WHERE which filters atomic rows before any grouping. GROUP BY then partitions the surviving rows into buckets, optional super-aggregates like ROLLUP or CUBE generate subtotals, and HAVING filters those aggregated buckets."

"Only then does the SELECT phase execute, evaluating projected expressions, aliases, and window function calculations. Finally, DISTINCT deduplicates the stream, ORDER BY sorts the rows, and TOP or OFFSET-FETCH truncates the result set."

"Understanding this sequence is critical for two reasons: First, it explains syntax boundaries—such as why column aliases created in SELECT cannot be referenced in WHERE or HAVING, but are valid in ORDER BY. Second, it dictates optimization: filtering rows early in WHERE before the GROUP BY phase significantly minimizes working memory grants and TempDB spilling compared to filtering post-aggregation in HAVING."
