01 · T-SQL Fundamentals, DDL, DML & All Aggregate Functions

The Ground-Zero Architectural Foundation: DDL vs DML Internals, TRUNCATE vs DELETE Page Mechanics, The 11 Phases of Logical Query Processing, 3-Valued Boolean Logic, SARGability, and All Aggregate Functions.

1. Ground-Zero Architectural Taxonomy: DDL, DML, DCL, TCL

The Pain Point: Why Is SQL Categorized Into Sub-Languages?

In standard programming languages like Java or Python, you write code that manages memory variables. In database engineering, code operates at different privilege levels and storage boundaries. SQL is divided into four distinct sub-languages, each operating with different transaction log footprints and database lock granularities:

1. DDL (Data Definition Language)

Commands: CREATE, ALTER, DROP, TRUNCATE, RENAME

What it does: Defines and modifies the schema structure and metadata in the database catalog (e.g. creating tables, adding columns, building indexes). DDL operations acquire heavy Schema Modification (Sch-M) Locks, blocking all concurrent reads and writes.

2. DML (Data Manipulation Language)

Commands: SELECT, INSERT, UPDATE, DELETE, MERGE

What it does: Queries and modifies the data rows stored inside existing schema structures. Operates with row/page/key locks, modifying 8 KB data pages in the buffer cache and writing to the Transaction Log.

3. TCL (Transaction Control Language)

Commands: BEGIN TRANSACTION, COMMIT, ROLLBACK, SAVEPOINT

What it does: Manages the boundary of ACID atomicity. Enforces whether an entire batch of modifications becomes permanent or rolls back completely.

4. DCL (Data Control Language)

Commands: GRANT, REVOKE, DENY

What it does: Security permissions. Dictates which database users or application roles can execute procedures or access tables.

The Classic Engineering Showdown: TRUNCATE vs DELETE

Both commands remove data from a table, but their physical mechanics inside the SQL Server storage engine are completely opposite. Choosing the wrong one in production can freeze a live financial system.

Architectural Attribute DELETE FROM TableName TRUNCATE TABLE TableName
Classification DML (Data Manipulation Language) DDL (Data Definition Language)
How it Works Under the Hood Row-by-Row: Traverses the B-tree, marks each row as deleted, updates index pointers, and records every single deleted row payload into the Transaction Log (LDF). Page Deallocation: Does not read individual rows! It simply updates the Index Allocation Map (IAM) tracking pages, marking entire 8 KB data pages and 64 KB extents as "free".
Transaction Log Impact Massive Log Generation: Deleting 10,000,000 rows generates gigabytes of transaction log records, risking disk exhaustion. Minimal Log Generation: Logs only the deallocation of extents (a few kilobytes total!).
Identity Value Reset Does not reset IDENTITY(1,1) counters. The next insert continues from the highest historical value. Resets the IDENTITY seed back to its original baseline definition (e.g. 1).
WHERE Clause Filtering Supported (e.g. WHERE OrderStatus = 'CANCELLED'). Not supported! It is strictly an all-or-nothing wipe of the entire table.
Trigger Execution Fires AFTER DELETE and INSTEAD OF DELETE triggers for each affected batch. Bypasses and does NOT fire triggers!
Foreign Key Restrictions Can execute if child tables contain no matching rows. Forbidden! Will fail immediately if the table is referenced by ANY foreign key constraint in another table, even if the child table is 100% empty!
Can it be Rolled Back? YES! Fully logged, rolls back cleanly. YES! (Common Interview Myth Debunked: TRUNCATE can be rolled back if executed inside an explicit BEGIN TRANSACTION!).

2. The 11 Phases of Logical Query Processing: What Really Happens Under the Hood

When you write a SQL query, you write it in lexical syntax order:

SELECT → FROM → JOIN → WHERE → GROUP BY → HAVING → ORDER BY

However, SQL is a declarative relational language based on set theory and relational calculus. The SQL Server query optimizer executes clauses in a strict mathematical sequence that differs fundamentally from lexical order. Each phase takes one or more virtual tables as input and emits a new virtual table as output.

flowchart TD Step1["Phase 1: FROM (Evaluate tables & Cartesian cross-products)"] --> Step2["Phase 2: ON (Filter join predicates)"] Step2 --> Step3["Phase 3: JOIN (Generate joined virtual table VT1)"] Step3 --> Step4["Phase 4: WHERE (Filter atomic rows before aggregation VT2)"] Step4 --> Step5["Phase 5: GROUP BY (Partition rows into group buckets VT3)"] Step5 --> Step6["Phase 6: WITH CUBE / ROLLUP (Generate multi-dimensional super-aggregates VT4)"] Step6 --> Step7["Phase 7: HAVING (Filter aggregated group buckets VT5)"] Step7 --> Step8["Phase 8: SELECT (Evaluate expressions, aliases & window functions VT6)"] Step8 --> Step9["Phase 9: DISTINCT (Deduplicate duplicate rows VT7)"] Step9 --> Step10["Phase 10: ORDER BY (Sort result set cursor VT8)"] Step10 --> Step11["Phase 11: TOP / OFFSET...FETCH (Paginate & truncate rows VT9)"]

Detailed Phase-by-Phase Execution Walkthrough:

Phase 1 to 3: FROM → ON → JOIN

The query engine identifies the source tables. If multiple tables are specified, a Cartesian product is logically generated, and the ON clause filters out rows that do not satisfy the join predicate. For outer joins (LEFT/RIGHT/FULL), unmatched preserved rows are added back with NULLs, emitting Virtual Table 1 (VT1).

Phase 4: WHERE

Filters individual rows from VT1 based on the predicate expression. Critical Principle: Rows are filtered before any grouping or aggregation occurs. This minimizes the data volume that must be held in working memory for the next phase.

Phase 5 & 6: GROUP BY & Multi-Dimensional Super-Aggregates (ROLLUP/CUBE)

Organizes the surviving rows into discrete buckets based on the grouping keys. If WITH ROLLUP or GROUPING SETS is specified, additional subtotal and grand-total rows are generated.

Phase 7: HAVING

Filters the aggregated buckets produced by Phase 5. Only groups that satisfy the aggregate condition (e.g. HAVING COUNT(*) > 10) are passed to the next phase.

Phase 8: SELECT

This is where the query projections, mathematical calculations, string manipulations, and Window Functions are finally evaluated! Column aliases (e.g. AS NetTotal) are born here.

Why you cannot use a SELECT alias in WHERE or HAVING: Because WHERE (Phase 4) and HAVING (Phase 7) execute long before SELECT (Phase 8). The alias does not exist yet!

Phase 9 to 11: DISTINCT → ORDER BY → TOP / OFFSET-FETCH

DISTINCT eliminates duplicate projected rows. Next, ORDER BY sorts the stream (which is why you can reference SELECT aliases in ORDER BY, because Phase 10 runs after Phase 8!). Finally, TOP or OFFSET...FETCH truncates the stream for client pagination.

3. Three-Valued Boolean Logic (3VL) & NULL Mechanics

What is NULL in Relational Theory?

In standard programming languages, a variable is either true or false. In SQL relational algebra (invented by E.F. Codd), NULL is not a value. It is not zero (0), not an empty string (''), and not a space. NULL represents the absence of a value—an unknown, unrecorded, or inapplicable state.

Because NULL represents the unknown, any equality or mathematical comparison with NULL cannot be proven true or false. It evaluates to a third truth state: UNKNOWN.

Boolean Expression Evaluation Result Why?
100 = NULL UNKNOWN Is 100 equal to an unknown value? We cannot know.
NULL = NULL UNKNOWN Are two unknown values equal to each other? They could be anything!
NULL <> NULL UNKNOWN Are two unknown values different? We cannot know.
TRUE AND UNKNOWN UNKNOWN If one half of an AND is unknown, the total result is unknown.
FALSE AND UNKNOWN FALSE Because one half is definitively FALSE, the AND condition is definitively FALSE!
TRUE OR UNKNOWN TRUE Because one half is definitively TRUE, the OR condition is definitively TRUE!
NOT (UNKNOWN) UNKNOWN The inverse of unknown is still unknown.

⚠️ The WHERE Clause Filter Rule for UNKNOWN

A WHERE clause only admits rows where the predicate evaluates to strictly TRUE. If an expression evaluates to FALSE or UNKNOWN, the row is discarded!

This is why writing: WHERE LimitPrice = NULL or WHERE LimitPrice <> 100 filters out every row where LimitPrice is NULL! You must strictly use the predicate: WHERE LimitPrice IS NULL or WHERE LimitPrice IS NOT NULL.

ISNULL() vs COALESCE(): The Deep Architectural Differences

Feature ISNULL(check_expr, replacement) COALESCE(expr1, expr2, ... exprN)
Standard Compliance Proprietary Microsoft T-SQL function. ANSI SQL Standard compliant.
Arguments Allowed Strictly exactly 2 arguments. Accepts 2 to unlimited arguments (returns the first non-null argument).
Data Type Resolution (The Silent Bug Trap!) Takes the data type and length of the first expression. If expr1 is VARCHAR(3) and replacement is VARCHAR(20), replacement is truncated to 3 characters! Takes the data type with the highest precedence among all expressions according to SQL Server type precedence hierarchy. No silent truncation!
Nullability of Result Always non-nullable if replacement expression is non-null. Can be nullable if all arguments are nullable.
Query Plan Evaluation Evaluates subqueries passed as arguments only once. Internally rewrites to a CASE WHEN expression; subqueries passed as parameters can be evaluated multiple times in older SQL Server builds!

NULLIF(): The Divide-by-Zero Defense Weapon

NULLIF(expression1, expression2) takes two arguments. If expression1 == expression2, it returns NULL; otherwise, it returns expression1.

💡 The Universal Financial Formula Guard:

-- If TotalTrades is 0, standard division throws fatal error 8134 (Divide by zero)!
-- NULLIF converts 0 to NULL. Dividing by NULL safely yields NULL without crashing the batch!
SELECT AccountID, (TotalNotional / NULLIF(TotalTrades, 0)) AS AvgTradeNotional
FROM DailyAccountTradingSummary;

4. String Pattern Matching & The LIKE Operator Masterclass

A. How the LIKE Operator Works Under the Hood

The LIKE operator determines whether a character string matches a specified pattern. Unlike standard equality (=) which checks for identical character matches, LIKE invokes SQL Server's string pattern evaluation engine.

Wildcard Character Matching Meaning Production Example Matches
% (Percent) Any string of zero or more characters. WHERE Ticker LIKE 'A%' 'A', 'AAPL', 'AMZN'
_ (Underscore) Strictly exactly one single character. WHERE CurrencyCode LIKE 'US_' 'USD', 'USX' (Does NOT match 'USDT')
[ ] (Brackets) Any single character within the specified character set or range. WHERE AccountNumber LIKE 'ACC-[0-9]%' 'ACC-101', 'ACC-882' (Does NOT match 'ACC-ABC')
[^ ] (Caret in Brackets) Any single character NOT within the specified character set. WHERE Tag LIKE '[^0-9]%' Any string that does NOT start with a number.

B. Escaping Wildcard Characters (The ESCAPE Clause)

What if your data actually contains literal percent signs or underscores (e.g. searching for a discount tag '10%_OFF')? If you write LIKE '%10%_OFF%', the percent and underscore are interpreted as wildcards!

The Solution: The ESCAPE Clause:

-- Declare '!' as the escape character:
SELECT ReferenceNote
FROM LedgerTransactions
WHERE ReferenceNote LIKE '%10!%__OFF%' ESCAPE '!';

C. The SARGability of LIKE: Index Seek vs Table Scan

✅ SARGable: Prefix Search (Index Seek)

WHERE ClientName LIKE 'Blackstone%';

Because the start of the string is fixed, the engine navigates down the B-tree to the 'B' range and performs an Index Seek!

🚫 Non-SARGable: Infix / Suffix Search (Full Table Scan)

WHERE ClientName LIKE '%Management';

Because the string starts with a wildcard, the B-tree cannot be navigated alphabetically. The engine must scan every page in the table!

🛡️ TRY_CAST() and TRY_CONVERT(): Immunity from Runtime Crashes

If an incoming CSV feed contains an invalid date like '2024-02-31' (February 31st), standard CONVERT() or CAST() throws a fatal runtime exception and halts the entire 1,000,000-row batch!

The Solution: Use TRY_CONVERT(). If the string is invalid, it returns NULL instead of crashing, allowing you to filter out bad rows cleanly:

-- Prevents batch aborts on corrupted incoming feeds:
SELECT RawDateString, TRY_CONVERT(DATE, RawDateString, 120) AS CleanDate
FROM IncomingTradeFeed
WHERE TRY_CONVERT(DATE, RawDateString, 120) IS NOT NULL;

E. Global Time Zone Conversions: AT TIME ZONE

Financial transactions are stored in UTC, but regional trading desks need to view orders in their local market time. SQL Server provides the AT TIME ZONE clause to handle time zones and daylight savings automatically:

-- Convert UTC Execution Timestamp to US Eastern and London Time:
SELECT 
    ExecutionID,
    ExecutedAt AS UTCTime,
    ExecutedAt AT TIME ZONE 'UTC' AT TIME ZONE 'Eastern Standard Time' AS WallStreetTime,
    ExecutedAt AT TIME ZONE 'UTC' AT TIME ZONE 'GMT Standard Time' AS LondonTime,
    ExecutedAt AT TIME ZONE 'UTC' AT TIME ZONE 'India Standard Time' AS MumbaiTime
FROM Executions;

6. Deep Dive: All SQL Server Aggregate Functions Explained from First Principles

An Aggregate Function performs a calculation across a set of values in a column and collapses them into a single scalar value. In relational theory, aggregate functions ignore NULL values in their calculations (with the single exception of COUNT(*)).

A. The COUNT Family: COUNT(*) vs COUNT(col) vs COUNT(DISTINCT) vs COUNT_BIG

Function What It Evaluates NULL Behavior Engine Optimization & Memory Cost
COUNT(*) Total number of rows in the table or group. Counts NULLs! Even if every column in a row is NULL, the row is counted. Zero Memory Grant: The optimizer picks the narrowest non-clustered index on the table to count leaf pages rapidly without reading the clustered index!
COUNT(col) Number of non-null occurrences in that specific column. Ignores NULLs. Rows where col IS NULL are excluded. Must scan the specific column's B-tree pages to verify non-null values.
COUNT(DISTINCT col) Number of unique, non-null values. Ignores NULLs. High Memory Grant: Forces SQL Server to sort or hash all values into a TempDB worktable to eliminate duplicates.
COUNT_BIG(*) Total row count returning a 64-bit BIGINT. Counts NULLs. Mandatory when tables exceed 2,147,483,647 rows (which throws integer overflow on COUNT(*)), and strictly required when creating Indexed Views.

B. SUM() and AVG(): Integer Truncation & Overflow Traps

☠️ Trap 1: Integer Division Truncation in AVG()

Suppose you have order quantities 5 and 4. What is AVG(Quantity) if Quantity is an INT?

In T-SQL, (5 + 4) / 2 = 4, NOT 4.5! T-SQL performs integer division and truncates the decimal portion silently!

The Fix: Always cast integer arguments to float or decimal: AVG(CAST(Quantity AS DECIMAL(18,4))).

⚠️ Trap 2: Arithmetic Overflow in SUM()

If you run SUM(Quantity) on a table with 50 million trades where Quantity is stored as INT, the sum will quickly exceed the maximum 32-bit signed integer value ($2,147,483,647$), triggering fatal Error 8115: Arithmetic overflow error converting expression to data type int.

The Fix: Cast the column to BIGINT inside the aggregate: SUM(CAST(Quantity AS BIGINT)).

C. Statistical Aggregates: STDEV, STDEVP, VAR, VARP

Financial risk modeling and quantitative trading rely on variance and standard deviation to compute volatility and Sharpe ratios:

  • STDEV(col): Computes the Sample Standard Deviation using $N-1$ degrees of freedom ($\sqrt{\frac{\sum (x - \bar{x})^2}{N - 1}}$). Use this when calculating volatility from a sample of trade ticks.
  • STDEVP(col): Computes the Population Standard Deviation using $N$ ($\sqrt{\frac{\sum (x - \bar{x})^2}{N}}$). Use this when evaluating the entire population of records.
  • VAR(col) / VARP(col): Computes statistical Sample Variance vs Population Variance.

D. Advanced Modern Aggregates (SQL Server 2017+)

1. STRING_AGG(expression, separator) WITHIN GROUP (ORDER BY ...)

Prior to SQL Server 2017, concatenating row values into a single delimited string required the infamous FOR XML PATH('') black-magic hack. STRING_AGG replaces this with a clean ANSI-compliant aggregate function.

-- Produces: "AAPL, MSFT, NVDA" sorted alphabetically:
SELECT 
    AccountID,
    STRING_AGG(Ticker, ', ') WITHIN GROUP (ORDER BY Ticker ASC) AS PortfolioTickers
FROM PortfolioPositions p
INNER JOIN Securities s ON p.SecurityID = s.SecurityID
GROUP BY AccountID;

2. CHECKSUM_AGG(column)

Computes an integer hash checksum across an entire column. Ideal for high-speed cache invalidation: an in-memory trading engine calculates CHECKSUM_AGG(BINARY_CHECKSUM(*)) on a reference table. If the returned integer changes, the engine knows data was modified and refreshes its cache, without scanning millions of rows!

3. APPROX_COUNT_DISTINCT(column)

Standard COUNT(DISTINCT col) on a table with 500,000,000 rows requires gigabytes of memory to sort and deduplicate distinct values, often spilling to TempDB. APPROX_COUNT_DISTINCT utilizes the HyperLogLog (HLL) probabilistic algorithm: it hashes column values into 64-bit binaries and tracks leading zero patterns across internal registers.

  • Memory Footprint: Consumes only ~1.5 KB of fixed memory regardless of table size!
  • Accuracy Guarantee: Provides 97% accuracy within a 2% standard error rate.
  • Speedup: Up to 50x faster than COUNT(DISTINCT) for multi-billion row tables.

E. Multi-Dimensional Super-Aggregates: ROLLUP, CUBE & GROUPING SETS

In business intelligence, management requests reports with subtotals across multiple dimensions. The naive approach is writing 4 separate queries and stitching them together with UNION ALL, scanning the table 4 times. SQL Server super-aggregates do this in a single scan:

Super-Aggregate Combinations Generated Best Suited For
GROUP BY ROLLUP (A, B) Hierarchical subtotals: (A, B), (A), and Grand Total (). Hierarchical data: Year → Quarter → Month, or Sector → Industry.
GROUP BY CUBE (A, B) All $2^N$ combinations: (A, B), (A), (B), and Grand Total (). Cross-dimensional OLAP analysis (Sector vs AssetClass).
GROUPING SETS (...) Strictly the custom grouping combinations you explicitly declare. Precise customized reporting layouts.
GROUPING_ID(A, B) Returns a bitmask integer (0, 1, 2, 3) indicating which columns are aggregated into subtotals. Distinguishing real NULL values in data from subtotal summary NULL rows.

7. SARGability (Search Argument Able) Internals

What is SARGability & Why Does It Dictate 90% of Performance?

A query predicate is SARGable if the SQL Server Query Optimizer can utilize an Index Seek down the B-Tree index to pinpoint matching rows directly, instead of scanning every single 8 KB data page in the entire table.

flowchart TD Predicate["Query Predicate (WHERE clause)"] --> Check{"Is Predicate SARGable?"} Check -- Yes --> Seek["Index Seek (B-Tree traversal)
Touches 3-4 pages in 0.5ms!"] Check -- No --> Scan["Table / Clustered Index Scan
Reads 5,000,000 pages from disk in 15 seconds!"]

The 3 Universal SARGability Violations (Anti-Patterns):

Violation 1: Wrapping Indexed Columns in Mathematical or String Functions

-- 🚫 NON-SARGABLE (Forces Full Table Scan):
-- The engine cannot predict the output of YEAR() without evaluating it for every single row!
SELECT OrderID FROM Orders WHERE YEAR(OrderTime) = 2024;

-- ✅ SARGABLE REFACTOR (Enables B-Tree Index Seek):
SELECT OrderID FROM Orders 
WHERE OrderTime >= '2024-01-01 00:00:00' AND OrderTime < '2025-01-01 00:00:00';

Violation 2: Implicit Data Type Conversions

-- If AccountNumber is VARCHAR(20) in the table, but the query passes NVARCHAR:
-- SQL Server type precedence rules dictate that VARCHAR must convert to NVARCHAR!
-- The engine rewrites the query internally to: WHERE CONVERT(NVARCHAR(20), AccountNumber) = N'ACC-1001'
-- This function wrapper completely disables the Index Seek!
SELECT AccountID FROM Accounts WHERE AccountNumber = N'ACC-1001'; -- 🚫

-- ✅ Ensure data types match strictly:
SELECT AccountID FROM Accounts WHERE AccountNumber = 'ACC-1001'; -- ✅ Index Seek!

Violation 3: Leading Wildcards in LIKE Predicates

-- 🚫 NON-SARGABLE: Leading wildcard requires scanning every string
SELECT ClientID FROM Clients WHERE ClientName LIKE '%Capital';

-- ✅ SARGABLE: Trailing wildcard seeks down the B-Tree alphabetically
SELECT ClientID FROM Clients WHERE ClientName LIKE 'Capital%';

8. 📋 How to Master This in an Interview

Interviewer Question: "Explain the Logical Query Processing Order in SQL Server and why it matters."

Staff Engineer Model Response:

"In SQL Server, queries do not execute in the syntactic order they are written (SELECT-FROM-WHERE). Instead, logical processing follows an 11-step sequence: FROM and ON first evaluate tables and joins, followed by WHERE which filters atomic rows before any grouping. GROUP BY then partitions the surviving rows into buckets, optional super-aggregates like ROLLUP or CUBE generate subtotals, and HAVING filters those aggregated buckets.

Only then does the SELECT phase execute, evaluating projected expressions, aliases, and window function calculations. Finally, DISTINCT deduplicates the stream, ORDER BY sorts the rows, and TOP or OFFSET-FETCH truncates the result set.

Understanding this sequence is critical for two reasons: First, it explains syntax boundaries—such as why column aliases created in SELECT cannot be referenced in WHERE or HAVING, but are valid in ORDER BY. Second, it dictates optimization: filtering rows early in WHERE before the GROUP BY phase significantly minimizes working memory grants and TempDB spilling compared to filtering post-aggregation in HAVING."

🎯 The Interviewer Grill Round (Trap Follow-Ups)

  • Trap: "Can TRUNCATE be rolled back inside an explicit transaction?"
    Answer: "Yes! Contrary to popular myth, TRUNCATE TABLE is a fully transaction-safe DDL command. If executed inside BEGIN TRANSACTION ... ROLLBACK TRANSACTION, the page deallocations recorded in the log are rolled back, and all data is completely restored."
  • Trap: "What is the difference between ISNULL and COALESCE regarding data type resolution?"
    Answer: "ISNULL strictly adopts the data type and length of the first argument. If the first argument is VARCHAR(3) and the replacement is VARCHAR(20), ISNULL truncates the replacement to 3 characters! COALESCE follows standard SQL Server data type precedence rules, taking the type with highest precedence among all arguments without truncation."
  • Trap: "Why does COUNT(*) execute faster than COUNT(ColumnName)?"
    Answer: "Because COUNT(*) counts rows, not column values. The SQL Server query optimizer can satisfy COUNT(*) by reading the leaf pages of the smallest, narrowest non-clustered index on the table, minimizing logical I/O reads. COUNT(ColumnName) must evaluate non-null values specifically in that column, which may require scanning larger indexes or the clustered index."
