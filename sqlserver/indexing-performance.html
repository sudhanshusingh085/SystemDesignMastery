06 · Indexing Internals, Execution Plans & Performance Tuning

B-Tree Page Mechanics, Clustered vs Non-Clustered Indexes, Covering Indexes with INCLUDE, Eliminating Key Lookups, Filtered Indexes, and DMV Deep Dives.

1. Physical B-Tree Architecture

SQL Server stores data in 8 KB pages. An index is structured as a balanced B-Tree (B+ Tree in relational terminology), organizing data pages into Root, Intermediate, and Leaf levels.

flowchart TD Root["Root Page (8 KB)
Pointers to intermediate range keys"] --> Int1["Intermediate Page A"] Root --> Int2["Intermediate Page B"] Int1 --> Leaf1["Leaf Page 1"] Int1 --> Leaf2["Leaf Page 2"] Int2 --> Leaf3["Leaf Page 3"] Int2 --> Leaf4["Leaf Page 4"]

Clustered Index

  • The Leaf Level IS the physical table data! The table rows are stored in the sorted order of the clustered index key.
  • A table can have only one clustered index because physical rows can only be sorted in one order.
  • Best clustered keys are: Unique, Narrow, Static, and Ever-Increasing (e.g. BIGINT IDENTITY).

Non-Clustered Index

  • The Leaf Level contains index key columns + a Row Locator.
  • If table has a Clustered Index, Row Locator = Clustered Key.
  • If table is a Heap (no clustered index), Row Locator = RID (File:Page:Slot).
  • A table can have up to 999 non-clustered indexes.

Heaps vs Clustered Tables: The Forwarded Records Disaster

A table without a clustered index is called a Heap. Rows are stored in no particular physical order, and rows are identified by an internal 8-byte RID (Row Identifier: FileNumber : PageNumber : SlotNumber).

☠️ The Forwarded Records Performance Killer

In a Heap, when a row contains variable-length columns (like VARCHAR) and an UPDATE expands the size of that row so it no longer fits on its current 8 KB data page, SQL Server cannot shift rows because the external RIDs would break. Instead, it moves the expanded row to a completely different page, leaving a Forwarding Pointer at the original slot!

The Consequence: Every subsequent query that reads that row must perform two separate page I/O reads (first to the forwarding pointer, then following the pointer to the real page). Over time, a heap accumulates millions of forwarded records, doubling disk I/O and destroying query performance!

The Fix: Convert the heap to a clustered table by creating a Clustered Index, or rebuild the heap using ALTER TABLE TableName REBUILD.

Clustered Index Key Selection: Ever-Increasing Identity vs Random GUID (NEWID)

Choosing the clustered index key is the single most critical physical design decision in SQL Server. An ideal clustered key must be Unique, Narrow, Static, and Ever-Increasing.

Key Strategy Insert Mechanics Page Split Frequency Index Fragmentation & Buffer Pool Impact
Ever-Increasing (BIGINT IDENTITY or NEWSEQUENTIALID) New rows are always appended strictly to the rightmost leaf page (the end of the B-tree). 0% Page Splits! Once a page fills to 8 KB, a new empty page is allocated at the end. 0% Fragmentation: Pages remain 100% full. Maximum cache density in RAM.
Random GUID (NEWID()) New rows are injected randomly into the middle of existing full pages throughout the B-tree. 50% Page Splits on every insert! SQL Server must split the full page, allocate a new page, and move 50% of the rows to make space. Severe Fragmentation: Pages are half-empty (50% air). Table occupies double the disk and RAM memory buffer cache!

2. Covering Indexes & The INCLUDE Clause

When a query references columns not present in a Non-Clustered Index, the engine must perform a Key Lookup (or Bookmark Lookup) back into the Clustered Index for every matching row.

The Tipping Point & The Key Lookup Cliff

If a query returns more than ~1-3% of total table rows, the cumulative cost of performing thousands of random I/O Key Lookups exceeds the cost of a full table scan. The optimizer will abandon your non-clustered index and execute a Clustered Index Scan!

The Solution: Covering Index via INCLUDE

-- Non-covering: Forces Key Lookup to fetch FillPrice and ExecutedAt
CREATE NONCLUSTERED INDEX IX_Executions_Order 
ON Executions (OrderID);

-- 100% COVERING INDEX: Eliminates Key Lookups completely!
CREATE NONCLUSTERED INDEX IX_Executions_Order_Covering
ON Executions (OrderID)
INCLUDE (FillPrice, FillQuantity, ExecutedAt);

Why INCLUDE is better than adding columns to the index key: Columns in the INCLUDE clause are stored strictly at the leaf level. They do not increase the size of intermediate B-tree index pages, preserving a high fan-out and shallow tree depth.

3. Reading Execution Plans: Key Operators & Warnings

Operator Severity What it Means in Production
Index Seek Optimal Navigates down the B-tree using SARGable predicates. Touches only relevant pages.
Clustered Index Scan Warning Reads every single page in the entire table from beginning to end.
Key Lookup Costly Random I/O lookups to retrieve non-indexed columns. Eliminate with INCLUDE.
Sort / Hash Spill (Yellow Warning ⚠️) Critical Memory Grant was too small; query ran out of RAM and spilled intermediate data onto TempDB disk! Fix statistics or memory grant.

4. Statistics & Cardinality Estimation: The Brain of the Optimizer

A. How the Optimizer Guesses Row Counts

The Cost-Based Optimizer (CBO) never reads raw table rows during query compilation; doing so would be too slow. Instead, it inspects Statistics Objects to predict how many rows will match a query predicate. This predicted row count is the Cardinality Estimate.

If the estimate is accurate, the optimizer chooses the perfect join algorithm and memory grant. If the estimate is wrong by orders of magnitude (e.g. expects 1 row, but receives 1,000,000), it generates catastrophic execution plans that spill to TempDB!

B. The 3 Components of a Statistics Object

  • Header: Metadata including the last time statistics were updated, total rows in the table, and sample rate.
  • Density Vector: Measures the uniqueness/unpopularity of column values ($Density = \frac{1}{\text{Distinct Values}}$). Used for equality predicates when values are unknown at compile time (like in stored procedures).
  • Histogram: Samples column data into up to 200 distinct steps (buckets), storing range boundary values (RANGE_HI_KEY), exact equal row counts (EQ_ROWS), and rows between steps (RANGE_ROWS).

⚠️ Stale Statistics & Auto-Update Thresholds

Historically, SQL Server automatically updated statistics only after 20% + 500 rows were modified. On a 100,000,000-row table, that required 20,000,500 modifications before statistics auto-updated! In modern SQL Server, a dynamic threshold ($\sqrt{1000 \times rows}$) updates statistics much more frequently.

DBA Command: To inspect a table's actual histogram steps live:

DBCC SHOW_STATISTICS ('Orders', 'IX_Orders_Account_OrderTime');

5. Query Store: The "Flight Data Recorder" of SQL Server

Before Query Store (introduced in SQL Server 2016), when a query suddenly ran slow due to an execution plan change (plan regression), diagnosing it required digging through transient DMVs or capturing heavy Profiler traces. Once the server restarted or plan cache was cleared, all diagnostic data was lost.

Query Store automatically and continuously captures a historical flight log of all queries, their compiled execution plan XMLs, runtime execution telemetry (CPU, duration, logical reads), and wait statistics, persisting them directly inside the database!

flowchart LR Exec["Query Executes"] --> Capture["Query Store In-Memory Ring Buffer"] Capture --> AsyncFlush["Asynchronous Disk Flush
(Persisted inside user database)"] AsyncFlush --> Analytics["Historical Plan Comparison & Plan Forcing"]

The Superpower: Plan Forcing via T-SQL

If a bad execution plan causes an emergency outage, a senior engineer can use Query Store to instantly force the known-good plan in 1 second without touching application code or recompiling stored procedures!

-- Instantly force Plan ID 44 for Query ID 128 to resolve a live production outage:
EXEC sp_query_store_force_plan @query_id = 128, @plan_id = 44;

-- Unforce plan once index or code fix is permanently deployed:
EXEC sp_query_store_unforce_plan @query_id = 128, @plan_id = 44;

Exercise 6.1: Designing a Covering Index to Eliminate a Critical Key Lookup
Easy
Context: Querying order fills: SELECT OrderID, FillQuantity, FillPrice FROM Executions WHERE OrderID = 100001;

Requirement: Inspect the current index on Executions(OrderID). Write the exact DDL to replace it with a 100% covering index with optimal key ordering and leaf-level columns.

💡 View Solution & Explanation ▼ 
-- Drop existing underperforming index
DROP INDEX IF EXISTS IX_Executions_OrderID ON Executions;

-- Create optimal covering index with leaf-level INCLUDE columns
CREATE NONCLUSTERED INDEX IX_Executions_OrderID_Covering
ON Executions (OrderID)
INCLUDE (FillQuantity, FillPrice, ExecutedAt)
WITH (FILLFACTOR = 90, ONLINE = ON);
Why ONLINE = ON: In production 24/7 trading systems, creating an index with ONLINE = ON keeps the underlying table accessible for concurrent SELECT, INSERT, and UPDATE queries without taking an exclusive table lock.
Exercise 6.2: Filtered Index for High-Volume Status Skew
Medium
Context: 99% of Orders are 'FILLED' (50M rows), 1% are 'PENDING' (50k rows).

Requirement: Order-matching engines frequently query WHERE OrderStatus = 'PENDING'. Creating a full index on OrderStatus wastes gigabytes of RAM. Create a Filtered Index that indexes strictly the pending orders.

💡 View Solution & Explanation ▼ 
CREATE NONCLUSTERED INDEX FIX_Orders_Pending
ON Orders (SecurityID, OrderTime)
INCLUDE (Quantity, LimitPrice, AccountID)
WHERE OrderStatus = 'PENDING';
Dramatic Benefits: This filtered index is 99% smaller than a full index, occupies only a few megabytes in the buffer pool, and costs zero maintenance when historical 'FILLED' records are queried or updated.
Exercise 6.3: Composite Index Column Ordering Rule (Equality Before Inequality)
Medium
Context: Query: WHERE AccountID = 1001 AND OrderTime >= '2024-01-01'

Requirement: Evaluate two proposed composite indexes: (A) (OrderTime, AccountID) vs (B) (AccountID, OrderTime). Explain why only one enables a true B-Tree Seek across both predicates.

💡 View Solution & Explanation ▼ 
-- Optimal Composite Index:
CREATE NONCLUSTERED INDEX IX_Orders_Account_OrderTime
ON Orders (AccountID, OrderTime)
INCLUDE (Quantity, LimitPrice);
The Golden Rule of Index Column Ordering: Always place Equality columns first, followed by Range/Inequality columns. If OrderTime were first, the engine would seek to the date boundary and then be forced to scan all accounts within that date range. With AccountID first, it seeks directly to Account 1001 and then scans only that account's specific date slice!
Exercise 6.4: Uncovering Missing Indexes via DMVs
Medium
Context: Production database health audit

Requirement: Write a DMV query joining sys.dm_db_missing_index_details, sys.dm_db_missing_index_groups, and sys.dm_db_missing_index_group_stats to identify the top 5 highest-impact missing indexes across the database.

💡 View Solution & Explanation ▼ 
SELECT TOP (5)
    CAST(s.avg_total_user_cost * s.avg_user_impact * (s.user_seeks + s.user_scans) AS BIGINT) AS ImprovementScore,
    d.statement AS TableName,
    d.equality_columns AS EqualityCols,
    d.inequality_columns AS InequalityCols,
    d.included_columns AS IncludedCols,
    s.user_seeks,
    s.last_user_seek
FROM sys.dm_db_missing_index_group_stats s
INNER JOIN sys.dm_db_missing_index_groups g ON s.group_handle = g.index_group_handle
INNER JOIN sys.dm_db_missing_index_details d ON g.index_handle = d.index_handle
ORDER BY ImprovementScore DESC;
DMV Metric: ImprovementScore calculates the aggregate estimated query cost reduction multiplied by execution frequency. It isolates indexes that will provide immediate system-wide relief.
Exercise 6.5: Detecting Unused and Write-Heavy Indexes
Medium
Context: Indexes slow down INSERT, UPDATE, and DELETE operations.

Requirement: Query sys.dm_db_index_usage_stats to find indexes where maintenance writes (user_updates) vastly exceed user reads (user_seeks + user_scans).

💡 View Solution & Explanation ▼ 
SELECT 
    OBJECT_NAME(i.object_id) AS TableName,
    i.name AS IndexName,
    u.user_updates AS TotalWrites,
    (u.user_seeks + u.user_scans + u.user_lookups) AS TotalReads,
    (u.user_updates - (u.user_seeks + u.user_scans + u.user_lookups)) AS WritePenaltyScore
FROM sys.indexes i
LEFT JOIN sys.dm_db_index_usage_stats u 
       ON i.object_id = u.object_id 
      AND i.index_id = u.index_id 
      AND u.database_id = DB_ID()
WHERE OBJECTPROPERTY(i.object_id, 'IsUserTable') = 1
  AND i.is_primary_key = 0
  AND i.is_unique = 0
  AND u.user_updates > 50000
  AND (u.user_seeks + u.user_scans + u.user_lookups) = 0
ORDER BY WritePenaltyScore DESC;
Index Bloat Removal: Unused non-clustered indexes on write-intensive tables (like Orders or Executions) waste storage, bloat backups, and introduce insert lock contention. Dropping zero-read indexes yields free write throughput.
Exercise 6.6: Index Fragmentation Analysis & Maintenance (REORGANIZE vs REBUILD)
Medium
Context: Page splits causing logical order fragmentation

Requirement: Write a query against sys.dm_db_index_physical_stats to identify fragmented indexes and dynamically execute either REORGANIZE (if fragmentation is between 10% and 30%) or REBUILD (if > 30%).

💡 View Solution & Explanation ▼ 
SELECT 
    OBJECT_NAME(ips.object_id) AS TableName,
    i.name AS IndexName,
    ips.avg_fragmentation_in_percent,
    ips.page_count,
    CASE 
        WHEN ips.avg_fragmentation_in_percent > 30 THEN 'ALTER INDEX ' + i.name + ' ON ' + OBJECT_NAME(ips.object_id) + ' REBUILD WITH (ONLINE = ON);'
        WHEN ips.avg_fragmentation_in_percent BETWEEN 10 AND 30 THEN 'ALTER INDEX ' + i.name + ' ON ' + OBJECT_NAME(ips.object_id) + ' REORGANIZE;'
        ELSE 'OPTIMAL'
    END AS MaintenanceCommand
FROM sys.dm_db_index_physical_stats(DB_ID(), NULL, NULL, NULL, 'LIMITED') ips
INNER JOIN sys.indexes i ON ips.object_id = i.object_id AND ips.index_id = i.index_id
WHERE ips.page_count > 1000 -- Ignore small tables
ORDER BY ips.avg_fragmentation_in_percent DESC;
REBUILD vs REORGANIZE: REORGANIZE defragments leaf pages in-place and is always an online, non-blocking operation. REBUILD drops and recreates the index B-tree from scratch, updating statistics with a full scan.
Exercise 6.7: Columnstore Index for Aggregating 100 Million Execution Rows
Hard
Context: End-of-quarter risk calculations across 100 million execution records

Requirement: Create a Non-Clustered Columnstore Index on the historical trading table to accelerate analytical aggregation queries (SUM, AVG) while preserving the underlying rowstore clustered index for OLTP transactions.

💡 View Solution & Explanation ▼ 
-- Non-Clustered Columnstore Index on OLTP table
CREATE NONCLUSTERED COLUMNSTORE INDEX NCCI_Executions_Analytics
ON Executions (OrderID, FillQuantity, FillPrice, LiquidityFlag, ExecutionFee, ExecutedAt);

-- Query executed in Batch Mode with 10x-100x speedup:
SELECT 
    LiquidityFlag,
    COUNT(*) AS FillCount,
    SUM(CAST(FillQuantity AS BIGINT)) AS TotalUnits,
    SUM(FillQuantity * FillPrice) AS GrossValue
FROM Executions
GROUP BY LiquidityFlag;
Batch Mode Execution: Columnstore indexes store data column-by-column in compressed 1-million-row rowgroups. Queries process 900 rows per CPU instruction vector (Batch Mode) instead of one row at a time, achieving up to a 100x performance leap on aggregations.
Exercise 6.8: Resolving a Memory Grant / Sort Spill Warning in an Execution Plan
Hard
Context: A complex settlement query triggers a yellow warning icon in SSMS: "Operator used TempDB to spill data during execution with spill level 1".

Requirement: Identify the cause of the spill (stale statistics leading to underestimated cardinality) and demonstrate how updating statistics or using query hints eliminates the TempDB spill.

💡 View Solution & Explanation ▼ 
-- 1. Identify stale statistics
DBCC SHOW_STATISTICS ('Orders', 'IX_Orders_Account_OrderTime');

-- 2. Update statistics with FULLSCAN to fix cardinality histogram
UPDATE STATISTICS Orders IX_Orders_Account_OrderTime WITH FULLSCAN;

-- 3. Alternatively, grant additional memory buffer via query hint:
SELECT o.AccountID, e.FillPrice
FROM Orders o
INNER JOIN Executions e ON o.OrderID = e.OrderID
ORDER BY e.FillPrice DESC
OPTION (MIN_GRANT_PERCENT = 10);
Spill Root Cause: When statistics are out of date, the optimizer underestimates the row count (e.g. expects 100 rows, but receives 1,000,000). The assigned RAM memory grant is insufficient, forcing the engine to spill unsorted pages to physical TempDB disk.

📋 How to Answer This in an Interview

Interviewer Question: "What is a Key Lookup, why is it dangerous for high-throughput systems, and how do you resolve it?"

Staff Engineer Response:

"A Key Lookup occurs when a query uses a Non-Clustered Index to evaluate a filter predicate, but the query's SELECT, JOIN, or WHERE clauses require additional columns that do not exist in that non-clustered index. To retrieve those missing columns, SQL Server must use the row locator (the clustered index key) stored at the leaf level of the non-clustered index to perform a secondary B-Tree seek into the clustered index.

For a single row, a Key Lookup costs less than a millisecond. But in high-throughput systems returning thousands of rows, Key Lookups convert sequential scanning into thousands of random, synchronous I/O page reads. Once the result set exceeds roughly 2-3% of the table's total rows—known as the Tipping Point—the optimizer abandons the index entirely and falls back to an expensive Clustered Index Scan.

The definitive architectural solution is to create a Covering Index using the INCLUDE clause. By appending the required payload columns to INCLUDE, they are stored exclusively at the leaf level of the non-clustered index. The query engine can satisfy the query 100% from the index without touching the clustered index, completely eliminating the Key Lookup."
