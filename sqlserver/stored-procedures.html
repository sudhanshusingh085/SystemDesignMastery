1. Stored Procedures & The Parameter Sniffing Trap

When a Stored Procedure executes for the first time, SQL Server inspects ("sniffs") the parameter values passed in by the caller and compiles an execution plan optimized specifically for that exact value. That compiled plan is cached in memory (Plan Cache) and reused for all subsequent calls.

🔥 The Disaster: Parameter Sniffing Asymmetry

Suppose AccountID = 1001 has 2 trades, but AccountID = 2002 has 5,000,000 trades.

  • If the procedure compiles first with AccountID = 1001, SQL Server generates an Index Seek + Key Lookup plan.
  • When AccountID = 2002 subsequently calls the procedure, SQL Server reuses that plan, attempting 5,000,000 Key Lookups! The server CPU hits 100% and queries time out.
  • Conversely, if it compiles with 2002 first, it generates an Index Scan, penalizing all small accounts with table scans!

Architectural Solutions for Parameter Sniffing:

Solution Technique Implementation Syntax Trade-Off
Query Recompile Hint OPTION (RECOMPILE) at query level Generates the perfect plan every time; adds slight CPU compilation overhead per execution. Best for non-sub-millisecond queries.
Optimize For Unknown OPTION (OPTIMIZE FOR UNKNOWN) Uses the density vector average from table statistics. Eliminates parameter bias.
Optimize For Specific Value OPTION (OPTIMIZE FOR (@AccountID = 1001)) Locks the plan to a known representative sweet spot.
Local Variable Masking DECLARE @LocalID INT = @ParamID; Hides value from optimizer during compile, forcing average density estimation.

2. Functions: Scalar UDFs vs Inline TVFs vs Multi-Statement TVFs

Scalar UDFs 🚫

Returns a single atomic value. Causes RBAR (Row-By-Agonizing-Row) execution: invoked once per row, forces context switching between SQL engine and T-SQL interpreter, and disables parallel query plans!

Inline Table-Valued (iTVF) ⚡

Contains a single RETURN (SELECT ...). SQL Server inlines it directly into the outer execution plan like a parameterized view. Supports parallel execution and index seeks!

Multi-Statement TVF (mTVF) ⚠️

Declares a @TableVariable return structure and uses BEGIN...END with procedural inserts. Suffers from lack of statistics, leading to severe cardinality misestimations.

3. Triggers & The Multi-Row Execution Trap

Triggers in SQL Server execute in response to DML events (AFTER or INSTEAD OF). Inside the trigger, SQL Server exposes two virtual, memory-resident system tables: inserted and deleted.

⚠️ The Classic Junior Bug: Single-Row Trigger Assumption

-- BROKEN TRIGGER ANTI-PATTERN:
CREATE TRIGGER trg_Orders_Broken ON Orders AFTER INSERT AS
BEGIN
    DECLARE @OrderID BIGINT;
    SELECT @OrderID = OrderID FROM inserted; -- FATAL!
    -- If a batch inserts 500 orders, @OrderID only holds the LAST row!
    -- 499 orders fail to process!
END;

The Golden Rule: The inserted and deleted pseudo-tables are relational sets. You must always write set-based joins against inserted and deleted.

Exercise 5.1: High-Performance Batch Order Placement via Table-Valued Parameter (TVP)
Hard
Context: A Java backend routing 5,000 orders in a single HTTP call to SQL Server.

Requirement: Create a User-Defined Table Type OrderBatchType, and write a stored procedure usp_PlaceBatchOrders that validates cash balances, inserts all valid orders atomically, and outputs rejected orders with failure reasons.

💡 View Solution & Explanation ▼ 
-- 1. Create User-Defined Table Type
CREATE TYPE OrderBatchType AS TABLE (
    AccountID INT NOT NULL,
    SecurityID INT NOT NULL,
    OrderSide VARCHAR(4) NOT NULL,
    OrderType VARCHAR(10) NOT NULL,
    Quantity INT NOT NULL,
    LimitPrice DECIMAL(18,4) NOT NULL
);
GO

-- 2. Stored Procedure consuming READONLY TVP
CREATE OR ALTER PROCEDURE usp_PlaceBatchOrders
    @OrderBatch OrderBatchType READONLY
AS
BEGIN
    SET NOCOUNT ON;
    SET XACT_ABORT ON;

    BEGIN TRY
        BEGIN TRANSACTION;

        -- Insert approved orders directly from TVP
        INSERT INTO Orders (AccountID, SecurityID, OrderSide, OrderType, Quantity, LimitPrice, OrderStatus, OrderTime)
        SELECT 
            b.AccountID,
            b.SecurityID,
            b.OrderSide,
            b.OrderType,
            b.Quantity,
            b.LimitPrice,
            'PENDING',
            SYSUTCDATETIME()
        FROM @OrderBatch b
        INNER JOIN Accounts a ON b.AccountID = a.AccountID
        WHERE a.Status = 'ACTIVE' 
          AND (b.OrderSide = 'SELL' OR a.CashBalance >= (b.Quantity * b.LimitPrice));

        COMMIT TRANSACTION;
    END TRY
    BEGIN CATCH
        IF @@TRANCOUNT > 0 ROLLBACK TRANSACTION;
        THROW;
    END CATCH
END;
GO
Why TVPs Win: Passing an array of 5,000 records via TVP replaces 5,000 individual network roundtrips with a single network transmission, boosting throughput by over 40x. TVPs must always be declared with READONLY.
Exercise 5.2: Refactoring a Slow Scalar UDF to an Inline TVF
Medium
Context: A legacy scalar function calculates Net Liquidation Value per account.

Requirement: Rewrite a scalar function into an Inline Table-Valued Function (iTVF) and demonstrate how to query it against 100,000 accounts using CROSS APPLY without triggering RBAR context-switching.

💡 View Solution & Explanation ▼ 
-- Refactored as High-Performance Inline Table-Valued Function (iTVF)
CREATE OR ALTER FUNCTION dbo.fn_GetAccountNetLiquidation_iTVF (@AccountID INT)
RETURNS TABLE
AS
RETURN (
    SELECT 
        a.AccountID,
        CAST(a.CashBalance + ISNULL(SUM(p.PositionUnits * p.CurrentMarketPrice), 0.00) AS DECIMAL(18,2)) AS NetLiquidationValue
    FROM dbo.Accounts a
    LEFT JOIN dbo.PortfolioPositions p ON a.AccountID = p.AccountID
    WHERE a.AccountID = @AccountID
    GROUP BY a.AccountID, a.CashBalance
);
GO

-- High-speed query across all accounts using CROSS APPLY:
SELECT 
    a.AccountID,
    a.AccountNumber,
    nl.NetLiquidationValue
FROM Accounts a
CROSS APPLY dbo.fn_GetAccountNetLiquidation_iTVF(a.AccountID) nl;
Optimizer Magic: SQL Server treats an inline TVF as an expand-in-place macro. The optimizer flattens the function into the outer query's join tree, unlocking parallel index seeks!
Exercise 5.3: Production Audit Trail with INSTEAD OF Trigger
Hard
Context: Preventing physical deletes on Accounts (Soft-delete architecture)

Requirement: Create an INSTEAD OF DELETE trigger on the Accounts table that intercepts any DELETE statement, sets Status = 'CLOSED' instead, and writes an entry into AuditLogs with before and after states.

💡 View Solution & Explanation ▼ 
CREATE OR ALTER TRIGGER trg_Accounts_SoftDelete
ON Accounts
INSTEAD OF DELETE
AS
BEGIN
    SET NOCOUNT ON;

    -- 1. Soft-delete the accounts
    UPDATE a
    SET a.Status = 'CLOSED',
        a.UpdatedAt = SYSUTCDATETIME()
    FROM Accounts a
    INNER JOIN deleted d ON a.AccountID = d.AccountID;

    -- 2. Audit the intercepted deletion event (Set-based)
    INSERT INTO AuditLogs (TableName, OperationType, RecordID, ChangedBy, ChangePayload)
    SELECT 
        'Accounts',
        'UPDATE',
        CAST(d.AccountID AS VARCHAR(50)),
        SUSER_SNAME(),
        CONCAT('Intercepted DELETE; AccountNumber: ', d.AccountNumber, ' status set to CLOSED.')
    FROM deleted d;
END;
GO
INSTEAD OF Mechanics: The trigger completely overrides the physical DELETE command. The engine populates the deleted pseudo-table with the rows targeted for deletion, allowing your custom logic to redirect the operation.
Exercise 5.4: Safe Dynamic SQL Search Procedure with sp_executesql
Medium
Context: Ad-hoc multi-attribute order search screen (Optional parameters)

Requirement: Write a stored procedure usp_SearchOrders that accepts optional filters: @AccountID INT = NULL, @SecurityID INT = NULL, @MinPrice DECIMAL = NULL, @MaxPrice DECIMAL = NULL. Use parameterized sp_executesql to prevent SQL injection and promote plan cache reuse.

💡 View Solution & Explanation ▼ 
CREATE OR ALTER PROCEDURE usp_SearchOrders
    @AccountID INT = NULL,
    @SecurityID INT = NULL,
    @MinPrice DECIMAL(18,4) = NULL,
    @MaxPrice DECIMAL(18,4) = NULL
AS
BEGIN
    SET NOCOUNT ON;

    DECLARE @SQL NVARCHAR(MAX) = N'
        SELECT OrderID, AccountID, SecurityID, OrderSide, Quantity, LimitPrice, OrderStatus, OrderTime
        FROM dbo.Orders
        WHERE 1 = 1';

    IF @AccountID IS NOT NULL
        SET @SQL += N' AND AccountID = @pAccountID';

    IF @SecurityID IS NOT NULL
        SET @SQL += N' AND SecurityID = @pSecurityID';

    IF @MinPrice IS NOT NULL
        SET @SQL += N' AND LimitPrice >= @pMinPrice';

    IF @MaxPrice IS NOT NULL
        SET @SQL += N' AND LimitPrice <= @pMaxPrice';

    DECLARE @ParamDef NVARCHAR(500) = N'
        @pAccountID INT,
        @pSecurityID INT,
        @pMinPrice DECIMAL(18,4),
        @pMaxPrice DECIMAL(18,4)';

    EXEC sp_executesql 
        @stmt = @SQL,
        @params = @ParamDef,
        @pAccountID = @AccountID,
        @pSecurityID = @SecurityID,
        @pMinPrice = @MinPrice,
        @pMaxPrice = @MaxPrice;
END;
GO
Why sp_executesql Beats EXEC(): sp_executesql enforces strongly-typed parameters. SQL Server caches the compiled execution plan for identical parameter patterns, eliminating SQL Injection vulnerabilities and preventing plan cache memory pollution.
Exercise 5.5: Enterprise Error Handling Framework with THROW & XACT_ABORT
Hard
Context: Multi-table financial settlement fund transfer

Requirement: Write a stored procedure usp_TransferSettlementCash that transfers cash between two accounts. Include complete enterprise error handling: SET XACT_ABORT ON, BEGIN TRY...BEGIN CATCH, transaction token verification (@@TRANCOUNT), and re-raising errors using modern THROW.

💡 View Solution & Explanation ▼ 
CREATE OR ALTER PROCEDURE usp_TransferSettlementCash
    @FromAccountID INT,
    @ToAccountID INT,
    @Amount DECIMAL(18,4)
AS
BEGIN
    SET NOCOUNT ON;
    -- XACT_ABORT ON ensures rollback even on statement timeouts / client disconnects
    SET XACT_ABORT ON;

    IF @Amount <= 0
    BEGIN
        THROW 50001, 'Transfer amount must be strictly greater than zero.', 1;
        RETURN;
    END

    BEGIN TRY
        BEGIN TRANSACTION;

        -- 1. Debit Source Account (Ensure sufficient funds)
        UPDATE Accounts 
        SET CashBalance = CashBalance - @Amount
        WHERE AccountID = @FromAccountID AND CashBalance >= @Amount;

        IF @@ROWCOUNT = 0
            THROW 50002, 'Insufficient funds or source account not found.', 1;

        -- 2. Credit Destination Account
        UPDATE Accounts 
        SET CashBalance = CashBalance + @Amount
        WHERE AccountID = @ToAccountID;

        IF @@ROWCOUNT = 0
            THROW 50003, 'Destination account not found.', 1;

        -- 3. Log to double-entry ledger
        INSERT INTO LedgerTransactions (AccountID, TransactionType, Amount, ReferenceNote)
        VALUES (@FromAccountID, 'WITHDRAWAL', -@Amount, CONCAT('Transfer to ', @ToAccountID)),
               (@ToAccountID, 'DEPOSIT', @Amount, CONCAT('Transfer from ', @FromAccountID));

        COMMIT TRANSACTION;
    END TRY
    BEGIN CATCH
        -- Check if transaction is active or uncommittable (XACT_STATE = -1)
        IF XACT_STATE() <> 0
            ROLLBACK TRANSACTION;

        -- Log failure to persistent error table before re-throwing
        INSERT INTO AuditLogs (TableName, OperationType, RecordID, ChangePayload)
        VALUES ('Accounts', 'DELETE', CAST(@FromAccountID AS VARCHAR(50)), 
                CONCAT('Error ', ERROR_NUMBER(), ': ', ERROR_MESSAGE(), ' on line ', ERROR_LINE()));

        -- THROW without arguments re-raises the original exception with stack trace preserved!
        THROW;
    END CATCH
END;
GO
THROW vs RAISERROR: Parameterless THROW; inside a CATCH block re-raises the original error verbatim with the exact line number and severity intact. XACT_STATE() = -1 signals an uncommittable transaction that must be rolled back.
Exercise 5.6: OUTPUT Parameters vs Return Codes
Easy
Context: Capturing generated keys and record counts back to calling applications.

Requirement: Write a procedure that inserts a new Client and returns both the generated ClientID via an OUTPUT parameter and an integer status code via RETURN.

💡 View Solution & Explanation ▼ 
CREATE OR ALTER PROCEDURE usp_RegisterClient
    @ClientName NVARCHAR(150),
    @ClientType VARCHAR(20),
    @NewClientID INT OUTPUT
AS
BEGIN
    SET NOCOUNT ON;

    IF EXISTS (SELECT 1 FROM Clients WHERE ClientName = @ClientName)
    BEGIN
        SET @NewClientID = -1;
        RETURN 1; -- Status code 1: Duplicate
    END

    INSERT INTO Clients (ClientName, ClientType)
    VALUES (@ClientName, @ClientType);

    SET @NewClientID = SCOPE_IDENTITY();
    RETURN 0; -- Status code 0: Success
END;
GO

-- How to call and retrieve OUTPUT parameters:
DECLARE @GeneratedID INT;
DECLARE @ReturnCode INT;

EXEC @ReturnCode = usp_RegisterClient 
    @ClientName = N'Point72 Asset Management',
    @ClientType = 'HEDGE_FUND',
    @NewClientID = @GeneratedID OUTPUT;

SELECT @ReturnCode AS ExitStatus, @GeneratedID AS AssignedClientID;
SCOPE_IDENTITY() vs @@IDENTITY: Always use SCOPE_IDENTITY()! @@IDENTITY returns the last identity value generated in any table in the current session—including any identity values created by background triggers!
Exercise 5.7: Converting a Slow Row-by-Row Cursor to a Set-Based Operation
Medium
Context: A nightly job calculates interest for margin accounts using a cursor.

Requirement: Take a legacy CURSOR iterating through 50,000 margin accounts and refactor it into an atomic set-based UPDATE with ledger journal inserts.

💡 View Solution & Explanation ▼ 
-- Set-Based Atomic Interest Accrual (Replaces 50,000 Cursor Iterations)
DECLARE @AnnualRate DECIMAL(5,4) = 0.0825;
DECLARE @DailyRate DECIMAL(18,8) = @AnnualRate / 365.0;

-- 1. Output table to capture debit amounts
DECLARE @Accruals TABLE (
    AccountID INT,
    InterestDebit DECIMAL(18,4)
);

-- 2. Atomic Set Update with OUTPUT clause
UPDATE a
SET a.CashBalance = a.CashBalance - CAST(ABS(a.CashBalance) * @DailyRate AS DECIMAL(18,4))
OUTPUT inserted.AccountID, CAST(ABS(deleted.CashBalance) * @DailyRate AS DECIMAL(18,4))
INTO @Accruals (AccountID, InterestDebit)
FROM Accounts a
WHERE a.AccountType = 'MARGIN' 
  AND a.CashBalance < 0; -- Negative balance represents borrowed margin

-- 3. Bulk insert ledger interest entries
INSERT INTO LedgerTransactions (AccountID, TransactionType, Amount, ReferenceNote)
SELECT AccountID, 'FEE', -InterestDebit, 'Daily Margin Debit Interest'
FROM @Accruals;
Set-Based Superiority: The cursor executes 50,000 individual transactions, locks, and log flushes. The set-based rewrite processes all 50,000 accounts in a single pass in under 40 milliseconds.
Exercise 5.8: Detecting and Mitigating Parameter Sniffing Live
Hard
Context: Querying order executions for skew distributions

Requirement: Demonstrate how to write a stored procedure using OPTION (OPTIMIZE FOR UNKNOWN) and evaluate its plan against OPTION (RECOMPILE).

💡 View Solution & Explanation ▼ 
CREATE OR ALTER PROCEDURE usp_GetOrdersByStatus
    @Status VARCHAR(20)
AS
BEGIN
    SET NOCOUNT ON;

    -- OPTION (OPTIMIZE FOR UNKNOWN) tells the optimizer to bypass sniffing
    -- and use the average statistics distribution histogram.
    SELECT 
        OrderID,
        AccountID,
        SecurityID,
        Quantity,
        OrderTime
    FROM Orders
    WHERE OrderStatus = @Status
    OPTION (OPTIMIZE FOR UNKNOWN);
END;
GO
When to use OPTIMIZE FOR UNKNOWN: If 99% of your orders are 'FILLED' and 0.1% are 'REJECTED', a sniffed plan for 'REJECTED' causes table scans when querying 'FILLED'. OPTIMIZE FOR UNKNOWN provides stable, consistent execution time regardless of which parameter is invoked first.

📋 How to Answer This in an Interview

Interviewer Question: "What is Parameter Sniffing in SQL Server, and what are your primary techniques to resolve it?"

Staff Engineer Response:

"Parameter Sniffing is the default behavior where SQL Server captures the runtime parameter values passed during a stored procedure's initial compilation and tailors the cached execution plan specifically to that parameter's cardinality.

In workloads with uniform data distribution, this is highly beneficial. However, in skewed tables—such as an institutional client with 5 million trades versus a retail client with 2 trades—a plan compiled for the 2-trade client uses an Index Seek + Key Lookup. When executed for the 5-million-trade client, those 5 million random I/O lookups saturate the storage subsystem and exhaust worker threads.

My remediation strategy follows a clear hierarchy:
1. OPTION (RECOMPILE): For complex queries executed a few hundred times a day, recompiling on each execution guarantees optimal plans tailored to the exact parameter without plan cache pollution.
2. OPTIMIZE FOR UNKNOWN: For high-frequency OLTP queries (thousands of executions per second) where compilation CPU overhead is unacceptable, this instructs the engine to build a stable plan using average column densities.
3. Conditional Branching: Splitting the procedure into separate internal queries (e.g. IF @IsHighVolume = 1 EXEC usp_HighVolume ELSE EXEC usp_LowVolume) to give each parameter profile its own independent, cached plan."
