1. Stored Procedures: Architecture, Lifecycle & Parameter Sniffing

A. Ground-Zero First Principles: Why Use Stored Procedures?

In application engineering, you could execute SQL by constructing raw string queries in Java or C# (e.g. "SELECT * FROM Orders WHERE AccountID = " + id) and sending them over a JDBC/ODBC connection. Why did enterprise database architecture introduce Stored Procedures?

  1. Pre-Compilation & Plan Cache Reuse: When an ad-hoc query arrives, SQL Server must parse the syntax, resolve object names, normalize, optimize, and compile an execution plan. A Stored Procedure compiles once, and its compiled binary execution plan is cached in memory (Plan Cache) for subsequent instant execution.
  2. Security & Privilege Segregation (Ownership Chaining): You can grant your backend Java application service account permission to EXECUTE dbo.usp_TransferFunds, while completely revoking direct SELECT, INSERT, UPDATE, and DELETE permissions on the underlying Accounts and LedgerTransactions tables! This guarantees that users cannot bypass business logic or tamper with data via SQL injection.
  3. Network Roundtrip Minimization: A complex trade settlement might require 15 database operations: validate margin, lock account, debit cash, credit security, update positions, log audit. Executing this in application code requires 15 separate network roundtrips over TCP/IP. A stored procedure executes all 15 operations locally on the database server in a single network roundtrip.

B. The Parameter Sniffing Trap: How Cached Plans Poison Performance

When a Stored Procedure executes for the very first time after creation or server restart, SQL Server inspects ("sniffs") the exact parameter values passed in by the caller. It builds an execution plan optimized specifically for that parameter's data distribution and stores it in the Plan Cache.

🔥 The Skew Disaster: How Parameter Sniffing Freezes Servers

Suppose you have a procedure usp_GetClientTrades @ClientID INT:

  • Client A (Retail User): Has placed only 2 trades in history.
  • Client B (Institutional Hedge Fund): Has placed 5,000,000 trades.

The Incident:

  1. At 8:00 AM, the server restarts. Client A happens to log in first and calls EXEC usp_GetClientTrades @ClientID = 'Retail_Client_A'.
  2. SQL Server sniffs the parameter, sees 2 rows, and compiles an Index Seek + Key Lookup plan (optimal for 2 rows). This plan is cached.
  3. At 8:05 AM, Client B calls the procedure. SQL Server pulls the cached plan and attempts to execute 5,000,000 Key Lookups!
  4. The database storage subsystem is battered with 5 million random I/O reads, CPU spikes to 100%, query timeouts cascade across the bank, and the application halts!

The 4 Engineering Solutions for Parameter Sniffing:

Remediation Technique Implementation Code Trade-Off / When to Use
Query-Level RECOMPILE OPTION (RECOMPILE) appended to statement Forces SQL Server to compile a fresh plan tailored to runtime parameters on every execution. Adds ~1-2ms CPU compilation time. Best for medium-frequency complex queries.
OPTIMIZE FOR UNKNOWN OPTION (OPTIMIZE FOR UNKNOWN) Instructs optimizer to ignore the sniffed value and compile a safe, middle-of-the-road plan based on average table density. Best for high-frequency queries.
OPTIMIZE FOR Specific Value OPTION (OPTIMIZE FOR (@ClientID = 1001)) Locks the cached plan to a representative sweet spot.
Local Variable Masking DECLARE @LocalID = @ClientID; WHERE ID = @LocalID; Masks the value from the compiler, preventing sniffing and falling back to density estimates.

2. Stored Procedures vs User-Defined Functions (UDFs)

A fundamental senior engineering concept is understanding the strict operational boundaries between a Stored Procedure and a Function:

Architectural Attribute Stored Procedure User-Defined Function (UDF)
Return Obligation Optional. Can return 0, 1, or multiple result sets, or output parameters. Mandatory. Must return a scalar value or a table result.
Usage in SQL Statements Cannot be called within SELECT, WHERE, or HAVING clauses. Must be executed via EXEC. Can be embedded directly inside SELECT expressions, JOIN predicates, and WHERE clauses.
DML Modification Can modify database state: Can execute INSERT, UPDATE, and DELETE on physical tables. Strictly Read-Only: Cannot modify physical database state or tables (no side-effects permitted).
Transactions Can initiate, commit, and roll back explicit transactions (BEGIN TRAN / COMMIT). Cannot manage transactions: Cannot start or commit transactions.
Dynamic SQL & Temp Tables Can execute dynamic SQL (sp_executesql) and create #temp tables. Cannot execute dynamic SQL or create #temp tables (only @table variables).

The Scalar UDF Trap: The Silent RBAR Performance Killer

A Scalar Function accepts parameters and returns a single atomic value (e.g. dbo.fn_CalculateTax(Price)).

☠️ Why Scalar Functions Destroy Query Performance

When you write: SELECT OrderID, dbo.fn_CalculateFee(Quantity, LimitPrice) FROM Orders;

  1. RBAR (Row-By-Agonizing-Row): SQL Server cannot optimize the function into a set-based vector. It must invoke the function once for every single row in the table! For 10 million orders, that is 10 million individual function executions!
  2. Engine Context Switching: Every row forces a CPU context switch between the Relational Storage Engine and the T-SQL Procedural Interpreter.
  3. Disables Parallel Query Plans: Prior to SQL Server 2019, referencing a scalar function forces SQL Server to run the entire query on a single CPU thread, completely disabling parallel multi-core execution!

The Solution: Inline Table-Valued Functions (iTVF)

An Inline Table-Valued Function (iTVF) contains a single RETURN (SELECT ...) statement with no BEGIN...END block. The query optimizer treats an inline TVF as a macro: it inlines the function directly into the calling query's execution plan, preserving parallel index seeks!

-- 🚫 AVOID: Scalar Function (RBAR, single-threaded, slow)
CREATE FUNCTION dbo.fn_GetPositionValue_Scalar (@Qty INT, @Price DECIMAL(18,4))
RETURNS DECIMAL(18,2) AS
BEGIN
    RETURN CAST(@Qty * @Price AS DECIMAL(18,2));
END;
GO

-- ⚡ PREFERRED: High-Performance Inline Table-Valued Function (Inlined by Optimizer)
CREATE FUNCTION dbo.fn_GetPositionValue_iTVF (@AccountID INT)
RETURNS TABLE AS
RETURN (
    SELECT 
        AccountID,
        SUM(PositionUnits * CurrentMarketPrice) AS TotalValuation
    FROM PortfolioPositions
    WHERE AccountID = @AccountID
    GROUP BY AccountID
);
GO

3. Table-Valued Parameters (TVPs): Bulk Ingestion Pattern

In high-throughput microservices, an order gateway might receive 2,000 trades per second. Calling a stored procedure 2,000 times in individual network calls creates massive TCP/IP latency.

Table-Valued Parameters (TVPs) allow an application (Java JDBC, C# ADO.NET) to pass an entire in-memory collection/array of rows as a single strongly-typed parameter into a stored procedure in one single network roundtrip.

-- Step 1: Define User-Defined Table Type
CREATE TYPE OrderBatchType AS TABLE (
    AccountID INT NOT NULL,
    SecurityID INT NOT NULL,
    Quantity INT NOT NULL,
    LimitPrice DECIMAL(18,4) NOT NULL
);
GO

-- Step 2: Stored Procedure consuming TVP (Must be READONLY)
CREATE PROCEDURE usp_ProcessOrderBatch
    @Batch OrderBatchType READONLY
AS
BEGIN
    SET NOCOUNT ON;
    
    INSERT INTO Orders (AccountID, SecurityID, Quantity, LimitPrice, OrderStatus)
    SELECT AccountID, SecurityID, Quantity, LimitPrice, 'PENDING'
    FROM @Batch;
END;
GO

4. Triggers: AFTER vs INSTEAD OF & The Multi-Row Trap

AFTER (FOR) Triggers

Fires after the triggering DML statement (INSERT, UPDATE, DELETE) has completed and constraints are validated. Ideal for audit logging and cascading ledger updates.

INSTEAD OF Triggers

Fires in place of the triggering statement. The original statement is intercepted and bypassed. Ideal for soft deletes and making non-updatable multi-table views writable.

⚠️ The Classic Multi-Row Trigger Bug

Inside a trigger, SQL Server exposes two virtual system tables: inserted and deleted.

A fatal mistake is assuming triggers fire once per row:
SELECT @ID = OrderID FROM inserted; -- BROKEN!

If an application executes INSERT INTO Orders SELECT ... FROM Staging inserting 5,000 rows, the trigger fires ONCE for the entire batch! The inserted table contains all 5,000 rows. Selecting into a scalar variable captures only one row, dropping the other 4,999 rows! You must always write set-based joins against inserted and deleted.

5. Enterprise Error Handling: THROW vs RAISERROR & XACT_ABORT

Modern T-SQL uses structured TRY...CATCH blocks with THROW and SET XACT_ABORT ON:

  • SET XACT_ABORT ON: Guarantees that if a runtime error or client timeout occurs, SQL Server automatically rolls back the entire transaction. Without this setting, certain errors leave transactions orphaned in an open, uncommitted state holding locks!
  • THROW vs RAISERROR: Parameterless THROW; inside a CATCH block re-throws the original exception verbatim, preserving the original error code, line number, and call stack. RAISERROR historically altered line numbers and required custom message registration.
CREATE PROCEDURE usp_TransferFundsAtomic
    @FromAccount INT,
    @ToAccount INT,
    @Amount DECIMAL(18,2)
AS
BEGIN
    SET NOCOUNT ON;
    SET XACT_ABORT ON; -- Mandatory for robust rollback!

    BEGIN TRY
        BEGIN TRANSACTION;

        UPDATE Accounts SET CashBalance = CashBalance - @Amount WHERE AccountID = @FromAccount;
        UPDATE Accounts SET CashBalance = CashBalance + @Amount WHERE AccountID = @ToAccount;

        COMMIT TRANSACTION;
    END TRY
    BEGIN CATCH
        -- Check if transaction is in an uncommittable state (-1)
        IF XACT_STATE() <> 0
            ROLLBACK TRANSACTION;

        -- Re-throw original error with stack trace intact
        THROW;
    END CATCH
END;
GO

📋 How to Master This in an Interview

Interviewer Question: "What is Parameter Sniffing in SQL Server Stored Procedures, and how do you resolve it?"

Staff Engineer Model Response:

"Parameter Sniffing is the default behavior where SQL Server inspects the runtime parameter values passed during a stored procedure's initial execution, compiling an execution plan tailored specifically to that parameter's data distribution and caching it in the Plan Cache for subsequent reuse.

While beneficial for uniform data distributions, it causes catastrophic performance degradation on skewed tables. For example, if a procedure compiles first for a client with 2 trades, the optimizer creates an Index Seek + Key Lookup plan. When an institutional client with 5 million trades subsequent calls that procedure, the engine reuses that plan, attempting 5 million random I/O Key Lookups and exhausting server resources.

My remediation strategy: 1. For medium-frequency complex queries, use OPTION (RECOMPILE) to ensure the optimizer builds a tailored plan on every execution. 2. For high-frequency OLTP queries where compilation CPU overhead is unacceptable, use OPTION (OPTIMIZE FOR UNKNOWN) to force compilation against the average statistical density vector. 3. When parameter ranges naturally segregate into distinct profiles (small vs huge), use procedural branching to separate the logic into distinct procedures with their own independent plan cache entries."

🎯 The Interviewer Grill Round (Trap Follow-Ups)

  • Trap: "What is the difference between a Stored Procedure and a Function?"
    Answer: "Functions are strictly read-only, cannot modify physical database state, cannot manage transactions, and must return a value, allowing them to be embedded inside SELECT and WHERE clauses. Stored Procedures can modify database state (DML), control transactions, execute dynamic SQL, create temp tables, and return zero, one, or multiple result sets, but must be called explicitly via EXEC."
  • Trap: "Why are Scalar UDFs considered an anti-pattern in high-throughput systems?"
    Answer: "Because they execute RBAR (Row-By-Agonizing-Row). For every row returned by the query, SQL Server forces a CPU context switch between the storage engine and T-SQL interpreter, and historically forces single-threaded serial execution, disabling multi-core parallelism. They should be rewritten as Inline Table-Valued Functions (iTVFs)."
  • Trap: "What is the danger of writing single-row variable assignments inside a Trigger?"
    Answer: "In SQL Server, triggers fire once per DML statement, not once per row. If a statement inserts or updates 10,000 rows in a batch, the inserted pseudo-table contains 10,000 rows. A scalar variable assignment (SELECT @id = id FROM inserted) arbitrarily captures only one row, dropping the other 9,999 rows. Triggers must always use set-based joins against inserted and deleted."
