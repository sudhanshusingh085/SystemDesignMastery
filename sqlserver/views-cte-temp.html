04 · Views, CTEs, Temporary Tables & PIVOT

Standard vs Indexed Views (SCHEMABINDING), Recursive CTEs for Hierarchical Tree Traversal, The Great TempDB Showdown (#Temp vs ##Global vs @Table), and Dynamic PIVOT.

1. Standard Views vs Indexed (Materialized) Views

A standard View is not a physical table; it is a saved SELECT query stored in the data dictionary. When queried, SQL Server expands the view definition into the outer query during compilation.

⚡ Indexed (Materialized) Views

An Indexed View has a physical Clustered B-Tree index created on it. The result set is physically materialized on disk and automatically synchronized by the SQL Server storage engine whenever the underlying base tables undergo INSERT, UPDATE, or DELETE operations.

Requirements for an Indexed View:

  1. Must be created WITH SCHEMABINDING (prevents changes to underlying table structures).
  2. Base tables must be referenced using two-part names (e.g. dbo.Orders).
  3. First index created must be a UNIQUE CLUSTERED INDEX.
  4. If using aggregation, must include COUNT_BIG(*), and cannot use DISTINCT, TOP, or UNION.

⚠️ The Enterprise Edition vs Standard Edition Trap: WITH (NOEXPAND)

In Enterprise Edition, the query optimizer automatically recognizes that a query can be satisfied by an indexed view and matches it, even if the query names the base tables! In Standard Edition, SQL Server will expand the indexed view back into base table joins unless you explicitly include the query hint WITH (NOEXPAND)!

2. Common Table Expressions (CTEs) & Recursion

A CTE is a named temporary result set defined within the execution scope of a single SELECT, INSERT, UPDATE, or DELETE statement. CTEs do not persist in TempDB; they are inlined into the execution plan.

Recursion Protection: By default, SQL Server caps recursion at 100 iterations. To modify this, append OPTION (MAXRECURSION 0) (unlimited) or a specific depth (e.g., OPTION (MAXRECURSION 500)).

3. The TempDB Showdown: #Temp vs ##Global vs @Table

One of the most pervasive myths in SQL Server engineering is that "Table variables live entirely in RAM while #temp tables live in TempDB". This is completely false! Both structures are allocated and backed by TempDB pages.

Feature Local Temp Table (#Temp) Global Temp Table (##Global) Table Variable (@Table)
Scope Current session / Current stored proc execution level. Global across all sessions on the entire instance. Current batch / Current stored procedure.
Statistics Yes! Column statistics generated and maintained; cost-based optimizer estimates cardinality accurately. Yes! Fully maintained. No column statistics! Historically estimated as exactly 1 row (causes catastrophic Nested Loops joins on 100k rows!).
Indexes Clustered and Non-Clustered indexes can be created anytime after table creation. Clustered and Non-Clustered indexes allowed. Only primary keys / unique constraints declared inline at definition (SQL 2014+ allows inline non-unique indexes).
Transactions Participates in explicit user transactions; rolls back cleanly on ROLLBACK TRAN. Participates in transactions; rolls back. Does not roll back! Changes made to a table variable survive a transaction rollback!
Dynamic SQL Visible to child dynamic SQL batches called via sp_executesql. Visible everywhere. Not visible to child dynamic SQL batches.

Exercise 4.1: Materialized Real-Time Portfolio Summary via Indexed View
Hard
Context: High-frequency portfolio valuation aggregation

Requirement: Create an indexed view v_AccountPortfolioValuation that computes total holding count, total units, and total market value grouped by AccountID. Include all required settings (SCHEMABINDING, COUNT_BIG), create the clustered index, and write a query using WITH (NOEXPAND).

💡 View Solution & Explanation ▼ 
-- 1. Create View with Schemabinding
CREATE OR ALTER VIEW dbo.v_AccountPortfolioValuation
WITH SCHEMABINDING
AS
SELECT 
    AccountID,
    COUNT_BIG(*) AS HoldingCount,
    SUM(CAST(PositionUnits AS BIGINT)) AS TotalUnits,
    SUM(CAST(PositionUnits * CurrentMarketPrice AS DECIMAL(18,2))) AS TotalMarketValue
FROM dbo.PortfolioPositions
GROUP BY AccountID;
GO

-- 2. Create Unique Clustered Index (Physically materializes data)
CREATE UNIQUE CLUSTERED INDEX CIX_v_AccountPortfolioValuation 
ON dbo.v_AccountPortfolioValuation (AccountID);
GO

-- 3. Production Query with NOEXPAND hint (Works on all SQL Server editions)
SELECT AccountID, HoldingCount, TotalUnits, TotalMarketValue
FROM dbo.v_AccountPortfolioValuation WITH (NOEXPAND)
WHERE AccountID = 1001;
Why NOEXPAND: WITH (NOEXPAND) forces the engine to read the precomputed materialized view index directly, achieving sub-millisecond aggregation without touching the base PortfolioPositions table.
Exercise 4.2: Recursive CTE for Multi-Tier Fund & Sub-Account Hierarchy
Hard
Context: Table InstitutionalEntities (EntityID, ParentEntityID, EntityName, AllocatedCapital)

Requirement: Master funds own feeder funds, which own individual algorithmic trading desks. Write a Recursive CTE that traverses the tree starting from the Master Fund (ParentEntityID IS NULL), outputting: EntityID, EntityName, DepthLevel, FullHierarchyPath (e.g. "Citadel Master > Quantitative Desk > High Frequency Desk"), and Cumulative Sub-Fund Capital.

💡 View Solution & Explanation ▼ 
-- Recursive Entity Hierarchy Traversal
WITH EntityHierarchyCTE AS (
    -- Anchor Member: Root master funds
    SELECT 
        EntityID,
        ParentEntityID,
        EntityName,
        AllocatedCapital,
        0 AS DepthLevel,
        CAST(EntityName AS NVARCHAR(1000)) AS FullHierarchyPath
    FROM InstitutionalEntities
    WHERE ParentEntityID IS NULL

    UNION ALL

    -- Recursive Member: Subordinate entities
    SELECT 
        child.EntityID,
        child.ParentEntityID,
        child.EntityName,
        child.AllocatedCapital,
        parent.DepthLevel + 1,
        CAST(parent.FullHierarchyPath + ' > ' + child.EntityName AS NVARCHAR(1000))
    FROM InstitutionalEntities child
    INNER JOIN EntityHierarchyCTE parent ON child.ParentEntityID = parent.EntityID
)
SELECT 
    EntityID,
    EntityName,
    DepthLevel,
    FullHierarchyPath,
    AllocatedCapital
FROM EntityHierarchyCTE
ORDER BY FullHierarchyPath
OPTION (MAXRECURSION 50);
Recursive Pattern: The anchor evaluates top-level entities. The recursive member joins child rows to the CTE itself. Casting FullHierarchyPath to a fixed NVARCHAR(1000) prevents data type length mismatch errors between iterations.
Exercise 4.3: High-Cardinality Staging: #Temp Table vs Table Variable Benchmark
Medium
Context: Batch processing 250,000 incoming FIX fills

Requirement: Write a script comparing the cardinality estimation and join plan for: (1) A table variable @Fills, and (2) A local temp table #Fills with a clustered index. Explain why table variables can trigger catastrophic Cartesian or Nested Loop spills.

💡 View Solution & Explanation ▼ 
-- Approach A: Local Temp Table with Clustered Index (Recommended for large datasets)
CREATE TABLE #Fills (
    FillID BIGINT PRIMARY KEY,
    OrderID BIGINT,
    FillQuantity INT,
    FillPrice DECIMAL(18,4)
);

INSERT INTO #Fills (FillID, OrderID, FillQuantity, FillPrice)
SELECT ExecutionID, OrderID, FillQuantity, FillPrice FROM Executions;

-- SQL Server creates statistics automatically; optimizer chooses Hash Match or Merge Join
SELECT o.AccountID, SUM(f.FillQuantity * f.FillPrice) AS TotalFilledValue
FROM Orders o
INNER JOIN #Fills f ON o.OrderID = f.OrderID
GROUP BY o.AccountID;

DROP TABLE #Fills;

-- Approach B: Table Variable (Dangerous for large datasets prior to SQL Server 2019)
DECLARE @FillsVar TABLE (
    FillID BIGINT PRIMARY KEY,
    OrderID BIGINT,
    FillQuantity INT,
    FillPrice DECIMAL(18,4)
);

INSERT INTO @FillsVar (FillID, OrderID, FillQuantity, FillPrice)
SELECT ExecutionID, OrderID, FillQuantity, FillPrice FROM Executions;

-- Optimizer estimated 1 row! Chooses Nested Loops with 250,000 seeks into Orders table!
SELECT o.AccountID, SUM(f.FillQuantity * f.FillPrice) AS TotalFilledValue
FROM Orders o
INNER JOIN @FillsVar f ON o.OrderID = f.OrderID
GROUP BY o.AccountID;
Engine Insight: Because table variables lack column statistics, the optimizer assumes they contain exactly 1 row. When joining with millions of records, it generates a Nested Loops join plan that seeks into the target table 250,000 times instead of performing a single Hash Join pass!
Exercise 4.4: Static PIVOT for Cross-Tab Portfolio Sector Allocations
Medium
Context: Accounts, Securities (Sector), PortfolioPositions

Requirement: Write a static PIVOT query that outputs one row per AccountID, with columns representing the total position market value in: [Technology], [Financials], [Semiconductors], and [Consumer Discretionary].

💡 View Solution & Explanation ▼ 
SELECT 
    AccountID,
    ISNULL([Technology], 0.00) AS Technology_Value,
    ISNULL([Financials], 0.00) AS Financials_Value,
    ISNULL([Semiconductors], 0.00) AS Semiconductors_Value,
    ISNULL([Consumer Discretionary], 0.00) AS Consumer_Value
FROM (
    SELECT 
        p.AccountID,
        s.Sector,
        CAST(p.PositionUnits * p.CurrentMarketPrice AS DECIMAL(18,2)) AS MarketValue
    FROM PortfolioPositions p
    INNER JOIN Securities s ON p.SecurityID = s.SecurityID
) AS SourceTable
PIVOT (
    SUM(MarketValue)
    FOR Sector IN ([Technology], [Financials], [Semiconductors], [Consumer Discretionary])
) AS PivotTable
ORDER BY AccountID;
PIVOT Rules: The source subquery must project strictly three things: (1) Row grouping keys (AccountID), (2) The pivot spreading column (Sector), and (3) The aggregation value (MarketValue). Any extra unprojected columns will unintentionally fragment the grouping rows!
Exercise 4.5: Dynamic PIVOT for Unknown Number of Stock Tickers
Hard
Context: New tickers are added daily; static column names will break.

Requirement: Write a stored procedure or dynamic SQL script that dynamically constructs the ticker column list using STRING_AGG() and pivots order volumes across all active tickers.

💡 View Solution & Explanation ▼ 
DECLARE @Columns NVARCHAR(MAX) = '';
DECLARE @SQL NVARCHAR(MAX) = '';

-- 1. Build comma-separated bracketed list of distinct tickers
SELECT @Columns = STRING_AGG(QUOTENAME(Ticker), ', ') WITHIN GROUP (ORDER BY Ticker)
FROM (SELECT DISTINCT Ticker FROM Securities WHERE IsActive = 1) AS t;

-- 2. Construct dynamic PIVOT query string
SET @SQL = '
SELECT AccountID, ' + @Columns + '
FROM (
    SELECT 
        o.AccountID,
        s.Ticker,
        o.Quantity
    FROM Orders o
    INNER JOIN Securities s ON o.SecurityID = s.SecurityID
) AS src
PIVOT (
    SUM(Quantity)
    FOR Ticker IN (' + @Columns + ')
) AS pvt
ORDER BY AccountID;';

-- 3. Execute safely via sp_executesql
EXEC sp_executesql @SQL;
Dynamic SQL Security: QUOTENAME(Ticker) escapes the string with square brackets (e.g. [AAPL]), neutralizing any potential SQL injection attacks from rogue ticker symbols.
Exercise 4.6: Normalizing Wide Tables using UNPIVOT
Medium
Context: A legacy risk system stores quarterly returns across wide columns: QuarterlyRisk (AccountID, Q1_Return, Q2_Return, Q3_Return, Q4_Return)

Requirement: Write an UNPIVOT query to convert these 4 quarterly columns into normalized rows with schema (AccountID, QuarterName, ReturnValue).

💡 View Solution & Explanation ▼ 
SELECT 
    AccountID,
    QuarterName,
    ReturnValue
FROM (
    SELECT AccountID, Q1_Return, Q2_Return, Q3_Return, Q4_Return
    FROM QuarterlyRisk
) AS WideTable
UNPIVOT (
    ReturnValue FOR QuarterName IN (Q1_Return, Q2_Return, Q3_Return, Q4_Return)
) AS UnpivotedTable;
UNPIVOT Nuance: UNPIVOT automatically suppresses rows where the value is NULL. All pivoted source columns must share the exact same data type (e.g. all DECIMAL(10,4)).
Exercise 4.7: Global Temporary Tables (##Global) for Cross-Session Audit Caching
Medium
Context: Nightly batch jobs running across multiple worker threads

Requirement: Demonstrate how a global temporary table (##GlobalSettlements) can be populated by a master orchestrator session, read concurrently by child sessions, and explain the exact lifecycle rules for when SQL Server automatically deallocates it.

💡 View Solution & Explanation ▼ 
-- In Master Orchestrator Session:
IF OBJECT_ID('tempdb..##GlobalSettlements') IS NOT NULL
    DROP TABLE ##GlobalSettlements;

CREATE TABLE ##GlobalSettlements (
    BatchID UNIQUEIDENTIFIER DEFAULT NEWID(),
    AccountID INT,
    NetCash DECIMAL(18,2)
);

INSERT INTO ##GlobalSettlements (AccountID, NetCash)
SELECT AccountID, CashBalance FROM Accounts;

-- Child Worker Sessions (Can read without creating their own copy):
SELECT * FROM ##GlobalSettlements WHERE NetCash > 1000000;
Deallocation Lifecycle: A global temporary table is automatically dropped by SQL Server when: (1) The session that created it disconnects, AND (2) All other sessions actively querying or referencing the table finish their current execution.
Exercise 4.8: Transaction Rollback Resilience in Table Variables
Hard
Context: Production error logging inside failed financial transactions

Requirement: Write a script proving that when an explicit transaction rolls back due to a business rule violation, changes made to a table variable are preserved, whereas changes made to a #temp table or base table are reverted.

💡 View Solution & Explanation ▼ 
-- Declare table variable and temp table
DECLARE @ErrorLog TABLE (Step VARCHAR(50), ErrorMsg VARCHAR(100));
CREATE TABLE #TempAudit (Step VARCHAR(50));

BEGIN TRANSACTION;
    INSERT INTO #TempAudit VALUES ('Step 1 Started');
    INSERT INTO @ErrorLog VALUES ('Step 1', 'Simulated Validation Failure');

    -- Transaction fails and is aborted:
    ROLLBACK TRANSACTION;

-- Inspect contents post-rollback:
SELECT * FROM #TempAudit; 
-- Result: 0 ROWS! (Rolled back cleanly)

SELECT * FROM @ErrorLog;  
-- Result: 1 ROW PRESERVED! ('Step 1', 'Simulated Validation Failure')

DROP TABLE #TempAudit;
Architectural Goldmine: Because table variables are non-transactional variables, they do not participate in transaction rollbacks! This unique behavior makes table variables ideal for logging error messages and audit failures inside CATCH blocks where the transaction must be aborted.

📋 How to Answer This in an Interview

Interviewer Question: "When would you use a #Temp Table versus a @Table Variable in SQL Server?"

Staff Engineer Response:

"The choice comes down to cardinality, query optimization, and transaction boundaries.

I choose #Temp Tables for medium to large datasets (more than ~100 rows) or when joining with other physical tables. Why? Because #temp tables have full column distribution statistics generated and updated by the query optimizer. The optimizer can choose optimal join algorithms like Hash Match or Merge Join, create additional non-clustered indexes post-population, and participate in parallel execution plans.

I choose @Table Variables for tiny lookup sets (under 50 rows) or specifically inside TRY...CATCH blocks where I need an in-memory audit log that survives a ROLLBACK TRANSACTION.

Historically, table variables had no column statistics, leading the optimizer to hardcode a cardinality estimate of exactly 1 row. If that table variable actually contained 100,000 rows, joining it with another large table triggered a disastrous Nested Loops join that ran for hours. While SQL Server 2019 introduced Table Variable Deferred Compilation to mitigate this, #temp tables remain the standard for high-throughput enterprise batch processing."
