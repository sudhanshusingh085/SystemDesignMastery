03 · Window Functions & Analytical Framing

Ranking Functions, Value Offset Functions (LAG/LEAD), The Fatal LAST_VALUE Framing Trap, and ROWS vs RANGE Engine Performance.

1. The OVER() Clause Architecture

Unlike standard GROUP BY aggregations which collapse rows into summary buckets, Window Functions compute values across a set of table rows while preserving individual row identity.

The Full Anatomy of a Window Function:

FUNCTION_NAME(expression) OVER (
    [PARTITION BY partition_column_1, ...]
    [ORDER BY sort_column_1 [ASC|DESC], ...]
    [ROWS | RANGE frame_specification]
)
flowchart LR Dataset["Input Dataset (Orders)"] --> Part["PARTITION BY SecurityID
(Divides into independent windows)"] Part --> Order["ORDER BY OrderTime
(Sorts rows within partition)"] Order --> Frame["ROWS BETWEEN...
(Defines physical sliding frame)"] Frame --> Calc["Compute Window Metric
(Running Sum, Rank, Delta)"]

2. Ranking Functions Comparison

SQL Server provides four distinct ranking functions. Understanding how they handle ties is a universal senior engineering interview test.

Value ROW_NUMBER() RANK() DENSE_RANK() NTILE(3)
$1,0001111 (Bucket 1)
$800 (Tie)2221 (Bucket 1)
$800 (Tie)3222 (Bucket 2)
$50044 (Skips 3!)3 (Continuous)2 (Bucket 2)
$3005543 (Bucket 3)
  • ROW_NUMBER(): Assigns a strictly unique, contiguous integer to every row. If values tie, ordering is non-deterministic unless unique tie-breaking columns are added to ORDER BY.
  • RANK(): Assigns identical ranks to ties, then skips subsequent rank numbers by the count of tied rows.
  • DENSE_RANK(): Assigns identical ranks to ties, but does not skip any rank numbers (ideal for "Find the 2nd highest salary/execution price").
  • NTILE(n): Divides the partition as equally as possible into n buckets (e.g. quintiles for credit risk scoring).

3. The Deadly LAST_VALUE Trap & ROWS vs RANGE

⚠️ The Fatal LAST_VALUE Default Framing Bug

Developers routinely run:
SELECT LAST_VALUE(FillPrice) OVER (PARTITION BY SecurityID ORDER BY ExecutedAt) FROM Executions;
...and wonder why LAST_VALUE() returns the current row's price instead of the last price in the partition!

The Reason: When an ORDER BY is supplied without an explicit framing clause, ANSI SQL mandates the default frame:
RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW.
Therefore, the "last value" in a frame that ends at the CURRENT ROW is always the current row itself!

The Fix: Explicitly expand the frame to the end of the partition:
LAST_VALUE(FillPrice) OVER (PARTITION BY SecurityID ORDER BY ExecutedAt ROWS BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING)

Engine Mechanics: ROWS vs RANGE Performance

Frame Mode Execution Engine Operator Performance Impact
ROWS BETWEEN... Stream Aggregate (In-Memory pointer arithmetic) Ultra-Fast: Processed in-place row-by-row in CPU registers.
RANGE BETWEEN... Segment / On-Disk Spool (TempDB worktable) 50x-100x Slower: SQL Server must spool duplicate values into TempDB to evaluate tie boundaries. Always specify ROWS!

Exercise 3.1: Finding the N-th Highest Executed Order Without Subquery Aggregation
Easy
Context: Table Executions (ExecutionID, OrderID, FillPrice)

Requirement: Write a query to find the 3rd highest distinct execution price across all equity trades. Ensure ties share the same ranking and do not distort the 3rd rank.

💡 View Solution & Explanation ▼ 
WITH PriceRankings AS (
    SELECT 
        FillPrice,
        DENSE_RANK() OVER (ORDER BY FillPrice DESC) AS PriceRank
    FROM Executions
)
SELECT DISTINCT FillPrice
FROM PriceRankings
WHERE PriceRank = 3;
Why DENSE_RANK: If the two highest prices are $500, $500, and the next is $450, RANK() would assign 1, 1, 3. DENSE_RANK() assigns 1, 1, 2, ensuring $450 is correctly identified as the 2nd distinct tier.
Exercise 3.2: Account Ledger Running Balance (Cumulative Sum)
Medium
Context: LedgerTransactions (TransactionID, AccountID, Amount, TransactionTimestamp)

Requirement: Calculate the real-time running cash balance for each account ordered by transaction timestamp. Ensure maximum performance by using an in-memory stream operator instead of TempDB spools.

💡 View Solution & Explanation ▼ 
SELECT 
    AccountID,
    TransactionID,
    TransactionTimestamp,
    TransactionType,
    Amount,
    -- Running Cumulative Balance with explicit ROWS framing
    SUM(Amount) OVER (
        PARTITION BY AccountID 
        ORDER BY TransactionTimestamp, TransactionID
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS RunningBalance
FROM LedgerTransactions
ORDER BY AccountID, TransactionTimestamp;
Crucial Best Practice: Adding TransactionID as a secondary sort key guarantees deterministic ordering. Explicitly writing ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW prevents SQL Server from defaulting to RANGE, slashing execution time by 90%+.
Exercise 3.3: Trade Slippage Detection using LAG and LEAD
Medium
Context: Table Executions for a given security

Requirement: For every execution of Apple (Ticker = 'AAPL'), calculate: (1) The fill price of the immediately preceding execution, (2) The absolute price delta, and (3) The percentage slippage compared to the prior trade.

💡 View Solution & Explanation ▼ 
SELECT 
    e.ExecutionID,
    e.ExecutedAt,
    e.FillPrice,
    LAG(e.FillPrice, 1, e.FillPrice) OVER (
        ORDER BY e.ExecutedAt, e.ExecutionID
    ) AS PreviousFillPrice,
    CAST(e.FillPrice - LAG(e.FillPrice, 1, e.FillPrice) OVER (
        ORDER BY e.ExecutedAt, e.ExecutionID
    ) AS DECIMAL(18,4)) AS PriceDelta,
    CAST((e.FillPrice - LAG(e.FillPrice, 1, e.FillPrice) OVER (
        ORDER BY e.ExecutedAt, e.ExecutionID
    )) * 100.0 / LAG(e.FillPrice, 1, e.FillPrice) OVER (
        ORDER BY e.ExecutedAt, e.ExecutionID
    ) AS DECIMAL(6,3)) AS PctSlippage
FROM Executions e
INNER JOIN Orders o ON e.OrderID = o.OrderID
INNER JOIN Securities s ON o.SecurityID = s.SecurityID
WHERE s.Ticker = 'AAPL'
ORDER BY e.ExecutedAt;
Third Parameter of LAG: LAG(column, offset, default_value). Providing e.FillPrice as the third argument avoids generating a NULL for the very first trade of the day, eliminating divide-by-zero errors in the percentage formula.
Exercise 3.4: 5-Day Moving Average of Trading Volume (Sliding Window)
Medium
Context: Daily aggregated trading volume per security

Requirement: Write a query calculating the 5-day rolling simple moving average (SMA) of trading volume for each security, covering the current day and the previous 4 trading days.

💡 View Solution & Explanation ▼ 
WITH DailySecurityVolume AS (
    SELECT 
        o.SecurityID,
        CAST(e.ExecutedAt AS DATE) AS TradeDate,
        SUM(CAST(e.FillQuantity AS BIGINT)) AS DailyShares
    FROM Executions e
    INNER JOIN Orders o ON e.OrderID = o.OrderID
    GROUP BY o.SecurityID, CAST(e.ExecutedAt AS DATE)
)
SELECT 
    SecurityID,
    TradeDate,
    DailyShares,
    AVG(CAST(DailyShares AS FLOAT)) OVER (
        PARTITION BY SecurityID 
        ORDER BY TradeDate
        ROWS BETWEEN 4 PRECEDING AND CURRENT ROW
    ) AS MovingAvg5DayVolume
FROM DailySecurityVolume
ORDER BY SecurityID, TradeDate;
Sliding Frame: ROWS BETWEEN 4 PRECEDING AND CURRENT ROW specifies a physical window of up to 5 rows (the current row plus up to 4 predecessors). For the first row, SQL Server dynamically averages whatever rows exist in the boundary without errors.
Exercise 3.5: Identifying Islands and Gaps in Settlement Statuses
Hard
Context: Table Orders (OrderID, OrderStatus, OrderTime)

Requirement: An order can transition through states. Detect consecutive "streaks" of FILLED orders (Gaps & Islands problem). Return the streak ID, start OrderID, end OrderID, and total count of orders in each uninterrupted filled streak.

💡 View Solution & Explanation ▼ 
WITH NumberedOrders AS (
    SELECT 
        OrderID,
        OrderStatus,
        OrderTime,
        ROW_NUMBER() OVER (ORDER BY OrderTime, OrderID) AS OverallRow,
        ROW_NUMBER() OVER (PARTITION BY OrderStatus ORDER BY OrderTime, OrderID) AS StatusRow
    FROM Orders
),
Islands AS (
    SELECT 
        OrderID,
        OrderStatus,
        OrderTime,
        (OverallRow - StatusRow) AS IslandID
    FROM NumberedOrders
    WHERE OrderStatus = 'FILLED'
)
SELECT 
    IslandID,
    MIN(OrderID) AS StreakStartOrderID,
    MAX(OrderID) AS StreakEndOrderID,
    MIN(OrderTime) AS StreakStartTime,
    MAX(OrderTime) AS StreakEndTime,
    COUNT(*) AS ConsecutiveFilledOrders
FROM Islands
GROUP BY IslandID
ORDER BY StreakStartTime;
The Classic ROW_NUMBER() - ROW_NUMBER() Trick: Subtracting a partitioned sequence from an unpartitioned sequence yields a constant integer for any contiguous streak of identical values. This is the gold-standard algorithm for Islands problems.
Exercise 3.6: Correcting the LAST_VALUE Frame for Market Open vs Close Comparison
Medium
Context: Table Executions with FillPrice, ExecutedAt

Requirement: For each security, compare the day's opening trade price (first execution of the day) and the day's closing trade price (last execution of the day) side-by-side on every execution row.

💡 View Solution & Explanation ▼ 
SELECT 
    o.SecurityID,
    e.ExecutionID,
    e.ExecutedAt,
    e.FillPrice,
    -- First value (Opening price)
    FIRST_VALUE(e.FillPrice) OVER (
        PARTITION BY o.SecurityID, CAST(e.ExecutedAt AS DATE)
        ORDER BY e.ExecutedAt, e.ExecutionID
        ROWS BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW
    ) AS DayOpenPrice,
    -- Corrected Last value (Closing price) with expanded frame
    LAST_VALUE(e.FillPrice) OVER (
        PARTITION BY o.SecurityID, CAST(e.ExecutedAt AS DATE)
        ORDER BY e.ExecutedAt, e.ExecutionID
        ROWS BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING
    ) AS DayClosePrice
FROM Executions e
INNER JOIN Orders o ON e.OrderID = o.OrderID;
Frame Comparison: FIRST_VALUE naturally works with the default frame because the first row is always in the frame. LAST_VALUE requires ROWS BETWEEN CURRENT ROW AND UNBOUNDED FOLLOWING to look ahead to the partition's ultimate record.
Exercise 3.7: Portfolio Risk Percentiles with NTILE vs CUME_DIST
Hard
Context: PortfolioPositions (AccountID, SecurityID, PositionUnits, CurrentMarketPrice)

Requirement: Calculate the gross position value (Units * Price) for each holding and assign: (1) Decile bucket (1-10) using NTILE, (2) Relative cumulative distribution rank using CUME_DIST(), and (3) Exact percentile rank using PERCENT_RANK().

💡 View Solution & Explanation ▼ 
WITH PositionValues AS (
    SELECT 
        AccountID,
        SecurityID,
        CAST(PositionUnits * CurrentMarketPrice AS DECIMAL(18,2)) AS PositionVal
    FROM PortfolioPositions
)
SELECT 
    AccountID,
    SecurityID,
    PositionVal,
    NTILE(10) OVER (ORDER BY PositionVal DESC) AS RiskDecile,
    CAST(CUME_DIST() OVER (ORDER BY PositionVal ASC) AS DECIMAL(5,4)) AS CumulativeDist,
    CAST(PERCENT_RANK() OVER (ORDER BY PositionVal ASC) AS DECIMAL(5,4)) AS PercentileRank
FROM PositionValues
ORDER BY PositionVal DESC;
Statistical Difference: CUME_DIST returns the proportion of rows with values less than or equal to the current row (between 0.0 and 1.0). PERCENT_RANK computes (Rank - 1) / (Total Rows - 1).
Exercise 3.8: High-Performance Deduplication Pattern via CTE and ROW_NUMBER
Hard
Context: Data cleansing on duplicate incoming order audit feeds

Requirement: Write a production-safe query that deletes all duplicate records in a staging table, retaining strictly the single most recent record based on LoggedAt.

💡 View Solution & Explanation ▼ 
-- Atomic In-Place CTE Deletion
WITH DeduplicationCTE AS (
    SELECT 
        LogID,
        TableName,
        RecordID,
        LoggedAt,
        ROW_NUMBER() OVER (
            PARTITION BY TableName, RecordID 
            ORDER BY LoggedAt DESC, LogID DESC
        ) AS RowNum
    FROM AuditLogs
)
DELETE FROM DeduplicationCTE
WHERE RowNum > 1;
T-SQL Power Feature: You can execute DELETE FROM CTE! SQL Server translates the deletion through the CTE directly onto the underlying physical table rows without needing temporary tables or join lookups.

📋 How to Answer This in an Interview

Interviewer Question: "What is the difference between ROWS and RANGE in a window frame, and why does it impact query latency?"

Staff Engineer Response:

"The difference lies in how rows are framed physically versus logically, which fundamentally dictates the execution engine operator used.

ROWS specifies an explicit, physical count of rows relative to the current position (e.g. ROWS BETWEEN 3 PRECEDING AND CURRENT ROW). Because the boundary is deterministic by row offset, SQL Server evaluates it using an in-memory Stream Aggregate operator. It simply maintains running variables in CPU registers, consuming zero additional memory and executing in linear O(N) time.

In contrast, RANGE specifies a logical value range based on the values in the ORDER BY clause. Because multiple rows might have duplicate values (ties), SQL Server cannot simply advance a pointer; it must materialize the rows into a Segment / On-Disk Spool in TempDB to examine peers before advancing.

Furthermore, when an ORDER BY is present without an explicit frame, SQL Server defaults to RANGE BETWEEN UNBOUNDED PRECEDING AND CURRENT ROW. In production queries over millions of rows, this default causes severe TempDB contention and spills. Replacing it with explicit ROWS framing commonly yields a 10x to 50x query speedup."
